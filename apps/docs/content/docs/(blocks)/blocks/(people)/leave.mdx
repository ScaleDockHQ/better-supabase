---
title: Leave
description: Leave types in days or hours, requests approved through the approvals module, and balances on the ledger block per member and year with grants, accruals, adjustments and a year-end carryover.
---

`leave` keeps time off per organization: the types an organization offers (vacation, sick leave, a day off in lieu), the requests members file, and balances kept on the [ledger](/docs/blocks/ledger). A request opens an approval request in the [approvals](/docs/blocks/approvals) module, and the final approval books it.

Requesting leave needs `leave.request`, reading other members' requests and balances needs `leave.read`, approving needs `leave.approve` (the default approval step), and managing types, adjusting balances and closing a year needs `leave.manage`. Admins get every permission and members get `leave.request`.

```bash
better-supabase add leave
```

The module needs `tenant`, `permissions` and `approvals`.

Server code calls the `leave` instance on `db`, in the caller's organization. With `gen.hooks` set, `better-supabase gen` writes the hooks:

```ts title="src/lib/supabase/hooks.ts"
export const { useList: useLeave } = defineDataHooks(
  "leave",
  (db: AppDb) => db.leave,
);
```

```ts
import { createLeave } from "better-supabase/blocks/leave";

const vacation = await db.leave
  .saveType(organizationId, {
    key: "vacation",
    name: "Vacation",
    allowance: 25,
    carryoverMax: 5,
  })
  .orThrow();
await db.leave
  .accrue(organizationId, { typeId: vacation.id, period: 2026 })
  .orThrow();

const request = await db.leave
  .request(organizationId, {
    typeId: vacation.id,
    startsOn: Temporal.PlainDate.from("2026-10-19"),
    endsOn: Temporal.PlainDate.from("2026-10-23"),
  })
  .orThrow();
// request.amount: 5 (working days), request.status: "pending"
```

```tsx title="src/features/leave/list.tsx"
"use client";

import { useLeave } from "@/lib/supabase/hooks";

const rows = useLeave({ limit: 50 });
```

## Types

`saveType` creates a type, or updates the one with the same `key`. A type counts in `days` (the default) or `hours`, is paid or not, and is tracked against a balance unless `tracked: false` (sick leave, for example, often isn't). `allowance` is what `accrue` grants when it names no amount, and `carryoverMax` caps what `closePeriod` carries into the next year. `archiveType` hides a type from new requests and keeps its history, and `types` lists the active ones (`archived: true` for all).

## Requests

`request` books working days between `startsOn` and `endsOn`, inclusive: the days in `workingDays` (Monday to Friday by default), so a request over a weekend counts five days for a full week. `partial: "morning"` or `"afternoon"` books half a day and needs one date. An hours type takes `hours` instead.

A request can't overlap another pending or approved request of the member (`LEAVE_OVERLAP`). For a tracked type it can't exceed the available balance (`LEAVE_BALANCE_EXCEEDED`) unless `allowNegative` is on. A request counts toward the year it starts in.

| Status      | Meaning                                                    |
| ----------- | ---------------------------------------------------------- |
| `pending`   | its approval request is open; it counts as `pending`       |
| `approved`  | the final step approved it; the ledger has a `taken` entry |
| `rejected`  | the approval request was rejected or expired               |
| `cancelled` | the requester or a manager cancelled it                    |

With the [employees block](/docs/blocks/employees) installed, every request
has an `employee_id` column: the employee behind the requester, kept in step
by triggers like time entries' (see [employees](/docs/blocks/employees#time-and-leave)).

Approvers decide with the approvals client, where the request's subject type is `leave_request`:

```ts
import { createApprovals } from "better-supabase/blocks/approvals";

const approvals = createApprovals({ transport });
await approvals.approve(request.approvalId!).orThrow();
```

`update(requestId, change)` changes a pending or approved request: its dates, `partial` or `startPart` and `endPart`, `hours`, `note` (an empty note clears it) or `fields`; what it leaves out keeps its value. The requester changes a pending request, which goes back to approval (the open approval request is cancelled and a new one opened). A member with `leave.manage` (or the employee's manager) also changes approved leave, which is booked again for the new amount, so a balance follows shortened or moved leave. `split(requestId, { gapStarts, gapEnds })` takes a gap out of approved leave, such as sick days during a holiday: the request ends the day before `gapStarts`, and a new approved request (`split`) takes the days after `gapEnds`, each booked for its own working days. The gap needs leave on both sides; shorten with `update` otherwise.

A type with `autoApprove: true` needs no approval: its requests are approved when they are made, also by the requester, and booked at once. Sick leave is the common case. The block's own types table has the column; on your table map `columns.types.autoApprove`.

`cancel(requestId)` cancels a pending request, or an approved one before the leave starts, for its requester, and any request for a member with `leave.manage`. It cancels a pending approval request with it. Cancelling an approved request writes an entry that gives the days back. `list` returns the caller's requests, earliest first, and `userId` or `everyone: true` read other members' with `leave.read`; `status`, `from` and `to` narrow it.

## Balances

Each member has a ledger account per type and year (amounts in hundredths of the type's unit), and every change to a balance is a ledger transaction of kind `leave.grant`, `leave.accrual`, `leave.adjustment`, `leave.taken`, `leave.carryover` or `leave.expiry` against the type's pool or taken account. A carryover moves the amount between the two years' accounts. `balances(organizationId)` returns the caller's balance of each tracked type this year (pass `userId` and `period` for others), with `granted`, `taken`, `pending` and `available`, which is the ledger total less pending requests. `ledger` lists the entries behind it.

`adjust` writes a grant or a correction for one member. `accrue` grants an amount, or the type's allowance, to every member or to `userIds`; give it an `idempotencyKey` and a member gets that accrual once, so a monthly cron can call it safely. `closePeriod(organizationId, 2026)` carries each member's remaining balance, up to `carryoverMax`, into 2027 and expires the rest. Running it twice writes nothing the second time.

## Configure

```ts title="better-supabase.config.ts"
blocks: {
  leave: {
    options: {
      workingDays: ["mon", "tue", "wed", "thu"],
      policy: { steps: [{ approvers: { role: "admin" } }], expiresIn: "P14D" },
    },
  },
},
```

`policy` is an [approvals policy](/docs/blocks/approvals) without `run`, since the final approval books the leave. `extraColumns` adds your own columns to requests, typed with the client's `fields` schema.

### Without the approvals block

`options.approvals: false` keeps the decision on the request, so leave runs without the [approvals block](/docs/blocks/approvals) (an `approval` column mapped to `null` does the same). A request stays `pending` until `decide(requestId, { approved, note? })` approves or rejects it: the service role, or a member with `leave.approve` who didn't ask for it. Approval books the leave like a final approval; rejection sets `rejected_at` and records `leave.rejected`. The requests table takes optional `rejectedAt`, `decidedBy` and `decisionNote` columns; without `rejectedAt` a rejection fails with `LEAVE_REJECTION_UNSUPPORTED`. An app that decides elsewhere calls `decide_leave_request` from its own flow. The service role decides for a user with `decidedBy` (`decided_by` in SQL), which is kept in the `decidedBy` column instead of an empty value; a member passing someone else, or `decidedBy` naming the requester, fails with the forbidden error. With `options.approver: "manager"`, the requester's manager in the [employees block](/docs/blocks/employees) (or the request's employee's manager) may also decide, next to holders of `leave.approve`. That needs the employees block's tables; the default is `"permission"`.

### Your own tables without a key or part-of-day column

Over your own tables, `columns.types.key` and `columns.requests.partial` can map to `null`. Without a key column, a type's `key` is its id: `saveType` with an existing type's id updates it, and any other key creates a type. Without a partial column, a request takes whole days (`LEAVE_PARTIAL_UNSUPPORTED` for `morning` or `afternoon`) or, for an hours type, hours, and reads return `full` or `hours`.

### Leave per employee

`options.owner: "employee"` keys requests and balances by an employee of the [employees block](/docs/blocks/employees) instead of by a user, so an employee without an account has leave too. The requests table needs `columns.requests.employee` (`employee_id`), and `columns.requests.user` may map to `null`. `request`, `list`, `balances`, `ledger` and `adjust` take `employeeId` (the caller's employee by default), and `accrue` takes `employeeIds`. The employee's own account requests and reads their leave with `leave.request`; their manager (the employee's `manager_id`) or a member with `leave.manage` requests and cancels it for them, and `leave.read` reads everyone's. Reads return `employeeId` next to `userId`, which is missing for an employee without an account.

With the approvals block, the user who files a request is its approval's requester, and a manager step (`approvers: { manager: true }`) asks that user's manager. `options.approvalOwner: "employee"` makes the request's employee the requester instead, so a manager who books leave for a report decides it and the employee can't approve their own leave, and points the manager step at the employee's manager. For an employee without an account, the filer stays the requester.

```ts title="better-supabase.config.ts"
leave: {
  options: {
    owner: "employee",
    approvalOwner: "employee",
    policy: { steps: [{ approvers: { manager: true } }] },
  },
},
```

### The part of the day a request starts and ends in

Over your own requests table, `columns.requests.startPart` and `endPart` map the part of the day a request starts and ends in: `full`, `morning`, `afternoon` or `hours`, which may be an enum. `request` takes `startPart` and `endPart`: a request that starts in the `afternoon` begins halfway through its first day, and one that ends in the `morning` stops halfway through its last. A day type books the working days less half a day for each, and an hours type books `hours` with any parts. Two requests overlap only when their half days do, so a morning and an afternoon on the same date fit. `partial` still works and fills both parts.

### Balances in your own table

`tables.balances` maps a table of yours that holds a balance as rows of signed amounts, instead of the [ledger block](/docs/blocks/ledger), which leave then doesn't need. Each row has the owner (`user` or `employee`), the `type`, a `kind` (`grant`, `accrual`, `taken`, `adjustment`, `carryover` or `expiry`, which may be an enum), the `amount` in the type's unit, and the `request` a taken row belongs to; `effectiveOn`, `expiresOn`, `note`, `key` and `createdBy` are optional.

```ts title="better-supabase.config.ts"
blocks: {
  leave: {
    tables: {
      requests: "public.time_off_requests",
      balances: "public.time_off_ledger",
    },
    columns: {
      requests: {
        user: null,
        employee: "employee_id",
        startPart: "start_part",
        endPart: "end_part",
        amount: "hours",
        partial: null,
      },
      balances: { user: null, employee: "employee_id", amount: "hours", request: "time_off_request_id" },
    },
    options: { owner: "employee", approvals: false },
  },
},
```

The balance on a date is the sum of the rows effective by then, where a credit that has expired counts only as far as the debits used it: taken leave uses the credits that expire first. `balances` reads it at the end of `period`, or today for this year, and a request checks it on its start date. Approving a request adds a `taken` row dated on its start, and cancelling it deletes that row. `adjust` adds a row and takes `expiresOn`. `closePeriod` adds an `expiry` row on 31 December for the balance above `carryoverMax`; it needs `effectiveOn`. An `idempotencyKey` needs `key`.

`adjust` and `accrue` take an `effectiveOn` date, such as a backdated correction or an accrual on the first of the month. Without `period` the entry belongs to that date's year; without `effectiveOn` it counts from the first day of the period, as before. Without an `effectiveOn` column they refuse a date (`LEAVE_EFFECTIVE_UNSUPPORTED`).

```ts
await leave
  .accrue(organizationId, {
    typeId: vacation.id,
    amount: 13.33,
    effectiveOn: Temporal.PlainDate.from("2026-11-01"),
  })
  .orThrow();
```

### Confidential leave types

Every member with `leave.read` reads everyone's leave, which is right for a team calendar but not for sick leave. Over your own types table, map `columns.types.confidential` to a boolean column, and leave of a confidential type stays with the people allowed to see it: the employee, their manager (with `options.owner: "employee"`) and members with `permissions.readConfidential` (`leave.manage` when unset). `list`, `balances`, `ledger` and the feeds leave the others out, and so does the read policy of the block's own requests table.

```ts title="better-supabase.config.ts"
blocks: {
  leave: {
    tables: { types: "public.time_off_types", requests: "public.time_off_requests" },
    columns: { types: { confidential: "is_confidential" } },
    permissions: { read: "time_off.read", readConfidential: "time_off.read_sickness" },
  },
},
```

A column derived from another one works too, such as `is_confidential boolean generated always as (category = 'sick') stored`. A feed shows confidential leave only while the link's creator holds the key.

### Changes to approved leave go back to approval

By default only a manager changes approved leave, and it stays approved. With `options.reapprove: true`, the requester may change their own approved leave too, and the change goes back to approval: the taken leave returns to the balance, `approvedAt` (and without the approvals block `decidedBy` and `decisionNote`) is cleared, and the request is pending again, with a new approval request when the approvals block runs. A type with `autoApprove` is approved and booked again at once. `permissions.reapprove` names a key whose holders may change anyone's leave the same way, whether or not `options.reapprove` is set. A manager's change keeps the leave approved as before.

```ts title="better-supabase.config.ts"
leave: {
  options: { reapprove: true },
  permissions: { reapprove: "timeOff.update" },
},
```

### A feed of approved leave

With [share-links](/docs/blocks/share-links), the organization's approved leave can be shared as a feed, for example to subscribe in a calendar app. A member with `leave.read` creates a link of subject type `leave_feed` whose subject id is the organization's id, and `feed(token)` (or `leave_feed(token)`, open to `anon`) returns the approved requests a year back and everything ahead. The link stops working when it is revoked or expires, and when its creator no longer holds `leave.read`. Turn the requests into iCalendar all-day events in your feed route.

```ts
const link = await shareLinks
  .create({ type: "leave_feed", id: organizationId })
  .orThrow();
const feed = await leave.feed(link.token).orThrow();
```

Each entry has `startPart` and `endPart`. `options.feed` takes more:

| Option             | Effect                                                                                                                                                                                                                                                                                    |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `teams`            | with the [teams](/docs/blocks/teams) block, a link of subject type `leave_team_feed` whose subject id is a team's id shares the leave of that team's members                                                                                                                              |
| `names`            | each entry carries the employee's `name`, or first and last name with the employees block's `name: "split"`; needs the employees block                                                                                                                                                    |
| `hideTypes`        | type keys whose `type` name the feed leaves out, such as `["sick"]`                                                                                                                                                                                                                       |
| `typeKey`          | the types table column `hideTypes` matches, such as `category`, instead of the type key                                                                                                                                                                                                   |
| `fields`           | each entry carries the request's extra columns, such as start and end times                                                                                                                                                                                                               |
| `teamColumn`       | a column of the employees table that names an employee's team, such as `department_team_id`: a team feed shares the leave of the employees whose column holds the team's id, including employees without an account, instead of the team's members; needs `teams` and the employees block |
| `teamName`         | a team feed carries the team's `teamName`; needs `teams`                                                                                                                                                                                                                                  |
| `organizationName` | `"schema.table.column"` of the organization's name, matched on that table's `id`; the feed carries it as `organizationName`                                                                                                                                                               |
| `confidential`     | `"busy"` lists the confidential leave the link's creator can't see under `busy`, with who and when but without the type, amount or fields; `"hide"` (the default) leaves it out; needs `columns.types.confidential`                                                                       |

```ts
leave: {
  options: { feed: { teams: true, names: true, hideTypes: ["sick"], fields: true } },
}
```

## Errors

| Hint                      | Cause                                                                                               |
| ------------------------- | --------------------------------------------------------------------------------------------------- |
| `LEAVE_FORBIDDEN`         | the caller lacks the permission for this                                                            |
| `LEAVE_INVALID`           | dates out of order, a half day over several dates, missing hours, a zero amount, or no working days |
| `LEAVE_OVERLAP`           | the member has a pending or approved request on these dates                                         |
| `LEAVE_BALANCE_EXCEEDED`  | the request is more than the available balance                                                      |
| `LEAVE_TYPE_NOT_FOUND`    | no active type has this id                                                                          |
| `LEAVE_REQUEST_NOT_FOUND` | no request the caller can see has this id                                                           |
| `LEAVE_REQUEST_CLOSED`    | the request is already cancelled or decided, or only approved leave is split                        |
| `LEAVE_EMPLOYEE_INVALID`  | no employee has this id, or the caller has no employee record                                       |

## Events

The block records `leave.requested`, `leave.approved`, `leave.rejected` (without the approvals block), `leave.cancelled`, `leave.updated` and `leave.split` (the new request) with `organizationId`, `id`, `userId`, `typeId`, `startsOn`, `endsOn`, `amount` and `approvalId`, and `leave.adjusted` with `kind`, `amount` and `period` for grants and adjustments. See [events](/docs/extending/events).

The block takes `hooks` around its methods; see [extending blocks](/docs/extending/blocks).

## Without the client

`db.leave` is this client. Code that does not go through `bsb.db()` builds it with a transport and an organization id:

```ts
import { createLeave } from "better-supabase/blocks/leave";

const leave = createLeave({ transport });

const vacation = await leave
  .saveType(organizationId, {
    key: "vacation",
    name: "Vacation",
    allowance: 25,
    carryoverMax: 5,
  })
  .orThrow();
await leave
  .accrue(organizationId, { typeId: vacation.id, period: 2026 })
  .orThrow();

const request = await leave
  .request(organizationId, {
    typeId: vacation.id,
    startsOn: Temporal.PlainDate.from("2026-10-19"),
    endsOn: Temporal.PlainDate.from("2026-10-23"),
  })
  .orThrow();
// request.amount: 5 (working days), request.status: "pending"
```
