title: Calendar
description: Calendars and events with RFC 5545 recurrence, per-occurrence edits, attendees, iCalendar import and export, and an iCal feed through a share link.
---

`calendar` stores calendars and their events in Postgres. A recurring event is
one row with an RFC 5545 `RRULE`; `occurrences()` expands it in TypeScript with
the same `expandRule` the [reminders block](/docs/blocks/reminders) uses, so
both agree on every date. Editing one occurrence writes an override row, and
editing "this and following" splits the series in two.

```bash
better-supabase add calendar
```

The block's entities are `calendar_event` (the `calendar_events` table, its primary entity) and `calendar` (the `calendars` table). Installing it registers `calendar_event` as a subject, searchable by title, description and location when the search module is installed. Rename them with `blocks.calendar.names`, for example `{ calendar_event: "meeting" }`. `calendarEventInputSchema` validates what `upsert` takes.

```ts
import { createCalendar } from "better-supabase/blocks/calendar";
```

The module requires `memberships` and `access`. With `share-links` it serves an
iCal feed, with `reminders` each event gets a recurrence rule that reminders
can attach to, with `leave` approved leave counts as out of office, and with
`outbox` its events are recorded.

## Tables

| Table                    | Holds                                                                                                                        |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| `calendars`              | A named calendar in an organization, with an IANA `tz` and an optional owner subject (`owner_type`, `owner_id`)              |
| `calendar_events`        | `starts_at`, `ends_at` (exclusive), `all_day`, `tz`, `status`, `rrule`, `exdates`, an optional subject, and override columns |
| `calendar_attendees`     | An email per event, with an optional user id, a `role` and a `response`                                                      |
| `calendar_working_hours` | A member's weekly hours in an organization: a `weekday` with a `starts_at` and `ends_at` time in their `tz`                  |

An override has `recurrence_id` (the series row) and `original_start` (the
occurrence it replaces) and shares the series' `uid`, as `RECURRENCE-ID` does
in iCalendar. Members read through the tables' policies; every write goes
through a function that checks `calendar.write`, or `calendar.manage` to
create and delete calendars. Deleting a user keeps the events they created.

## Events and occurrences

```ts
const calendar = createCalendar({ transport });

const { id: calendarId } = await calendar
  .createCalendar(organizationId, "Team", { tz: "Europe/Amsterdam" })
  .orThrow();

await calendar
  .upsert(calendarId, {
    title: "Stand-up",
    startsAt: Temporal.Instant.from("2026-03-23T08:00:00Z"),
    endsAt: Temporal.Instant.from("2026-03-23T08:15:00Z"),
    tz: "Europe/Amsterdam",
    rrule: "FREQ=WEEKLY;BYDAY=MO",
  })
  .orThrow();

const week = await calendar
  .occurrences([calendarId], {
    from: Temporal.Instant.from("2026-03-30T00:00:00Z"),
    until: Temporal.Instant.from("2026-04-06T00:00:00Z"),
  })
  .orThrow();
```

A series follows its `tz`: the stand-up stays at 09:00 in Amsterdam across
the daylight saving change, so its UTC time moves. Each occurrence has a
stable `key` (the series id and its original start), its `start` and `end`,
and the `event` row that applies, which is the override when there is one.

| Method                                | Does                                                                                     |
| ------------------------------------- | ---------------------------------------------------------------------------------------- |
| `upsert(calendarId, input)`           | Inserts an event, or updates the one with `input.id`; keys left out keep their value     |
| `events(calendarIds, range)`          | The rows that can fall in the range: single events, series and overrides                 |
| `occurrences(calendarIds, range)`     | The occurrences in the range, with EXDATEs removed and overrides applied                 |
| `editOccurrence(occurrence, changes)` | Changes one occurrence: an override for a series, an update for a single event           |
| `editFollowing(occurrence, changes)`  | Changes this occurrence and every later one, splitting the series unless it is the first |
| `cancelOccurrence(occurrence)`        | Adds an `EXDATE` and drops the occurrence's override, or deletes a single event          |
| `delete(eventId)`                     | Deletes an event with its overrides                                                      |
| `setAttendee`, `removeAttendee`       | Invites or removes an attendee by email                                                  |
| `respond(eventId, response)`          | The signed-in user answers: `accepted`, `declined`, `tentative` or `needs-action`        |

`editFollowing` ends the old series the second before the occurrence (its
`COUNT` becomes an `UNTIL`) and starts a new series there with the remaining
count and a new uid. EXDATEs and overrides after the split move to the new
series. `splitRule(rrule, dtstart, at)` computes both rules if you need them
yourself.

## Availability

Each member can set weekly working hours, mark time as out of office or focus
time, and anyone in the organization with `calendar.read` can ask when a set of
members is busy. Postgres computes the answer, so a series' recurrence, an
override and an approved leave request all count without the client loading
every event.

```ts
import { commonFreeTime } from "better-supabase/blocks/calendar";

await calendar
  .setWorkingHours(organizationId, {
    tz: "Europe/Amsterdam",
    hours: [
      { weekday: 1, start: "09:00", end: "17:00" },
      { weekday: 3, start: "13:00", end: "17:00" },
    ],
  })
  .orThrow();

await calendar
  .upsert(calendarId, {
    title: "Deep work",
    kind: "focus_time",
    autoDecline: true,
    startsAt: Temporal.Instant.from("2030-03-06T08:00:00Z"),
    endsAt: Temporal.Instant.from("2030-03-06T10:00:00Z"),
  })
  .orThrow();

const day = {
  from: Temporal.Instant.from("2030-03-06T00:00:00Z"),
  until: Temporal.Instant.from("2030-03-07T00:00:00Z"),
};
const freeBusy = await calendar
  .freeBusy(organizationId, [ada, bob], day)
  .orThrow();
const free = commonFreeTime(freeBusy, day, {
  minimum: Temporal.Duration.from({ minutes: 30 }),
});
```

An event's `kind` is `event`, `out_of_office` or `focus_time`, and its
`transparency` is `opaque` or `transparent` (the iCalendar `TRANSP` property,
which `importIcs` and `exportIcs` map). A member is busy during:

- events on calendars they own (`owner_type` `user`), except transparent and
  cancelled ones;
- events they are invited to and haven't declined;
- approved leave, when the [leave block](/docs/blocks/leave) is installed: a
  full day, or the morning or afternoon half, in their working-hours zone.

`freeBusy` returns, per member, the merged `busy` ranges, the
`outOfOffice` and `focusTime` ranges on their own, and their `workingHours`
for the range when they set some. Ranges are clipped to the range you ask
for; one call covers at most 62 days and 100 members. `commonFreeTime` is a
pure function over that answer: it removes everyone's busy time and keeps the
time inside everyone's working hours (pass `workingHours: false` to skip that).

Recurring events expand in SQL with `calendar_rule_starts`, a PL/pgSQL port of
`expandRule`; an integration test runs both over the same rules, including
daylight saving changes, and expects the same instants.

### Auto-decline

An out-of-office block always declines new invitations that it covers. A
focus time block declines them when `autoDecline` is set. The decline happens
when the invitation is written, and when a block is saved it declines the
open invitations it already covers. Approved leave counts as out of office.
A recurring block, and an invitation to a recurring event, is never declined
automatically; the member answers those.

| Method                                     | Does                                                                    |
| ------------------------------------------ | ----------------------------------------------------------------------- |
| `setWorkingHours(organizationId, input)`   | Replaces a member's hours; managers pass `userId` to set someone else's |
| `workingHours(organizationId, userIds?)`   | The hours of the members that set them                                  |
| `freeBusy(organizationId, userIds, range)` | Busy, out-of-office, focus and working-hours ranges per member          |

To offer an appointment schedule (a link where others book time with a
member), use the [bookings block](/docs/blocks/bookings#appointment-schedules)
with the member as a resource's host: its slots then skip the times this
section reports as busy.

## iCalendar

`importIcs` parses an RFC 5545 file and upserts its events by `UID`, and
`RECURRENCE-ID` events become overrides of their series. Importing the same
file again updates the events instead of duplicating them. `exportIcs` writes
the calendar back, with a `VTIMEZONE` for every zone its events use.

```ts
const summary = await calendar.importIcs(calendarId, text).orThrow();
// { created: 12, updated: 0, skipped: 1 }

const ics = await calendar
  .exportIcs({ id: calendarId, name: "Team", tz: "Europe/Amsterdam" })
  .orThrow();
```

The parser and writer are in the package (`parseIcs`, `toIcs`): they unfold
and fold lines at 75 octets, escape `TEXT`, and read `TZID`, UTC, floating and
all-day times, `DURATION`, `EXDATE`, `STATUS`, `TRANSP` and `ATTENDEE`. `VALARM` and
`VTODO` are skipped.

## iCal feed

With `share-links` installed, a share link to a calendar (`subjectType:
"calendar"`) works as a subscription URL. `calendar_feed(token)` is open to
`anon`, hashes the token before the lookup and returns nothing for a revoked,
expired or unknown token, or a link whose organization is not the calendar's.

```ts
const link = await shareLinks
  .create(organizationId, "calendar", calendarId, "view")
  .orThrow();
```

```ts title="app/calendars/[token]/route.ts"
export async function GET(
  _request: Request,
  { params }: { params: Promise<{ token: string }> },
) {
  const { token } = await params;
  const ics = await calendar.feed(token).orThrow();
  if (ics === null) return new Response("Not found", { status: 404 });
  return new Response(ics, {
    headers: { "content-type": "text/calendar; charset=utf-8" },
  });
}
```

## React

`useCalendar` loads the occurrences of a visible range and returns them in the
shape an event calendar renders. The hook is a registry item: install it with
`npx shadcn add @better-supabase/use-calendar`, which writes
`hooks/use-calendar.ts` into the app. The hook is typed structurally, so it
needs no UI library.

```tsx
"use client";

import { useCalendar } from "@/hooks/use-calendar";

const { events, loading, editOccurrence, editFollowing, cancelOccurrence } =
  useCalendar({ calendarIds, range: { start, end } });
```

Each event's `id` is the occurrence key and its `data` is the occurrence, so
a drop or a resize maps back with `fromEventCalendarUpdate`.
`toEventCalendarResources` turns calendars into resources for a resource view;
by default each event's resource is its calendar, and `resourceOf` picks
another one, such as the event's subject.

## Vue

`useBlockController` from `better-supabase/vue` runs `createCalendarController`
with its options, as
[Block controllers](/docs/frontend/block-controllers#vue-svelte-and-solid) explains.
`state` is a shallow ref of the snapshot and `actions` are the controller's
actions. The work starts on mount, and the controller is disposed with the
component.

```vue title="Component.vue"
<script setup lang="ts">
import { useBlockController, useSupabase } from "better-supabase/vue";
import {
  createCalendar,
  createCalendarController,
} from "better-supabase/blocks/calendar";
import { rpcTransport } from "better-supabase/blocks";

const { calendarId } = defineProps<{ calendarId: string }>();
const supabase = useSupabase();
const { state } = useBlockController(
  createCalendarController,
  {
    client: createCalendar({ transport: rpcTransport(supabase) }),
    calendarIds: [calendarId],
    range: { start: new Date(), end: new Date(Date.now() + 7 * 86_400_000) },
  },
  false,
);
</script>

<template>
  <ul>
    <li v-for="occurrence in state.occurrences ?? []" :key="occurrence.key">
      {{ String(occurrence.start) }}
    </li>
  </ul>
</template>
```

Call `actions.setRange(range)` when the visible range changes.

## Svelte

`useBlockController` from `better-supabase/svelte` runs
`createCalendarController` with its options. It returns a readable store of the
snapshot, read with `$`, with the actions on `.actions`. The work starts on
mount, and the controller is disposed with the component.

```svelte title="Component.svelte"
<script lang="ts">
  import {
    getBetterSupabase,
    useBlockController,
  } from "better-supabase/svelte";
  import {
    createCalendar,
    createCalendarController,
  } from "better-supabase/blocks/calendar";
  import { rpcTransport } from "better-supabase/blocks";

  let { calendarId }: { calendarId: string } = $props();
  const { supabase } = getBetterSupabase();
  const calendar = useBlockController(createCalendarController, {
    client: createCalendar({ transport: rpcTransport(supabase) }),
    calendarIds: [calendarId],
    range: { start: new Date(), end: new Date(Date.now() + 7 * 86_400_000) },
  }, false);
</script>

<ul>
  {#each $calendar.occurrences ?? [] as occurrence (occurrence.key)}
    <li>{String(occurrence.start)}</li>
  {/each}
</ul>
```

## Solid

`useBlockController` from `better-supabase/solid` runs
`createCalendarController` with its options. `state()` reads the snapshot
through `from`, and `actions` are the controller's actions. The work starts on
mount, and the controller is disposed with the owner.

```tsx title="Component.tsx"
import { For } from "solid-js";
import { useBlockController, useSupabase } from "better-supabase/solid";
import {
  createCalendar,
  createCalendarController,
} from "better-supabase/blocks/calendar";
import { rpcTransport } from "better-supabase/blocks";

export function Component(props: { calendarId: string }) {
  const supabase = useSupabase();
  const { state } = useBlockController(
    createCalendarController,
    {
      client: createCalendar({ transport: rpcTransport(supabase) }),
      calendarIds: [props.calendarId],
      range: { start: new Date(), end: new Date(Date.now() + 7 * 86_400_000) },
    },
    false,
  );
  return (
    <ul>
      <For each={state().occurrences ?? []}>
        {(occurrence) => <li>{String(occurrence.start)}</li>}
      </For>
    </ul>
  );
}
```

## Hooks

`before_calendar_event_save(tenant, calendar, item)` runs before an insert or
update and can raise to refuse it; `after_calendar_event_save(event)` runs
after it. See [block hooks](/docs/extending/blocks#hooks).

## Errors

| Hint                          | When                                                                                             |
| ----------------------------- | ------------------------------------------------------------------------------------------------ |
| `CALENDAR_FORBIDDEN`          | The caller lacks `calendar.write` or `calendar.manage`                                           |
| `CALENDAR_NOT_FOUND`          | The calendar does not exist                                                                      |
| `CALENDAR_EVENT_NOT_FOUND`    | The event does not exist in that calendar                                                        |
| `CALENDAR_EVENT_INVALID`      | A missing start or end, an end before the start, a bad status, or an override without a series   |
| `CALENDAR_TZ_INVALID`         | `tz` is not an IANA time zone                                                                    |
| `CALENDAR_HOURS_INVALID`      | Working hours that aren't `{ weekday 1-7, start HH:MM, end HH:MM }` with the end after the start |
| `CALENDAR_RANGE_INVALID`      | A free/busy range longer than 62 days, or no members or more than 100                            |
| `CALENDAR_SPLIT_INVALID`      | The split is at or before the series' first occurrence                                           |
| `CALENDAR_ATTENDEE_NOT_FOUND` | The caller is not invited to the event                                                           |
| `CALENDAR_RESPONSE_INVALID`   | The response is not one of the four values                                                       |

day and agenda views, drag to move and resize, and resource views from
`toEventCalendarResources`. Install it with
`npx shadcn@latest add @reui/event-calendar`; the free examples

in the `application/event-calendar` category build full scheduling screens on
it; their source is licensed per user, so copy them into your app from
[reui.io](https://reui.io).

## Your own fields

`blocks.calendar.options.extraColumns` adds columns to the `calendar_events` table,
keyed by column name with their SQL type. Pass `createCalendar` a Standard Schema
for them as `fields`: `upsert` and the occurrence edits take them next to the block's own keys and
validate them (a bad value is a `validation` error), and `events` return them
parsed. A column the module already uses is refused. See
[your own fields](/docs/extending/blocks#your-own-fields).

```ts
const client = createCalendar({
  transport,
  fields: z.object({ priority: z.number().int().positive().nullable() }),
});
```
