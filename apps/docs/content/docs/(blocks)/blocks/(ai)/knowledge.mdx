---
title: Knowledge
description: Documents chunked and embedded per organization, agent, project, chat or user, with hybrid search that ranks full text and vector matches together.
---

The `knowledge` block stores what an assistant can look things up in:
documents, split into chunks that each carry an embedding and a
`tsvector`. Search runs full text and vector similarity and fuses the two
rankings with reciprocal rank fusion, so a query finds both the exact term
and a paraphrase. Row level security decides which documents a caller
sees.

```bash
better-supabase add knowledge   # adds tenant, access and vector-search as well
```

| Table                 | Holds                                                                                                  |
| --------------------- | ------------------------------------------------------------------------------------------------------ |
| `knowledge_documents` | One row per document: tenant, owner, `scope` and `scope_id`, `title`, `source`, `metadata`, `status`   |
| `knowledge_chunks`    | The chunks of a document in order: `content`, `token_count`, `embedding`, `embedding_model`, the `tsv` |

A document belongs to one scope:

| Scope          | `scope_id`                         | Who reads it                             |
| -------------- | ---------------------------------- | ---------------------------------------- |
| `organization` | none                               | every member with the read permission    |
| `agent`        | the agent                          | every member with the read permission    |
| `project`      | the project                        | the owner                                |
| `chat`         | an [AI chat](/docs/blocks/ai-chat) | the owner, and whoever can read the chat |
| `user`         | the owner (the caller by default)  | the owner                                |
| `subject`      | none; `subject_type`, `subject_id` | whoever can read the record              |

Members with the manage permission read every document in the tenant
except `subject` ones, which follow the record (see
[Record knowledge](#record-knowledge)).
A new document is `user` scoped unless you pass `scope`.

| Permission         | Lets a member                                        | Default roles              |
| ------------------ | ---------------------------------------------------- | -------------------------- |
| `knowledge.read`   | read organization and agent documents                | `owner`, `admin`, `member` |
| `knowledge.write`  | add `user`, `project` and `chat` documents           | `owner`, `admin`, `member` |
| `knowledge.manage` | add organization and agent documents, read every one | `owner`, `admin`           |

Rename the keys with `blocks.knowledge.permissions.read`, `.write`
and `.manage`.

| Option       | Default           | Sets                                                                     |
| ------------ | ----------------- | ------------------------------------------------------------------------ |
| `dimensions` | `1536`            | The embedding size; 384 for `gte-small` in Edge Functions                |
| `type`       | `vector`          | `vector` or `halfvec`, as in [vector search](/docs/blocks/vector-search) |
| `textSearch` | `simple`          | The text search configuration of the `tsv` column, such as `english`     |
| `embedQueue` | `knowledge_embed` | The [jobs](/docs/blocks/queue) queue a new document is enqueued on       |

## Server

Server code calls the `knowledge` instance on `db`, in the caller's organization. With `gen.hooks` set, `better-supabase gen` writes the hooks:

```ts title="src/lib/supabase/hooks.ts"
export const { useList: useKnowledge } = defineDataHooks(
  "knowledge",
  (db: AppDb) => db.knowledge,
);
```

```ts
const rows = await db.knowledge.list({ limit: 50 }).orThrow();
```

```tsx title="src/features/knowledge/list.tsx"
"use client";

import { useKnowledge } from "@/lib/supabase/hooks";

const rows = useKnowledge({ limit: 50 });
```

`transport` acts as the user. `service` writes embeddings, which only the
server does. The `embedder` is anything with a `model` name and an
`embed(values)` method; [`better-supabase/ai-sdk/embeddings`](/docs/ai-sdk/embeddings)
builds one from an AI SDK model, and `files` (an [AI files](/docs/blocks/ai-files)
client) lets `ingest.file` read uploads.

| Group         | Methods                                                           |
| ------------- | ----------------------------------------------------------------- |
| `collections` | `create`, `update`, `remove`, `list`, `grant`, `revoke`, `grants` |
| `documents`   | `create`, `get`, `list`, `write`, `remove`                        |
| `ingest`      | `text`, `file`, `queue`                                           |
| (top level)   | `process`, `embedJob`, `drain`, `search`, `reembed`               |

## Ingest and embed

```ts
const doc = await knowledge.ingest
  .text(organizationId, { title: "Refund policy", text, source: "handbook" })
  .orThrow();
```

`ingest.text` creates the document and writes its chunks with
`chunk(text)`: about 2,000 characters each, cut at a paragraph, line,
sentence or word break, with a short overlap. The document starts
`pending`. Embedding happens on the server:

- With the [`jobs`](/docs/blocks/queue) module installed, a new document is
  enqueued on `knowledge_embed`; register `knowledge.embedJob()` as its
  handler. The last failed attempt marks the document `failed` with the
  error.
- Without a queue, call `knowledge.process(doc.id)` (in `after()`, for
  example) or `knowledge.drain()` from a cron job. `drain` tries each
  document `attempts` times (3 by default) and marks it `failed` only
  after the last attempt.

Each pending chunk comes with a hash of its text, and an embedding is
written only while the chunk still has that text: a chunk rewritten during
the embedding call stays pending for the next round. The embedder must
return one finite vector per chunk, all of one length; anything else fails
with `invalid_input` and the hint `EMBEDDING_INVALID`.

`documents.write(id, chunks)` replaces the chunks; a chunk whose text and
model didn't change keeps its embedding, so editing one paragraph re-embeds
one chunk. `reembed({ model })` marks documents embedded by another model
`pending` again after you change models.

`ingest.file(organizationId, fileId)` reads a ready AI files upload. It
extracts text, JSON, XML and YAML; pass `extract` to `createKnowledge` for
PDFs and other formats.

With the jobs block installed, `ingest.queue(organizationId, fileId)` moves
that work off the request: it creates a pending document for the file and
enqueues it on `knowledge_ingest` (the `ingestQueue` option). Register
`knowledge.ingestJob()` as that queue's handler on the server; it reads the
file, extracts its text and writes the chunks, which enqueues their
embedding. The handler runs as the service role, so give `createKnowledge`
an AI files client with a service transport. The last failed attempt marks
the document `failed`.

```ts
const handlers = {
  knowledge_ingest: knowledge.ingestJob(),
  knowledge_embed: knowledge.embedJob(),
};
```

## Search

```ts
const hits = await knowledge
  .search(organizationId, "how fast are refunds paid", {
    scopes: [{ scope: "organization" }, { scope: "chat", id: chatId }],
    k: 8,
  })
  .orThrow();
```

Each hit has the `documentId`, the chunk `index`, its `content`, the
document `title` and a fused `score`. Without an embedder the search is
full text only; pass `{ text, embedding }` to reuse an embedding you
already have. `filter` matches documents whose `metadata` contains an
object.

## Collections

A collection groups documents with a visibility and a priority. An
`automatic` collection shows up in every search of its organization, a
`restricted` one only for the users and teams it is granted to (and for
members with the manage permission), and a `disabled` one in no search. A
search ranks the chunks of a higher priority collection first; pass
`collections` to search only some of them.

```ts
const policies = await knowledge.collections
  .create(organizationId, { name: "HR policies", visibility: "restricted" })
  .orThrow();
await knowledge.collections
  .grant(policies.id, { teamId: peopleTeamId })
  .orThrow();
await knowledge.ingest
  .text(organizationId, { title: "Leave", text, collectionId: policies.id })
  .orThrow();
const hits = await knowledge
  .search(organizationId, "parental leave", { collections: [policies.id] })
  .orThrow();
```

Team grants need the [`teams`](/docs/blocks/teams) block, and their
`team_id` column takes the teams id type (`uuid` or `bigint`). Each grant
keeps its collection's `organization_id`, so data lifecycle exports and
deletes it with the tenant. Removing a collection keeps its documents,
without a collection.

An adopted `knowledge_collections` table may declare `visibility` as an
enum: the module writes and compares it through the column's type, and
`blocks.knowledge.values.collections.visibility` maps its labels.

## Record knowledge

With the [`subjects`](/docs/blocks/subjects) block installed, a document can
belong to one record, such as a drive folder, a case or a ticket. Pass
`scope: "subject"` and the record's subject type and id:

```ts
const doc = await knowledge.ingest
  .text(organizationId, {
    title: "Lease",
    text,
    scope: "subject",
    subject: { type: "drive_node", id: folderId },
  })
  .orThrow();
const notes = await knowledge.documents
  .list(organizationId, { subject: { type: "drive_node", id: folderId } })
  .orThrow();
const hits = await knowledge
  .search(organizationId, "when does the lease renew", {
    scopes: [{ scope: "subject", type: "drive_node", id: folderId }],
  })
  .orThrow();
```

A member reads, lists and searches the document only while
`can_subject(subject_type, subject_id, 'read')` is true: the record is
visible to them, they hold the subject type's read permission, and its
check function (a drive node's grants, for example) lets them read. Share
the folder and its knowledge follows; revoke the grant and it goes. The
owner and members with the manage permission get no exception, and the
collection the document is in must still be readable. Creating one needs
read access to the record too, or it fails with the hint
`KNOWLEDGE_DOCUMENT_SUBJECT_NOT_FOUND`. Scope `subject` without both a type
and an id, or a type or id with another scope, fails with
`KNOWLEDGE_DOCUMENT_INVALID`.

Without the subjects block the `subject` scope is not accepted. The
`subject_type` and `subject_id` columns are optional: map them to your own
columns on an adopted `knowledge_documents` table, or leave them out.

## System documents

The service role creates a system collection with `collections.create(null, ...)`
and a system document with `documents.create(null, ...)` or
`ingest.text(null, ...)`. A system document has no organization and no owner,
and every organization reads and searches it, so product help or a shared
handbook is written once. A system document can join a system collection
only; an organization's documents join its own collections or a system one.

## AI SDK

[`better-supabase/ai-sdk/embeddings`](/docs/ai-sdk/embeddings) gives you
the embedder, a reranker, a search tool for the model and source parts
for the answer.

## Hooks

`createKnowledge` takes `hooks`, keyed by method name, that run your code
before and after a call: refuse it with a `DbError`, rewrite its arguments
or observe the result (see [extending blocks](/docs/extending/blocks#hooks)). Methods in a group take their hooks under the group's name,
such as `hooks: { documents: { create: { before } } }`.

## Without the client

`db.knowledge` is this client. Code that does not go through `bsb.db()` builds it with a transport and an organization id:

```ts title="lib/knowledge.ts"
import { embedWith } from "better-supabase/ai-sdk/embeddings";
import {
  createKnowledge,
  rpcTransport,
} from "better-supabase/blocks/knowledge";

export const knowledgeFor = (supabase: SupabaseClient, admin: SupabaseClient) =>
  createKnowledge({
    transport: rpcTransport(supabase),
    service: rpcTransport(admin),
    embedder: embedWith("openai/text-embedding-3-small"),
  });
```
