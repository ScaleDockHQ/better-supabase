---
title: Field encryption
description: Per-tenant data keys in Supabase Vault that encrypt app table columns and custom fields at rest, with decryption only through definer functions that check scope and can audit each read.
---

`field-encryption` stores selected values as ciphertext. Each owner (a
tenant, a user, or the app for tables without a scope) gets one random data
key in [Supabase Vault](https://supabase.com/docs/guides/database/vault), and
pgcrypto encrypts the value with AES-256 before the row is written. The key
never leaves the database, and nothing in your config or repository holds key
material.

```bash
better-supabase add field-encryption
```

Install it, then mark what to encrypt:

- a [column of your table](/docs/repository/tables#encrypted-columns) with
  `encrypted: true` under `tables.<name>.columns` in the config, or in the
  table's `@bsb encrypted` tag, read back through `public.<table>_reveal`;
- a [custom field](/docs/blocks/custom-fields#encrypted-fields) with
  `encryptDefinition(id)`, read back through `readValues`.

Set `auditReads` on either to write a `read` entry to the
[audit log](/docs/blocks/audit#read-audits) each time a value is decrypted.

## What is stored

A value is stored as `bsf1:` followed by the base64 of the pgcrypto message.
The data key is a Vault secret named `bs:field-key:<owner>`, where the owner
is `tenant:<id>`, `user:<id>` or `app`. A key is created on the first write
of its owner and is never rotated in place.

The seal trigger never seals a value that already starts with `bsf1:`. An
upsert's `excluded` row was sealed by its insert attempt, so its values are
stored once, not wrapped twice. The one exception is a row that moves to
another owner with the value unchanged: the trigger opens it with the old
owner's key and seals it with the new one.

| Function                                | Who                    | What it does                                            |
| --------------------------------------- | ---------------------- | ------------------------------------------------------- |
| `field_encrypt(owner, value)`           | service role           | Encrypts a value with the owner's key, creating the key |
| `field_decrypt(owner, value)`           | service role           | Decrypts a value; `null` when the key was dropped       |
| `field_lookup(owner, value)`            | service role           | The lookup hash of a value under the owner's lookup key |
| `drop_field_key(owner)`                 | service role           | Deletes the owner's keys, which shreds every value      |
| `field_key`, `field_seal`, `field_open` | nobody through the API | The helpers the definer functions call                  |
| `field_lookup_key`, `field_hash`        | nobody through the API | The lookup helpers the definer functions call           |

Signed-in users can't call any of them. They read plaintext only through the
definer functions of the table or block that owns the value, which check the
caller's scope first.

## Searching encrypted values

Add `lookup: true` to an encrypted column to find rows by an equal value
without decrypting them. The column gets a `<column>_lookup bytea` column and
an index on it. The seal trigger fills it with an HMAC-SHA256 of the value,
lowercased and without whitespace, under a second key of the owner:
`bs:field-lookup-key:<owner>` in Vault, next to the data key. The hash is
written before the value is sealed, again with the new owner's key when a row
moves, and from the stored value when the hash is missing, was written by
hand or no longer matches a changed ciphertext.

```ts title="better-supabase.config.ts"
tables: {
  patients: {
    columns: {
      bsn: { type: "text", format: "bsn", encrypted: true, lookup: true },
    },
  },
},
```

In a declarative schema, tag the column with `@bsb lookup bsn` next to
`@bsb encrypted bsn`. Then call `public.<table>_find(column, value)`. It
returns the ids of the rows the caller reaches whose lookup matches, hashing
the value once for each tenant the caller is a member of (each owner in the
table, for the service role):

```ts
const { data } = await supabase.rpc("patients_find", {
  lookup_column: "bsn",
  value: "111222333",
});
```

From server code with the service role, compare the column with
`better_supabase.field_lookup('tenant:<id>', value)` in your own query. Pass
the value as Postgres prints the column type, since that is what the trigger
hashes.

A lookup matches equal values only, ignoring case and whitespace; it finds no
prefix or range. Within one owner, rows with the same value have the same
hash, so anyone who can select the lookup column sees which rows are equal,
though not the value. Rows written before you set `lookup` have no hash:
`update <table> set <column> = <column>` fills it.

## Shredding

`drop_field_key('tenant:<id>')` deletes the tenant's data key and lookup key
from Vault. Every value sealed under it then reads as `null` and no lookup
finds it, in the database and in every
backup taken after the key's Vault row is gone, so dropping the key is how
you erase a tenant's encrypted data without rewriting rows. It records a
`field_key.dropped` event and a `security` audit entry with the owner, never
the key.

## Limits

- The database only sees ciphertext, so an encrypted column can't be part of
  a unique key, an index, a reference, a search column, a subject title or
  URL, a rollup or a lookup. Equal values are found through `lookup` (see
  [Searching encrypted values](#searching-encrypted-values)); for anything
  else, compare the values after `reveal` in server code.
- `text[]` columns, identities and references can't be encrypted. A custom
  field can be encrypted when its type is `text`, `email`, `url`, `bsn`,
  `iban` or `phone_e164`. Custom fields have no lookup column.
- A [data export](/docs/blocks/data-lifecycle) copies the stored ciphertext.
  Reveal the values in server code before you hand an export to a person.
- The `inline` custom fields layout keeps values on an adopted table and is
  not encrypted.
- Row policies you add to an app table yourself don't apply to `reveal`: it
  checks the table's own scope, the same one its generated policies use.
- The service role and `postgres` can always decrypt. Encryption at rest
  protects backups, replicas, logs and a leaked `select`, not a compromised
  service key.
