---
title: Imports
description: Import runs with an external record map. A rerun inserts new keys, skips unchanged ones, updates changed ones and leaves user edits alone, and CSV files get a suggested mapping and a dry run.
---

`imports` is the counterpart of the data-lifecycle exporter. `parseCsv` reads RFC 4180 CSV (`SPEC_PINS.rfc4180`). `defineImport` names the source, a Standard Schema for one row, a row key and an `insert` function. `suggestMapping` pairs headers to fields. `dryRun` validates every row and returns errors without writing. `runImport` records the run, skips keys that already imported, inserts the rest in batches of 100 and finishes with `import.completed` or `import.failed`. Pass `accessToken` to read a token before every batch; an auth failure is retried once. A dropped batch returns `resumeFrom`, and passing that as `resume` continues the same run from that chunk.

```bash
better-supabase add imports
```

```ts
import { defineImport, runImport } from "better-supabase/blocks/imports";
```

The row key makes a rerun skip a row that already imported.

## Runs and the record map

A run reads one source system for one tenant. `imports.runs.start` creates it
as `pending`, and only one run per tenant and source is `pending` or `running`
at a time: a second start fails with `IMPORT_RUN_ACTIVE`. `runs.get`,
`runs.list` and `runs.cancel` read and end runs. A run has these options:

| Option          | Meaning                                                                                   |
| --------------- | ----------------------------------------------------------------------------------------- |
| `dryRun`        | Runs every write, rolls it back and reports only the counts.                              |
| `full`          | The run sends the whole source, so `finish` marks the records it did not send as missing. |
| `inputChecksum` | Identifies the input, so a caller can tell a repeated file.                               |
| `correlationId` | Links the run to the caller's own job.                                                    |
| `scopeAliases`  | `[{ scope, of, entities }]`: a scope reuses the records another scope imported.           |

Every key a run writes is kept in `import_records`, unique per tenant,
source, scope, entity, external key and role. The server calls
`imports.upsertBatch(run, entity, items)` with items of `{ key, scope, data,
refs }`, and each item ends in exactly one outcome:

- `inserted`: the key is new, so the target writes a row.
- `unchanged`: the hash of `data` matches the last import, so nothing is
  written and no audit row exists.
- `updated`: the hash differs and nobody changed the row since the import.
- `conflicted`: the hash differs, but a user changed the row after the import.
  The row stays as the user has it.
- An item that fails (`IMPORT_ITEM_INVALID`, or the target's own hint) is
  listed in the run's `errors` and the batch goes on.

`imports.finish(run)` ends a running run. On a `full` run it sets
`went_missing_at` on records the run did not send and counts them as `missing`.
It never deletes a target row. It emits `import.entity_completed` for each
entity and then `import.completed`, or `import.failed` when the run has
errors. A dry run emits nothing. `imports.resolve(run, entity, keys)` maps
keys to the subjects they imported, and `imports.markRunning(run)` moves a
pending run on before its first batch.

`counts` is `{ <entity>: { inserted, updated, unchanged, conflicted, missing } }`
and `errors` is `[{ entity, key, code, message }]`.

### Import targets

An entity is written by a target: `{ subjectType, write, updatedAt? }`. A
block contributes one with the `imports` contribution kind, and an app lists
its own under `blocks.imports.options.targets`:

```ts title="better-supabase.config.ts"
export default defineConfig({
  blocks: {
    imports: {
      options: {
        targets: {
          customer: {
            subjectType: "customer",
            write: "public.import_customer",
            updatedAt: "public.import_customer_updated_at",
          },
        },
      },
    },
  },
});
```

`write` is `(run uuid, item jsonb, subject_id text) returns jsonb`. It
receives the item with its `tenant`, and `subject_id` is `null` for an
insert. It returns `{ subjectId, role?, subjectType?, updatedAt? }`, or an
array of them when one record writes several subjects (the first `primary`
role is the one `resolve` returns). `updatedAt` is
`(subject_id text) returns timestamptz`; without it a changed hash always
overwrites. `ownedHash` is `(subject_id text) returns text` over the columns
the importer writes. A newer `updated_at` is a conflict only when that hash
changed. When only the stamp moved, the library realigns it and applies the
row. `naturalKey` is `(tenant, item jsonb) returns text`. When no import record
exists and it returns a subject, the write updates that row. `refs` maps each
ref field to the entity it points at. The batch resolves those keys in one
query and passes `resolved` to the write. A missing key is the warning
`IMPORT_REF_MISSING`. A conflict, an error and a warning are stored on `import_run_issues`. A later run that
applies the key sets `resolved_at`. `list_import_issues` pages them with a
total capped at 10,000. `resolve_import_conflict` takes `keep` (the database
value becomes the baseline) or `overwrite` (the next batch may write the
source). `rebase_import_records(tenant, source, entities, keys)` copies the
current stamp and hash onto the stored row. An entity without a target fails
the batch with `IMPORT_TARGET_UNKNOWN`.

`replaces: true` swaps a block's target for the app's `write` of the same
entity. The batch loop, the hash and the record map stay the library's, so a
later library change to that loop still runs. `before` and `after` name
`(run uuid, item jsonb, subject_id text) returns jsonb` functions: `before`
replaces the item, `after` replaces the write result. A null from either
keeps the value it received.

A target can add `batch: "schema.function"`, `(run uuid, items jsonb) returns
jsonb`, to write a whole batch in set-based statements. The items that need a
write (not unchanged, not conflicted) arrive as one array of what `write`
receives as `item`, plus `subjectId`. It returns an array with one answer per
item in order: what `write` returns, or `{ "error": { code, message } }` for an
item it refused without writing. When it raises, each item runs through `write`
on its own, so one bad row costs only its own error. A key that repeats inside
a batch is written after the earlier one is recorded, as with `write`. A batch
target pays off when the per-row work is in the function, not in triggers on the
table: on the local fixture, 3,000 customers took 356 ms through `batch` and
365 ms through `write`, because the customer triggers dominate.

These blocks contribute targets:

| Block           | Entity               | Writes                                                                                |
| --------------- | -------------------- | ------------------------------------------------------------------------------------- |
| `catalog`       | `supplier_item`      | A supplier's price list row, by supplier and code                                     |
| `catalog`       | `product_identifier` | An EAN or a supplier or manufacturer code on a variant                                |
| `catalog`       | `discount_group`     | A customer or product discount group, with the customers of a customer group          |
| `catalog`       | `discount_rule`      | A rule of the discount matrix, by group codes                                         |
| `inventory`     | `stock_count`        | An open stock count with its lines, by location                                       |
| `custom-fields` | `field_value`        | A custom field value of a record the record map knows, checked against its field type |

The [catalog page](/docs/blocks/catalog#importing-price-lists-and-codes) lists
the `data` each one takes.

Pass `target: { entity, item }` to `defineImport` and `hooks.upsertBatch` to
`runImport` to write a file through the record map instead of `insert`.
`appTableImport` keeps its repository `insert` for now.

| Hint code                | When                                                            |
| ------------------------ | --------------------------------------------------------------- |
| `IMPORT_RUN_ACTIVE`      | A run of the same tenant and source is `pending` or `running`.  |
| `IMPORT_RUN_NOT_RUNNING` | A batch or `finish` targets a run that is not `running`.        |
| `IMPORT_TARGET_UNKNOWN`  | No target is registered for the entity.                         |
| `IMPORT_ITEM_INVALID`    | An item has no key or no data object, or the target rejects it. |

## Upsert into an app table

`appTableImport` builds an import that updates the rows a file already has
instead of skipping them. It takes the table's repository and `key`, one of
the table's `unique` sets (or its primary key), and throws when the key is
not one. `previewImport` validates the file like `dryRun` and counts the
rows it would create, change and leave unchanged, without writing:

```ts
import {
  appTableImport,
  previewImport,
  runImport,
} from "better-supabase/blocks/imports";

const tasks = appTableImport({
  table: "tasks",
  columns: TaskRow,
  repository: db.tasks,
  key: ["projectId", "title"],
  update: "fill",
});

const { preview, errors } = await previewImport(tasks, csv, mapping);
// preview: { created: 12, changed: 3, unchanged: 40 }
```

`update` decides what happens to a row that exists. `fill`, the default,
writes only the fields that are empty in the database, so a rerun never
overwrites an edit. `overwrite` writes every field the file has. Pass the
definition to `runImport` without `importedKeys`, so a rerun updates rows
instead of skipping them. The [upsert import](/recipes) recipe maps the
columns, shows the preview and runs the import.

## Import mode

`import_upsert_batch` begins an import session for the batch it writes, so a
migration of historical rows does not fire the side effects of live traffic.
`better_supabase.begin_import_session(run)` does the same for a transaction
you control. It is callable by the service role only, needs a running run, and
sets the run id and the correlation id `import:<run>` for the rest of the
transaction. `better_supabase.import_run()` returns the run id inside a
session, and only to the service role: a user session that sets the setting
itself still gets `null`, so a user can never turn the mode on.

Two options decide what the mode does:

```ts
blocks: {
  imports: {
    options: {
      events: { default: "skip", "customer.imported": "tag" },
      audit: "summary",
    },
  },
}
```

`events` maps an outbox event type (or `default`) to `skip`, `tag` or `emit`.
An event with no entry is skipped, so a run fires no webhook and no workflow
unless you list the event. `tag` emits the event with `importRunId` in its
payload, and `emit` leaves it as it is. `audit` is `rows` (the default) or
`summary`. In `rows` mode the audit log keeps one entry per changed row, tagged
with the actor kind `integration` and the correlation id `import:<run>`. In
`summary` mode a row writes no entry, and `finish_import_run` writes one
`import.entity_completed` entry per entity that inserted or updated rows, so a
second identical run adds none. The row audit triggers carry the check in their
`when` clause, so `audit_row_change` does not start for a row of a `summary`
import.

A quote or invoice whose number is already taken fails by default. Put
`onTaken: "next_free"` in the item's `data` and the import issues the next free
number instead and reports `IMPORT_NUMBER_REASSIGNED` as a warning; an unknown
value is `IMPORT_ITEM_INVALID`.

A state machine accepts any declared status on insert in import mode. It
writes one history row from no status to the inserted status with the reason
`imported`, and no `status.changed` event.

Write your own SQL functions against the same condition with
`ctx.importing()` (`better_supabase.import_run() is not null`). The mode
guards these hooks:

| Hook                                                        | In import mode                                              |
| ----------------------------------------------------------- | ----------------------------------------------------------- |
| `emit_event` (every event, so webhooks and workflows)       | skipped, tagged or emitted by `imports.events`              |
| Audit row changes and `audit_event`                         | tagged `integration`; one summary per entity with `summary` |
| State machine insert                                        | one `imported` history row, no event                        |
| `ctx.notify` (comment, inbox, task and other notifications) | not sent                                                    |
| Accounting auto-posting of a document (`bookSource`)        | not posted; post the entries with their own import          |
| Orders: stock taken when an order is paid                   | not taken                                                   |
| Shipments: stock taken when a shipment ships                | not taken                                                   |

Explicit calls stay as they are: `adjust_stock`, `count_stock`,
`move_stock`, production consumption and the ledger postings of an explicit
payment or credit call. Import those through their own targets with the
quantities and balances of the source system.

## Importing historical documents

The invoices, quotes and orders blocks contribute import targets, so a
migration keeps each document as it was issued. The entities are `invoice`,
`credit_note`, `quote` and `order`; the database functions behind them are
`import_invoice`, `import_credit_note`, `import_quote` and `import_order`.

Each document keeps its number, its original dates and its final status. The
document is written in import mode: no events, no stock movement and no
accounting auto-post. An invoice payment keeps its real date through
`payments`. A stored tax total per code and the stored document totals are
taken as given and compared with the tax block's computation. A difference
becomes an item warning (`IMPORT_TAX_MISMATCH`, `IMPORT_TOTALS_MISMATCH`) in
the `warnings` of the batch outcome, and the item is still written.

The buyer is stored as given in the `buyer` column. With the
[legal entities](/docs/blocks/legal-entities) block on, the item's
`legalEntity` sets `legal_entity_id`. Importing the same document again
writes nothing. Set `data.update` to `apply` to write the header and, when the
line count is unchanged, the line title and tax. A different line count
replaces the lines inside the import session. A void or paid document keeps
its postings unless `data.repost` is true. `data.settlement` of `row` writes
`paid`, `partially_paid` or `open` on the invoice without a payment or a
ledger entry. `suppliedOn` fills `supplied_on`, and fills the issue date when
`issuedOn` is empty. A blank title keeps the number template. A line with a
product is `product`. A payment term code and a tax rate that matches one
code are resolved when those blocks are installed. A negative total becomes a
credit note when `resolved.original` or `originalId` names the invoice, and
stays an invoice with `IMPORT_CREDIT_WITHOUT_ORIGINAL` when it does not. A
credit note in `settlement` `row` with no original records the same warning
and posts nothing. A document edited after the import is reported as a
conflict, and a document whose source changed yields
`IMPORT_DOCUMENT_CHANGED` while `update` stays `keep`.

### Opening open items

The `open_item` entity writes an opening list of what customers owe and what
suppliers are owed. Each item takes `number`, `side` (`customer` or
`supplier`), `issuedOn`, `dueOn`, `currency`, the open `balance` in minor units
and the `company` or `contact`. The item keeps its original dates, so the
ageing is right on day one. It goes through `import_invoice_document`, so
sending the same list again writes nothing.

## Over your own tables

Map `tables.runs` onto the app's import table. Optional columns can be `null`.

## Run an import in one call

`run({ organizationId, source, entities, batchSize?, maxBatchSize?, targetBatchMs?, onBatch? })` is for the service role. It starts a run, marks it running, writes each entity's items in batches of `batchSize` in the order given, then finishes the run. Item errors do not stop the run: they come back in `errors`. When the run cannot start or a batch call fails, the run is cancelled and the error is returned.

The batch size adapts. A batch that takes longer than `targetBatchMs` (default 30,000) halves the next one, and with `maxBatchSize` set a batch under half of it doubles the next one up to that size. A batch that hits the statement timeout (SQLSTATE `57014`) is split in two and each half is sent again, down to one item. The result's `suggestedBatchSize` is the size to start the next run of the source with. Two batches of one run can write at the same time: `import_upsert_batch` reads the run without a row lock and only the counts update at its end locks the row.

## Mapper versions and the record map

`runs.start({ mapperVersion })` stores the version of the mapping code that produced a run's items (`ImportRun.mapperVersion`). After a mapper fix, `reapply_import_records(tenant, source, mapper_version, entity?)` clears the content hash of the source's records that a run of another version last wrote, and returns how many; the next run counts them as changed and rewrites them through their target (a row a user edited since stays as it is). `export_import_hashes(tenant, source, entity?)` lists the record map as `{ entity, scope, key, role, hash, subjectType, subjectId }` objects in key order, so you can compare what a source sends with what was imported without reading the rows. Both are service-role functions.

## Large imports in chunks

A source with millions of rows writes in chunks, so a worker pool shares the work and a retry never writes a chunk twice. Cut each entity's items into chunks, store them, queue one job per chunk and let workers process them:

```ts
for (const [chunk, items] of chunksOf(rows, 500).entries()) {
  await imports.chunks
    .store({ runId, entity: "customer", chunk, items })
    .orThrow();
}

await db.$rpc("enqueue_import_chunks", {
  run: runId,
  entity: "customer",
  chunks: count,
});

// In the worker process, with an `imports` queue whose schema is importChunkSchema:
await runImportWorker({ imports, queue, concurrency: 4, signal });
```

`chunks.process` claims the chunk, writes it with `upsertBatch` and marks it done in one transaction, so a failure leaves it pending, a done chunk answers what it answered, and a chunk another worker holds is skipped (a claim older than five minutes is taken over). `chunks.progress(runId)` returns `{ pending, claimed, done }`; call `runs.finish` once nothing is pending or claimed. `importChunkHandler(imports)` is the job handler for a worker you run yourself. The chunk rows go with the run and with a tenant purge.

## Hooks

`createImports` takes `hooks`, keyed by method name, that run your code
before and after a call: refuse it with a `DbError`, rewrite its arguments
or observe the result (see [extending blocks](/docs/extending/blocks#hooks)).
