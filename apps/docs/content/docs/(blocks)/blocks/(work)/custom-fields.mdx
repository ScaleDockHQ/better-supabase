---
title: Custom fields
description: Field definitions, options and typed values, with a permission check for sensitive values.
---

`custom-fields` stores definitions (`entity`, `key`, `label`, `type`, `required`, `sensitive`, `permission`) and one typed value per subject.

```bash
better-supabase add custom-fields
```

Server code calls the `custom-fields` instance on `db`, in the caller's organization. With `gen.hooks` set, `better-supabase gen` writes the hooks:

```ts title="src/lib/supabase/hooks.ts"
export const { useList: useCustomFields } = defineDataHooks(
  "customFields",
  (db: AppDb) => db.customFields,
);
```

```ts
import {
  CUSTOM_FIELD_TYPES,
  createCustomFields,
} from "better-supabase/blocks/custom-fields";

const customer = { type: "customer", id: customerId };

const tier = await db.customFields
  .saveDefinition("customer", "tier", "Tier", "option")
  .orThrow();
await db.customFields.setValue(customer, tier.id, "gold").orThrow();
const values = await db.customFields.readValues(customer).orThrow();
```

```tsx title="src/features/custom-fields/list.tsx"
"use client";

import { useCustomFields } from "@/lib/supabase/hooks";

const rows = useCustomFields({ limit: 50 });
```

Definitions belong to an entity (`listDefinitions(entity)`,
`saveDefinition(entity, key, label, type, sensitive?)`), and values to a
subject, a `RecordRef` (`{ type, id }`): `readValues(subject)` and
`setValue(subject, definitionId, value)`. Every call acts in the block's
`tenant`, which `createBlocks` and `createBlockClient` pass from the request;
a call without one fails with `invalid_request` and the hint
`TENANT_REQUIRED`.

## Types

`CUSTOM_FIELD_TYPES` lists the types a definition takes. A value is stored as text whatever the type; the type tells the form and the UI what it holds. The names match the [app table formats](/docs/repository/tables), so a field and a column that hold the same thing use the same word.

| Type                                     | Holds                         | Forms field type          |
| ---------------------------------------- | ----------------------------- | ------------------------- |
| `text`, `number`, `date`, `bool`, `json` | the value                     | the same name             |
| `option`                                 | one option value              | `option`                  |
| `multi_option`                           | a JSON array of option values | `multi`                   |
| `email`, `url`                           | an address                    | `email`, `url`            |
| `user`                                   | a user id                     | `text`                    |
| `rating`                                 | 1 to 5                        | `integer`, bounded 1 to 5 |
| `currency`                               | an integer of minor units     | `integer`                 |

A [form](/docs/blocks/forms) field that names a `customField` answers with the forms field type in the last column, and a form field's own `min`, `max` or `options` win over the definition's. The check on `type` is named `bsb_field_definitions_type`; `upgrade` drops the inline check an older install created and adds the named one.

A sensitive value is returned only when `can` passes for the field's `permission`, or `custom_fields.sensitive.read` when the field names none. A provider implements field-level grants behind that key.

## Encrypted fields

With the [`field-encryption`](/docs/blocks/field-encryption) block
installed, `encryptDefinition(id)` stores a `text`, `email` or `url` field's
values as ciphertext under the tenant's data key, and encrypts the values it
already has. It needs `custom_fields.manage`, and there is no way back.
`listDefinitions` reports `encrypted` on each definition. `setValue` and
`readValues` work as before: the definer functions encrypt on write and
decrypt for callers that pass `custom_fields.read` (and the sensitive
permission for a sensitive field).

`options.auditReads: true` writes one `field_value.viewed` entry with the
category `read` to the [audit log](/docs/blocks/audit#read-audits) for each
`readValues` call that returns an encrypted or sensitive value, with the
subject and the value ids. It needs the `audit` block.

```ts title="better-supabase.config.ts"
blocks: {
  "field-encryption": {},
  "custom-fields": { options: { auditReads: true } },
},
```

`options.layout` is `normalized` (the default), `inline` or `keyed` ([below](#keyed-layout)). Inline layout stores the definition columns on the value row and skips the definitions table, which fits an existing table that keeps one value per row.

## Keyed layout

`options.layout: "keyed"` keeps each field on its value row, the way a table of
attributes per record does: every row carries its `key`, `label` and `type`,
and its value sits in the column of that type (`valueNumber` for `number`,
`rating` and `currency`, `valueDate`, `valueBool`, `valueJson` for `json` and
`multi_option`, `valueUrl` and `valueEmail` when you map them, `valueText`
for the rest). There are no definition or option tables, and the module writes
three functions instead of the definition ones:

| Function                                                                                            | What it does                                                                                                                                                                                                   |
| --------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `set_field_value(tenant, subject_type, subject_id, key, label, type, value jsonb, rank, if_absent)` | Sets the field `key` of the record: a new row, or the existing one with its label, type and value replaced. Every other value column is set to null. `if_absent` fails with `FIELD_EXISTS` instead of updating |
| `read_field_values(tenant, subject_type, subject_id)`                                               | The record's fields as `{ id, subjectType, subjectId, key, label, type, rank, value, createdAt, updatedAt }`, ordered by `rank` and then `key`                                                                 |
| `delete_field_value(value_id)`                                                                      | Removes one value and records `field_value.deleted`                                                                                                                                                            |

The client calls them as `setField(record, { key, label, type, value, rank?,
ifAbsent? })`, `readFields(record)` and `deleteValue(id)`. Writing needs
`custom_fields.manage`, a record that exists in the tenant, and the record's
`fields` action when [`config.records`](/docs/blocks/sql#actions-granted-per-row)
declares one (such as `fields: "product.update"`); a value that doesn't fit its type fails with
`FIELD_VALUE_INVALID`.

A record type can keep its id in its own column of the values table instead
of `subject_type` and `subject_id`, so the table keeps a real foreign key per
record type. Name it in `on.<type>.column`; when every type in `on` names one,
map `subjectType` and `subjectId` to `null`. A type column that stores other
labels than the block's, such as `boolean` for `bool`, maps them through
[`values`](/docs/blocks/own-schemas#your-columns-values):

```ts title="better-supabase.config.ts"
export default defineConfig({
  blocks: {
    "custom-fields": {
      tables: { definitions: null, options: null, values: "public.attributes" },
      columns: {
        values: {
          tenant: "organization_id",
          definition: null,
          optionId: null,
          valueJson: null,
          valueEmail: null,
          rank: null,
          subjectType: null,
          subjectId: null,
          type: "value_type",
          valueText: "text_value",
          valueNumber: "number_value",
          valueDate: "date_value",
          valueBool: "boolean_value",
          valueUrl: "url_value",
        },
      },
      values: { values: { type: { bool: "boolean" } } },
      on: {
        product: {
          table: "public.products",
          idType: "uuid",
          column: "product_id",
        },
        asset: { table: "public.assets", idType: "uuid", column: "asset_id" },
      },
      options: { layout: "keyed" },
    },
  },
});
```

Reading needs `custom_fields.read` in the tenant. With
`options.readAccess: "record"`, `read_field_values` checks each record instead:
the record is in the tenant and `can_subject(type, id, 'read')` passes, so the
record's own policies and its `read` action decide, and `permissions.read` is
not checked. It needs the `subjects` block. The keyed layout has no sensitive
values, so `permissions.sensitive` is not checked either.

`rank` is a fractional text key by default, ordered with `collate "C"`. With
`options.rankType: "integer"`, the managed table's `rank` column is an
`integer`, and over your own table the rank text is cast to the type of the
column `rank` maps to, so an existing `position integer` column works. Pass the
rank as a string of digits, such as `rank: "3"`; reads return it as a string too.
`rankType` and `readAccess` apply only to the keyed layout.

```ts title="better-supabase.config.ts"
"custom-fields": {
  columns: { values: { rank: "position" } },
  options: { layout: "keyed", rankType: "integer", readAccess: "record" },
},
```

The normalized and inline layouts keep their functions. In them too,
`set_field_value` asks the record's `fields` action when its type declares one.

## Over your own tables

To run over tables you already have, map `tables.definitions`, `tables.options` and `tables.values`. Set a column to `null` when the existing table does not have it. For the inline layout, map `values.definition` to `null` and set `layout` to `inline`.

## Order

Field definitions of an entity are ordered by `rank`, a fractional key (see [Rank](/docs/blocks/rank)). A new definition goes after the last one, and `reorderDefinition(id, { previous, next })` moves it between the definitions with those keys. `listDefinitions(entity)` returns an entity's definitions in that order, each with its `rank` key, for callers with `custom_fields.read`. Version 2 of the module replaced the integer `position` column with `rank`: the upgrade backfills keys in the old order and drops `position`. The inline layout has no rank column.

## Without the client

`db.customFields` is this client. Code that does not go through `bsb.db()` builds it with a transport and an organization id:

```ts
import {
  CUSTOM_FIELD_TYPES,
  createCustomFields,
} from "better-supabase/blocks/custom-fields";

const fields = createCustomFields({ transport, tenant: organizationId });
const customer = { type: "customer", id: customerId };

const tier = await fields
  .saveDefinition("customer", "tier", "Tier", "option")
  .orThrow();
await fields.setValue(customer, tier.id, "gold").orThrow();
const values = await fields.readValues(customer).orThrow();
```
