---
title: Incidents
description: Incidents with a severity, a status timeline, affected components and postmortems, and a public status page that anyone can read through one function that returns only public fields.
---

`incidents` is for running an outage and telling customers about it. You open
an incident with a severity and the components it affects, post timeline
updates as it moves from investigating to resolved, and write a postmortem
afterwards. Each organization can publish one status page: the public
components with their status and daily uptime, and the public incident
updates. Visitors read it without signing in.

```bash
better-supabase add incidents
```

```ts
import { createIncidents } from "better-supabase/blocks/incidents";
```

The module requires `memberships` and `access`. With
[notifications](/docs/blocks/notifications) the commander is notified when an
incident opens, with `outbox` it records the events, with `audit` every
change is audited, and with [tasks](/docs/blocks/tasks) postmortem action
items are tasks. The choices behind the anonymous surface are in
[ADR 0084](https://github.com/ScaleDockHQ/better-supabase/blob/main/docs/decisions/0084-anonymous-status-page.md).

## Tables

| Table                               | Holds                                                                                                    |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `incident_status_components`        | The services a status page reports on: a name, a group, whether it is `public`, and its current `status` |
| `incident_status_component_history` | One row per status a component held, with its start and end, for the uptime history                      |
| `incidents`                         | The title, description, severity, status, whether it is public, the commander, and the start and end     |
| `incident_updates`                  | The timeline: each update's status, text and whether it is public                                        |
| `incident_impacts`                  | The components an incident affects and how                                                               |
| `incident_postmortems`              | One postmortem per incident: summary, impact, root cause and resolution                                  |
| `incident_postmortem_actions`       | With `tasks`: the tasks that are a postmortem's action items                                             |
| `incident_status_pages`             | One page per organization, with a slug unique across organizations                                       |

Members with `incidents.read` read every table. `anon` has no privileges on
any of them.

## Components

Server code calls the `incidents` instance on `db`, in the caller's organization. With `gen.hooks` set, `better-supabase gen` writes the hooks:

```ts title="src/lib/supabase/hooks.ts"
export const { useList: useIncidents } = defineDataHooks(
  "incidents",
  (db: AppDb) => db.incidents,
);
```

```ts
const api = await db.incidents
  .saveComponent(organizationId, { name: "API", group: "Platform" })
  .orThrow();
await db.incidents
  .saveComponent(organizationId, { name: "Primary database", public: false })
  .orThrow();
```

```tsx title="src/features/incidents/list.tsx"
"use client";

import { useIncidents } from "@/lib/supabase/hooks";

const rows = useIncidents({ limit: 50 });
```

A component is public unless `public` is `false`. Its status is never set by
hand: it is the worst impact of the open incidents on it (`maintenance`,
`degraded`, `partial_outage`, `major_outage`), and `operational` when none is
open. Every change is kept in the history the uptime is read from. Components
and the status page need `incidents.manage`.

## Run an incident

```ts
const incident = await incidents
  .open(organizationId, {
    title: "Elevated API errors",
    severity: "sev2",
    public: true,
    commanderId,
    message: "We are looking into elevated error rates.",
    impacts: [{ componentId: api.id, impact: "partial_outage" }],
  })
  .orThrow();

await incidents
  .postUpdate(incident.id, {
    status: "identified",
    body: "A replica fell behind; failing over.",
    public: false,
  })
  .orThrow();
await incidents
  .postUpdate(incident.id, { status: "resolved", body: "Resolved." })
  .orThrow();
```

An incident starts `investigating` with severity `sev3` unless you pick one,
and is private unless `public` is `true`. `message` becomes the first
timeline update. Each `postUpdate` adds to the timeline and moves the
incident to the update's status (`investigating`, `identified`, `monitoring`
or `resolved`); resolving sets `resolvedAt` and returns its components to
`operational`. An update is public when the incident is, unless it says
otherwise. `setImpacts` replaces the affected components. Opening, updating,
posting and writing the postmortem need `incidents.write`.

## Postmortems

```ts
await incidents
  .savePostmortem(incident.id, {
    summary: "Replica lag caused failed writes.",
    rootCause: "A replica on an undersized disk",
  })
  .orThrow();
await incidents.publishPostmortem(incident.id).orThrow();
```

A postmortem can be drafted at any time and is published once the incident
is resolved, with `incidents.manage`. The status page shows only its summary.

### Action items

With the [tasks](/docs/blocks/tasks) block installed, each action item is a
task, so it has an assignee, a due date and a state, and shows up in the
assignee's task lists:

```ts
const action = await incidents
  .addPostmortemAction(postmortem.id, {
    title: "Alert on replica lag",
    assigneeId: ownerId,
    dueAt: Temporal.Now.instant().add({ hours: 72 }),
  })
  .orThrow();

await incidents.removePostmortemAction(action.id).orThrow();
```

`addPostmortemAction` creates the task in the incident's organization and
links it in `incident_postmortem_actions`. A postmortem's `actions` lists the
linked tasks with their title, state, due date and close time.
`removePostmortemAction` removes the link and keeps the task. Both need
`incidents.write`, and deleting the task removes the link.

Action items are tasks, so the block needs `tasks` for them. `savePostmortem`
no longer takes `actionItems`, and `incident_postmortems` has no `action_items`
column. The `incidents` upgrade step copies the items of a database that still
has the column into tasks through `add_incident_postmortem_action`, then drops
the column (ADR 0149). An item is a string or an object with a `title` (or
`text`, `name`, `description`), an optional `assigneeId` and an optional
`dueAt`. An assignee or due date that doesn't parse is dropped from the task,
and an item without a title becomes "Action item N". The step skips a
postmortem that already has linked actions and stops with an error, instead of
dropping the column, when it holds items it can't copy.

## Status page

```ts
await incidents
  .saveStatusPage(organizationId, {
    slug: "acme",
    title: "Acme status",
    published: true,
  })
  .orThrow();

const page = await incidents.publicStatusPage("acme", 30).orThrow();
```

`publicStatusPage(slug, days)` works with the publishable key, signed in or
not. It returns `undefined` unless the page is published. Otherwise it
returns the page title and description, the overall status, each public
component with its status, `uptimePercent` and one entry per day (1 to 90
days, default 90) with its worst status and minutes of outage, and the public
incidents that are open or resolved in the window. Each incident carries its
title, severity, status, start and end, the public components it affects, its
public updates (newest first) and the summary of a published postmortem.
Descriptions, commanders, private updates, private components, root causes,
action items and ids of organizations and members never appear.

`publicStatusPage` is the only function `anon` may call. The pgTAP test in
`supabase/tests/database/incidents.test.sql` checks that, and that a private
incident never shows on the page.

| Method                                     | Returns                                       |
| ------------------------------------------ | --------------------------------------------- |
| `saveComponent(organizationId, input)`     | the component                                 |
| `deleteComponent(componentId)`             | its id                                        |
| `components(organizationId)`               | the components in order                       |
| `open(organizationId, input)`              | the incident                                  |
| `update(incidentId, changes)`              | the incident                                  |
| `postUpdate(incidentId, input)`            | the update                                    |
| `setImpacts(incidentId, impacts)`          | the incident                                  |
| `get(incidentId)`                          | the incident with its timeline and postmortem |
| `list(organizationId, options)`            | the incidents, newest first                   |
| `savePostmortem(incidentId, input)`        | the postmortem                                |
| `publishPostmortem(incidentId)`            | the published postmortem                      |
| `addPostmortemAction(postmortemId, input)` | the action item (with `tasks`)                |
| `removePostmortemAction(actionId)`         | the postmortem (with `tasks`)                 |
| `saveStatusPage(organizationId, input)`    | the page                                      |
| `statusPage(organizationId)`               | the organization's page, or `undefined`       |
| `publicStatusPage(slug, days)`             | the public page, or `undefined`               |

## Regulatory reporting

An incident can carry a reporting profile for the regimes that set deadlines
for it: NIS2 (Directive (EU) 2022/2555), DORA (Regulation (EU) 2022/2554) and
the Cyber Resilience Act (Regulation (EU) 2024/2847). The pins are in
`SPEC_PINS.euNis2`, `SPEC_PINS.euDora` and `SPEC_PINS.euCra`.

```ts
const profile = await db.incidents
  .saveRegulatoryProfile(incident.id, {
    regimes: ["nis2", "cra"],
    awareAt: Temporal.Instant.from("2026-11-01T09:00:00Z"),
    activelyExploited: true,
  })
  .orThrow();

await db.incidents
  .submitFiling(incident.id, "nis2", "early_warning", {
    reference: "CSIRT-2026-0412",
  })
  .orThrow();
```

`saveRegulatoryProfile` plans one filing per deadline from `awareAt`:

| Regime | Stage         | Due                                                                            |
| ------ | ------------- | ------------------------------------------------------------------------------ |
| NIS2   | early_warning | 24 hours after awareness                                                       |
| NIS2   | notification  | 72 hours after awareness                                                       |
| NIS2   | final         | one month after the notification was submitted                                 |
| DORA   | initial       | 24 hours after awareness, or 4 hours after a `major` classification, if sooner |
| DORA   | intermediate  | 72 hours after the initial report                                              |
| DORA   | final         | one month after the intermediate report                                        |
| CRA    | early_warning | 24 hours after awareness of an actively exploited vulnerability                |
| CRA    | notification  | 72 hours after awareness                                                       |
| CRA    | final         | 14 days after `measureAvailableAt`, once you set it                            |

`submitFiling` records when the report went out, who sent it and the
reference the authority gave, and moves the next stage's deadline to count
from the submission. `filings(organizationId)` lists the open deadlines, the
earliest first.

With the reminders block installed, each open deadline is also a reminder for
the incident's commander (or the person who saved the profile), two hours
before it is due. The incidents block does not require reminders: without it
the deadlines are stored and listed, and nothing is scheduled. Reading needs
`incidents.read`, and saving a profile or a submission needs `incidents.write`.

The module plans the deadlines the regulations name. Whether an incident is
significant, major or reportable is your decision, and the profile stores it.

## Errors

| Hint                                   | Cause                                                                                      |
| -------------------------------------- | ------------------------------------------------------------------------------------------ |
| `INCIDENTS_FORBIDDEN`                  | the caller lacks `incidents.read`, `.write` or `.manage`                                   |
| `INCIDENTS_INVALID`                    | a field is invalid, such as a slug that isn't 2 to 63 lowercase letters, digits and dashes |
| `INCIDENT_NOT_FOUND`                   | no incident with this id in an organization the caller reads                               |
| `STATUS_COMPONENT_NOT_FOUND`           | no component with this id                                                                  |
| `INCIDENT_POSTMORTEM_NOT_FOUND`        | the incident has no postmortem                                                             |
| `INCIDENT_POSTMORTEM_ACTION_NOT_FOUND` | no postmortem action item with this id                                                     |
| `INCIDENT_NOT_RESOLVED`                | the postmortem of an unresolved incident can't be published                                |
| `INCIDENT_FILING_NOT_FOUND`            | no filing is planned for this regime and stage                                             |
| `STATUS_PAGE_SLUG_TAKEN`               | another organization uses this slug                                                        |

## Events

`incident.opened`, `incident.updated`, `incident.resolved`,
`incident_postmortem.published`, `incident_profile.updated`,
`incident_filing.submitted` and `status_component.changed`. The
[events page](/docs/extending/events) lists their payloads.

## Without the client

`db.incidents` is this client. Code that does not go through `bsb.db()` builds it with a transport and an organization id:

```ts
const incidents = createIncidents({ transport });

const api = await incidents
  .saveComponent(organizationId, { name: "API", group: "Platform" })
  .orThrow();
await incidents
  .saveComponent(organizationId, { name: "Primary database", public: false })
  .orThrow();
```
