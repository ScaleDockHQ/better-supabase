---
title: Approvals
description: Approval requests with steps per subject type and action, approvers by permission, role, team, user or the requester's manager, tenant policies that tighten the configured ones, confirm or authorize modes, single-use approvals bound to a request fingerprint, delegation, expiry and reminders.
---

`approvals` files a request for an action on a subject (send an invoice, publish a page), asks each step's approvers in turn, and runs what the policy unlocks once the last step is approved. Requests snapshot their policy, so a config change leaves pending requests alone. Filing a request needs `approvals.request` and read access to the subject, reading other people's requests needs `approvals.read`, and cancelling someone else's request needs `approvals.manage`. Who may decide a step comes from the policy, not from a permission key.

With the [drive](/docs/blocks/drive#labels-and-approvals) installed, requests on `drive_node` follow the node's grants: listing them needs read access to the node, and filing one needs write access. `drive.requestApproval` files them for one revision of a file.

```bash
better-supabase add approvals
```

Server code calls the `approvals` instance on `db`, in the caller's organization. With `gen.hooks` set, `better-supabase gen` writes the hooks:

```ts title="src/lib/supabase/hooks.ts"
export const { useList: useApprovals } = defineDataHooks(
  "approvals",
  (db: AppDb) => db.approvals,
);
```

```ts
import { createApprovals } from "better-supabase/blocks/approvals";

const invoice = { type: "invoice", id: invoiceId };

const request = await db.approvals
  .request(invoice, { action: "send", reason: "Q3 invoice" })
  .orThrow();
const waiting = await db.approvals.list({ assigned: true }).orThrow();
const onInvoice = await db.approvals
  .list({ subject: invoice, status: null })
  .orThrow();
await db.approvals.approve(request.id, "Looks right").orThrow();
```

```tsx title="src/features/approvals/list.tsx"
"use client";

import { useApprovals } from "@/lib/supabase/hooks";

const rows = useApprovals({ limit: 50 });
```

`request(subject, input)` takes the subject as a `RecordRef` (`{ type, id }`), and `request` and `list` act in the block's `tenant`, an organization id or a function that returns the current one. `createBlocks` and `createBlockClient` pass the request's tenant; a call without one fails with `invalid_request` and the hint `TENANT_REQUIRED`. Each request carries `subject` and `organizationId`.

## Configure policies

`options.policies` maps a subject type, then an action, to its steps. The subject type comes from [`config.subjects`](/docs/blocks/sql#subject-registry), which decides who can read the subject.

```ts title="better-supabase.config.ts"
blocks: {
  approvals: {
    options: {
      policies: {
        invoice: {
          send: {
            steps: [
              { approvers: { permission: "invoices.approve" }, required: 2 },
              { approvers: { users: ["8b0f6c1e-0000-4000-8000-000000000001"] }, required: "all" },
            ],
            expiresIn: "P7D",
            run: { transition: "sent" },
          },
        },
      },
    },
  },
},
```

| Option                                        | Default       | What it does                                                                                                                                       |
| --------------------------------------------- | ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `steps[].approvers`                           | none          | `permission`, `role` (membership role), `team` (a [teams](/docs/blocks/teams) id), `users` or `manager: true`; any match may decide                |
| `steps[].required`                            | `1`           | Approvals the step needs; `"all"` with `users` means every listed user, and with only `permission` every holder of it when the request is filed    |
| `steps[].escalateAfter`, `steps[].escalateTo` | none          | After the step waited this ISO 8601 duration, `escalate_approvals()` lets the `escalateTo` approvers decide it too                                 |
| `effects`                                     | none          | Tags such as `money-movement` that tenant and platform policies match on                                                                           |
| `expiresIn`                                   | none          | An ISO 8601 duration such as `P7D`; `expire_approvals()` closes the request after it                                                               |
| `selfApproval`                                | `false`       | Whether the requester may decide a step                                                                                                            |
| `mode`                                        | `"authorize"` | `"confirm"` lets the requester approve their own request as a second look; see [confirm or authorize](#confirm-or-authorize)                       |
| `run`                                         | none          | `{ transition: "<status>" }` through the [state machine](/docs/blocks/state-machine), or `{ queue: "<queue>" }` through [jobs](/docs/blocks/queue) |

A subject can have one pending request per action (`APPROVAL_PENDING`). A rejection on any step closes the request. An approver decides a step once, and `delegate(id, userId)` hands their place on the step to another member of the organization, who is then asked.

A floor under the action `"*"` covers every action of its subject type that has no floor of its own, such as every tool an AI agent can call. With `required: "all"` and only `approvers.permission`, the request asks every holder of the permission in the organization (the requester only with `selfApproval`), resolved to `users` when it is filed; nobody holding it fails with `APPROVAL_APPROVERS_EMPTY`. It needs an access model that lists holders (the roles or catalog model, or a provider or custom model with `holdersOf`).

Policies are fixed per subject type and action. To pick one by the record's values, such as the finance chain for an expense over 500, give each chain its own action and let a tenant-edited [rule](/docs/blocks/automations#actions) choose it: `approvalsAction` from `better-supabase/blocks/automations` files the request for the action in the matching rule's `config.action`.

## Confirm or authorize

A policy's `mode` says what an approval proves. `authorize`, the default, means someone other than the requester decided every step (unless `selfApproval` is on). `confirm` means the requester looked again: they may approve their own request, and their approval finishes it at once, whatever steps remain. Other approvers still decide the steps as usual. Use `confirm` for a deliberate second click before a risky action, and `authorize` when another person has to agree.

`steps[].approvers.manager: true` lets the requester's manager decide the step. The manager comes from the [employees](/docs/blocks/employees) block: the requester's employee record names a manager, whose user decides while they are an active member of the organization and not offboarded. A policy that names a manager needs the employees block in managed mode.

## Tenant policies

With `options.tenantPolicies: true`, each organization keeps its own policies in the `approval_policies` table, and the configured policies act as the platform's floor. A tenant policy names the subject type and action of a configured policy (`APPROVAL_POLICY_UNKNOWN` otherwise) and can only tighten it:

- its steps run after the floor's steps and those of earlier tenant policies;
- `authorize` outranks `confirm`, and `confirm` outranks a floor that asks for nothing;
- `selfApproval` stays on only when every matching policy allows it;
- the shortest `expiresIn` wins.

A floor with `steps: []` asks for nothing until a tenant policy adds a step or a mode, so an organization can opt into approvals for an action the platform leaves open. Without `tenantPolicies`, a floor needs at least one step or `mode: "confirm"`.

`conditions` is a [filter tree](/docs/platform/list#filter-trees) over the subject type's [rule fields](/docs/blocks/automations#fields), matched against the request's `payload`. A policy without conditions always applies. Conditions need the [automations](/docs/blocks/automations) block; without it, saving a policy with conditions fails with `APPROVAL_CONDITIONS_UNSUPPORTED`. With `options.conditions: "payload"`, the block matches the tree itself against the payload by each rule's `path`, without automations or rule fields: numbers compare as numbers, everything else as text, with the operators of the filter tree (`is`, `gt`, `between`, `is_any_of`, `contains`, `has_any_of` and the rest). An unknown operator fails with `APPROVAL_CONDITIONS_INVALID`. Put what a condition needs, such as `actorKind` or `amount`, in the request's `payload`.

A tenant policy can match more than one floor: `subjectType: "*"` matches every subject type and `action: "*"` every action, and `effect` limits it to floors that declare that effect. One policy then covers every money-moving tool:

```ts
await db.approvals
  .savePolicy({
    subjectType: "*",
    action: "*",
    effect: "money-movement",
    name: "Money moves",
    steps: [{ approvers: { permission: "finance.approve" }, required: 1 }],
  })
  .orThrow();
```

A tenant policy still needs a floor it tightens: one for its subject type, action and effect, where `*` matches any (`APPROVAL_POLICY_UNKNOWN` otherwise).

### Platform policies

With `options.platformPolicies: true` (next to `tenantPolicies`), rows of `approval_policies` without an organization are platform policies: platform staff with `approvals.manage` edit them at runtime with `savePolicy(input, { platform: true })`, `listPolicies({ platform: true })` lists them, and they apply to every organization before its own policies. A platform policy also stands in for a floor the config doesn't have, so a subject type and action can need approval without a deploy, and tenant policies can tighten it.

```ts
await db.approvals
  .savePolicy({
    subjectType: "invoice",
    action: "send",
    name: "Large invoices",
    conditions: {
      id: "root",
      type: "group",
      combinator: "and",
      rules: [
        {
          id: "amount",
          type: "rule",
          path: ["amount"],
          operator: "gt",
          value: 10000,
        },
      ],
    },
    steps: [{ approvers: { manager: true }, required: 1 }],
  })
  .orThrow();

const needed = await db.approvals
  .requirement("invoice", "send", { amount: 25000 })
  .orThrow();
```

Saving and removing a policy needs `approvals.manage` and goes to the audit log; `listPolicies` needs `approvals.read`. `requirement(subjectType, action, payload)` returns the merged policy for a payload, or `null` when nothing is required, so the app can run the action without a request. `request` refuses a request nothing requires with `APPROVAL_NOT_REQUIRED`.

## Requests without an organization

`options.tenantless` lists subject types whose requests may have no organization, for a personal AI chat or a platform action. `request(subject, { action, tenantless: true })` files one as the signed-in user, `list({ tenantless: true })` lists them and `requirement(..., { tenantless: true })` checks one. Their approvers are named users, a provider's `isApprover`, or platform staff holding the step's `permission`; roles, teams and managers belong to an organization and don't match. Platform policies apply to them; tenant policies don't. A request without an organization for any other subject type fails with `APPROVAL_TENANT_REQUIRED`, and these requests send no notifications. `organizationId` is `null` on them.

## Escalation

A step with `escalateAfter` and `escalateTo` lets the fallback approvers decide it too once it waited that long, counted from the request or the previous step's last decision. Schedule `escalate_approvals()` like the reminders; it marks the step `escalated`, records `approval.escalated` and asks the fallback approvers. The original approvers keep deciding. It needs the requests table's policy column.

```ts
steps: [
  {
    approvers: { manager: true },
    escalateAfter: "PT48H",
    escalateTo: { permission: "finance.approve" },
  },
],
```

## Deciding for a user

Code that runs as the service role, such as a chat bot or a workflow, decides for the user who clicked: `approve(id, comment, { decidedBy: userId })` and `reject` record that user as the approver. The service role skips the approver check, but the requester still can't decide their own request unless the policy allows it, and a user decides a step once. A signed-in caller who names someone else fails with `APPROVAL_FORBIDDEN`.

## Use an approval once

`isApproved` answers whether a subject was approved, which suits a status change. For an operation such as a refund or an export, bind the approval to the exact request and use it once. Pass a fingerprint when you file the request, and call `consume` with the same fingerprint right before the operation runs:

```ts
import { approvalFingerprint } from "better-supabase/blocks/approvals";

const operation = { refund: invoiceId, amount: 2500, currency: "EUR" };
const fingerprint = await approvalFingerprint(operation);

const request = await db.approvals
  .request(invoice, { action: "refund", payload: operation, fingerprint })
  .orThrow();
```

Once the request is approved, the code that runs the refund consumes it first:

```ts
await db.approvals
  .consume(request.id, await approvalFingerprint(operation))
  .orThrow();
await refund(operation);
```

`approvalFingerprint` hashes the value as JSON with sorted keys, with SHA-256. `consume` marks the request `consumedAt` and fails with `APPROVAL_NOT_APPROVED` before the final approval, `APPROVAL_CONSUMED` on a second call and `APPROVAL_FINGERPRINT_MISMATCH` when the operation changed. The requester, a member with `approvals.manage` and the service role may consume a request.

## Run the approved action

With `run: { transition }`, the final approval calls `transition()` for the subject. Mark the edge with `requiresApproval` on the machine so nobody can skip the request:

```ts title="better-supabase.config.ts"
"state-machine": {
  options: {
    machines: {
      invoice: { table: "public.invoices", column: "status", initial: "draft", transitions: { draft: ["sent"] }, requiresApproval: { draft: ["sent"] } },
    },
  },
},
```

With `run: { queue }`, the final approval enqueues a job with `requestId`, `organizationId`, `subjectType`, `subjectId`, `action` and the request's `payload`. Without `run`, check `isApproved(subject, action)` or handle `approval.approved`. [Access requests](/docs/blocks/access-requests) file their requests here with their own policy, and the final approval grants the role. [Time tracking](/docs/blocks/time-tracking) files submitted timesheets the same way, and the final approval locks the week.

## Tool calls and support sessions

When the [AI chat](/docs/blocks/ai-chat) or impersonation module is
installed next to approvals, its waiting requests become approval requests
too, so one approvals inbox lists them:

| Module        | `subjectType`      | `subjectId`                 | `action` | Who decides                                                                                      |
| ------------- | ------------------ | --------------------------- | -------- | ------------------------------------------------------------------------------------------------ |
| ai-chat       | `ai_tool_approval` | the tool call's approval id | `run`    | the chat's owner, or the users the provider's `isApprover` allows for kind `ai-tool`             |
| impersonation | `support_request`  | the support request id      | `start`  | platform staff with the approve permission, or the provider's `isApprover` for `support-session` |

The module that filed the request keeps deciding who approves it, so the
policy's approvers, roles and delegation don't apply (`delegate` refuses with
`APPROVAL_DELEGATE_INVALID`). A decision syncs both ways: approving or
rejecting the request with `approve` or `reject` decides the tool call or the
support request, and `decide_ai_tool_approval` or `approve_support_request`
closes the request. A rejected support request can no longer start a
session. Only the requester, the eligible approvers and the service role read
these requests; `approvals.read` alone doesn't show them. A support request
without a tenant stays in `support_requests` only.

## Approvers from your authorization provider

Under the `provider` access model, a provider that sets
`authorization.functions.isApprover` can name approvers the policy doesn't:
`approval_eligible` also allows a user the template accepts for kind
`<subject type>.<action>` (for example `refund.approve`), the subject id
and the request's tenant. The requester never counts, even with
`selfApproval`. The policy's own approvers still decide as well. See
[Authorization providers](/docs/extending/authorization-providers).

Server code can ask the same question through the hooks' `approverOf`. Pass
it with the user the transport runs as, and `approve`, `reject` and
`delegate` refuse with `APPROVAL_FORBIDDEN` unless both the SQL check and
the hook allow the caller:

```ts
const approvals = createApprovals({
  transport: sqlTransport(postgres.asUser(ctx.auth.claims)),
  authorization: { approverOf: hooks.approverOf },
  approver: { userId: ctx.auth.claims.sub, claims: ctx.auth.claims },
});
```

## Delegation and out-of-office

`delegate(id, userId)` hands the caller's place on the current step of one
request to another member of the organization. It never outlives the
request. This block does not store out-of-office covers, where one user
approves for another until a date.

When your authorization provider keeps covers, let it own them: its
`isApprover` answers for the cover, and `approval_eligible` passes the
request's `requested_by` as `{requester}` so a cover never lets the
requester's own delegator approve. Every module that waits for an approval
then honours the same covers. Configure covers in the provider only, and
don't mirror them with `delegate` calls. Without such a provider, call
`delegate` per request. Under the `provider` model, `delegate` checks that
the delegate is a member through the provider's `memberIdsFor` when the
provider sets it. See
[Authorization providers](/docs/extending/authorization-providers#out-of-office-covers).

## Resume a workflow when a request is decided

A request's id is a random uuid, so it works as the token a paused workflow
waits on: only `decide_approval`, after its approver check, can end the
wait. Call `wakeOnApproval` from your outbox consumer, and it resumes the
run waiting on the request with `{ approved, status, requestId }` for
`approval.approved`, `approval.rejected`, `approval.expired` and
`approval.cancelled`. See
[Workflow SDK](/docs/blocks/workflow-sdk#approvals-that-expire).

```ts title="app/api/outbox/route.ts"
import { wakeOnApproval } from "better-supabase/workflow-sdk";

for (const event of events) await wakeOnApproval(event);
```

## Expiry and reminders

Schedule both functions with pg_cron or the [jobs](/docs/blocks/queue) drain. `remind_approvals(after)` asks the current step's approvers again for requests pending longer than `after` (default one day), once per `after`.

```sql
select cron.schedule('expire-approvals', '*/15 * * * *', 'select better_supabase.expire_approvals()');
select cron.schedule('remind-approvals', '0 9 * * *', 'select better_supabase.remind_approvals()');
```

## Notifications, events and hooks

With the [notifications](/docs/blocks/notifications) module, the current step's approvers get `approval.requested` (and `approval.reminder`), a delegate gets `approval.delegated`, and the requester gets `approval.approved`, `approval.rejected` or `approval.expired`. Approvers named by permission are reached through the notification's permission audience.

The module records `approval.requested`, `approval.approved`, `approval.rejected`, `approval.cancelled`, `approval.expired`, `approval.delegated`, `approval.consumed` and `approval.escalated`, each with `organizationId`, `subjectType`, `subjectId`, the request `id`, `action`, `status` and `step`. Tenant policies record `approval_policy.saved` and `approval_policy.removed` with `organizationId`, `id`, `subjectType` and `action`. Every event but `approval.expired` also goes to the [audit log](/docs/blocks/audit). It calls `before_approval_request`, `after_approval_request`, `before_approval_decide` and `after_approval_decide`.

## With ReUI

An approvals inbox renders `list({ assigned: true })` in a ReUI data grid with approve and reject actions. A request sheet shows `get(id)`: the steps as a stepper with the current `step` highlighted, and `decisions` as a timeline. Show the approve buttons only when `canDecide` is true.

## Over your own requests table

The requests and decisions tables can be your own: map `tables.requests` and `tables.decisions` and their `columns`, as with every block table. Logical columns your table lacks map to `null`, and the block leaves out what needs them: without `policy` a request follows the live policy, without `step` a policy has one step, and a reason, payload, expiry, reminder, delegate or comment the table has no column for is refused (`APPROVAL_REASON_UNSUPPORTED` and the like). A status column may be an enum. Your other columns stay as they are, or take the request's values through `extraColumns`.

```ts title="better-supabase.config.ts"
approvals: {
  tables: {
    requests: "public.approval_requests",
    decisions: "public.approval_decisions",
  },
  columns: {
    requests: { tenant: "organization_id", decidedAt: "closed_at", remindedAt: null },
    decisions: { request: "request_id", tenant: "organization_id", delegateTo: null },
  },
},
```

## Your own fields

`blocks.approvals.options.extraColumns` adds columns to the `approval_requests` table,
keyed by column name with their SQL type. Pass `createApprovals` a Standard Schema
for them as `fields`: `request` take them next to the block's own keys and
validate them (a bad value is a `validation` error), and every request read return them
parsed. A column the module already uses is refused. See
[your own fields](/docs/extending/blocks#your-own-fields).

```ts
const client = createApprovals({
  transport,
  fields: z.object({ priority: z.number().int().positive().nullable() }),
});
```

## Without the client

`db.approvals` is this client. Code that does not go through `bsb.db()` builds it with a transport and an organization id:

```ts
import { createApprovals } from "better-supabase/blocks/approvals";

const approvals = createApprovals({ transport, tenant: organizationId });
const invoice = { type: "invoice", id: invoiceId };

const request = await approvals
  .request(invoice, { action: "send", reason: "Q3 invoice" })
  .orThrow();
const waiting = await approvals.list({ assigned: true }).orThrow();
const onInvoice = await approvals
  .list({ subject: invoice, status: null })
  .orThrow();
await approvals.approve(request.id, "Looks right").orThrow();
```
