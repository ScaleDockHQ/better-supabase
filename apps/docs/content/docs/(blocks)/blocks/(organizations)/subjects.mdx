---
title: Subjects
description: The app-wide registry of record types, with titles, links, access checks and a my-work list across blocks.
---

`subjects` turns the record types in `config.subjects` into SQL functions
every block can call. A comment, a task or a notification points at a
subject by type and id, and these functions give its title, its URL and
whether the caller may see it. It needs the
[`permissions`](/docs/blocks/permissions) block.

```bash
better-supabase add subjects
```

## SQL functions

| Function                                                              | Returns                                                                        |
| --------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| `subject_types()`                                                     | The registered types                                                           |
| `subject_title(subject_type, subject_id)`                             | The record's title                                                             |
| `subject_url(subject_type, subject_id)`                               | The record's URL in the app                                                    |
| `subject_titles(refs jsonb)`                                          | Titles and URLs for a batch of `{ type, id }` refs                             |
| `can_subject(subject_type, subject_id, action)`                       | Whether the caller may perform the action on the record                        |
| `can_subject_for(member, subject_type, subject_id, action)`           | The same check for another user, for server code                               |
| `record_summary(subject_type, subject_id, sections, seen_at)`         | A record page header: title, path and a count per section, with what is new    |
| `my_work(tenant, page_size)`                                          | The caller's open items across the installed blocks                            |
| `subject_presence_allowed(topic)`                                     | Whether the caller may join the Realtime presence topic `presence:<type>:<id>` |
| `add_subject_member(subject_type, subject_id, user_id, team_id, ...)` | Puts a user or a team on the record's team                                     |
| `end_subject_member(member_id, ends_on)`                              | Ends a record team membership                                                  |
| `list_subject_members(subject_type, subject_id)`                      | The record's team                                                              |
| `my_subjects(tenant, subject_type, page_size, cursor)`                | The records whose team the caller is on today                                  |
| `record_subject_read(subject_type, subject_id, purpose)`              | Logs a read of a record whose type has `auditReads`                            |
| `subject_access_log(subject_type, subject_id, since, max_rows)`       | Who read the record and when                                                   |
| `has_subject_role(subject_type, subject_id, roles)`                   | Whether the caller is on the record's team today in one of `roles`             |

The functions live in the block schema (`better_supabase` by default), and a
type registered in `config.subjects` gets a branch in each one.

## Client

`better-supabase/blocks/subjects` reads the same functions from the client.
The `subject-link`, `subject-chip` and `my-work` recipes render them.

`members` manages the record teams of the types that declare
`subjects.<type>.team`:

```ts
import { createSubjects } from "better-supabase/blocks/subjects";

const subjects = createSubjects({ transport });

await subjects.members
  .add({ type: "patient", id: patientId }, { userId: nurseId, role: "lead" })
  .orThrow();

const { items, nextCursor } = await subjects.members
  .mine(organizationId, { subjectType: "patient" })
  .orThrow();
```

`end(memberId, { endsOn })` ends a membership, and `list(subject)` reads the
record's team. A membership granted through an
[access request](/docs/blocks/access-requests#record-access) has an `endsAt`
instant as well. [Record teams](/docs/blocks/sql#record-teams) covers the
config, the roles and who may manage a team.

`reads` reads and writes the read log of the types that set
`subjects.<type>.auditReads`. The blocks' read functions log on their own, including the activity list,
the attachment list and the custom field values of one record, and only when
they return rows;
`log(subject, { purpose })` logs a read from a screen that selects the row
itself, and `list(subject, { since, limit })` returns who read it:

```ts
const entries = await subjects.reads
  .list({ type: "patient", id: patientId })
  .orThrow();
```

Plain Data API selects are not logged. [Record read log](/docs/blocks/sql#record-read-log)
covers the config, who may list the log and how to send every read through
the functions.

The [SQL modules page](/docs/blocks/sql#subject-registry) covers the
registry's SQL and merges, and [Record types](/docs/repository/record-types)
covers how to declare a type.
