---
title: Block SQL
description: The SQL a block installs into your declarative schema. The files are idempotent, and you commit them with the app.
---

`better-supabase add` writes a block's SQL into `supabase/schemas`, and
`supabase db schema declarative sync` turns them into a migration. The files are plain SQL that
you can read and commit, so nothing runs behind your back. Every module can be
re-run safely, and it keeps everything it creates in the `better_supabase`
schema. `add` renders the new modules next to the ones `blocks`
already lists, so a module sees what is installed (billing's foreign key to
the organizations table, for example), and writes only the named modules and
the ones they need.

`add` also lists the new modules in `blocks` of your config file, in
the form it already uses: `tags: {}` in an object, `"tags"` in a list. It
edits the object literal you pass to `defineConfig()` and leaves the rest of
the file as it is. When `blocks` is not a literal it can follow, such as
a variable or a spread, it changes nothing and prints the entries to add
instead. `--dry-run` says what it would add.

```bash
better-supabase add audit queue pgtap
supabase db schema declarative sync -f better_supabase_block
better-supabase add --adopt
better-supabase blocks list --installed
```

After the SQL, `add` wires the clients of blocks that have one into
`lib/blocks.ts` and prints the registry command for your framework's glue.

The extensions a module's schema file creates (`pgmq` for `queue`,
`pg_jsonschema` for `jsonb-schemas`, `vector` for `vector-search`) have to
exist before the schema migration applies, because objects in it use them: a
check constraint on `jsonb_matches_schema`, a pgmq queue. A schema diff can
leave them out of its migration, so `add` and `upgrade`
write the ones no migration creates yet into
`supabase/migrations/<stamp>_better_supabase_extensions.sql`, stamped before
the schema migration you create next. A migration you wrote yourself that
creates the extension counts too, so the CLI writes nothing for it.
`add --adopt` refuses to write the data migration while a module extension is
missing from every earlier migration; run `upgrade`, then create the schema
migration again after the extensions migration.

A schema diff only captures objects, so each module's rows and settings (its
`better_supabase.blocks` row, the reserved slugs, the rate-limit role
setting) go to a second file in `supabase/better-supabase-data/`, outside the schema folder:
pg-delta loads every file under `supabase/schemas`, nested folders included,
and refuses a table that has rows afterwards. When `database.sql.dir` is a folder
inside the schema folder (`supabase/schemas/block`), the data files still go
next to the schema folder, and `declarative_schema_path` in
`supabase/config.toml` moves both. `better-supabase add --adopt` writes those files into one
migration, stamped after the newest one so it runs after the schema migration.
Its statements are idempotent, and it writes nothing when the latest data
migration already has them. `add` and `upgrade` say when to run it.

Event triggers belong to no schema, so a diff limited to some schemas
(`supabase db schema declarative sync -s public,better_supabase`) leaves
them out of its migration. Run the sync without `-s` when you use `audit`
(`bsb_audit_forget_dropped`) or `rls-guard` (`bsb_ensure_rls`). Their data
files repeat the event triggers (`drop event trigger if exists`, then
`create event trigger`), so the `add --adopt` migration creates them even when
the schema migration lacks them, and
[doctor BS323](/docs/cli/doctor#bs323) reports a module event trigger that
the database, or every migration, lacks.

## Commands

| Command                     | What it does                                                      | Side effects  |
| --------------------------- | ----------------------------------------------------------------- | ------------- |
| `add <block...>`            | Writes the module files and config entries, and wires the clients | Writes files. |
| `add --adopt`               | Writes the data migration from `supabase/better-supabase-data`    | Writes files. |
| `upgrade`                   | Writes the upgrade steps, then every module file again            | Writes files. |
| `remove <block...>`         | Takes blocks out of the config and deletes their module files     | Writes files. |
| `blocks list --installed`   | Lists the installed blocks with their versions                    | None.         |
| `blocks view <block> --sql` | Prints the SQL `add` would write for one block                    | None.         |

[`init`](/docs/cli/init#add) describes `add`, `remove` and `upgrade` and
their flags.

## Workflows

`database.sql.workflow` says how the modules reach a migration. There are three:

| Workflow     | What `add` and `upgrade` write                       | How the migration is made                                |
| ------------ | ---------------------------------------------------- | -------------------------------------------------------- |
| `pg-delta`   | Module files in `supabase/schemas` (the default)     | `supabase db schema declarative sync -f <name>`          |
| `migra`      | Module files in `supabase/schemas`                   | `supabase db diff -f <name>`, with the stack stopped     |
| `migrations` | One migration, `<stamp>_better_supabase_modules.sql` | The CLI writes it; apply it with `supabase migration up` |

```ts title="better-supabase.config.ts"
export default defineConfig({
  database: { sql: { workflow: "migrations" } },
  blocks: ["audit", "queue"],
});
```

When `database.sql.workflow` is unset, the CLI reads `supabase/config.toml`: pg-delta
when `[experimental.pgdelta] enabled = true`, migra when that key is `false`,
when `[db.migrations] schema_paths` is set or when `supabase/schemas` already
holds files without pg-delta, and pg-delta otherwise. `migrations` is never
detected, so an app picks it in the config.
`better-supabase init --workflow <name>` writes the key.

### pg-delta (Declarative Schemas 2.0)

pg-delta is the Supabase CLI's diff engine (2.119 or later) and the default
for projects that `supabase init` creates. It orders the schema files by
dependency and carries grants, comments and `security_invoker` on views into
the migration. It needs `[experimental.pgdelta] enabled = true` in
`supabase/config.toml`; `better-supabase init`, `add` and `upgrade` add
it to an existing `config.toml` under this workflow.

### migra (Declarative Schemas 1.0)

The legacy engine reads `supabase/schemas` while the stack is stopped. The
CLI and doctor name its command, `supabase db diff -f better_supabase_block`.
When `supabase/config.toml` lists `[db.migrations] schema_paths`, migra reads
only the files those entries match, so `add` names any module file no
entry matches and prints the lines to add before the schemas that call their
functions. Without `workflow: "migra"` in the config,
[doctor](/docs/cli/doctor#bs316) reports BS316. Supabase's
[switch guide](https://supabase.com/docs/guides/local-development/declarative-database-schemas#switching-to-pg-delta)
lists the steps to move to pg-delta.

### Migrations only

This workflow is for an app without declarative schemas. `add` and `upgrade`
write nothing to `database.sql.dir`. `add` and `upgrade` write one migration that
holds, in order, the extensions, the upgrade steps, each module's schema with
its `@bsb-block` line, the realtime topic policies and the data statements.
Every statement can run again, so each new migration carries all the modules,
not only the changes. A command writes a new one only when the statements
differ from the newest `*_better_supabase_modules.sql`.

- `upgrade --check` and [doctor BS304](/docs/cli/doctor#bs304) compare
  against that newest migration.
- `blocks list --installed`, `upgrade` and doctor read the installed versions from its
  `@bsb-block` lines.
- `add --adopt` writes nothing, because the rows are already in the migration.
- `gen` writes the read-sets module into `<stamp>_better_supabase_read_sets.sql`.
- The pgTAP files still go to `database.sql.testsDir`.

`invitations` and `organizations` need `memberships` and `access`, so adding one
pulls those in as well. They read the active tenant from the source in
`blocks.permissions.activeTenant`: by default the tenant the server resolved for the
request, then the claim named by `auth.tenant.claim` (`tenant_id` by default).
The roles come from `blocks.permissions.roles`. Change modules through `blocks` (see
[below](#existing-tables-managed-and-custom)) rather than by editing
the files: `upgrade` rewrites them, and doctor reports a hand edit.

When the config's [authorization provider](/docs/extending/authorization-providers)
has a token hook that owns the `memberships` claim (`tokenHook.ownedClaims`),
`add tenant` stops, because two hooks would write that claim. Pass
`--allow-hook-overlap` to write it anyway,
for example to keep the helpers while you migrate. Modules that need `tenant`,
such as `invitations`, are written without `--allow-hook-overlap`, with `tenant` as a
dependency and a note: its memberships table backs `has_organization_role()`, and no
hook should call `membership_claims()`. `entitlements` needs `tenant` only
with `auth.entitlements.memberships: "tenant"`: with a provider, it reads the
provider's `memberIds` functions instead. See
[entitlements with an authorization provider](/docs/blocks/entitlements#with-an-authorization-provider).

```sql
select better_supabase.track_updated_at('public.customers');
select better_supabase.track_actor('public.customers');
select better_supabase.audit('public.customers', ignore => '{updated_at}');

create policy "admins update" on public.customers for update to authenticated
  using (organization_id in (select better_supabase.member_organization_ids('{owner,admin}')))
  with check (organization_id in (select better_supabase.member_organization_ids('{owner,admin}')));
```

`member_organization_ids()` returns the user's organizations as a set, so Postgres runs
it once per statement and compares each row against the result. Calling
`has_organization_role(organization_id)` in a policy runs it once per row instead; keep
that one for functions and single checks. `with check` stops an update from
moving a row into an organization the user can't manage.

Admins can invite members, viewers and other admins. Only an owner, or the
service role, can invite an owner, and the invitee has to confirm their email
address before `accept_invitation` adds them.

Module tables use `gen_random_uuid()` keys. Postgres 18's `uuidv7()` gives
time-ordered keys that keep indexes compact, and the modules move to it once
hosted Supabase runs Postgres 18
([supabase/postgres#2051](https://github.com/supabase/postgres/pull/2051)).

Errors raised by the modules carry a stable code in the `hint` field, for example
`SLUG_RESERVED`, `SLUG_INVALID`, `INVITATION_INVALID`, `INVITATION_EXPIRED`,
`INVITATION_ROLE_FORBIDDEN` or `INVITATION_EMAIL_UNCONFIRMED`. They come back as
typed `DbError`s through the repository.

## Scope and naming

A block's rows belong to a tenant by default. `database.sql.owner` sets that for
every block, and `blocks.<name>.scope` for one block.

| Scope              | Rows belong to                                      | Checks                                                       |
| ------------------ | --------------------------------------------------- | ------------------------------------------------------------ |
| `tenant` (default) | a tenant, through the `memberships` module          | the access contract: `can`, `tenant_ids_with`, `is_platform` |
| `user`             | the signed-in user, whose id the scope column holds | the scope column is the caller's id                          |
| `none`             | one shared space                                    | any signed-in user                                           |

```ts title="better-supabase.config.ts"
export default defineConfig({
  database: { sql: { owner: "user" } },
  blocks: { tags: {}, comments: {}, notifications: {} },
});
```

Outside `tenant` scope a block needs neither the `memberships` module nor the
access contract, so `add` leaves them out, and its scope column is
nullable: a user's id by default (`default auth.uid()`) in `user` scope, null
in `none` scope. The block's functions take the same arguments in every
scope. In `user` scope they replace the scope id a signed-in caller passes
with the caller's own id, and in `none` scope with null, so one user can't
write into another's rows. `none` scope admits accounts that signed up and
refuses anonymous sign-ins (the `is_anonymous` claim). Blocks that need tenants (organizations,
invitations, billing and most business blocks) run only in `tenant` scope,
and `add` refuses them in another one; set their `scope` to `tenant` to
keep them per tenant while the rest of the app runs per user.
`memberships` and `access` always run in `tenant` scope.

| Runs in       | Blocks                                                                                                                |
| ------------- | --------------------------------------------------------------------------------------------------------------------- |
| every scope   | `tags`, `comments`, and the blocks without tenant data (`notifications`, `profiles`, `queue`, `outbox`, `audit`, ...) |
| `tenant` only | every other block that requires `memberships` or `access`, and the blocks that require one of them                    |

In `tenant` scope each table a client can reach also gets a restrictive
`bsb_tenant_scope` policy, and so does each tenant table in `tables`. It
keeps rows to the caller's organizations and to what the block's own
policies grant (an invitee's invitation, a guest's granted invoice, a
user's own rows). Postgres combines permissive policies with `or`, so a
policy you add to a block table, even `using (true)`, can widen access
within the caller's organizations but never to another organization's
rows.

`blocks.memberships.names.organization` renames the tenant concept in the SQL
the blocks write:
`workspace` turns the `organizations` table into `workspaces`,
`organization_id` into `workspace_id`, `create_organization` into
`create_workspace` and `member_organization_ids` into `member_workspace_ids`.

```ts title="better-supabase.config.ts"
export default defineConfig({
  blocks: {
    memberships: { names: { organization: "workspace" } },
    organizations: {},
  },
});
```

`blocks.<name>.functions` renames single functions next to `tables` and
`columns`. Its keys are the default names, or the names after the tenant
rename; an unknown function is an error.

```ts title="better-supabase.config.ts"
blocks: {
  tags: { functions: { create_tag: "make_tag" } },
},
```

`blocks.<name>.names` renames a block's own entities. A string is the new
singular noun; an object takes it as `name`, plus `plural` when the English
plural is wrong, `url` for the page of one row and `subject: false` to keep
the entity out of the subject registry. A bare string for `entities` renames
the block's primary entity. `task: "ticket"` turns the `tasks` table into
`tickets`, `task_assignees` into `ticket_assignees`, `create_task` into
`create_ticket` and the subject type `task` into `ticket`:

```ts title="better-supabase.config.ts"
blocks: {
  tasks: { entities: { task: { name: "ticket", url: "/tickets/{id}" } } },
  contacts: { entities: { company: "account" } },
},
```

An entity rename reaches the TypeScript side too: method names, argument and
result keys, event types and the generated types. See
[Typed blocks](/docs/blocks/typed-blocks).

Every block that owns tables names its nouns this way, from `quotes`
(`quote`) and `orders` (`order`, `cart`) to `ai-chat` (`chat`, `project`) and
`hiring` (`job`, `application`, `interview`). Quotes, invoices, orders,
bookings and forms are also record types, so comments, attachments, tags and
activity can point at them. Chats, AI documents and knowledge documents stay
plain entities: only their owner or scope reads them, and a record type would
open them to every member with the block's read permission. JSON payload keys
the clients read (`orderId`, `promotionId`), the `/memories` path and ledger
account keys stored in rows (`invoices:cash:<code>`) keep their names.

You can rename the entities of a block you already installed. Change
`blocks.<name>.names`, then run `better-supabase upgrade`. It reads the
names from each file's `@bsb-names` line, compares the old and new module
SQL and writes guarded `alter ... rename` statements for the tables, columns,
indexes, policies, triggers and functions, so the rows stay where they are.
It also moves the permission keys in a role and permission catalog and the
stored `subject_type` values (comments, attachments, activity) to the new
names. Each statement checks that the old name still exists, so running it
twice changes nothing. Three things don't move: number sequence keys, outbox
events already recorded and your own hook functions (`before_work_item_create`),
so rename those yourself. When the two versions of a module don't pair up
object by object, `upgrade` stops with `config_invalid` and names the
module.

Some names stay as they are, so the TypeScript clients and event consumers
work under any tenant name:

- Function parameters, such as `organization` in `list_members`.
- Event types and payload keys (`organization.created`, `organizationId`)
  and permission keys.
- The access contract (`can`, `tenant_ids_with`, `is_platform`).
  `blocks.permissions.functions` keeps its meaning: the templates of the `custom`
  model.
- Tables and columns of your own that a block maps by name.

A tenant name that would rename a table or column to a name a block already
uses is refused. `team`, for example, can't run with `teams`, `profiles` or the
other blocks with a `team_id` column.

`better-supabase gen` writes the names to `blocks.generated.ts`, and
`defineBlocks` makes the block clients call the renamed functions; see
[renamed blocks](/docs/blocks/create-blocks#renamed-blocks).

## Existing tables: managed and custom

Each module has a contract: the functions policies, other modules and the
TypeScript side call. `blocks.<module>.ownership` decides what stands behind it.

| Ownership           | The module writes                                                                                       |
| ------------------- | ------------------------------------------------------------------------------------------------------- |
| `managed` (default) | its tables, policies and functions, and over a table your schema already has, only the columns it lacks |
| `custom`            | nothing: you write the contract functions, and [doctor](/docs/cli/doctor#bs307) checks them             |

`better-supabase blocks list --installed` marks custom modules, and `blocks view --sql <module>` shows
the signatures a custom module must provide. Not every module supports
`custom`; `memberships` and `access` do.

### Over your own tables

A managed block decides per table whether to create it. The CLI reads the
tables your app already has: your declarative schema files, or the schema
snapshot or live database for an app on migrations. When one of them is at the
block's default name, or at the name `blocks.<name>.tables` maps, the block
skips its `create table` for it. It adds only the columns it needs that your
table lacks, with `add column if not exists` (nullable unless the column has a
default), and writes its functions, policies, triggers and indexes over your
table. Tables the app doesn't have are created as usual. Most block tables can
run this way, and an optional column can still map to `null` to turn its
feature off.

There is no setting for this. An `ownership: "adopt"` left from an older
version fails config validation until you delete it or run
[`better-supabase codemod`](/docs/cli/codemod). The block's policies and
triggers on your table are named `bsb_<table>_<command>` and `bsb_<name>`,
and it never recreates your table or revokes your grants.
[Your own schemas](/docs/blocks/own-schemas) explains what the CLI detects,
the names, the doctor findings and how block files are protected.

The other keys rename what the module reads and writes, so an app keeps its
own names:

```ts title="better-supabase.config.ts"
export default defineConfig({
  blocks: {
    memberships: {
      tables: { memberships: "public.organization_users" },
      columns: { memberships: { tenant: "organization_id", lastUsedAt: null } },
      options: { claimFormat: "map" },
    },
    invitations: { permissions: { invite: "organization.members.invite" } },
  },
});
```

| Key                | What it sets                                                                                                                                                                                                                                          |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ownership`        | `managed` or `custom`                                                                                                                                                                                                                                 |
| `schema`           | the schema of the module's functions and managed tables (`database.sql.schema`, then `better_supabase`); `queue` takes none, and `access` keeps its functions in `better_supabase`                                                                    |
| `tables`           | logical table to `table` or `schema.table`; `null` for an optional table you don't have                                                                                                                                                               |
| `columns`          | logical table to logical column to column name; `null` for an optional column                                                                                                                                                                         |
| `idType`           | the tenant id type: `uuid` (default), `text`, `bigint` or `integer`                                                                                                                                                                                   |
| `permissions`      | block action to permission key, checked through the [access contract](/docs/repository/permissions)                                                                                                                                                   |
| `options`          | module options, listed on each module's page                                                                                                                                                                                                          |
| `hooks`            | where the module looks for the app's [SQL hooks](/docs/extending/events#sql-hooks)                                                                                                                                                                    |
| `events`           | `false` stops the module writing its events to the outbox                                                                                                                                                                                             |
| `audit`            | `false` stops the module writing its actions to the [audit log](/docs/blocks/audit#module-actions)                                                                                                                                                    |
| `api`              | a schema for the Data API that gets entry points for the module's functions (`database.sql.api` by default; see below), or `false` for none                                                                                                           |
| `ownTablePolicies` | `block` (default) or `app`: whether the module adds its `bsb_` policies, permissive and restrictive, on your tables (`database.sql.ownTablePolicies` by default; see [keeping your own policies](/docs/blocks/own-schemas#keeping-your-own-policies)) |

[`better-supabase add --adopt <block> --tables <schema.table>`](/docs/cli/presets#adopting-tables)
proposes the `tables` and `columns` of a block entry from the tables in
the database and reports what can't map, and
[`add --preset <code> --adopt`](/docs/cli/presets#adopting-existing-tables)
does the same for every block of a preset that has tables under its default
names.

A column of your table keeps the type the module writes, which is `text` for
names, kinds and subject types. A few of those may be an enum or a domain
instead, because the module casts what it writes through
`better_supabase.as_column_type` and compares as text: status columns, the
tags `kind` and `subjectType`, the numbering `entity` and the profiles
`locale`. Any other text
column the module writes a parameter or computed value into must take a text
value: `upgrade` and `add --adopt` refuse an enum there when the schema files
declare it, and doctor reports it as [BS342](/docs/cli/doctor#bs342). A
column the module only writes string literals into may be an enum whose
labels include those literals.

`organizations` and `profiles` also take `options.extraColumns`: your own
columns, keyed by name with their SQL type, which the module adds to its
managed table, copies on writes and returns from its reads. A name the module
already uses is refused. [Extending blocks](/docs/extending/blocks#your-own-fields)
shows how to type them in TypeScript.

### Calling a module over the Data API

The module schema holds tables and helpers that policies call, so it never
belongs in `[api] schemas` (doctor reports it as
[BS312](/docs/cli/doctor#bs312)). To call a module from a browser or an
isolate without a Postgres connection, give it an API schema:

```ts title="better-supabase.config.ts"
blocks: {
  settings: { api: "api" },
  notifications: {
    api: { schema: "api", functions: ["list_notifications", "notification_counts"] },
  },
},
```

To give every module the same API schema, set `database.sql.api` once. A module that
sets its own `api` keeps it, and `api: false` leaves a module without entry
points. `database.sql.schema` works the same way for the module schema.

```ts title="better-supabase.config.ts"
sql: {
  api: "api",
},
blocks: {
  settings: {},
  notifications: {},
  queue: { api: false },
},
```

`add` then writes a `security invoker` function in `api` for each module
function that `anon`, `authenticated` or `service_role` may execute, or only
those listed in `functions`, with the same name and arguments, granted to the
same of those roles. A list in `functions` adds to the functions the block's
TypeScript client calls, which always get a wrapper: with
`functions: ["check_rate_limit"]`, `rate-limit` still writes
`check_rate_limits` for `checkAll` and `purge_rate_limits` for `purge`. The wrapper runs as the caller, so the module's own
permission checks and RLS still apply, and a service function such as
`flag_definitions` stays callable by `service_role` only. Each wrapper
revokes execute from `public` and from every API role it isn't meant for,
so `alter default privileges in schema api grant execute on functions to
anon` (a common setup for an exposed schema) doesn't let `anon` call a
member or service function. Helpers that a
module grants to `authenticated` only so its own policies and triggers can
call them get no entry point, and `functions` refuses them:
`guard_membership_role` (organizations), `invitation_tenant_ids` and
`platform_invitations_readable` (invitations), `comment_subject_readable`
(comments), the `attachment_*` and `object_clean` policy helpers
(attachments), `incoming_webhook_tenant_ids` and
`incoming_webhook_subject_readable` (webhooks-in), `data_export_object_allowed`
(data-lifecycle), `mfa_satisfied` (mfa) and `session_active` (sessions). A
wrapper an earlier `upgrade` wrote for one of them is dropped. Add the
schema to `[api] schemas` in `config.toml` and pass it to the transport:

```ts
const client = createSettings({
  settings,
  transport: rpcTransport(supabase, { schema: "api" }),
});
```

An app server that reaches the database only through PostgREST uses the same
wrappers with a service-role client, for example for feature flags and
announcements:

```ts
const transport = rpcTransport(serviceClient, { schema: "api" });
const flags = createFlagsProvider({ transport });
const announcements = createAnnouncements({ transport });
const outbox = createOutbox({ transport, source: "https://app.example.com" });
```

An unknown table, column or module, or an ownership a module doesn't support, stops
`add` and `upgrade` with the valid names. Each file's header records the
module version and mode (`-- @bsb-block tenant@2 managed`), and the data migration
records them in `better_supabase.blocks`. An option a module doesn't read
stops `add` as well, so a misspelled option can't fall back to its default
without notice. Only `blocks.permissions` takes the access keys (`model`, `roles`,
`functions`, `activeTenant` and the rest).

## Audit log

`audit(table)` records every insert, update and delete of a table. The other
parameters name and filter what it writes:

```sql
select better_supabase.audit(
  'public.customers',
  ignore => '{updated_at}',
  redact => '{tax_id}',
  category => 'billing',
  event_prefix => 'customer',
  target_type => 'customer'
);
```

`audit()` keeps these settings on the table's `bsb_audit` trigger, as the
JSON argument of `audit_row_change`, and writes no rows. So a call in a
schema file leaves nothing a schema diff refuses (pg-delta rejects a table
that has rows after loading the schema), and the generated migration carries
the trigger with its settings; no data migration is needed. You can also
write the trigger yourself, which pg-delta orders after the table:

```sql title="supabase/schemas/020_customers.sql"
create trigger bsb_audit after insert or update or delete on public.customers
  for each row execute function better_supabase.audit_row_change(
    '{"ignore": ["updated_at"], "redact": ["tax_id"], "event_prefix": "customer"}'
  );
```

The argument takes `ignore`, `redact`, `key_columns` (the primary key by
default), `category`, `event_prefix`, `target_type`, `tenant_column` and
`label_column`, `tenant_path` and `tenant_function`. `audit_settings(table)`
returns a table's settings.

### Writes the secret key makes for a member

`server.admin({}, { as: userId })` sends the `x-bsb-actor` header on every
request. `better_supabase.acting_member()` returns that user for a service
caller (the `service_role` key or a direct admin connection) and null for
anyone else, so a signed-in user cannot name another user by sending the
header. The audit trigger and `audit_event()` record the acting member as the
actor when `auth.uid()` is null, and `track_actor()` uses it for `created_by`
and `updated_by`. Only `service_role` may execute `acting_member()`; the audit
and actor triggers run as their owner, so they call it for every writer. Your
own function that calls it must be `security definer` too.

A child table without a tenant column can still record its tenant.
`tenant_path => 'group_id -> directory_groups.organization_id'` reads
`organization_id` from the `directory_groups` row that `group_id` references;
each further `-> table.column` continues from there. `audit()` resolves every
hop through a single-column foreign key and fails when a hop has none.
`tenant_function => 'public.tenant_of(jsonb)'::regprocedure` instead names a
function that receives the row as `jsonb` and returns the tenant. The trigger
tries the row's own tenant column first, then the path, then the function.

When `ignore` is not empty, `audit()` installs two triggers: `bsb_audit` for
inserts and deletes, and `bsb_audit_update` with a `WHEN` clause that skips an
update where only ignored columns changed, so a write such as `last_run_at`
never starts the trigger. Calling `audit()` again without `ignore`, or
`unaudit()`, removes `bsb_audit_update`.

Each `audit()` call replaces every setting on the trigger: the last call
wins, and arguments it leaves out go back to their defaults. A second
`audit('public.customers')` therefore clears the app's `ignore` and
`redact`. Code that registers a table the app may already audit, such as another
package's migration, reads `audit_settings(table)` first
and passes the app's `ignore` and `redact` back in, or leaves the call to the
app. The pgTAP file `upgrade` writes for each audited table checks the
settings of the last call in the schema files and migrations, so it fails
when a function or seed replaces them at run time. A later call in a
migration changes what that file expects, so review the generated test in
the diff.

Tables
registered before this release keep their rows in `audited_tables`, and the
trigger reads them while it has no argument; calling `audit()` again moves
them onto the trigger.

`redact` columns are stored as `[redacted]` in the old and new records. The
event type is `<event_prefix>.created`, `.updated` or `.deleted` (the table
name without a prefix), and `tenant_column` overrides the tenant column for
this table. Events that are not row changes, like a sign-in or an export, go
through `audit_event`. It returns the entry id, and a repeated
`idempotency_key` returns the first entry instead of writing a second:

```sql
select better_supabase.audit_event(
  event_type => 'invoice.exported',
  category => 'billing',
  tenant => '6d1f...',
  metadata => '{"format":"csv"}',
  idempotency_key => 'export-42'
);
```

A job, a webhook handler or an admin tool that records an event as the
service role can say who acted and from where: `actor_id`, `actor_kind`
(such as `job` or `api-key`), `actor_label`, `request_id` (the request it
handled), `scope` (an adopted log's own value, or `memberships` and `platform`),
and, with the restricted table, `ip`, `user_agent` and `session_id`. The function takes these only from the
service role and direct admin connections; for any other caller it uses
`auth.uid()`, the request's JWT and headers, so a user can't record an event
in someone else's name. For the service role these three come only from
the arguments, never from the request, so a server that calls
`audit_event` over the Data API doesn't store its own address and user
agent as the user's. An event whose `restricted`, `ip`, `user_agent` and
`session_id` are all empty writes no restricted row. Without the restricted
table, passing `ip`, `user_agent` or `session_id` fails with `22023`, as
`restricted` does:

```sql
select better_supabase.audit_event(
  event_type => 'export.finished',
  actor_kind => 'job',
  actor_label => 'Nightly export',
  ip => '198.51.100.7',
  user_agent => 'export-worker/1.0',
  restricted => '{}'
);
```

The impersonation columns come from the caller's `act` claim. An event
about impersonation that the admin's own token records, such as a support
session starting or ending, passes them as `support_session`,
`impersonated_by` and `impersonation_reason`. The service role may pass any
values; another caller only itself as `impersonated_by`, and only from a
token without an `act` claim, whose values win otherwise:

```sql
select better_supabase.audit_event(
  event_type => 'support_session.started',
  category => 'security',
  support_session => session_id,
  impersonated_by => auth.uid(),
  impersonation_reason => reason
);
```

An app's own `security definer` function that acts for a client, such as a
role editor saving permissions, runs as its owner but still carries the
client's JWT, so `audit_event` would replace its actor context with the
client's. Such a function calls `better_supabase.audit_event_trusted`
instead: it takes the same arguments and honours `actor_id`, `actor_kind`,
`actor_label`, `scope` and the request details from its caller, with
`actor_id` defaulting to `auth.uid()`. Only its owner, the service role and
the roles in `trustedRoles` may execute it, so a client can't call it to
forge an actor, and the module writes no Data API entry point for it:

```sql
create function public.save_role_permissions(role_id uuid, keys text[])
returns void language plpgsql security definer set search_path = '' as $$
begin
  -- write the permissions, then:
  perform better_supabase.audit_event_trusted(
    event_type => 'role.permissions_saved',
    record_id => role_id::text,
    actor_kind => case when better_supabase.is_platform('roles.manage') then 'support' else 'user' end,
    scope => 'platform'
  );
end;
$$;
```

The module options (`blocks.audit.options`):

| Option                | Default                  | What it does                                                                                                                                                                                                                                                                                      |
| --------------------- | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tenantColumn`        | `auth.tenant.column`     | the tenant column of audited tables                                                                                                                                                                                                                                                               |
| `appendOnly`          | `true` when managed      | triggers reject updates, deletes and truncate; only `purge_audit_log`, running as its owner, deletes                                                                                                                                                                                              |
| `readPolicy`          | `false`                  | members read their tenants' entries with the `view` permission, platform staff all of them with `viewAll` (needs [access](/docs/repository/permissions))                                                                                                                                          |
| `impersonators`       | `show`                   | `hide` keeps the impersonation columns from `authenticated`                                                                                                                                                                                                                                       |
| `restricted`          | `false`                  | old and new records, IP address, user agent and metadata go to a separate `audit_events_restricted` table that only `service_role` reads; without it, `audit_event(restricted => ...)` fails with `22023`                                                                                         |
| `eventRoles`          | `['service_role']`       | the roles that can call `audit_event`                                                                                                                                                                                                                                                             |
| `trustedRoles`        | `[]`                     | roles besides the owner and `service_role` that can call `audit_event_trusted`, such as the owner role of your definer functions when it isn't the module's owner                                                                                                                                 |
| `eventCategory`       | `system`                 | the category of an `audit_event` call without one                                                                                                                                                                                                                                                 |
| `eventSource`         | `app`                    | the source of an `audit_event` call without one                                                                                                                                                                                                                                                   |
| `exempt`              | `[]`                     | `schema.table` globs (`public.*_archive`) that [doctor BS315](/docs/cli/doctor#bs315) doesn't expect an audit trigger on                                                                                                                                                                          |
| `tenantLabel`         | the organizations module | `schema.table.column` that `tenant_label` copies, matched on `tenantLabelKey` (`id` by default), for apps without the `organizations` module                                                                                                                                                      |
| `values`              | none                     | only over a log of your own: its values for `scope`, `actorKind`, `outcome`, `source` and `category`, see below                                                                                                                                                                                   |
| `metadataColumns`     | none                     | only over a log of your own: its own columns that `audit_event` fills from a key of its `metadata`, such as `{ ticket_id: "ticketId" }`; the value is converted to the column's type, a missing key leaves the column to its default, and `list_audit_events` returns the columns under `columns` |
| `keepMappedMetadata`  | `false`                  | keeps the keys `metadataColumns` maps in the stored `metadata` too; by default they are removed, since the columns hold them                                                                                                                                                                      |
| `requestIdHeader`     | `x-request-id`           | the Data API header `request_id` is read from when the `better_supabase.request_id` setting is empty                                                                                                                                                                                              |
| `correlationIdHeader` | `x-correlation-id`       | the Data API header `correlation_id` is read from when the `better_supabase.correlation_id` setting is empty                                                                                                                                                                                      |

`add` and `upgrade` read the `audit(...)` calls and `bsb_audit` triggers in
your schema files and migrations, and write a pgTAP file per audited table to `database.sql.testsDir`
(`supabase/tests/900_better_supabase_audit_public_customers.test.sql`). It
checks that the table has the `bsb_audit` trigger and is registered with the
same `ignore` and `redact` lists, then runs an insert, an update and a delete
on a copy of the table and checks the entries: one per change, without the
ignored columns, with the redacted values masked. `supabase test db` runs it
with your other tests, and `upgrade --check` fails when a registration changed
and the file is stale. A later `unaudit(...)` call or `drop table` removes
the table's file on the next `upgrade`. Calls with computed arguments, such
as `audit(format(...))`, are skipped.

Dropping an audited table also drops its registration: the module installs
a `sql_drop` event trigger (`bsb_audit_forget_dropped`) that deletes the
table's row from `better_supabase.audited_tables`, so install the module as
`postgres`, which supautils lets create event triggers. `unaudit` takes the
table name as text, so a migration can still call
`select better_supabase.unaudit('public.old_notes')` after the table is
gone; it then clears the registrations of tables that no longer exist.
Tables dropped before the event trigger existed keep their rows; the
module's data file deletes them, so the next `add --adopt` migration cleans
them up, and [doctor BS322](/docs/cli/doctor#bs322) reports any that remain
on a database.

An app with its own audit table keeps it: map `blocks.audit.tables.log` and
`columns.log` to your names, and `null` the columns you don't want (the row
snapshots or `supportSession`, for example). The module then writes into your
table and never creates it; it adds the columns it needs that your table
lacks.

When your log uses its own words for the same values, map them with
`options.values`: the module's value to yours, per column. Writes store your
values, and `list_audit_events` (and so `createAudit`) reads them back as
the module's, so exports and OCSF mapping keep working. Doctor reports the
option as migration-only ([BS314](/docs/cli/doctor#bs314)).

```ts title="better-supabase.config.ts"
export default defineConfig({
  blocks: {
    audit: {
      tables: { log: "public.activity_log" },
      columns: {
        log: {
          tenant: "workspace_id",
          actorKind: "actor_type",
          tenantLabel: "workspace_name",
        },
      },
      options: {
        values: {
          scope: { tenant: "workspace", platform: "global" },
          actorKind: { user: "member", service: "api" },
          outcome: { success: "ok", failure: "error" },
          source: { database: "db" },
          category: { data: "record", system: "platform" },
        },
        tenantLabel: "public.workspaces.title",
        tenantLabelKey: "workspace_id",
      },
    },
  },
});
```

`source` covers row changes (`database`) and `audit_event` calls alike, and
`category` maps the defaults (`data` for row changes, `eventCategory` for
events) and any category a registration or an `audit_event` call names.
Values without a mapping are stored as they are. Two module values can't map
to the same stored value, because reads couldn't tell them apart.

### Context columns

Every entry also records what an audit page shows, as it was at the time:

| Column           | What it holds                                                                                       |
| ---------------- | --------------------------------------------------------------------------------------------------- |
| `actor_kind`     | `user`, `service`, `support`, `impersonation`, `oauth-client` or `system`, from the claims          |
| `actor_label`    | the actor's `full_name` metadata or email                                                           |
| `tenant_label`   | the organization's name, with the `organizations` module or `options.tenantLabel`                   |
| `target_label`   | the value of the table's `label_column` (`audit(..., label_column => 'title')`), or `audit_event`'s |
| `summary`        | `audit_event(summary => ...)`                                                                       |
| `request_id`     | the request id, see below                                                                           |
| `correlation_id` | `audit_event(correlation_id => ...)`, or the request's correlation id, see below                    |
| `scope`          | `tenant`, or `platform` for entries without a tenant                                                |

With `restricted`, the restricted table also keeps the `session_id` claim and
`changed_values`: `{ column: { old, new } }` for each changed column (every
column on insert and delete), redacted like the records and cut at 1000
characters, so one change can be revealed without the whole rows. A managed
log has all of these columns; on a log of your own the module writes the
ones that `columns.log` and `columns.restricted` don't map to `null`.

### Request and correlation ids

Row changes and `audit_event` calls record the request id and the correlation
id of the request that made them, so an audit page can show one user action
as the event plus the rows it changed. Each id comes from the first of:

1. the `audit_event` argument (`request_id` counts only for the service role
   and direct admin connections, like the other actor details),
2. the transaction-local setting `better_supabase.request_id` or
   `better_supabase.correlation_id`, which a server sets over direct Postgres
   with `set_config(..., true)`,
3. the Data API request header, `x-request-id` or `x-correlation-id` unless
   the `requestIdHeader` and `correlationIdHeader` options name others.

`better_supabase.request_id_or_null(value)` keeps an id of 1 to 128
characters from `A-Z`, `a-z`, `0-9` and `. _ : ; , @ / + = -` and turns
anything else into null, so an invalid value falls through to the next
source. The ids are metadata a client can set; never use them for access
decisions. [`createServer`](/docs/auth/server#request-and-correlation-ids)
sends both on every request without configuration.

A managed log indexes `correlation_id`. Group an action's entries with the
`for_correlation_ids` filter, or in SQL:

```sql
select occurred_at, op, event_type, table_name, record_id, changed
from better_supabase.audit_events
where correlation_id = 'checkout/42'
order by occurred_at, id;
```

From TypeScript, `audit.list({ correlationId: ctx.correlationId })` returns
the same entries.

### Registering many tables

A project with a hundred tenant tables doesn't write a hundred `audit(...)`
lines by hand. `audit_schema_calls` prints them for every table in a schema
with the tenant column, minus exempt name patterns:

```sql
select better_supabase.audit_schema_calls('public', 'organization_id', '{audit_%,%_archive}');
```

Paste the output into a schema file, and override single tables with their
own `audit(...)` call after it. Static calls keep their place in a pg-delta
diff; a loop over the catalog in a schema file runs before the tables exist
(doctor [BS318](/docs/cli/doctor#bs318)). For a migration or a one-off script,
`audit_schema(schema, tenant_column, exempt)` registers the tables that aren't
registered yet and returns how many. Doctor [BS315](/docs/cli/doctor#bs315)
flags any table left out.

The [audit block](/docs/blocks/audit) reads the log from TypeScript: a list
query, NDJSON and OCSF exports, and retention per tenant. In SQL,
`list_audit_events` lists the entries the caller can read, and
`reveal_audit_entry(entry)` returns an entry's restricted details and records
the read as `audit.revealed`. `reveal_audit_entries(entries)` does the same
for a list of entry ids, such as one page of an export: it returns the
details of the entries the caller may reveal, skips the rest, and records
one `audit.revealed` entry per tenant with the ids in `metadata.entries`.

## Retention

The audit log, the webhook inbox and delivery log, the rate-limit counters
and the job archives only grow. Each module has a purge function that deletes
rows older than an interval, at most `batch` rows per call (10,000 by
default), and returns how many it deleted. Only `service_role` can call them.

| Function                                                                         | TypeScript                                   | Deletes                                                                                                            |
| -------------------------------------------------------------------------------- | -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `purge_audit_log(older_than => '1 year')`                                        | `purgeAuditLog(source, options)`             | `audit_events` entries older than `older_than`, or than the tenant's own interval                                  |
| `purge_webhooks(older_than => '30 days')`                                        | `inbox.purge()`, `purgeWebhookInbox(source)` | processed messages; `include_dead => true` also deletes dead ones                                                  |
| `purge_job_archive(queue, older_than => '7 days', dead_older_than => '30 days')` | `jobs.purge()`                               | completed jobs, and dead jobs after their own retention (`pgmq.a_<queue>`, or `job_messages` on the table backend) |
| `purge_idempotency_keys()`                                                       | `idempotency.purge()`                        | expired idempotency keys                                                                                           |
| `purge_webhook_deliveries(older_than => '30 days')`                              | `webhooks.purge()`                           | succeeded and canceled outgoing deliveries; `include_dead => true` also deletes dead ones                          |
| `purge_rate_limits()`                                                            | `rateLimit.purge()`                          | counters whose window has ended or whose rule was removed                                                          |
| `purge_usage_history(older_than => '400 days')`                                  | `usage.purgeHistory()`                       | usage history entries                                                                                              |
| `purge_usage_events(older_than => '30 days')`                                    | `usage.purgeEvents()`                        | idempotency keys of recorded usage                                                                                 |

Schedule them with [pg_cron](https://supabase.com/docs/guides/cron) at a quiet
hour. Enable the extension once (`create extension pg_cron with schema
pg_catalog`), then:

```sql
select cron.schedule('purge-audit-log', '15 3 * * *', $$select better_supabase.purge_audit_log()$$);
select cron.schedule('purge-webhooks', '30 3 * * *', $$select better_supabase.purge_webhooks()$$);
select cron.schedule('purge-emails-archive', '45 3 * * *', $$select better_supabase.purge_job_archive('emails')$$);
select cron.schedule('purge-idempotency-keys', '0 4 * * *', $$select better_supabase.purge_idempotency_keys()$$);
select cron.schedule('purge-webhook-deliveries', '45 3 * * *', $$select better_supabase.purge_webhook_deliveries()$$);
select cron.schedule('purge-rate-limits', '*/15 * * * *', $$select better_supabase.purge_rate_limits()$$);
```

Tenants can keep entries for different periods, a plan's retention for
example. Write an `audit_retention(tenant)` function that returns an interval
(or null for the default) in the schema `blocks.audit.callbacks` points at, and
`purge_audit_log` uses it for every entry. Like every SQL hook, it is
optional: the module calls hooks through dynamic SQL, so `supabase db lint`
passes without them. To decide in TypeScript instead,
call `purgeAuditLog` from [`better-supabase/blocks/audit`](/docs/blocks/audit) in a scheduled job:

```ts
import { purgeAuditLog } from "better-supabase/blocks/audit";

await purgeAuditLog(postgres.admin, {
  olderThan: "1 year",
  retention: async (tenant) =>
    tenant ? await plans.auditDays(tenant) : undefined,
});
```

Each TypeScript method takes the same options in camel case (`olderThan` in
seconds or as an interval, `includeDead`, `batch`) and returns how many rows
it deleted as a `Result`. Each object also has a `purgeJob(options)` that
returns a job handler, so the purges can run on the [jobs](/docs/blocks/queue)
scheduler instead of pg_cron. They work over a service SQL connection or a
service-role transport, so an app without a direct connection can schedule
them too:

```ts
const jobs = createQueue({
  sql: postgres.admin,
  queues: { purge: v.object({}) },
});

await jobs.schedule("retention", "0 4 * * *", "purge", {}).orThrow();

await jobs.work("purge", async (payload, job, signal) => {
  await idempotency.purgeJob()(payload, job, signal);
  await jobs.purgeJob({ deadOlderThan: "90 days" })(payload, job, signal);
});
```

When a table holds more old rows than one batch, the next run picks up the
rest; run the job more often, or raise `batch`, until it keeps up. Keep the
webhook retention above your senders' retry window: a retried message whose id
was purged is stored and processed again.

## Support sessions

`impersonation` records who viewed the app as whom, for
[support mode](/docs/auth/impersonation). It needs `permissions` and `audit`.
`start_support_session(target, reason, ttl, read_only, metadata, tenant)`
checks `is_platform('impersonation.start')` for the caller, ends the caller's
previous session, writes `support_session.started` to the audit log and returns the
session as jsonb. An admin has one active session (a unique index). It refuses
a target with platform permissions and a writable session unless the options
below allow them. Under the `provider` access model, a target holds platform
permissions when a row in `invitations.options.platformRoles.table` names them,
and, with `platformRoles.through.where`, only when that row's role matches the
condition, so a roles table that also holds tenant roles counts only its
platform ones. `end_support_session(session_id)` ends it for its admin
(`ended_by` is `admin`), a caller with `impersonation.revoke` (`revoked`) or the
service role, which alone passes `ended_by`. `expire_support_sessions()`,
for the service role only, ends every running session past its expiry with
`ended_by` set to `expired` and returns them, so each one gets its
`support_session.ended` entry. `active_support_session` called
as the admin checks `impersonation.start` again. Errors carry `SUPPORT_FORBIDDEN`,
`SUPPORT_SELF`, `SUPPORT_TARGET_MISSING`, `SUPPORT_TARGET_PLATFORM`,
`SUPPORT_WRITES_DISABLED`, `SUPPORT_TTL`, `SUPPORT_REASON_REQUIRED` or
`SUPPORT_APPROVAL_REQUIRED` in the `hint`.

A start needs a second admin by default (`options.approval: "distinct"`).
The admin asks with `request_support_session(target, reason, read_only,
metadata, tenant)`, which runs the same checks as a start and stores a row in
`support_requests`. Another admin approves it with
`approve_support_request(request_id)`. `start_support_session` then uses the
newest approved, unused request for the same admin, target and tenant (a
read-only approval never starts a writable session) and records its id and
approver in the `support_session.started` audit entry. A request is open for
`approvalTtl` and starts one session.

The requester never approves their own request: `approve_support_request`
refuses it with `SUPPORT_SELF_APPROVAL`, and the
`support_requests_distinct_approver` check constraint refuses the row even
for the service role. Clients can read their own requests but can't insert
or update the table. Without an authorization provider, an approver needs
`is_platform('impersonation.start')` (rename it with
`blocks["impersonation"].permissions.approve`). With one that sets
[`isApprover`](/docs/extending/authorization-providers#approvals), the module
calls it with `{kind}` `'support-session'` and `{subject}` the request id
instead. The service role may pass `admin_id`, `approved_by` and
`approver_id` for decisions the server already made; `approved_by` still
can't be the admin. `support_request(request_id)` returns a request to the
service role, its requester and its approvers, and
`approved_support_request(target, tenant, read_only)` the request a start
would use. Errors carry `SUPPORT_REQUEST_MISSING`, `SUPPORT_REQUEST_DECIDED`
(another admin approved it) or `SUPPORT_REQUEST_CLOSED` (expired or used).

A read-only session (`read_only` true, the default) is refused by every
`security definer` write granted to `authenticated` or `anon`, with
`ACTOR_READ_ONLY` and SQLSTATE `42501`. The same refusal covers a support
`act` unless `read_only` is `false`, an agent `act` with `read_only: true`,
an impersonation `act` or one of another `kind`, and an `act` that has
`session_id` and no `kind`. Reads are unchanged.
These functions stay callable so the session can be opened and closed:
`start_support_session`, `end_support_session` and `expire_support_sessions`.
`check_request` stays callable too: it counts the request for the rate limit
and runs before reads.
With an authorization provider, set `authorization.functions.actorMayWrite`
and the writes call that instead of the built-in check.

| Option                 | Default    | What it does                                                                    |
| ---------------------- | ---------- | ------------------------------------------------------------------------------- |
| `maxTtl`               | `4 hours`  | the longest session `start_support_session` accepts                             |
| `requireReason`        | `true`     | refuses a start or request with an empty or blank reason                        |
| `approval`             | `distinct` | `none` starts without a second admin's approval                                 |
| `approvalTtl`          | `1 hour`   | how long a request stays open for approval and a start                          |
| `allowWrites`          | `false`    | accepts `read_only => false`                                                    |
| `allowPlatformTargets` | `false`    | lets a session target platform staff                                            |
| `auditCategory`        | `support`  | the audit log category of `support_session.started` and `support_session.ended` |
| `claimsHook`           | none       | `schema.function` of your access token hook, for `support_target_claims`        |

The permission keys are `impersonation.start`, `impersonation.read` and `impersonation.revoke`;
rename them with `blocks["impersonation"].permissions`. The hooks
`before_support_start(admin, target, reason, metadata)`,
`after_support_start(session_id)` and `after_support_end(session_id)` run in
the schema `hooks.schema` names. The module runs over an existing sessions
table: the `memberships`, `readOnly`, `endedBy` and `metadata` columns are
optional. It still creates `support_requests` unless `tables.requests` names
your own table; `tables.requests: null` needs `options.approval: "none"`.

```ts title="better-supabase.config.ts"
blocks: {
  "impersonation": {
    tables: { sessions: "public.impersonation_sessions" },
    columns: { sessions: { admin: "impersonator_id", metadata: null } },
    permissions: { start: "system.users.impersonate" },
    options: { claimsHook: "public.custom_access_token_hook" },
  },
},
```

## Rate limiting writes

Auth rate-limits sign-ins, but the Data API has no limit of its own: a signed-in
user can call `insert` or an RPC as often as they like. The `rate-limit` module
counts writes in PostgREST's
[pre-request hook](https://docs.postgrest.org/en/v12/references/transactions.html#pre-request),
before the query runs:

```bash
better-supabase add rate-limit
```

```sql
-- 5 invites per user per minute, 300 writes per user per minute overall.
select better_supabase.set_rate_limit('/rpc/send_invite', 5, interval '1 minute');
select better_supabase.set_rate_limit('*', 300, interval '1 minute');

-- Per tenant instead of per user: count by the tenant_id claim.
select better_supabase.set_rate_limit('/customers', 1000, interval '1 hour', key_claim => 'tenant_id');

-- Remove a rule.
select better_supabase.set_rate_limit('/customers', null);
```

- A scope is `*`, a table path (`/customers`) or an RPC path
  (`/rpc/send_invite`). Every matching rule counts, so `*` and a path rule
  both apply.
- Only `POST`, `PATCH`, `PUT` and `DELETE` count. GET and HEAD run read-only
  and may be served by a [read replica](/docs/guides/read-replicas). A `POST`
  to `/rpc` for a `stable` or `immutable` function also runs in a read-only
  transaction, so `check_request()` skips it instead of failing the call.
- Callers without the claim (anonymous) are counted by the right-most
  `x-forwarded-for` hop, the one the API gateway appends; clients can forge
  the hops before it. The service role is never limited.
- Counters live in an unlogged table: fast, and reset after a crash.
- A write over the limit fails with HTTP 429 and a `Retry-After` header. The
  repository returns it as a `rate_limited` [`DbError`](/docs/concepts/results)
  with `retryAfter` in seconds, and `problemResponse()` passes the header on.

The module's data file sets `pgrst.db_pre_request` on the `authenticator`
role, and only if no other pre-request function is set. Neither diff engine
captures role settings, so the setting ships in the migration `add --adopt`
writes. Doctor warns (BS313) when a live database has no pre-request hook, or
one that doesn't call `check_request()`. If you already have a pre-request
function, keep it and call the check from it. Put it in a schema the Data API doesn't expose, so clients
can't call it through `/rpc`. Set `options.preRequest: false` to leave the
setting to your own function: the data file then removes a setting that
still points at `check_request()` instead of adding one.

```ts title="better-supabase.config.ts"
export default defineConfig({
  blocks: { "rate-limit": { options: { preRequest: false } } },
});
```

```sql
create schema if not exists private;
create or replace function private.pre_request() returns void language plpgsql as $$
begin
  perform better_supabase.check_request();
  -- your checks
end $$;
```

The hook runs only for the Data API. Queries through
[`better-supabase/postgres`](/docs/auth/postgres) and `ctx.sql` aren't limited.

### Limits in route handlers

Public endpoints often limit by something other than a claim: a token in the
URL, an organization, an AI chat thread. `hit_rate_limit(scope, key)` counts
one hit of `key` with the same rules and counters, and `createRateLimit` from
[`better-supabase/rate-limit`](/docs/rate-limit) calls it from a route handler. `rateLimited()`
answers a refused hit with a `problem+json` 429 and `Retry-After`:

```ts
import { createRateLimit, rateLimited } from "better-supabase/rate-limit";

const limits = createRateLimit({ sql: postgres.admin });

export async function POST(
  request: Request,
  { params }: { params: { token: string } },
) {
  const hit = await limits.check("public-webhook", params.token).orThrow();
  if (!hit.allowed)
    return rateLimited(hit, { instance: new URL(request.url).pathname });
  // handle the request
}
```

Apps that reach the database over the Data API instead of a direct
connection pass a service-role `BlockTransport`, like the other blocks:
`createRateLimit({ transport: rpcTransport(adminClient) })`. It calls
`check_rate_limit(scope, key, max_requests, period)`, which returns the same
decision as JSON; with `blocks.rate-limit.api` set, pass the API schema
as `rpcTransport(adminClient, { schema: "api" })`. The `hooks` option runs
around `check` and `purge`, and the `purgeJob` handler calls `purge` through
them. `createBlocks` builds it from its shared `transport`, like the other
blocks.

The limit is the scope's rule from `set_rate_limit`, or one given per call
(`check("chat", threadId, { max: 20, period: "1 minute" })`). A scope with
neither fails with `RATE_LIMIT_UNKNOWN`. Counters are shared by every
instance, unlike an in-memory map on serverless functions.
`purge_rate_limits()` removes counters without a rule after a day, so keep a
per-call `period` under a day or define the rule.

### Several limits at once

A sign-in route often limits per user, per IP and per organization.
`checkAll` counts one hit against several limits in one database round trip
(`check_rate_limits(hits)`), and the hit counts only when every limit allows
it, so a refused attempt leaves all counters as they were. Each limit takes
its own scope and key; two windows on the same key take two scopes, such as
`login:minute` and `login:day`:

```ts
const hit = await limits
  .checkAll([
    { scope: "login:user", key: email, rule: { max: 5, period: "15 minutes" } },
    { scope: "login:ip", key: ip, rule: { max: 50, period: "1 hour" } },
  ])
  .orThrow();

if (!hit.allowed) return rateLimited(hit);
```

`blocked` names the first limit over its maximum (`index`, `scope`, `key`),
`retryAfter` is the longest wait of the refusing limits, `remaining` the
lowest of all, and `results` holds one decision per limit. The counters are
locked in a fixed order, so concurrent calls over the same keys never
deadlock. A list that names one scope and key twice fails with
`RATE_LIMIT_HITS`, a scope without a rule or a per-call one with
`RATE_LIMIT_UNKNOWN`.

### Limits as middleware

The [Hono](/docs/frameworks/hono#rate-limits) and
[oRPC](/docs/frameworks/orpc#rate-limits) adapters wrap `check` in a
`rateLimit()` middleware. Responses then carry the `RateLimit` field of
draft-ietf-httpapi-ratelimit-headers (`SPEC_PINS.ratelimitHeaders`), and
`RateLimit-Policy` when the route gives a `rule`. A refused request gets a
429 with `Retry-After`. Elsewhere, `rateLimitHeader()` and
`rateLimitPolicyHeader()` from `better-supabase/server` build the two fields.

## Enforcing jsonb shapes

Give a `json` entry a `schema` and `better-supabase add jsonb-schemas` adds a
[pg_jsonschema](https://supabase.com/docs/guides/database/extensions/pg_jsonschema)
check constraint, so the database rejects rows the generated types would
reject. `schema` takes a JSON Schema object, or any Standard JSON Schema value
(zod 4, valibot, arktype):

```ts title="better-supabase.config.ts"
import { toStandardJsonSchema } from "@valibot/to-json-schema";
import * as v from "valibot";

export const CustomerMetadata = toStandardJsonSchema(
  v.object({
    source: v.string(),
    tier: v.optional(v.picklist(["free", "pro"])),
  }),
);

export default defineConfig({
  gen: {
    json: {
      "customers.metadata": {
        import: "./lib/metadata.ts#CustomerMetadata",
        schema: CustomerMetadata,
      },
    },
  },
  blocks: ["jsonb-schemas"],
});
```

Each constraint is added `not valid` and then validated in its own
statement, so existing rows that don't match make the migration fail. Fix
those rows first. On a large table, move the `validate constraint` statement
to a later migration: adding a `not valid` check blocks writes only briefly,
and validating takes a lock that lets writes continue. Re-run `add` after
you change a schema.

Next to each constraint, a `before insert or update` trigger of the same name
calls pg_jsonschema's `jsonschema_validation_errors`. A row that fails raises
SQLSTATE `23514` with the hint `JSON_SCHEMA_INVALID` and the errors as a JSON
array in `DETAIL`, so the repository returns a `validation` error with one
issue per schema error, at the column's database name:

```ts
// metadata came from a request body as { source: "web", tier: "gold" }
const result = await db.customers.update(id, { metadata });
if (!result.ok && result.error.kind === "validation") {
  result.error.issues;
  // [{ message: '"gold" is not one of ["free","pro"]', path: ["metadata"] }]
}
```

The check constraint stays for rows written while triggers are off, such as a
restore with `session_replication_role = replica`; its failures also map to
`validation`, with one issue for the whole value.

## Subject registry

Tags, comments, attachments, reminders and the other modules that attach to
your rows take the record types they attach to from `on`. Declare the types
once in `config.subjects`, and every block that you don't give its own `on`
uses the registry.

A record type is lowercase letters, digits, hyphens and underscores, starting
with a letter, such as `purchase_order` or `purchase-order`, so a type your
rows already store with hyphens can be registered as it is. Blocks write it
as a string value; a trigger or function named after it takes underscores in
place of hyphens (`bsb_field_history_purchase_order`), so two types that
differ only there, such as `purchase-order` and `purchase_order`, are refused.

```ts title="better-supabase.config.ts"
import { defineConfig } from "better-supabase/config";

export default defineConfig({
  records: {
    task: {
      table: "public.tasks",
      idType: "uuid",
      title: "title",
      url: "/projects/{project_id}/tasks/{id}",
      permissions: { read: "tasks.read", update: "tasks.update" },
      rank: { column: "rank", group: "status" },
    },
    customer: { table: "public.customers", title: "name" },
  },
  blocks: ["memberships", "permissions", "subjects", "tags", "comments"],
});
```

| Key           | Default           | What it sets                                                                                                                                                   |
| ------------- | ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `table`       | required          | The table, as `table` or `schema.table`                                                                                                                        |
| `id`          | `id`              | The id column                                                                                                                                                  |
| `idType`      | compared as text  | The id column's type (`uuid`, `bigint`), so lookups use its index                                                                                              |
| `tenant`      | `organization_id` | The tenant column, or `false` for a subject without one                                                                                                        |
| `title`       | none              | The column `subject_title` returns                                                                                                                             |
| `url`         | none              | A path template whose `{column}` placeholders `subject_url` fills from the row                                                                                 |
| `permissions` | none              | Action to permission key, or to `{ key, rows, owner, also, check }` (see below); `read` is the key modules check before they attach to the row                 |
| `scope`       | none              | A record scope to check the keys in, for subjects without a tenant                                                                                             |
| `cascade`     | none              | Delete a module's rows when the subject row is deleted                                                                                                         |
| `deletedAt`   | none              | A soft-delete column; rows where it is set count as gone                                                                                                       |
| `search`      | none              | `title` and `body` columns for search, plus `description`, `exclude`, `from` and `watch` ([Search](/docs/blocks/search#labels-descriptions-and-archived-rows)) |
| `rank`        | none              | The rank column and an optional group column (such as `status`) that `move` uses                                                                               |
| `readAccess`  | `tenant`          | `record` makes `custom-fields` show a value only to members who can read the record, through the `read` entry                                                  |
| `team`        | none              | `{ actions }`: the actions a record team grants on each row ([Record teams](#record-teams))                                                                    |
| `auditReads`  | `false`           | Log each read through the blocks' read functions in the audit log ([Record read log](#record-read-log))                                                        |

A block's `on` works three ways:

- unset: the block uses every registered type. Blocks that need a tenant
  skip the types with `tenant: false`.
- a list of names, `on: ["task"]`: the block uses those registered types, and
  an unknown name fails `gen` (doctor reports it as BS346).
- an object: each entry merges onto the registered one, and the block's
  keys win, so an entry for a registered type can leave out `table` and
  `idType`. `add`, `upgrade`, `gen` and doctor read the merged entry. A type
  the registry lacks needs its own `table`.

`webhooks-in` never falls back to the registry, because its subjects are the
tables that inbound events write to.

Subject types are lowercase letters, digits and underscores. The
`notifications` block's own `on` keys may also contain hyphens
(`time-off-request`), because its `subject_type` column takes any text.

The `subjects` module installs four functions in the `better_supabase`
schema. Each runs as the caller, so the subject table's own policies decide
what is visible:

| Function                                          | Returns                                                                                                                                                                                                          |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `subject_types()`                                 | The registered types                                                                                                                                                                                             |
| `subject_title(subject_type, id)`                 | The `title` column, or null when the row is hidden, deleted or the type has no title                                                                                                                             |
| `subject_url(subject_type, id)`                   | The `url` template filled from the row, or null                                                                                                                                                                  |
| `subject_titles(refs)`                            | A `jsonb` array of `{ type, id, title, url }` for up to 500 `{ type, id }` refs, as the caller; hidden, deleted and unknown refs are left out ([Subjects](/docs/repository/record-types))                        |
| `can_subject(subject_type, id, action)`           | True when the caller can see the row and holds the action's key from `permissions` in the row's tenant                                                                                                           |
| `can_subject_for(user, subject_type, id, action)` | The same for another user, service role only: the row exists and `can_user` grants the action's key; false for an action without a key or a provider that can't answer for others, and a share link never counts |

An action without a key in `permissions` checks only that the caller can see
the row. The service role passes every key check.

#### Actions granted per row

An action can be granted in more ways than a tenant key. Give it an object
instead of a key:

```ts title="better-supabase.config.ts"
export default defineConfig({
  records: {
    file: {
      table: "public.files",
      idType: "uuid",
      permissions: {
        read: { key: "file.read", rows: "file" },
        share: { key: "file.update", rows: "file" },
      },
    },
    thread: {
      table: "public.threads",
      permissions: { share: { owner: "owner_user_id" } },
    },
  },
});
```

| Key     | Grants the action when                                                                                           |
| ------- | ---------------------------------------------------------------------------------------------------------------- |
| `key`   | the caller holds the key in the row's tenant, or on the record through `scope`, as a plain key does              |
| `rows`  | the authorization provider lists the row among the rows of that resource the caller holds `key` on (needs `key`) |
| `owner` | the uuid column it names holds the caller's id                                                                   |
| `also`  | never alone: the caller must also hold this key in the row's tenant (or on `scope`)                              |
| `check` | the SQL function it names, `(subject_id <idType>) returns boolean`, returns true for the row and the caller      |

Any one of `key`, `rows` and `owner` grants the action. With `also`, the
caller needs that key too, so `{ key: "file.read", rows: "file", also:
"files.access" }` asks for a row grant (or the key) and the tenant key both.
`rows` is the resource as the provider
names it in SQL (`file_node`); it needs `blocks.permissions.model: "provider"`
and a provider with the `rowsWith` template (see
[Authorization providers](/docs/extending/authorization-providers)). For
`can_subject_for`, row grants count only when the provider also has
`rowsWithFor`, and `owner` compares the column with the given user.

`check` names a schema-qualified function, such as
`better_supabase.drive_node_writable`, that answers for the caller
(`auth.uid()`). Use it when the grants live in your own tables, as the drive's
per-node grants do. Alone it decides the action; next to `key`, `rows` or
`owner` the function must return true as well, so
`{ key: "drive.read", check: "better_supabase.drive_node_readable" }` asks
for the key and a grant on the node. A null result counts as false.
`can_subject` still requires that the caller can see the row.
`can_subject_for` can't run the function for another user, so it returns
false for that action. The function runs inside every check, so keep it a
cheap `stable` lookup.

Blocks that act on a record ask `can_subject` for the action when the record
type declares it, on top of their own key: `tags` checks `tag` before it
puts a tag on a record or takes it off, `custom-fields` checks `fields` before
it sets or deletes a value, `share-links` checks `share` before it creates,
lists or revokes a link, and `comments` follows `read`, `comment` and
`moderate`. A record type that declares none of them keeps the block's own
checks.

A block that checks whether the caller may read a record (tags, attachments,
share links, versions, relations and the others that take `on`) reads the
same `read` entry: with `rows` or `owner`, the key, the provider's row grants
and the owner column each grant the read, as in `can_subject`. An `on` entry
that sets its own `permission` keeps that key.

#### Record teams

Give a record type a `team` to put people on one record: a patient's care
team, the account team on a customer, the investigators on a case. Members of
the record's team get the listed actions on that row, on top of what their
tenant role grants.

```ts title="better-supabase.config.ts"
export default defineConfig({
  records: {
    patient: {
      table: "public.patients",
      title: "name",
      permissions: { read: "patients.read" },
      team: { actions: ["read", "write"] },
    },
    customer: {
      table: "public.customers",
      title: "name",
      permissions: { read: "customers.read", write: "customers.update" },
      team: { actions: ["read", "write"] },
    },
    case: {
      table: "public.cases",
      title: "title",
      team: { actions: ["read"] },
    },
  },
  blocks: ["memberships", "permissions", "teams", "subjects"],
});
```

An action with a `permissions` entry stays open to holders of that key, and
the team grants it too, so a care team reads its patients without
`patients.read`. An action that only `team` lists, such as `write` on
`patient`, is granted to the team alone. A type with a team needs a tenant
column, because each membership row belongs to the record's tenant.

A type a block registers, such as `person` from
[contacts](/docs/blocks/contacts#use-them-as-subjects), takes `team` and
`auditReads` on its entity in `blocks.<name>.names`. Setting either on an
entity that isn't a subject, or that sets `subject: false`, fails when the
config loads.

The `subjects` block stores the members in `subject_members`. A row names a
user or a team from the [`teams`](/docs/blocks/teams) block, a role and the
days it counts (`starts_on` and `ends_on`, both included). A membership
counts from `starts_on` through `ends_on`, so access stops the day after a
membership ends, without a job to revoke it. A row the
[access-requests](/docs/blocks/access-requests#record-access) block grants
also has `ends_at`, the exact time it stops counting, and `emergency` for
[emergency access](/docs/blocks/access-requests#emergency-access); the client
reads it as `endsAt`.

| Function                                                                                   | What it does                                                                                        |
| ------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------- |
| `add_subject_member(subject_type, subject_id, user_id, team_id, role, starts_on, ends_on)` | Puts a user or a team on the record, or reopens their membership in that role with the new dates    |
| `end_subject_member(member_id, ends_on)`                                                   | Ends a membership; it counts through `ends_on`, today by default                                    |
| `list_subject_members(subject_type, subject_id)`                                           | The record's team, current and past, for a caller who can read the record                           |
| `my_subjects(tenant, subject_type, page_size, cursor)`                                     | The records whose team the caller is on today, with their roles, title and URL, up to 200 a page    |
| `has_subject_role(subject_type, subject_id, roles)`                                        | Whether the caller is on the record's team today in one of `roles`, for a rule only some roles pass |

Adding and ending a membership needs `subjects.manage` in the record's tenant
(the `admin` role has `subjects.*`), or `can_subject(..., 'manage')` on a type
that declares a `manage` action. The service role may always call them. With an
[authorization provider](/docs/extending/authorization-providers), list
`subjects.manage` among its permissions or set
`blocks.subjects.permissions.manage` to a key it has. Roles
are `lead` and `member` unless you set
`blocks.subjects.options.recordTeam.roles`. The functions fail with these
hints:

| Hint                       | When                                                                                                 |
| -------------------------- | ---------------------------------------------------------------------------------------------------- |
| `SUBJECT_MEMBER_INVALID`   | The type has no team, both or neither of user and team are set, an unknown role, or bad dates or ids |
| `SUBJECT_MEMBER_NOT_FOUND` | The record or the membership doesn't exist                                                           |
| `SUBJECT_MEMBER_FORBIDDEN` | The caller may not manage the record's team                                                          |

A caller reads their own membership rows, those of their teams, every row in
a tenant where they hold `subjects.manage`, and the team of any record they
can read. `add` and `end` emit `subject_member.added` and
`subject_member.ended` when the outbox is installed, and the audit log
records them under `access`.

The team counts in `can_subject`, `can_subject_for` and the blocks that call
them. Blocks that check a record's `read` entry inline (tags, attachments
and the others that take `on`) still check only the key. The `represents`
relation kind from `contacts` accepts only targets of a type with a team,
when one is declared.

#### Record read log

Set `auditReads: true` on a type to log who reads its records. It needs the
[`audit`](/docs/blocks/audit) block and a tenant column.

```ts title="better-supabase.config.ts"
export default defineConfig({
  subjects: {
    patient: {
      table: "public.patients",
      title: "name",
      permissions: { read: "patients.read" },
      team: { actions: ["read"] },
      auditReads: true,
    },
  },
  blocks: ["memberships", "permissions", "audit", "subjects", "comments"],
});
```

The read functions of the blocks then call `record_subject_read` after their
own access check, for a record the caller may read: `record_summary`
(`subjects`), `list_comments` (`comments`), `list_activity` with a subject
(`timeline`), `list_status_history` (`state-machine`) and `read_field_values`
(`custom-fields`) when it returns values. Each read writes a `subject.accessed`
entry under the `read` category ([Read logging](/docs/blocks/audit#read-logging)).
A function that runs as plain SQL, such as `list_attachments` or
`activities_of`, doesn't log; call `reads.log` from the screen that shows it.

| Function                                                                        | What it does                                                                     |
| ------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `record_subject_read(subject_type, subject_id, purpose)`                        | Logs that the caller read the record, with an optional purpose of 500 characters |
| `subject_access_log(subject_type, subject_id, since timestamptz, max_rows int)` | Who read the record and when, newest first, up to 500 entries                    |

`record_subject_read` logs nothing for a type without `auditReads`, a missing
record, a record the caller can't read or a call without a user, so the
service role's reads aren't logged. A second read of the same record by the
same member within `blocks.subjects.options.reads.collapseSeconds` (60 by
default, 0 logs every read) writes no new entry, unless it gives another
purpose or only one of the two was under
[emergency access](/docs/blocks/access-requests#emergency-access).
Under a read-only [support session](#support-sessions) a logged
read fails with `ACTOR_READ_ONLY`, as every audited read does.

`subject_access_log` is for the holders of `audit.read` in the record's
tenant, the leads on the record's team today, the record's own
[guest](/docs/blocks/guests) and a guest who represents it with `act`
authority. It fails with these hints:

| Hint                     | When                                                   |
| ------------------------ | ------------------------------------------------------ |
| `SUBJECT_READ_INVALID`   | The type doesn't log reads, or the purpose is too long |
| `SUBJECT_READ_NOT_FOUND` | The record doesn't exist                               |
| `SUBJECT_READ_FORBIDDEN` | The caller may not see who read the record             |

A plain `select` over the Data API is not logged: PostgREST runs it without
calling a function. To make every read go through the logging functions,
revoke `select` on the record's table from `authenticated` and read it
through the blocks' functions or your own security definer function that
calls `record_subject_read`.

With a registry, `gen` also emits the types in `database.types.ts`:

```ts
import {
  type RecordRef,
  type SubjectType,
  subjectTypes,
} from "./lib/supabase/schema";

const ref: RecordRef<SubjectType> = { type: "task", id: taskId };
```

Doctor reports a registered table or column the database lacks (BS331) and a
registered table without row level security (BS332).

### Merging subject records

When two rows of a subject table are merged, one call moves every module's
rows from the dropped record to the kept one:

```sql
perform better_supabase.merge_subject_refs('public.customers', keep::text, drop::text);
```

Each module that stores rows per subject installs a handler, and
`merge_subject_refs` runs them all:

| Module          | What moves                                                                                 |
| --------------- | ------------------------------------------------------------------------------------------ |
| `comments`      | Comments; the activity feed stays on the dropped record                                    |
| `attachments`   | Attachments                                                                                |
| `reactions`     | Reactions, except one the same person already left on the kept record with the same emoji  |
| `tags`          | Taggings, except a tag the kept record already has                                         |
| `relations`     | Links on either end; a link that becomes a self-link or a duplicate is deleted             |
| `guests`        | Guest grants, except a grant the guest already has on the kept record                      |
| `passes`        | Passes issued for the record                                                               |
| `billable-time` | Rates on the record, except a rate the kept record already has for the same member and day |
| `leases`        | Leases of the party                                                                        |
| `donations`     | Gifts, pledges and receipts of the donor                                                   |
| `dispatch`      | Work orders opened for the record                                                          |
| `shipments`     | Shipments sent for the record                                                              |
| `contracts`     | Contracts with the record as their counterparty                                            |

The function isn't granted to any API role. Call it from your own `security
definer` function that has already checked the caller, as the parties
`merge_companies` and `merge_people` functions do. Merging doesn't re-check a
relation kind's `single` or `acyclic` rule.

To move your own tables in the same call, add a function with the signature
`(subject_table text, keep text, drop text)`, owned by the role that owns the
migrations, and give it the comment `better-supabase:subject-merge`. The
dispatcher skips marked functions another role owns.

```sql
create function app.deals_subject_merge(subject_table text, keep text, drop text)
returns void language plpgsql security definer set search_path = '' as $$
begin
  if subject_table = 'better_supabase.companies' then
    update app.deals set company_id = keep::uuid where company_id = drop::uuid;
  end if;
end;
$$;
revoke execute on function app.deals_subject_merge(text, text, text) from public, anon, authenticated;
comment on function app.deals_subject_merge(text, text, text) is 'better-supabase:subject-merge';
```

## RLS on every new table

`better-supabase add rls-guard` installs an event trigger that enables row level
security on every table created with `create table`, `create table as` or
`select into`, so a table never reaches the Data API without RLS. The trigger
also fires after `alter table`, so `disable row level security` is undone right
away. Tables in
the Supabase-managed schemas (`auth`, `storage`, `realtime`, `extensions`
and the others) and in `pg_*` schemas are skipped.

```sql
create table public.notes (id bigint primary key, body text);
-- relrowsecurity is now true; add policies before granting access.
```

A table with RLS and no policies denies every API role, so add its policies
in the same migration. Apply the migration as `postgres`: event triggers
need a superuser, and on Supabase the supautils extension lets `postgres`
create them. Tables that already exist keep their setting.

## Keeping files current

Every file starts with a header that marks it as managed. Its number comes
from the module's position in the registry, so its path stays the same when
you add other modules. List the modules you use in the config:

```ts title="better-supabase.config.ts"
export default defineConfig({
  database: { sql: { testsDir: "supabase/tests" } },
  blocks: ["audit", "queue", "invitations"],
});
```

`better-supabase upgrade` rewrites those files after an upgrade, and
`upgrade --check` fails in CI when a file is out of date. Use
`blocks view --sql <module>` to copy a module into a hand-written migration instead.
`add`, `upgrade` and `add --adopt` take `--dry-run` to show what they would write, and
`--tests-dir <dir>` overrides `database.sql.testsDir` for the pgTAP module.

| Option                          | Default                                                                                                |
| ------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `database.sql.workflow`         | detected from `supabase/config.toml` ([Workflows](#workflows))                                         |
| `database.sql.dir`              | `supabase/schemas`                                                                                     |
| `database.sql.prefix`           | `900_better_supabase`                                                                                  |
| `database.sql.testsDir`         | `supabase/tests`                                                                                       |
| `database.sql.schema`           | `better_supabase`, for every module that sets no `schema`                                              |
| `database.sql.api`              | unset; the Data API schema for every module that sets no `api`                                         |
| `database.sql.ownTablePolicies` | `block`; `app` keeps every module's policies off your tables unless it sets its own `ownTablePolicies` |
| `blocks`                        | `[]`                                                                                                   |

## Upgrading modules

When a release changes a module in a way the schema diff can't follow (a
renamed column, a backfill that must run before a new constraint), the module's
version goes up and the release ships a forward step. Run the upgrade after you
update the package:

```bash
better-supabase upgrade
```

It reads the version from each file's `@bsb-block` line (a file without one,
written before the line existed, counts as version 1). It then writes the
forward steps into `<timestamp>_better_supabase_block_upgrade.sql` in the
`migrations` folder next to your `config.toml` and rewrites the module files. Create the schema migration afterwards, so the
steps run first. `upgrade --check` exits with 1 when a module is behind or
a file is stale, and `--dry-run` lists the steps without writing. The pgTAP
files a module writes for your tables (the audit tests, say) carry no module
version; `upgrade --check` keeps them current, and `upgrade` leaves them
out.

A renamed function, table or claim keeps working for at least one minor
version. The module file keeps a wrapper under the old name (a view for a
table), marked `-- Deprecated since`, and doctor reports code that still uses
it (BS309). A renamed column has no wrapper: `upgrade` renames it, and
doctor reports the old name in your SQL before you upgrade. A module declares
these moves in `NAMES.migrations` (the version, the table, its old name and
the old column names), and `upgrade` renders them after your table and
entity renames, so the step renames the right table under any config. The
[stability page](/docs/extending/stability#sql-module-objects-and-claims) lists
what each module guarantees.

## Existing triggers

`track_updated_at()` and `audit()` warn when the table already has a trigger
that does the same work (a `moddatetime` or `touch_updated_at` trigger, or
another audit trigger), because both would run on every write. Pass
`replace_trigger => true` to drop the existing trigger in the same call:

```sql
select better_supabase.track_updated_at('public.customers', replace_trigger => true);
select better_supabase.audit('public.customers', replace_trigger => true);
```

Doctor reports a table that still has both (BS310).

## Rendering modules in code

`better-supabase/sql` exports what `add` and `upgrade` use, for build scripts
and tests that write the files themselves. `moduleLayout(config)` returns the
paths, `renderBlocks` returns the files with their managed headers (dependencies
included), and `resolveBlocks` lists the modules a set of names pulls in.

```ts title="scripts/write-block.ts"
import { resolveConfig } from "better-supabase/config";
import { moduleLayout, renderBlocks, resolveBlocks } from "better-supabase/sql";

import config from "../better-supabase.config.ts";

const layout = moduleLayout(resolveConfig(config, process.cwd()));
const modules = resolveBlocks(["audit", "queue"], layout).map((m) => m.name);
const files = renderBlocks(["audit", "queue"], layout);
```

`compileReadSets` turns the read sets in `generated.ts` into the SQL views and
functions that `better-supabase gen` writes. `moduleBody(name, layout)`
returns one module's SQL without its header, `customContracts` the functions
custom-mode modules must provide, and `moduleFileVersion(contents)` the version
and mode in a file's header.

`moduleFilePaths(names, layout)` maps each module a set of names pulls in to its
schema and test paths without rendering it. `modulePermissionKeys(blocks, names)`
lists the permission keys those modules check, with the action, the key after
`blocks.<module>.permissions` and whether a tenant or a platform check asks for
it. Under `blocks.permissions.model: 'provider'`, `add` and doctor (BS411) check
each key against the provider's `permissions`; a script can do the same:

```ts title="scripts/check-module-keys.ts"
import { resolveConfig } from "better-supabase/config";
import { modulePermissionKeys } from "better-supabase/sql";

import config from "../better-supabase.config.ts";

const { sql, authorization } = resolveConfig(config, process.cwd());
const scopeOnly = new Set(
  (authorization?.permissions ?? [])
    .filter((entry) => entry.sqlComplete === true)
    .map((entry) => entry.key),
);
for (const { module, action, key } of modulePermissionKeys(
  blocks,
  blockNames,
)) {
  if (!scopeOnly.has(key)) console.error(`${module}.${action}: ${key}`);
}
```

## Policies

`better-supabase/sql` builds, renders and reads row level security policies.
`policy()` makes a typed `Policy`, `renderPolicy()` writes the `create policy`
statement, and `readPolicies()` and `readGrants()` read them back from a script
without being fooled by comments, strings or dollar-quoted bodies.

```ts
import { policy, renderPolicy } from "better-supabase/sql";

renderPolicy(
  policy({
    table: "app.notes",
    name: "notes_read",
    command: "select",
    roles: ["authenticated"],
    using: "bsb.is_member(tenant_id)",
  }),
  { drop: true },
);
```

### The rule DSL

A `Rule` is a small tree: `public`, `owner`, `member`, `can`, `compare`,
`null`, `and`, `or` and `not`. `rulePolicy()` renders it into a policy that
calls only `bsb.is_member`, `bsb.can`, `bsb.owns` and `bsb.uid`, and
`renderRulePolicy()` puts the tree in a `-- @bsb rule` comment above the
statement. `readRulePolicies()` recovers the tree and reports `inSync: false`
once someone edits the SQL by hand, so a UI knows to show the SQL instead of
the tree.

`policyFunctionsSql()` returns the `bsb` schema with the four functions.
`uid()` and `owns()` are fixed. `is_member()` and `can()` delegate to the
functions you name, so your own tables or an authorization library answer
them. A hand written policy is kept as it is; `disallowedPolicyCalls()` lists
the calls in it that are not one of the four functions, which is how you check
it against the same rule.

## Table tags

A table you own carries its better-supabase features as `@bsb` tags in the table comment (ADR 0102). Free text and tags share the comment, and only the block that starts at `@bsb` is parsed. Tags are separated by `;`, and a tag takes `key=value` pairs.

```ts
import {
  parseBsbComment,
  setBsbTag,
  commentOnTableSql,
} from "better-supabase/sql";

const comment = "Invoices. @bsb subject title=number; realtime";

parseBsbComment(comment);
// { text: "Invoices.", tags: [{ name: "subject", args: { title: "number" } }, { name: "realtime", args: {} }] }

const next = setBsbTag(comment, "audit", { name: "audit", args: {} });

commentOnTableSql("public.invoices", next);
// comment on table public.invoices is 'Invoices. @bsb subject title=number; realtime; audit';
```

`setBsbTag` with `undefined` removes a tag and keeps the text.
