---
title: Expenses
description: Collect expense reports with lines, categories and receipts, check spend policies on submit, approve through the approvals block, and post the approved total and its reimbursement on the ledger.
---

`expenses` lets members file expense reports. A report has lines, each in a
category, with receipts uploaded as attachments. Categories carry a spend
policy, which `submit` checks before the report goes to the
[approvals](/docs/blocks/approvals) block. An approved report posts on the
[ledger](/docs/blocks/ledger), and so does its reimbursement, so what the
organization owes a member is a ledger balance.

```bash
better-supabase add expenses
```

```ts
import { createExpenses } from "better-supabase/blocks/expenses";
import { money } from "better-supabase/commerce";
```

The module requires `tenant`, `access`, `approvals` and `ledger`. With
`outbox` it records the `expense_report.*` events, with `audit` every change
is audited, and with [attachments](/docs/blocks/attachments) lines take
receipts. Amounts are bigint minor units
([ADR 0037](https://github.com/ScaleDockHQ/better-supabase/blob/main/docs/decisions/0037-money-on-the-wire.md)),
and how the approved total posts on the ledger is in
[ADR 0080](https://github.com/ScaleDockHQ/better-supabase/blob/main/docs/decisions/0080-recurring-charges-on-the-ledger.md).

## Tables

| Table                | Holds                                                                                                     |
| -------------------- | --------------------------------------------------------------------------------------------------------- |
| `expense_categories` | A category per organization, by `key`, with its currency, `limit_amount` and `receipt_over`               |
| `expense_reports`    | A member's report: the title, the currency, the approval, and the approval and reimbursement transactions |
| `expense_lines`      | A line: the category, the day, the amount, the description and the merchant                               |

A member reads their own reports and lines. Members with `expenses.read`
read every report of the organization. Writes go through the functions:
`expenses.submit` to file reports, `expenses.approve` to approve them (the
approvals block checks it), and `expenses.manage` for categories and
reimbursement.

## Your own columns

Columns you add to the `expense_reports` table in your schema files are fields, and the client's `fields` schema types them.

Server code calls the `expenses` instance on `db`, in the caller's organization. With `gen.hooks` set, `better-supabase gen` writes the hooks:

```ts title="src/lib/supabase/hooks.ts"
export const { useList: useExpenses } = defineDataHooks(
  "expenses",
  (db: AppDb) => db.expenses,
);
```

```ts
const rows = await db.expenses.list({ limit: 50 }).orThrow();
```

```tsx title="src/features/expenses/list.tsx"
"use client";

import { useExpenses } from "@/lib/supabase/hooks";

const rows = useExpenses({ limit: 50 });
```

`create` validates them before the call, and every read that returns a report parses them under `report.fields`.

## Categories and spend policies

```ts
const expenses = createExpenses({ transport, tenant: organizationId });

await expenses
  .saveCategory({
    key: "travel",
    name: "Travel",
    limit: money(150_000n, "EUR"),
    receiptOver: money(2_500n, "EUR"),
  })
  .orThrow();
```

`limit` caps a report's total in the category. `receiptOver` requires a
receipt on every line above it, and needs the attachments block. Archiving a
category keeps its lines; a report with a line in an archived category can't
be submitted.

### Categories over your own table

A categories table of yours may lack the `key` and `currency` columns: map them
to `null`. Without a key column, a category's `key` is its id: `saveCategory`
with the id of an existing category updates it, and any other key creates
one. Without a currency column, map `limitAmount` and `receiptOver` to `null`
too, since a limit is in a currency. The ledger names a category's account by
its id then.

Columns you add to the categories table in your schema files,
such as a ledger code or an icon. `saveCategory({ ..., fields })` writes them
in the same statement, and every category read returns them under `fields`.

```sql title="supabase/schemas/expense_categories.sql"
alter table "better_supabase"."expense_categories" add column "gl_code" text;
alter table "better_supabase"."expense_reports" add column "icon_name" text;
```

## File and submit a report

```ts
const report = await expenses
  .create({ title: "Client visit, Lisbon", currency: "EUR" })
  .orThrow();

const line = await expenses
  .addLine(report.id, {
    categoryId,
    spentOn: Temporal.PlainDate.from("2026-10-14"),
    amount: money(18_900n, "EUR"),
    description: "Flight",
    merchant: "TAP",
  })
  .orThrow();

const findings = await expenses.check(report.id).orThrow();
await expenses.submit(report.id).orThrow();
```

A receipt is an attachment on the line: upload it with the
[attachments](/docs/blocks/attachments) client and the subject
`{ type: "expense_line", id: line.id }`. The line's `receipts` counts the
uploads that finished and weren't flagged as infected.

`check` returns what the spend policy would refuse: a category over its
limit, a line over its receipt threshold without a receipt, or a line in an
archived category. `submit` fails with `EXPENSE_POLICY_VIOLATION` while there
are findings, and otherwise opens an approval. Lines can't change while the
report is submitted; a rejected report can be edited and submitted again.

| Method                               | Returns                                                                                                            |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| `saveCategory(input)`                | the category, created or updated by key                                                                            |
| `archiveCategory(categoryId)`        | the archived category                                                                                              |
| `restoreCategory(categoryId)`        | the restored category (records `expense_category.restored`; `archiveCategory` records `expense_category.archived`) |
| `categories({ includeArchived })`    | categories                                                                                                         |
| `create(input)`                      | the caller's draft report                                                                                          |
| `addLine(reportId, line)`            | the line                                                                                                           |
| `updateLine(lineId, update)`         | the line                                                                                                           |
| `removeLine(lineId)`                 | the report without the line                                                                                        |
| `check(reportId)`                    | the spend policy findings, empty when it may submit                                                                |
| `submit(reportId)`                   | the report with its approval                                                                                       |
| `reimburse(reportId, input)`         | the reimbursed report                                                                                              |
| `cancel(reportId)`                   | the cancelled report                                                                                               |
| `get(reportId)`                      | the report with its lines                                                                                          |
| `list({ status, userId, everyone })` | reports, newest first                                                                                              |

## Approval and the ledger

The report's status follows its approval: `submitted` while it's pending,
`approved` or `rejected` once it's decided. Members with `expenses.approve`
decide it through the approvals block. When the approval is final, the
report posts on the ledger: each category's total on its expense account
(`expenses:category:<key>:<currency>`) against the member's payable account
(`expenses:payable:<user>:<currency>`).

```ts
await expenses
  .reimburse(report.id, { reference: "payout-2026-10-31" })
  .orThrow();
```

`reimburse` settles the payable account from expense cash
(`expenses:cash:<currency>`) and needs `expenses.manage`. Each posting has a
key per report (`expense:<id>:approved`, `expense:<id>:reimbursed`), so it
can't post twice. `cancel` withdraws a report that isn't approved yet and
cancels its pending approval.

### Without the approvals block

`options.approvals: false` (or an `approval` column mapped to `null`) runs
expenses without the [approvals block](/docs/blocks/approvals). A submitted
report waits until `decide(reportId, { approved, note? })` approves or
rejects it: the service role, or a member with `expenses.approve` who doesn't
own it. Approval posts on the ledger like a final approval; rejection sets
`rejected_at` and records `expense_report.rejected`, and the owner can change
the report and submit it again. The reports table takes optional
`rejectedAt`, `decidedBy` and `decisionNote` columns. The service role decides for a user with `decidedBy` (`decided_by` in SQL), which is kept in the `decidedBy` column instead of an empty value; a member passing someone else, or `decidedBy` naming the owner, fails with the forbidden error. `decideExpense` takes `decidedBy` the same way.

With `options.approver: "manager"`, the owner's manager in the [employees block](/docs/blocks/employees) may also call `decideExpenseReport` and `decideExpense`, next to holders of `expenses.approve`. With `owner: "employee"`, the manager of the expense's employee decides. The option needs the employees block's tables and defaults to `"permission"`.

The database guards reports the way it guards [expenses without reports](#decision-rules) (ADR 1091). A client's own insert or update of the reports table (as `authenticated` or `anon`) can't write the owner or the stamp columns (`submittedAt`, `approvedAt`, `rejectedAt`, `decidedBy`, `decisionNote`, `reimbursedAt`, `cancelledAt`, the approval and the transactions), and a new report is a draft of the caller. A report moves from draft or rejected to submitted, from submitted to approved or rejected, from draft, submitted or rejected to cancelled, and from approved to reimbursed; any other change fails with `EXPENSE_TRANSITION_INVALID`. The trigger stamps `decidedBy` and clears the decision when a rejected report goes in again. From approved onward a report keeps its owner, currency and lines for every writer, and a client can't change them once it is submitted, until it is rejected (`EXPENSE_REPORT_LOCKED`). A data migration disables `bsb_expense_report_guard` or `bsb_expense_line_guard` for its own transaction, as for `bsb_expense_guard`.

## In the books

With the [accounting](/docs/blocks/accounting#postings-from-other-blocks)
block installed, an approved report books in the purchase journal (the
`expense` role against payable to the member) and its reimbursement in the
bank journal, in the same transaction. Expenses without a report book
nothing.

A line can carry `dimensions` (`addLine(reportId, { ..., dimensions: { project: "PRJ-12" } })`).
The report books one expense line per distinct dimension set, so
[project costing](/docs/blocks/billable-time#project-costing) counts each line
on its project. An `expense_lines` table of yours without the `dimensions`
column refuses it (`EXPENSE_DIMENSIONS_UNSUPPORTED`). Dimension keys must be
dimensions the accounting block accepts.

## Expenses without reports

Map `tables.reports` and `tables.lines` to `null` and each expense is one row of `tables.expenses` instead: the block's own table, or yours. It needs neither the approvals block nor the ledger, and the app decides each expense, unless [approvals decide it](#approvals-for-expenses-without-reports). Without the ledger, the ledger's subjects (`ledger_account`) aren't registered either, so comments, messaging and search don't reach for its tables.

```ts title="better-supabase.config.ts"
blocks: {
  expenses: {
    tables: { reports: null, lines: null, expenses: "public.expenses" },
    columns: {
      expenses: {
        tenant: "organization_id",
        user: null,
        employee: "employee_id",
        category: null,
        amount: "amount_cents",
        approvedAt: null,
        rejectedAt: null,
      },
    },
    options: { owner: "employee" },
  },
},
```

An expense belongs to a member (`user`), or with `options.owner: "employee"` to an employee of the [employees block](/docs/blocks/employees), who may have no account. Its state lives in a `status` column (`draft`, `submitted`, `approved`, `rejected` or `reimbursed`, which may be an enum), or in the `approvedAt` and `rejectedAt` timestamps next to `submittedAt` and `reimbursedAt`. `category`, `description`, `merchant`, `decidedBy`, `decidedAt`, `decisionNote`, `reimbursedBy`, `reimbursement` and `createdBy` are optional.

| Method                                    | Who                                                                                                                                                                          |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `createExpense(input)`                    | the owner with `expenses.submit`, their manager, or `expenses.manage`; takes `employeeId`                                                                                    |
| `updateExpense(id, update)`               | the same, while the expense is a draft or rejected; a key left out keeps its value, `null` clears `categoryId`, `description` or `merchant`, and `fields` sets extra columns |
| `submitExpense(id)`                       | the same, for a draft expense; only the owner resubmits a rejected one                                                                                                       |
| `withdrawExpense(id)`                     | the same, for a submitted expense, which goes back to draft                                                                                                                  |
| `purgeExpense(id)`                        | the same, for a draft expense                                                                                                                                                |
| `decideExpense(id, { approved, note? })`  | the service role, or `expenses.approve` for a submitted expense the caller neither owns nor created, unless nobody else can decide it                                        |
| `reopenExpense({ expenseId, reason })`    | a decider who is neither the owner nor the creator, for an approved expense that isn't reimbursed or invoiced; it goes back to submitted                                     |
| `reimburseExpense(id, { reference? })`    | the service role or `expenses.manage`, for an approved expense                                                                                                               |
| `reverseExpenseReimbursement(...)`        | the reimburse key, with `{ expenseId, reason }`, for a reimbursed expense, which goes back to approved                                                                       |
| `expenseSelfDecides(id)`                  | whether the caller decides the expense as its owner or creator, for a UI that shows the rule                                                                                 |
| `expenseSelfDecidesMany(ids)`             | the ids among `ids` the caller decides as owner or creator, in one call for a list                                                                                           |
| `getExpense(id)`, `listExpenses(options)` | the owner, their manager, or `expenses.read`; `listExpenses` takes `status`, `userId`, `employeeId` and `everyone`                                                           |

Amounts are `Money` in minor units. Each change records `expense.created`, `expense.submitted`, `expense.approved`, `expense.rejected`, `expense.reimbursed`, `expense.reopened`, `expense.reimbursement_reversed`, `expense.withdrawn` or `expense.purged`. `purgeExpense` removes a draft expense for good; a rejected or reimbursed expense is a record of what was claimed, so it stays and its status is the archive. Extra columns (`options.extraColumns`) are written in the insert itself, so a `not null` column without a default or a check across columns holds from the first write.

`permissions.deleteSubmitted` names a key whose holders may delete a submitted or approved expense that isn't reimbursed; a reimbursed expense stays. Without it, only a draft is deleted.

### Decision rules

The database keeps an expense's decision honest, for the functions and for an app that writes the table itself (ADR 1090):

- **Allowed transitions.** `draft` and `submitted` go both ways (the owner, or the `update` key); `submitted` goes to `approved` or `rejected` (a decider); `rejected` goes to `draft` or `submitted` (the owner); `approved` goes back to `submitted` with `reopenExpense` and to `reimbursed` with the reimburse key; `reimbursed` goes back to `approved` only with `reverseExpenseReimbursement`. Every other change fails with `EXPENSE_TRANSITION_INVALID`, so an approved or reimbursed expense never goes straight to draft, and `withdrawExpense` refuses a decided expense.
- **Stamped by the database.** A trigger on the expenses table sets `decidedBy` and `decidedAt` when an expense is approved or rejected, `reimbursedBy` and `reimbursedAt` when it is reimbursed, and clears the decision when it goes back to submitted or draft. A client's own insert or update (as `authenticated` or `anon`, not through a block function) can't write the status or any of these columns, and a new row starts as a draft.
- **The owner or creator never decides.** Neither the expense's owner nor its creator (`createdBy`) may approve or reject it, unless nobody else can. Who else counts depends on the approver mode: with `approver: "permission"` (the default), any other active member who holds `expenses.approve`; with `approver: "manager"`, also the owner's direct manager while an active member with a login; with `options.decider`, also every active manager with a login up the owner's chain, because the app's function may let them decide. Without a decider, managers higher up don't count, because they can't decide the expense either. With `standaloneApprovals`, the approvals block keeps the owner out as the requester, keeps the creator out of the request's queue while someone else can decide (`excludedUserIds`, which needs the approval requests' policy column), and the expense refuses the creator's decision under the same rule. That is the leave block's `selfDecideWhenTopOfChain` rule. The audit entry of such a decision carries `selfDecided: true`, and `expenseSelfDecides(id)` (`expense_self_decides` in SQL) tells a UI whether the caller is in that case; `expenseSelfDecidesMany(ids)` answers for a list. An access model that can't answer for other users never lets them.
- **The creator is stamped.** A client's own insert records the caller as `createdBy`, whatever it names, and a client can't change it later. The service role names a creator with `createExpense({ createdBy })`, or with `fields.created_by` when the table has extra columns; a security definer function that writes the table keeps the creator it sets. Without one the caller, then the owner, is recorded. An expense whose `createdBy` is null counts the decider as its creator, so it is decided or reopened only when nobody else can; backfill the column on rows from before 0.73.
- **Frozen once submitted.** A client's own write can't change the amount, currency, category or owner of an expense that isn't a draft; withdraw it first. From approved onward they don't change for any writer; reopen it first. The owner changes only in draft, and a client needs the `create` or `update` key for it.
- **Data migrations.** The transitions and the freeze hold for the service role too. A migration that must correct history (an import, a repair after a bug) disables the trigger for its own transaction and turns it back on before it commits: `alter table <expenses> disable trigger bsb_expense_guard;`, the fix, then `alter table <expenses> enable trigger bsb_expense_guard;`. Don't use `session_replication_role = replica`, which also skips foreign keys and audit triggers. App code never does this.
- **Reasons in the audit.** `reopenExpense` and `reverseExpenseReimbursement` need a reason, which the audit entry keeps as `metadata.reason`.

With `options.invoicedColumn`, a column of yours that is set once the expense is billed onward, `reopenExpense` refuses an invoiced expense:

```ts title="better-supabase.config.ts"
blocks: {
  expenses: {
    options: { invoicedColumn: "invoice_id" },
  },
}
```

When the invoice's status matters, name a function instead: `options.invoicedCheck: "public.expense_invoiced"`, a function `(expense_id uuid) returns boolean` that answers true while the expense is on an invoice that isn't cancelled. A null answer counts as invoiced. Set one of the two options, not both.

```sql title="supabase/schemas/expense_invoiced.sql"
create function public.expense_invoiced(expense_id uuid)
returns boolean
language sql
stable
set search_path = ''
as $$
  select exists (
    select 1 from public.expenses e join public.invoices i on i.id = e.invoice_id
    where e.id = expense_invoiced.expense_id and i.status <> 'cancelled'
  )
$$;
```

`options.decider` (`"schema.function"`, `(id uuid) returns boolean`) lets more callers decide an expense through `decideExpense`, such as the managers up the owner's reporting chain, as in the [leave block](/docs/blocks/leave). A null answer denies. It needs `standaloneApprovals` off.

A state conflict, such as deciding an expense that is already decided, fails with SQLSTATE `PT409`: PostgREST answers HTTP 409, and the typed client returns a `conflict` error with the hint (see [Errors](#errors)).

With `options.companyExpenses: true`, `createExpense({ company: true, ... })` records an expense of the organization itself, without a member or employee. It needs `expenses.manage` (or the service role), and the owner column must allow null; the block's own table does. `listExpenses({ everyone: true })` returns them with the rest.

### Approvals for expenses without reports

With `options.standaloneApprovals: true`, each submitted expense files a request with the [approvals block](/docs/blocks/approvals) (subject type `expense`, action `approve`) under `options.policy`, by default one step for holders of `expenses.approve`. The expense's owner is the requester, so they can't approve their own expense, and with `owner: "employee"` a manager step (`approvers: { manager: true }`) asks the employee's manager. The request's final approval or rejection approves or rejects the expense, with the decider in `decidedBy` and the decision's comment in `decisionNote`. While the request is pending, `decideExpense` fails with `EXPENSE_IN_APPROVAL`; `withdrawExpense` and `deleteExpense` cancel it. It needs the approvals block.

```ts title="better-supabase.config.ts"
expenses: {
  tables: { reports: null, lines: null },
  options: {
    owner: "employee",
    standaloneApprovals: true,
    policy: { steps: [{ approvers: { manager: true } }] },
  },
},
```

### A key per action

`expenses.manage` covers everything done for someone else. Name a key per action in `permissions` to split it; an action without its own key checks `manage`.

| Key               | What it allows                                                                    |
| ----------------- | --------------------------------------------------------------------------------- |
| `create`          | `createExpense` for another member or employee, and company expenses              |
| `update`          | `updateExpense`, `submitExpense` and `withdrawExpense` on someone else's expense  |
| `purge`           | `purgeExpense` on someone else's expense; falls back to `delete`, then `manage`   |
| `withdraw`        | `withdrawExpense` on someone else's submitted expense; falls back to `update`     |
| `delete`          | the former key of `purgeExpense`, still read when `purge` is unset                |
| `deleteSubmitted` | `purgeExpense` on a submitted or approved expense; no fallback                    |
| `reimburse`       | `reimburseExpense`, `reverseExpenseReimbursement`, and `reimburse_expense_report` |
| `categories`      | `save_expense_category` and `archive_expense_category`                            |

A payroll role that may only mark expenses reimbursed:

```ts title="better-supabase.config.ts"
blocks: {
  expenses: {
    permissions: {
      manage: "expense.manage",
      create: "expense.create",
      update: "expense.update",
      delete: "expense.delete",
      reimburse: "expense.reimburse",
      categories: "expense.manage_policies",
    },
  },
},
```

The owner and their manager keep their own access, whatever these keys say.

## On a record page

`expensesBinding` loads a member's expense reports, newest first, through `expenses.list({ userId })`. The subject's `id` is the member's user id. Reports belong to a member, not to an employee, so an employee's page passes the employee's user id. The organization comes from `options.tenant`, and reading another member's reports needs `expenses.read`. It goes stale on `expense_report.*` events and has no writes, because filing or deciding a report takes money, lines and receipts.

## Events

`expense_report.created`, `expense_report.submitted` (with the approval),
`expense_report.approved` and `expense_report.reimbursed` (with the ledger
transaction) and `expense_report.cancelled`. A rejection is the approvals
block's `approval.rejected` event, or `expense_report.rejected` without the
approvals block. The
[events page](/docs/extending/events) lists their payloads.

## Without the client

`db.expenses` is this client. Code that does not go through `bsb.db()` builds it with a transport and an organization id:

```sql title="supabase/schemas/expense_reports.sql"
alter table "better_supabase"."expense_reports" add column "project_code" text;
```

## File a report

`file({ title, currency, note, lines, submit })` creates the report, adds each line and submits it. Pass `submit: false` to leave it as a draft.

## Paging categories, reports and expenses

`categoryPage`, `reportPage` and, when reports are off, `expensePage` page by keyset (ADR 1077). `categories`, `list` and `listExpenses` stay as deprecated aliases until 0.70. Category filters are `currency` and `archived`. Report filters are `userId`, `status`, `currency` and `mine` (`["true"]` limits a member with `expenses.read` to their own reports), and `q` searches the title. Expense filters add `categoryId`, and `q` searches the description and merchant.

```ts
const reports = await expenses
  .reportPage({ filters: { status: ["submitted"], mine: ["true"] } })
  .orThrow();

const facets = await expenses.reportFacets().orThrow();
const categories = await expenses.categoryPage({ q: "travel" }).orThrow();
```

A cursor belongs to the sort it came from, so start again from the first page when `sort` changes. A sort, filter, facet or text the entity does not declare returns an `invalid_input` error. [Block lists](/docs/extending/block-lists) describes the options every block list shares.
