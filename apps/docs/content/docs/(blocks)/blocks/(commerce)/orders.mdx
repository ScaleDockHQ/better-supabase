---
title: Orders
description: Carts for anonymous and signed-in shoppers, a checkout that prices from the catalog, quotes tax, reserves stock and takes the payment once, then fulfillments, returns, refunds and invoices.
---

`orders` turns [catalog](/docs/blocks/catalog) variants into orders. A cart
belongs to the signed-in user, which can be an anonymous Supabase user, so a
shopper can fill one before creating an account. Checkout prices the cart
from the catalog, quotes tax through a `TaxProvider`, places the order with
a number from `numbering`, reserves its stock when
[inventory](/docs/blocks/inventory) is installed, and creates the payment
through a `PaymentProvider` with an idempotency key. After the sale it
records fulfillments, returns, refunds and the invoice.

```bash
better-supabase add orders
```

Server code calls the `orders` instance on `db`, in the caller's organization. With `gen.hooks` set, `better-supabase gen` writes the hooks:

```ts title="src/lib/supabase/hooks.ts"
export const { useList: useOrders } = defineDataHooks(
  "orders",
  (db: AppDb) => db.orders,
);
```

```ts
const rows = await db.orders.list({ limit: 50 }).orThrow();
```

```tsx title="src/features/orders/list.tsx"
"use client";

import { useOrders } from "@/lib/supabase/hooks";

const rows = useOrders({ limit: 50 });
```

The module needs `tenant`, `permissions` and `catalog`. It uses `inventory` for
reservations and stock movements, `promotions` for discount codes,
`numbering` for order and invoice numbers, `state-machine` for the
status column, and `outbox` for events, each when it is installed. The
providers are described on the [commerce](/docs/concepts/commerce) page; both
are optional, and without `payments` only free orders can be placed.

## Permissions

| Key              | What it allows                                                                 |
| ---------------- | ------------------------------------------------------------------------------ |
| `orders.read`    | Read every cart and order in the organization                                  |
| `orders.manage`  | Shipping rates, fulfillments, returns, refunds, cancelling orders and stations |
| `orders.prepare` | Send orders to the kitchen and move their lines through the preparation states |

Shoppers need neither key: a user reads and edits their own carts and reads
their own orders. Placing an order, recording a payment, merging carts and
expiring orders are service-only, so pass a `service` transport as above.

## Carts

```ts
await supabase.auth.signInAnonymously();

const cart = await orders
  .createCart(organizationId, { currency: "EUR" })
  .orThrow();
await orders.addToCart(cart.id, variantId, 2).orThrow();
await orders.setCartLine(cart.id, variantId, 1).orThrow(); // 0 removes the line
await orders
  .setCartDetails(cart.id, {
    email: "ada@example.com",
    shippingAddress: {
      line1: "Damrak 1",
      city: "Amsterdam",
      postalCode: "1012 LG",
      country: "NL",
    },
  })
  .orThrow();

const priced = await orders.priceCart(cart.id).orThrow();
// { lines, subtotal, discountTotal, shippingTotal, total, problems }
```

`createCart` returns the caller's open cart for the organization and
currency, and creates one when there is none. Only variants of active
products can be added (`ORDERS_VARIANT_UNAVAILABLE`). `priceCart` reads
today's catalog price for each line; a line whose price changed carries
`previousUnitAmount`, and `problems` lists what keeps the cart from checkout
(an unavailable or unpriced line, a missing shipping rate or address).

When an anonymous shopper signs in to an existing account, Supabase gives
them a different user id. Move their carts on the server:

```ts
await orders.mergeCarts(anonymousUserId, signedInUserId).orThrow();
```

Lines for the same variant add up, and the cart's promotion codes move
with them. Linking an identity to the anonymous user
(`supabase.auth.linkIdentity`) keeps the id, so it needs no merge.

## Shipping

```ts
await orders
  .saveShippingRate(organizationId, {
    name: "Standard",
    countries: ["NL", "BE"],
    amount: money(495n, "EUR"),
    freeOver: money(5000n, "EUR"),
  })
  .orThrow();

const options = await orders.shippingOptions(cart.id).orThrow();
await orders.setShippingRate(cart.id, options[0].id).orThrow();
```

A `flat` rate charges `amount`; a `weight` rate adds `amountPerKg` for each
started kilogram of the variants' weights. `freeOver` makes the rate free once
the discounted subtotal reaches it. A cart with only digital variants needs
no rate.

## Checkout

```ts
const { order, payment } = await orders
  .checkout(cart.id, { returnUrl: "https://shop.example.com/thanks" })
  .orThrow();
// Hand payment.clientSecret to the browser to confirm the payment.
```

`checkout` prices the cart, quotes tax for its lines and shipping, and
places the order in one transaction with the quote's total. If a price
changed in between, it fails with `ORDERS_PRICE_CHANGED` and the shopper
sees the new total. Placing converts the cart, assigns the order number
(`SO-0001` from the `order` sequence when one is configured), copies each
line's SKU, title and price, redeems the cart's promotions and reserves the
stock at `locationId`, or at the location with the most available.

The order starts as `pending_payment` and holds its stock for 30 minutes
(the `paymentWindowMinutes` module option). The payment is created with the
idempotency key `order:<id>:payment`, so calling `checkout` again for the
same cart returns the same order and the same payment. A free order is paid
at once.

With the [invoices block](/docs/blocks/invoices) installed, the payment that
marks an order paid also creates its invoice: one line per order line (the
title and quantity, the net amount and the tax rate it was charged), a
shipping line, issued today and paid in full by the order's payment. The
order's invoice number is that invoice's identifier, and `record_payment`
returns its `invoiceId`.

### Payment events

Route the provider's webhook to `orders.webhook`. It verifies the delivery,
then applies each payment and refund event:

```ts title="app/api/payments/route.ts"
export async function POST(request: Request) {
  const outcomes = await orders.webhook(request).orThrow();
  return Response.json({ handled: outcomes.length });
}
```

When the captured amount reaches the total, the order becomes `paid`: its
reservations turn into `sale` movements, it gets an invoice number
(`INV-00001` from the `invoice` sequence) and the sale is committed to the
tax provider. A failed commit is logged; retry it with `commitTax(orderId)`.
With `capture: "manual"` the funds are held until `orders.capture(orderId)`.

`cancelOrder(orderId)` cancels an unpaid order, releases its stock and its
open payments. Schedule `orders.job` to cancel orders whose payment window
passed:

```ts
await jobs.schedule("orders:expire", "*/5 * * * *", "orders.expire", {});
```

## After the sale

```ts
const shipment = await orders
  .createFulfillment(order.id, { carrier: "PostNL" }) // every unit not fulfilled yet
  .orThrow();
await orders
  .shipFulfillment(shipment.id, { trackingNumber: "3SABC123" })
  .orThrow();
await orders.deliverFulfillment(shipment.id).orThrow();

const ret = await orders
  .requestReturn(order.id, [{ lineId, quantity: 1 }], "too small")
  .orThrow();
await orders.receiveReturn(ret.id).orThrow(); // restocks tracked variants

await orders
  .refund(order.id, { amount: money(2420n, "EUR"), returnId: ret.id })
  .orThrow();
// { status: "succeeded", orderStatus: "paid", refundedTotal, taxReversal }

const invoice = await orders.invoice(order.id).orThrow();
// { number: "INV-00001", issuedAt, order }
```

An order becomes `fulfilled` when every unit is in a fulfillment and
`completed` when they are all delivered. `refund` defaults to everything
paid and not refunded yet, refunds through the provider with the key
`refund:<id>`, and reverses the refunded share of each line's tax. Refunding
the whole total moves the order to `refunded`.

| Status            | Next                                                      |
| ----------------- | --------------------------------------------------------- |
| `pending_payment` | `paid`, `cancelled`                                       |
| `confirmed`       | `paid`, `fulfilled`, `cancelled`                          |
| `paid`            | `fulfilled`, `refunded`                                   |
| `fulfilled`       | `paid` (a cancelled fulfillment), `completed`, `refunded` |
| `completed`       | `refunded`                                                |

To change these rules, register a [state machine](/docs/blocks/state-machine)
on the orders `status` column; the module then leaves the check to it.

## Orders from documents

Staff enter phone and wholesale orders, and other blocks turn their records
into orders, without a cart:

```ts
const { order, created } = await orders
  .fromLines(organizationId, {
    currency: "EUR",
    lines: [
      { variantId, quantity: 2 },
      { title: "Setup", quantity: 1, unitAmount: money(5000n, "EUR") },
    ],
    email: "buyer@example.com",
    locationId: warehouse.id,
    origin: { type: "work_order", id: workOrder.id },
  })
  .orThrow();
// order.status === "confirmed"; created is false when the origin already had an order

const fromQuote = await orders.fromQuote(quote.id).orThrow();
```

Both make a `confirmed` order: it is due, and it can be fulfilled before it
is paid. A line with a `variantId` takes the variant's price, title and SKU
unless you pass them, and with the [inventory block](/docs/blocks/inventory)
each line that ships allocates its stock at `locationId` (the first location
with stock by default), backordering what isn't there. A fulfillment ships
from the allocation, and cancelling the order releases it. Line quantities
are whole units.

`fromQuote` needs the [quotes block](/docs/blocks/quotes) and an accepted
quote (`ORDERS_QUOTE_NOT_ACCEPTED`). It copies the counted lines and the
quote's totals, and orders a quote once. A quote line counts as a variant
line when its `product` is a `product_variant`. A line with a fractional
quantity can't be ordered (`ORDERS_QUANTITY_INVALID`).

`orderFromQuoteAction` from `better-supabase/blocks/orders` is the quotes
conversion action: without a `create`, it calls `orders.fromQuote` on the
`orders` client in the action's clients.

## Kitchen

With `options.kitchen`, each order line gets a preparation state at a
station, for a kitchen display and an order board. The option is off by
default and adds three tables: `kitchen_stations`, `kitchen_routes` (which
station prepares a product) and `order_line_preparations`.

```ts title="better-supabase.config.ts"
export default defineConfig({
  blocks: { orders: { options: { kitchen: true } } },
});
```

```ts
const grill = await orders.kitchen
  .saveStation(organizationId, {
    key: "grill",
    name: "Grill",
    default: true,
    productIds: [burgerId],
  })
  .orThrow();

await orders.kitchen.send(orderId, { [lineId]: "no onions" }).orThrow();

const tickets = await orders.kitchen
  .queue(organizationId, { stationId: grill.id })
  .orThrow();
// [{ orderId, number, sentAt, lines: [{ lineId, title, quantity, state, note }] }]

await orders.kitchen.setState(lineId, "preparing").orThrow();
await orders.kitchen.bump(orderId, "ready", grill.id).orThrow(); // every line at the grill

const cards = await orders.kitchen.board(organizationId).orThrow();
// [{ orderId, number, state, counts: { queued, preparing, ready, served } }]
```

`send` queues each line of a paid or placed order at the station its product
is routed to, or at the default station, and skips lines already sent, so
calling it again is safe. A cancelled or refunded order can't be sent
(`ORDERS_KITCHEN_CLOSED`). A line moves through `queued`, `preparing`,
`ready` and `served`; `setState` can also move it back, which clears the
later timestamps. `bump` moves every line of the order (or of one station)
up to a state and leaves lines that are further along. The board shows the
orders sent since a day ago by the state of their least advanced line.

Each change broadcasts a `preparation` message with `{ lineId, orderId,
stationId, state }` on the private Realtime topic `kitchen:<organizationId>`,
which members with `orders.read` or `orders.prepare` can receive. The
`KITCHEN_EVENT` and `kitchenTopic(organizationId)` exports name them:

```tsx
const kitchen = defineTopic("kitchen:{organizationId}");

useBroadcast(
  kitchen,
  { organizationId },
  { [KITCHEN_EVENT]: () => router.refresh() },
);
```

The [kitchen display](/docs/registry/ui-recipes/kitchen-display) and
[order state board](/docs/registry/ui-recipes/order-state-board) recipes
build both screens from this API.

## Events

| Event                                          | When                                       |
| ---------------------------------------------- | ------------------------------------------ |
| `order.placed`                                 | `checkout` places the order                |
| `order.paid`                                   | The captured amount reaches the total      |
| `order.cancelled`                              | `cancelOrder` or an expired payment window |
| `order.fulfilled`, `order.completed`           | Every unit is fulfilled, then delivered    |
| `order.refunded`                               | A refund succeeds                          |
| `fulfillment.shipped`, `fulfillment.delivered` | A fulfillment step                         |
| `return.requested`, `return.received`          | A return step                              |
| `order.prepared`                               | Every kitchen line is ready or served      |
| `order.served`                                 | Every kitchen line is served               |

They are subject events on the `order` subject (`organizationId`,
`subjectType` and `subjectId`), so the
[watcher sink](/docs/blocks/notifications#watchers) can notify an order's
watchers. The payloads are listed on the [events](/docs/extending/events)
page.

## Metrics

`orderMetrics({ currency })` defines three [metrics](/docs/blocks/metrics) over the orders table: `orders` counts placed orders by `placed_at`, and `revenue` and `average_order_value` sum and average the `total` of paid orders in that currency by `paid_at`, in minor units. `ORDER_METRIC_EVENTS` maps `order.placed` and `order.paid` to them for the metrics sink.

```ts title="app/api/outbox/route.ts"
import {
  ORDER_METRIC_EVENTS,
  orderMetrics,
} from "better-supabase/blocks/orders";

const metrics = orderMetrics({ currency: "EUR", tz: "Europe/Amsterdam" });
const app = createBlocks(
  { transport: service },
  {
    metrics: metricsBlock
      .with({ sink: { on: ORDER_METRIC_EVENTS } })
      .using((options) => createMetrics({ ...options, metrics })),
  },
);
```

Pass the same definitions to `blocks.metrics.options.metrics`. The [commerce preset page](/docs/presets/commerce#metrics) adds units sold from the order lines.

## Your own fields

`options.extraColumns` adds columns to `orders`. `checkout` writes them when it places the order from `fields`,
and `checkout`, `getOrder`, `capture` and `invoice` return them in `fields`. Pass a Standard Schema as `fields`
to type them: writes are validated before they reach the database (a
`validation` error), and reads are parsed. `hooks` refuses, rewrites or
observes any method; see [extending blocks](/docs/extending/blocks).

```ts title="better-supabase.config.ts"
export default defineConfig({
  blocks: { orders: { options: { extraColumns: { channel: "text" } } } },
});
```

```ts
const client = createOrders({
  transport,
  fields: v.object({ channel: v.optional(v.picklist(["web", "pos"])) }),
});
await client.checkout(cartId, { fields: { channel: "pos" } });
```

## Hooks

The SQL module calls `before_order_place`, `after_order_place`,
`before_fulfillment_create`, `after_fulfillment_create`,
`before_refund_create` and `after_refund_create` when you define them (see
[blocks](/docs/extending/blocks)). The TypeScript client takes `hooks` keyed
by method name.

## Not included

Orders doesn't export e-invoices (EN 16931), issue credit notes, sell
subscriptions or license keys for digital goods, or handle B2B quotes and
purchase orders from customers.

## Over your own tables

Carts, cart lines, shipping rates, orders, order lines, payments,
fulfillments, returns and refunds can be tables your app already has (see
[Over your own tables](/docs/blocks/sql#over-your-own-tables)); the fulfillment
and return lines and the kitchen tables stay the block's own. The cart and
order `email` and `billingAddress`, the shipping rate `freeOver`, the order
`cancelReason` and `taxTransaction`, the fulfillment `trackingUrl` and the
return and refund `reason` may map to `null`. A call that sets one of them
then fails with an `ORDERS_<COLUMN>_UNSUPPORTED` hint, and reads return
`null`. Status columns may be enums or domains: the block casts what it
writes to the column's type.

## Without the client

`db.orders` is this client. Code that does not go through `bsb.db()` builds it with a transport and an organization id:

```ts title="lib/orders.ts"
import { fixedRates, stripePayments } from "better-supabase/commerce";
import { createOrders, sqlTransport } from "better-supabase/blocks/orders";

export const orders = createOrders({
  transport: sqlTransport(ctx.postgres),
  service: sqlTransport(servicePostgres),
  payments: stripePayments({
    stripe: { secretKey: env.STRIPE_SECRET_KEY },
    webhookSecret: env.STRIPE_WEBHOOK_SECRET,
  }),
  tax: fixedRates({ rates: { NL: { standard: "0.21" } } }),
});
```
