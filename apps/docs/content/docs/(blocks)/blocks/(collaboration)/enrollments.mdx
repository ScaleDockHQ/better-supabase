---
title: Enrollments
description: Programs of steps per organization, and enrollments of a party, a member or any record in them with step progress and completion. Onboarding checklists run on it.
---

`enrollments` keeps programs of ordered steps per organization and enrolls
subjects in them: a party in a customer onboarding plan, a member in a
training path, or any record your app owns. Each enrollment tracks which
steps are done, completes when the last one is, and can be cancelled while
it is active. [Onboarding](/docs/blocks/onboarding) checklists run on the
same tables.

Reading programs and enrollments needs `enrollments.read`, enrolling and
changing an enrollment needs `enrollments.enroll`, and managing programs
needs `enrollments.manage`. Admins get all three and members get
`enrollments.read`. A user enrolled as a `user` subject always reads their own
enrollment and completes or resets its steps, and a user a step is assigned
to completes or resets that step.

```bash
better-supabase add enrollments
```

The module needs `memberships` and `access`. Enrollments in an organization go to
the outbox, and program changes go to the audit log as well.

Server code calls the `enrollments` instance on `db`, in the caller's organization. With `gen.hooks` set, `better-supabase gen` writes the hooks:

```ts title="src/lib/supabase/hooks.ts"
export const { useList: useEnrollments } = defineDataHooks(
  "enrollments",
  (db: AppDb) => db.enrollments,
);
```

```ts
import { createEnrollments } from "better-supabase/blocks/enrollments";

await db.enrollments
  .saveProgram({
    key: "customer-onboarding",
    name: "Customer onboarding",
    subjectTypes: ["party"],
    steps: [
      { id: "kickoff", title: "Kickoff call" },
      { id: "import", title: "Import data" },
      { id: "training", title: "Train the team" },
    ],
  })
  .orThrow();

const enrollment = await db.enrollments
  .enroll("customer-onboarding", { type: "party", id: partyId })
  .orThrow();

await db.enrollments.complete(enrollment.id, "kickoff").orThrow();
```

```tsx title="src/features/enrollments/list.tsx"
"use client";

import { useEnrollments } from "@/lib/supabase/hooks";

const rows = useEnrollments({ limit: 50 });
```

| Option     | Default | What it does                   |
| ---------- | ------- | ------------------------------ |
| `maxSteps` | `100`   | The most steps a program holds |

| Table                 | Holds                                                                                                                                                  |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `enrollment_programs` | One row per program: `key`, `name`, `subject_types`, the ordered `steps` and `version`                                                                 |
| `enrollments`         | One row per program and subject: the step snapshot, `completed_steps`, `status`, `starts_at` and `ends_at`                                             |
| `enrollment_steps`    | One row per completed step, and one open row per step with an assignee or a due date: `assignee_role`, `assignee_user_id`, `due_at` and `completed_at` |

## Programs

`saveProgram(program)` creates a program, or changes one when you pass its
`id`. Keys left out keep their value, and a program's key can't change.
`subjectTypes` limits the subject types it enrolls; leave it empty to enroll
any. Each step has an `id` (lower-case letters, digits, `_`, `.` or `-`) and
an optional `title` and `description`.

Changing the steps raises the program's `version`. Pass the `version` you read
to fail with `ENROLLMENTS_PROGRAM_CONFLICT` when someone else changed it
first. Turn a program off with `enabled: false` to stop new enrollments; its
enrollments stay. `deleteProgram(id)` deletes a program with its enrollments.

## Enrolling

`enroll(program, subject)` enrolls a subject and returns its enrollment.
Enrolling an enrolled subject returns the same enrollment, and enrolling a
cancelled one starts it again with its completed steps. A `user` subject
takes the user's id, so the user can follow their own progress.

An enrollment keeps the program's step ids from when it enrolled, so changing
a program doesn't change running enrollments. Enrolling the subject again
takes the program's current steps and recounts its progress against them.

## Assignees and due dates

A step can name who it is for and when it is due. `assignee` is `{ role }`
for the members with a role or `{ userId }` for one user, and `due` is
`{ days, from }`: whole days, from -3650 to 3650, after the enrollment's
`start` or `end`. A negative number counts back, so `{ days: -2, from: "end" }`
is two days before the end.

```ts
await db.enrollments
  .saveProgram({
    key: "customer-onboarding",
    name: "Customer onboarding",
    steps: [
      {
        id: "kickoff",
        assignee: { role: "admin" },
        due: { days: 2, from: "start" },
      },
      {
        id: "import",
        assignee: { userId: csmId },
        due: { days: 14, from: "start" },
      },
      { id: "review", due: { days: -2, from: "end" } },
    ],
  })
  .orThrow();

const enrollment = await db.enrollments
  .enroll(
    "customer-onboarding",
    { type: "party", id: partyId },
    { endsAt: Temporal.Instant.from("2026-12-01T00:00:00Z") },
  )
  .orThrow();

const mine = await db.enrollments
  .openSteps({ userId, dueBefore: nextWeek })
  .orThrow();
```

Each step with an assignee or a due date gets a row in `enrollment_steps`
when the subject enrolls, with the assignee and `due_at` rendered from the
enrollment's dates. The start is `startsAt`, or `enrolledAt` when it has
none; a step due from the end has no `due_at` until the enrollment has an
`endsAt`. The row stays open (`completed_at` is null) until the step is done,
so a query or an index on `due_at` finds what is overdue.

`setDates(enrollmentId, { startsAt, endsAt })` changes the dates and renders
the due dates again; keys you leave out keep their value and `null` clears
one. `enroll(program, subject, dates)` sets them right after enrolling.
Saving a program doesn't move existing due dates: they follow its new steps
when the subject enrolls again or its dates change, and a completed step
stays completed. An enrollment's `schedule` lists its scheduled steps in
step order with `dueAt` and `completedAt`.

`openSteps(filter)` returns the open scheduled steps of active enrollments,
soonest due first and undated last: filter by `role`, `userId` or
`dueBefore`. Without `enrollments.read`, it returns the steps assigned to the
caller. Onboarding checklists have no schedules.

## Progress

`complete(enrollmentId, step)` marks a step done and `reset` marks it not
done. Completing the last step sets `status` to `completed` with
`completedAt`; resetting a step of a completed enrollment makes it active
again. `cancel(enrollmentId)` cancels an active enrollment: its completed steps
stay, a cancelled enrollment takes no new steps, and a completed one can't be
cancelled.

`enrollment(program, subject)` returns one subject's enrollment, or `null`.
`list()` returns the organization's enrollments, most recently changed first:
filter by `program`, `subject` or `status`, and pass `before` with the last
enrollment's `updatedAt` for the next page. Without `enrollments.read`, `list`
returns the caller's own enrollments.

`enrollmentsBinding` loads a record's enrollments for a record page and
reloads on the enrollment events. See [Record bindings](/docs/repository/record-bindings).

## Onboarding

Each onboarding checklist runs as the program `onboarding:<checklist>`. The
organization is enrolled in an organization checklist, and the user, without
an organization, in a user checklist. Those programs live in your
`defineChecklist` calls instead of `enrollment_programs`, so `saveProgram`
can't change them and their enrollments can't be cancelled. See
[Onboarding](/docs/blocks/onboarding).

## Sequences

Each [sequence](/docs/blocks/sequences) run is an enrollment in the program
`sequence:<sequence id>`. The sequences block adds its `sequence_*` columns
to `enrollments`, keeps the step that runs next as an open step row with
`due_at`, and pauses a run with `paused_at`. A run that ends early is
`cancelled` with the reason in `cancel_reason`. The sequences client owns
these enrollments: schedules and `open_enrollment_steps` skip them.

| `enrollment(tenant, program, subject_type, subject_id)`                        | `authenticated`, `service_role` | A subject's enrollment, or null            |

| `set_enrollment_dates(enrollment_id, dates)`                                   | `authenticated`, `service_role` | Sets the dates and renders due dates again |
| `open_enrollment_steps(tenant, assignee_role, assignee_user, due_before, ...)` | `authenticated`, `service_role` | Open steps with an assignee or a due date  |

## Errors

| Hint                            | Cause                                                                                                                           |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| `ENROLLMENTS_FORBIDDEN`         | the caller lacks the permission                                                                                                 |
| `ENROLLMENTS_INVALID`           | an invalid program, step assignee or due date, a step outside the program, invalid dates, or a change to a cancelled enrollment |
| `ENROLLMENTS_PROGRAM_NOT_FOUND` | no program in the organization has this id or key                                                                               |
| `ENROLLMENTS_PROGRAM_EXISTS`    | a program with this key already exists                                                                                          |
| `ENROLLMENTS_PROGRAM_CONFLICT`  | the program changed since you read its `version`                                                                                |
| `ENROLLMENTS_NOT_FOUND`         | no enrollment the caller can see has this id                                                                                    |

## Events

| Event                                                                                             | Data                                                                                                            |
| ------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `enrollment_program.created`, `enrollment_program.updated`, `enrollment_program.deleted`          | `organizationId`, `id`, `key`, `version`                                                                        |
| `enrollment.created`, `enrollment.step_completed`, `enrollment.completed`, `enrollment.cancelled` | `organizationId`, `id`, `program`, `subjectType`, `subjectId`, `status`, `step`, `completedSteps`, `totalSteps` |
| `enrollment.paused`, `enrollment.resumed`                                                         | the same data                                                                                                   |

`step` is set for `enrollment.step_completed`, and `reason` for an
`enrollment.cancelled` that has one. Only enrollments in an
organization emit events, so a user's own onboarding checklist doesn't. A
rule on `enrollment.completed` can hand a customer to their account manager
once onboarding is done.

## With ReUI

There is no prebuilt enrollments UI. List enrollments in a `data-grid` with
the subject, a `Progress` of `completedSteps` over `totalSteps` and `status`
as a `Badge` (`success-light` for completed, `secondary` for cancelled). Show
an enrollment's steps as a `Stepper` or a checklist of `Checkbox` rows, and
edit a program's steps in a `Sheet` with a sortable list. List `openSteps`
in a `data-grid` with the due date and a `destructive-light` `Badge` once it
is overdue. Confirm
`cancel` with an `AlertDialog`.

## Why it works this way

An enrollment snapshots the program's step ids, so changing a program never
rewrites a subject's history: progress counts only the steps it enrolled
with. The tenant is nullable so a user's own onboarding checklist fits the
same tables, and the module's internal functions let other blocks drive
programs they own without going through `enrollment_programs`.

Due dates are rendered into rows rather than computed on read so the
database can index and filter them: overdue work is one indexed query, and
a rule or a reminder reads `due_at` like any other column. The rows are
rendered again whenever the dates or the enrollment's steps change.

## Without the client

`db.enrollments` is this client. Code that does not go through `bsb.db()` builds it with a transport and an organization id:

```ts
import { createEnrollments } from "better-supabase/blocks/enrollments";

const enrollments = createEnrollments({ transport, tenant: organizationId });

await enrollments
  .saveProgram({
    key: "customer-onboarding",
    name: "Customer onboarding",
    subjectTypes: ["party"],
    steps: [
      { id: "kickoff", title: "Kickoff call" },
      { id: "import", title: "Import data" },
      { id: "training", title: "Train the team" },
    ],
  })
  .orThrow();

const enrollment = await enrollments
  .enroll("customer-onboarding", { type: "party", id: partyId })
  .orThrow();

await enrollments.complete(enrollment.id, "kickoff").orThrow();
```
