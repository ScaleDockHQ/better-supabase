---
title: Contacts
description: Companies and people an organization works with, with lifecycle stages, owners, roles such as customer or supplier, payment terms, credit limits, a supplier status, who works where with a role and a primary contact, dedupe by domain and email, merges and keyset-paged search.
---

`contacts` keeps the companies and people an organization sells to, supports or hires: the counterparty that deals, quotes, invoices, tickets and applications point at. A company has a name, a domain, a website, a VAT id, an address, an owner and a lifecycle stage. A person has a name, an email, a phone, a title, an avatar, an owner, a lifecycle stage, optionally the user they sign in as, and identities: their addresses on channels. `company_people` records who works where, with a role and one primary contact per company.

Reading needs `contacts.read`, creating, changing, linking and archiving needs `contacts.write`, merging needs `contacts.manage`, and setting a supplier status needs `contacts.approve_supplier`. Admins get every permission, and members get `contacts.read` and `contacts.write`.

```bash
better-supabase add contacts
```

The module needs `memberships` and `access`.

Server code calls the `contacts` instance on `db`, in the caller's organization. With `gen.hooks` set, `better-supabase gen` writes the hooks:

```ts title="src/lib/supabase/hooks.ts"
export const { useList: useContacts } = defineDataHooks(
  "contacts",
  (db: AppDb) => db.contacts,
);
```

```ts
import { createContacts } from "better-supabase/blocks/contacts";

const acme = await db.contacts
  .saveCompany(organizationId, {
    name: "Acme",
    domain: "acme.com",
    ownerId: userId,
  })
  .orThrow();
const ada = await db.contacts
  .savePerson(organizationId, {
    name: "Ada Lovelace",
    email: "ada@acme.com",
    title: "CTO",
  })
  .orThrow();
await db.contacts
  .linkPerson(acme.id, ada.id, { role: "Champion", primary: true })
  .orThrow();
```

```tsx title="src/features/contacts/list.tsx"
"use client";

import { useContacts } from "@/lib/supabase/hooks";

const rows = useContacts({ limit: 50 });
```

## Search column

`searchColumn: true` adds a stored `search_tsv` tsvector column and a GIN index
to companies and people. The `deals`, `tasks`, `invoices` and `drive` blocks
take the same option (on the deals, task items, invoices and extracted drive
texts). It is off by default. Query it with
`search_tsv @@ websearch_to_tsquery('simple', 'term')`.

## Companies and people

`saveCompany` and `savePerson` create a record when the input has no `id`, and change the keys the input names otherwise: a key left out keeps its value, and `null` clears it. A new record needs a `name` (`PARTY_NAME_REQUIRED`). Domains and emails are stored in lower case, and an active record can't share its domain or email with another in the organization (`PARTY_DOMAIN_TAKEN`, `PARTY_EMAIL_TAKEN`), so an import finds the existing record instead of a duplicate.

A lifecycle stage is one of `options.companyLifecycles` (default `lead`, `prospect`, `customer`, `churned`) or `options.personLifecycles` (default `lead`, `mql`, `sql`, `opportunity`, `customer`); a new record starts at the first (`PARTY_LIFECYCLE_INVALID` for another value). `archiveCompany(id)` and `archivePerson(id)` hide a record from the lists, and `archived: false` restores it.

`linkPerson(companyId, personId, { role, primary })` links a person to a company or changes the link; a primary link replaces the company's previous primary contact. `peopleOf(companyId)` returns the company's people, primary contact first, and `unlinkPerson` removes a link.

## Roles

A company or person can hold several roles at once, such as a customer that is also a supplier. The roles come from `options.roles` (default `customer`, `supplier`, `funder`, `partner`), each a lowercase name. `setRoles(partyId, roles)` replaces a record's roles, sorted and without duplicates, and needs `contacts.write` (`PARTY_ROLES_INVALID` for a role the options don't list). It returns `{ type: "company", company }` or `{ type: "person", person }`.

```ts title="better-supabase.config.ts"
blocks: {
  contacts: { options: { roles: ["customer", "supplier", "reseller"] } },
},
```

```ts
import { money } from "better-supabase/commerce";

await db.contacts.setRoles(acme.id, ["customer", "supplier"]).orThrow();
await db.contacts
  .saveCompany(organizationId, {
    id: acme.id,
    customerTermsId: net30.id,
    creditBlock: "soft",
    creditLimit: money(500_000n, "EUR"),
  })
  .orThrow();
const suppliers = await db.contacts
  .listCompanies(organizationId, { role: "supplier" })
  .orThrow();
```

`saveCompany` and `savePerson` also take the commercial terms: `customerTermsId` and `supplierTermsId` (a [payment term](#payment-terms)), `creditLimit`, an amount in minor units with its currency (`PARTY_TERMS_INVALID` otherwise), and `creditBlock`. `null` clears any of them. A returned record carries `roles`, `customerTermsId`, `supplierTermsId`, `creditLimit`, `creditBlock`, `language` and `supplierStatus`. `listCompanies` and `listPeople` filter on one `role` and on a `supplierStatus`.

`creditBlock` is `none`, `soft` or `hard`, and a party without one counts as `hard`. Over the credit limit, `hard` makes `issue` on a sales invoice and `place` on an order fail with `INVOICE_CREDIT_LIMIT_EXCEEDED` or `ORDER_CREDIT_LIMIT_EXCEEDED`, `soft` lets the call through and returns the overage in the result's `warnings`, and `none` skips the check. A caller with `orders.override_credit` and the service role skip it too.

## Payment terms

A payment term is a named set of due days and an optional early-payment discount. `savePaymentTerm(organizationId, input)` creates or changes one by `code`, and `paymentTerms(organizationId)` lists them. It needs `contacts.manage` and fails with `PAYMENT_TERM_INVALID`, `PAYMENT_TERM_CODE_TAKEN` or `PAYMENT_TERM_NOT_FOUND`.

```ts
await db.contacts
  .savePaymentTerm(organizationId, {
    code: "2-10-NET30",
    name: "2 percent in 10 days, net 30",
    days: 30,
    discountBps: 200,
    discountDays: 10,
  })
  .orThrow();
```

`discountBps` is the discount the buyer may deduct when paying within `discountDays` (at most `days`). `creditRestrictionBps` is a discount the buyer may deduct whatever the payment date: the invoice's tax is computed on the reduced amount, in `invoice_tax_lines`, and the header `tax_total` stays as issued. A new invoice copies the customer's `customerTermsId` (a purchase bill copies `supplierTermsId`) into `payment_terms_id`, and `issue` stores `terms_days`, `discount_due_on` and `discount_amount_early` from it.

## Language and delivery

`language` on a company or person is the language tag of their documents. `setDeliveryPreferences(partyId, preferences)` replaces the party's list of `{ documentType, channel, copies, email }`, where `channel` is `email`, `post` or `portal` and each document type and channel pair appears once (`DELIVERY_PREFERENCE_INVALID` otherwise). `deliveryPreferences(partyId)` reads it. Payment terms and delivery preferences also have [import](/docs/blocks/imports) targets named `payment_term` and `document_delivery_preference`.

## Suppliers

`setSupplierStatus(partyId, status, reason)` records where a supplier stands: `approved`, `conditional` or `blocked`, or `null` for not assessed. It needs `contacts.approve_supplier`, which admins hold, so a buyer who edits the record can't approve the supplier. A change writes `company.supplier_status_changed` or `person.supplier_status_changed` with the previous status and the reason, and an audit entry. Together with the `supplierStatus` list filter, this keeps the approved supplier list that ISO 9001 clause 8.4 asks for.

```ts
await db.contacts
  .setSupplierStatus(acme.id, "conditional", "Certificate renewal pending")
  .orThrow();
const approved = await db.contacts
  .listCompanies(organizationId, {
    role: "supplier",
    supplierStatus: "approved",
  })
  .orThrow();
```

With [qualifications](/docs/blocks/qualifications) installed and `company` among its `holderTypes`, `supplierStatusFromQualifications(companyId)` returns `approved` when the company's gap report lists no missing or expired qualification, and `conditional` otherwise. It only reads; pass the result to `setSupplierStatus` to apply it, for example from a nightly job:

```ts
const status = await db.contacts
  .supplierStatusFromQualifications(acme.id)
  .orThrow();
await db.contacts
  .setSupplierStatus(acme.id, status, "From qualifications")
  .orThrow();
```

## Search and pages

`listCompanies` and `listPeople` return the active records by name, 50 per page (at most 200). `search` matches the name and the domain or email, and `lifecycle` and `ownerId` filter. Pass the page's `next` as `cursor` for the next page:

```ts
const page = await parties
  .listPeople(organizationId, { search: "acme", limit: 25 })
  .orThrow();
const more = page.next
  ? await parties
      .listPeople(organizationId, { search: "acme", cursor: page.next })
      .orThrow()
  : undefined;
```

The lists, `peopleOf` and the tables all run as the caller: a member reads the organization's records through the `contacts.read` policy, and PostgREST reads the tables directly.

## Merge duplicates

`mergeCompanies(keep, drop)` and `mergePeople(keep, drop)` fill the kept record's empty fields from the dropped one, move the dropped record's links to it, and archive the dropped record with `merged_into` set. Merging needs `contacts.manage` (`PARTY_MERGE_INVALID` for records of two organizations, one record twice, or one already merged). In the same transaction the merge moves the dropped record's comments, attachments, reactions, tags, relations and guest grants to the kept record ([Merging subject records](/docs/blocks/sql#merging-subject-records)). The `company.merged` and `person.merged` events carry `mergedId`, so a consumer can move the app's own references, such as deals, to the kept record, or the app can add its own merge handler in SQL. A merge is written to the audit log.

## Use them as subjects

Installing the block registers `company` and `person` as subjects, so [comments](/docs/blocks/comments), [tags](/docs/blocks/tags), [attachments](/docs/blocks/attachments), [pipelines](/docs/blocks/pipelines) and the activity feed attach to them. Set their pages on the entities, or `subject: false` to register one yourself:

```ts title="better-supabase.config.ts"
export default defineConfig({
  blocks: {
    contacts: {
      names: {
        company: { url: "/companies/{id}" },
        person: { url: "/people/{id}" },
      },
    },
  },
});
```

An entity also takes `team` and `auditReads`, as a type in `subjects` does. A care app gives each client a record team and logs who reads their record ([Record teams](/docs/blocks/sql#record-teams), [Record read log](/docs/blocks/sql#record-read-log)):

```ts title="better-supabase.config.ts"
export default defineConfig({
  blocks: {
    contacts: {
      names: {
        person: {
          name: "client",
          team: { actions: ["read", "write"] },
          auditReads: true,
        },
      },
    },
  },
});
```

The [`care`](/docs/presets/care) preset sets both on `person`.

With the [notifications](/docs/blocks/notifications) module installed, the owner watches a company or person when they become its owner, and a level they already chose stays.

## Identities

A person's addresses on channels, such as an email address or a WhatsApp number, are its identities in `person_identities`. An address on a channel belongs to one person of the organization, so the [inbox](/docs/blocks/inbox) and the [Chat SDK adapters](/docs/chat-sdk) find the person behind an incoming message, and a conversation's contact is that person, with their company, deals and history.

```ts
await parties
  .addIdentity(ada.id, { channel: "whatsapp", address: "+31612345678" })
  .orThrow();

const sender = await parties
  .findByIdentity(organizationId, "whatsapp", "+31612345678")
  .orThrow();
```

`identities(personId)` lists a person's addresses. `addIdentity(personId, { channel, address, verified })` adds one, or marks it verified with `verified: true`; an address another person of the organization holds fails with `PARTY_IDENTITY_TAKEN`. `removeIdentity(identityId)` removes one and returns `false` when there was none. `findByIdentity(organizationId, channel, address)` returns the person or `undefined`. Merging two people moves the dropped person's identities and inbox conversations to the kept one.

## Representatives

With the [relations](/docs/blocks/relations) block installed, `contacts` contributes the relation kind `represents` (inverse `represented_by`): a person who speaks for a record, such as a client's guardian, a student's parent or a patient's emergency contact. The source is always a `person`; the target is any subject. Each link carries a `role` and an `authority` in its data, and optionally the dates it holds:

```ts
await db.relations
  .link(
    { type: "person", id: adaId },
    { type: "client", id: clientId },
    {
      kind: "represents",
      data: { role: "guardian", authority: "act", valid_until: "2027-06-30" },
    },
  )
  .orThrow();
```

| Key           | Values                                                                                                            |
| ------------- | ----------------------------------------------------------------------------------------------------------------- |
| `role`        | `legal_representative`, `guardian`, `mentor`, `curator`, `parent`, `contact_person`, `emergency_contact`, `other` |
| `authority`   | `inform` (kept informed) or `act` (acts on the record's behalf)                                                   |
| `valid_from`  | optional, an ISO date the link starts                                                                             |
| `valid_until` | optional, an ISO date the link ends, on or after `valid_from`                                                     |

`link` refuses other data with `RELATION_DATA_INVALID`, and a source that isn't a person with `RELATION_TYPE_NOT_ALLOWED`. A link is active from `valid_from` through `valid_until`, both inclusive; outside them it stays as history. Declare `represents` in the relations block's `kinds` to replace the contributed kind and its checks.

```ts
const people = await db.contacts
  .representativesOf("client", clientId)
  .orThrow();
const mine = await db.contacts.representedByMe(organizationId).orThrow();
```

`representativesOf(type, id)` returns everyone who represents a record, with their name, email and phone, the role, the authority, the dates and whether the link is `active`, active links first. It reads through the caller's access to the links. `representedByMe(organizationId)` is for a [guest](/docs/blocks/guests#representatives-as-guests) who acts for a person: the records that person actively represents. With `guests.representation` set, those records open to the guest without a grant.

## Extra columns

`options.extraColumns` adds columns to `companies`, such as a segment or an industry. `saveCompany` writes them from `fields`, and every company it returns carries them in `fields`:

```ts title="better-supabase.config.ts"
blocks: {
  contacts: { options: { extraColumns: { segment: "text", employees: "integer" } } },
},
```

Pass a Standard Schema as `fields` to type them: `saveCompany` validates the fields it writes (a `validation` error, before the database), and `saveCompany`, `mergeCompanies` and `listCompanies` parse them on read.

```ts
const parties = createContacts({
  transport,
  fields: v.object({
    segment: v.optional(v.string()),
    employees: v.optional(v.number()),
  }),
});
await parties.saveCompany(organizationId, {
  name: "Acme",
  fields: { segment: "smb" },
});
```

People take app fields through [custom fields](/docs/blocks/custom-fields) with the `person` subject.

## Events

| Event                                                    | Data                                                                        |
| -------------------------------------------------------- | --------------------------------------------------------------------------- |
| `company.created`, `company.updated`, `company.archived` | `organizationId`, `companyId`, `name`                                       |
| `company.merged`                                         | `organizationId`, `companyId`, `name`, `mergedId`                           |
| `company.person_linked`, `company.person_unlinked`       | `organizationId`, `companyId`, `personId`, `role`                           |
| `company.supplier_status_changed`                        | `organizationId`, `companyId`, `name`, `status`, `previousStatus`, `reason` |
| `person.created`, `person.updated`, `person.archived`    | `organizationId`, `personId`, `name`                                        |
| `person.merged`                                          | `organizationId`, `personId`, `name`, `mergedId`                            |
| `person.supplier_status_changed`                         | `organizationId`, `personId`, `name`, `status`, `previousStatus`, `reason`  |

`setRoles` writes `company.updated` or `person.updated`.

## Hooks

The module calls `before_company_save(tenant, company uuid, attrs jsonb)`, `after_company_save(company uuid, created boolean)`, `before_person_save` and `after_person_save` around its saves. A `before_` hook raises to refuse the write. The TypeScript client takes `hooks` for its methods (see [extending blocks](/docs/extending/blocks)).

## Wire it to ReUI

The ReUI CRM Contacts Directory reads `listPeople` for its grid, with the Filters `search` and lifecycle values passed through, and its bulk owner action calls `savePerson` with `ownerId` per selected row (or the [bulk](/docs/blocks/bulk) block for many at once). Its CSV import maps rows to `savePerson`, and an email that is taken points at the existing record.

## Errors

| Hint                            | Cause                                                                                                                     |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `PARTY_FORBIDDEN`               | the caller lacks `contacts.write`, or `contacts.manage` for a merge, or `contacts.approve_supplier` for a supplier status |
| `PARTY_ATTRS_INVALID`           | the attributes aren't an object                                                                                           |
| `PARTY_NAME_REQUIRED`           | a new record has no name                                                                                                  |
| `PARTY_LIFECYCLE_INVALID`       | not a configured lifecycle stage                                                                                          |
| `PARTY_DOMAIN_TAKEN`            | another active company has the domain                                                                                     |
| `PARTY_EMAIL_TAKEN`             | another active person has the email                                                                                       |
| `PARTY_NOT_FOUND`               | no such record                                                                                                            |
| `PARTY_MERGE_INVALID`           | the records can't be merged                                                                                               |
| `PARTY_IDENTITY_INVALID`        | an identity has no channel or no address                                                                                  |
| `PARTY_IDENTITY_TAKEN`          | another person of the organization has the address                                                                        |
| `PARTY_ROLES_INVALID`           | a role isn't in `options.roles`                                                                                           |
| `PARTY_SUPPLIER_STATUS_INVALID` | not `approved`, `conditional` or `blocked`, or a reason over 2000 characters                                              |
| `PARTY_TERMS_INVALID`           | an unknown payment term, a bad credit block, or a credit limit without whole minor units and a currency                   |
| `PAYMENT_TERM_INVALID`          | a code, name, days or discount outside its range, or a discount window longer than the due days                           |
| `PAYMENT_TERM_CODE_TAKEN`       | another term of the organization has the code                                                                             |
| `PAYMENT_TERM_NOT_FOUND`        | no such payment term                                                                                                      |
| `DELIVERY_PREFERENCE_INVALID`   | a preference without a known channel, or a repeated document type and channel                                             |
| `PARTY_FIELD_UNSUPPORTED`       | an adopted table has no column for the key                                                                                |

## Without the client

`db.contacts` is this client. Code that does not go through `bsb.db()` builds it with a transport and an organization id:

```ts
import { createContacts } from "better-supabase/blocks/contacts";

const parties = createContacts({ transport });
const acme = await parties
  .saveCompany(organizationId, {
    name: "Acme",
    domain: "acme.com",
    ownerId: userId,
  })
  .orThrow();
const ada = await parties
  .savePerson(organizationId, {
    name: "Ada Lovelace",
    email: "ada@acme.com",
    title: "CTO",
  })
  .orThrow();
await parties
  .linkPerson(acme.id, ada.id, { role: "Champion", primary: true })
  .orThrow();
```

In SQL the same calls are `better_supabase.set_party_roles(party, roles)`, `better_supabase.set_supplier_status(party, status, reason)` and `better_supabase.supplier_status_from_qualifications(party)`, each checking the caller's permission.
