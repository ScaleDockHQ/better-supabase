---
title: Drive
description: Folders and files on the attachments module. Access is granted to users or teams and inherited down the tree, storage policies enforce it on the objects too, and versions, trash and share-links add revisions, a bin, stars, recent items and folder links.
---

`drive` keeps a tree of folders and files per organization. A file is a node that points at an [attachment](/docs/blocks/attachments), so uploads, scanning and signed downloads work as they do there. Access is granted on a node to a user, a team or an organization role and applies to everything under it: a viewer on `Projects` can read `Projects/Launch/plan.pdf`. The same check runs in the drive functions, in the policies on the attachment rows and in restrictive policies on `storage.objects`, so a signed URL never opens a file the caller can't read.

```bash
better-supabase add drive
```

`drive` installs `drive-files` with it, which adds what needs the attachments module: uploads and revisions, the storage policies, the bin, stars, recent items, folder links and the purge. Install [versions](/docs/blocks/versions), [trash](/docs/blocks/trash), [share-links](/docs/blocks/share-links) and [teams](/docs/blocks/teams) for revisions, the bin, stars and links, and team grants.

Server code calls the `drive` instance on `db`, in the caller's organization. With `gen.hooks` set, `better-supabase gen` writes the hooks:

```ts title="src/lib/supabase/hooks.ts"
export const { useList: useDrive } = defineDataHooks(
  "drive",
  (db: AppDb) => db.drive,
);
```

```ts
import { createAttachments } from "better-supabase/blocks/attachments";
import { createDrive, rpcTransport } from "better-supabase/blocks/drive";

const transport = rpcTransport(supabase);

const projects = await db.drive
  .createFolder(organizationId, { name: "Projects" })
  .orThrow();
const upload = await db.drive
  .upload(organizationId, {
    parentId: projects.id,
    name: file.name,
    mimeType: file.type,
    size: file.size,
  })
  .orThrow();
await supabase.storage
  .from(upload.attachment.bucket)
  .uploadToSignedUrl(upload.attachment.path, upload.token, file);
await db.drive.commit(upload.node.id, upload.attachment.id).orThrow();

await db.drive.share(projects.id, { type: "team", id: designTeam }, "editor");
await db.drive.share(projects.id, { type: "role", id: memberRoleId }, "viewer");
const { signedUrl } = await db.drive.download(upload.node.id).orThrow();
```

```tsx title="src/features/drive/list.tsx"
import { useDrive } from "@/lib/supabase/hooks";

const rows = useDrive({ limit: 50 });
```

## Access

Each node has a role for the caller: the highest role granted on the node or any folder above it, or `null` when nothing is granted. Members with `drive.manage` have the top role on every node in the organization, and the service role always does. Reading anything needs `drive.read`, and creating a node at the root needs `drive.create`.

| Role     | What it allows                                                     |
| -------- | ------------------------------------------------------------------ |
| `viewer` | List, open and download the node and everything under it           |
| `editor` | Create, upload, rename, move, trash and restore revisions under it |
| `owner`  | Share and unshare, and everything an editor can do                 |

Add your own roles to the ladder with `roles`, lowest first. A `commenter` between `viewer` and `editor` becomes the comment role (`commentRole`): `drive_can_comment(node)` is true from that role up, so a commenter reads and comments but doesn't change the file. A `manager` above `editor` with `shareRole: "manager"` lets people share and set download blocks without being the top role. Without a `commenter`, the comment role is the write role.

The creator of a node gets the top role on it. Grants with an `expiresAt` stop applying after that time. `drive_role(node)` and `drive_can(node, role)` are SQL functions, so your own policies can use them too. The block's own read policy uses `id in (select drive_readable_ids())` instead, which returns every node `drive_can(node, read)` is true for in one call, so Postgres runs it once per statement rather than once per row; prefer it in your policies on large drives.

With `roleFunctions.node` or `roleFunctions.drive`, the block calls a schema-qualified function you name with the node or drive id and the caller's user id, and uses the role it returns. The function returns one of `roles`, or null. It replaces the block's own grants at that level, while the tenant `drive.read` check still applies. Use it when your own rules already decide who may read a node or a drive, such as an AuthorizationProvider.

When an [authorization provider](/docs/extending/authorization-providers) grants access per row, set `{ rows, roles }` instead of a function name: `rows` is the provider's resource and `roles` maps each role of `roles` to the permission key that grants it. The block generates the check through the provider's `rowsWith` template (`blocks.permissions.model: "provider"`), and the caller gets the highest role whose key they hold on the node or drive.

```ts title="better-supabase.config.ts"
drive: {
  options: {
    roleFunctions: {
      node: {
        rows: "file_node",
        roles: {
          viewer: "fileNode.read",
          editor: "fileNode.update",
          owner: "fileNode.manage",
        },
      },
    },
  },
},
```

## Configure

```ts title="better-supabase.config.ts"
blocks: {
  drive: {
    options: {
      roles: ["viewer", "commenter", "editor", "manager", "owner"],
      writeRole: "editor",
      shareRole: "manager",
      conflict: "rename",
    },
  },
},
```

| Option          | Default                         | What it does                                                                           |
| --------------- | ------------------------------- | -------------------------------------------------------------------------------------- |
| `roles`         | `["viewer", "editor", "owner"]` | The roles, lowest first; the first one reads and the last one is the top role          |
| `writeRole`     | `editor`, else the top role     | The role that may create, rename, move and trash                                       |
| `shareRole`     | the top role                    | The role that may share and unshare, break locks and block downloads                   |
| `commentRole`   | `commenter`, else `writeRole`   | The role `drive_can_comment` checks                                                    |
| `previewPrefix` | `_previews`                     | The storage folder preview pages go to, in the attachment's bucket                     |
| `memberRole`    | none                            | A role every member of the organization has on every node                              |
| `uploadRole`    | none                            | A role, outside `roles`, that adds files to a folder without reading it                |
| `conflict`      | `fail`                          | What a duplicate name in a folder does: `fail`, `rename` (`plan (2).pdf`) or `replace` |
| `subjectType`   | `drive_node`                    | The subject type of nodes in events, audit entries, attachments, versions and trash    |
| `drives`        | `false`                         | Several drives per organization, with drive-level grants and connected drives          |
| `driveKinds`    | `["shared"]`                    | The kinds a drive can have; the first is the default                                   |
| `sources`       | `["google-drive", "onedrive"]`  | The providers a connection can mirror                                                  |
| `roleFunctions` | none                            | App functions or provider row grants that give the caller's role                       |
| `readPolicy`    | `true`                          | The block's read policies; `false` leaves them to the app                              |
| `extraColumns`  | none                            | Columns on the node table that `fields` reads and writes                               |

Each call that creates, renames or moves a node can pass its own `conflict`. Names compare case-insensitively within one folder.

## Upload-only access

Set `uploadRole` to give people a folder they can drop files into without seeing what's in it, such as a `contributor` on an `Inbox` folder. The role sits outside the `roles` ladder, and you grant it on a folder like any other role. It needs the node table's `createdBy` column, because a contributor keeps access to the files they added.

```ts title="better-supabase.config.ts"
drive: {
  options: { uploadRole: "contributor" },
},
```

```ts
await db.drive.share(inbox.id, { type: "user", id: vendorId }, "contributor");

// As the contributor:
const file = await db.drive
  .contribute(organizationId, {
    parentId: inbox.id,
    name: invoice.name,
    mimeType: invoice.type,
    size: invoice.size,
  })
  .orThrow();
await supabase.storage
  .from(file.attachment.bucket)
  .uploadToSignedUrl(file.attachment.path, file.token, invoice);
await db.drive.commitContribution(file.id, file.attachment.id).orThrow();
```

A contributor can't list, open or download the folder or anything in it, including their own files: `get` and `list` return `DRIVE_NOT_FOUND` for them. `contribute` takes a free name (`invoice (2).pdf`) so a contributor never learns which names the folder already holds, and it returns the new file's id and its upload, not the node. The contributor may upload a revision of a file they added and commit it, and nothing else; renaming, moving, trashing and sharing still need the write or share role. `drive_can_upload(folder)` is the check in SQL, true for the upload role and for the write role. Granting the upload role on a file fails with `DRIVE_ROLE_UNKNOWN`.

The upload role works on node grants, not on drive grants. When your grant table's `role` column is an enum, add the upload role's value to it.

## File requests

A file request lets anyone with a link send files into a folder, without an account. It is a [share link](/docs/blocks/share-links) with the role `upload`, so it takes the same expiry, use limit and password. `createFileRequest` needs the share role on the folder, and the token comes back once:

```ts
const request = await db.drive
  .createFileRequest(inbox.id, {
    expiresAt: Temporal.Now.instant().add({ hours: 72 }),
    maxUses: 10,
    password: "harbor-pier",
  })
  .orThrow();
const url = `https://app.example.com/send/${request.token}`;
```

The page behind that URL posts the file to your server, which sends it on with a drive client made from the service transport and the service storage client:

```ts title="src/app/send/[token]/actions.ts"
"use server";

const drive = createDrive({
  transport: serviceTransport,
  storage: serviceStorage,
});
const sent = await drive
  .uploadToRequest(token, file, { name: file.name, password })
  .orThrow();

if (sent.passwordRequired) {
  return { passwordRequired: true };
}
```

`uploadToRequest` resolves the token, creates the file in the folder under a free name, uploads the bytes and commits them. Each file counts one use of the link, and the files a link takes are counted per link under the scope `drive_link_upload` when the [rate-limit](/docs/blocks/sql) module is installed: 20 an hour, unless `set_rate_limit('drive_link_upload', ...)` sets another rule. Past the limit the call fails with `rate_limited` and the hint `DRIVE_LINK_RATE_LIMITED`. A wrong or missing password returns `{ passwordRequired: true }` instead of an error. A view or download link fails with `DRIVE_LINK_ROLE_INVALID`.

A file that came through a request has the `source` `request` and no creator, and `drive.node_created` carries that `source`, so a sink can tell the folder's owner a file arrived. Unlike files mirrored from a connection, request files aren't read-only: the folder's editors rename, move and trash them like any other file. When your node table's `source` column is an enum, add `request` to it.

Pass a [Standard Schema](https://standardschema.dev) for the `extraColumns`
as `fields` to `createDrive`: every node the client returns has its `fields`
parsed, and `createFolder` and `upload` validate the ones you set before the
call (see [extending blocks](/docs/extending/blocks#your-own-fields)).

## Drives, connections and legal holds

With `drives` on, every node belongs to a drive: `drive_drives` holds the drives of an organization, `drive_drive_grants` their grants and `drive_connections` the external accounts they mirror. A top-level node needs a drive; a child stays in its parent's drive. Drive-level grants apply to every node in the drive, on top of node grants, and a drive's owner and members with `drive.manage` have the top role on it.

```ts
const drive = await db.drive
  .createDrive(organizationId, { name: "Projects", kind: "shared" })
  .orThrow();
const folder = await db.drive
  .createFolder(organizationId, { name: "Launch", driveId: drive.id })
  .orThrow();
const roots = await db.drive
  .list(organizationId, { driveId: drive.id })
  .orThrow();

await db.drive.shareDrive(drive.id, { type: "team", id: designTeam }, "editor");
```

`drives(organizationId)` lists the drives the caller can read, `drive(id)` reads one, and `renameDrive`, `deleteDrive`, `shareDrive`, `unshareDrive` and `driveGrants` manage them. `deleteDrive` fails while any node in the drive is under a legal hold.

A connection is the caller's link to an external account: `connect(organizationId, provider, name)` records one and `connections(organizationId)` lists the caller's own. `createDrive(organizationId, { name, connectionId })` creates a drive that mirrors that account, owned by the connection's user. Mirrored nodes have a `source` other than `internal`, an `externalId` and `externalMetadata`, and the nodes are read-only: only the service role's `drive_sync_batch` changes them. Renaming, moving, sharing, uploading and trashing them fails with `DRIVE_READ_ONLY`.

A legal hold keeps a node and everything under it from being purged. `hold(id, until)` sets `legalHoldUntil`, `releaseHold(id)` clears it, and every node reports `held` when it or something under it is held. `delete(id)` fails with `DRIVE_HELD` while a hold applies, and `trash(id)` refuses to move a held subtree to the bin. Configure trash with the node's hold column so a held batch stays there:

```ts title="better-supabase.config.ts"
trash: {
  on: {
    drive_node: { deletedAt: "deleted_at", held: "legal_hold_until" },
  },
},
```

`purge(binId)` then raises `TRASH_HELD`, and `purge_expired_trash` skips the batch until the hold ends.

## Files and revisions

`upload` creates the file node and a pending attachment, then signs an upload URL. After the upload, `commit` makes the attachment the file's content. `uploadRevision` uploads new content for an existing file the same way; with versions installed, each commit saves a revision, `revisions(id)` lists them and `restoreRevision(id, revisionId)` makes an old one current again.

`download(id)` signs a download URL for the current content through the `attachments` option, the attachments block over the same transport; `createBlocks` passes it as the `attachments` port when the set has `attachmentsBlock`. Without it, `download` fails with the hint `DRIVE_ATTACHMENTS_CLIENT`. With `requireScan` on the attachments block (the default), a file that isn't scanned clean yet can't be downloaded.

## Check-out, download blocks and previews

`lock(id)` checks a file out for the caller. Until the lock ends (8 hours by default, at most 30 days), nobody else may upload a revision, commit, restore a revision, rename, move, trash or delete it; trashing or deleting a folder fails while a file under it is checked out. Those calls fail with `DRIVE_LOCKED`, and the error's detail names `lockedBy` and `lockedUntil`. Locking needs the write role. `unlock(id)` ends the caller's own lock, and `unlock(id, { force: true })` lets the share role end someone else's. The service role ignores locks. Every node reports `lockedBy`, `lockedUntil` and `lockNote` while a lock applies; an expired lock reads as no lock.

```ts
await db.drive
  .lock(fileId, {
    until: Temporal.Now.instant().add({ hours: 2 }),
    note: "Redlining",
  })
  .orThrow();
// edit, upload a revision, commit
await db.drive.unlock(fileId).orThrow();
```

`blockDownloads(id)` keeps the original of a node, and of everything under it, from callers below the write role; `blockDownloads(id, false)` lifts it. With `drives` on, `blockDriveDownloads(driveId)` does the same for a whole drive. Setting a block needs the share role. A blocked caller still lists and opens the node and reads its previews, but the storage policy refuses the original and `download(id)` fails with the hint `DRIVE_DOWNLOAD_BLOCKED`. Every node reports `downloadBlocked` (the flag on the node itself) and `downloadable` (whether the caller may download it). `drive_can_download(node)` is the same check in SQL.

A preview is the file's pages rendered as images, stored in the attachment's bucket under `previewPrefix/<organization>/<node>/<attachment>/<page>`. Readers of the node may open them even when downloads are blocked. `previews(id)` returns `pages`, `bucket`, `prefix` and the page `paths`, and `previewUrls(id)` signs them. Uploading a new revision resets the count until the new pages are rendered.

The drive doesn't render pages itself. Pass a `PreviewRenderer` (a PDF rasterizer, an office converter, an image resizer) to `createDrivePreviews` with a service-role transport and storage, then run its job or its sink:

```ts
import { createDrivePreviews } from "better-supabase/blocks/drive";

const previews = createDrivePreviews({
  transport: serviceTransport,
  storage: serviceStorage,
  renderer: {
    apiVersion: 1,
    name: "pdfium",
    render: async (file, { maxPages }) => renderPdfPages(file, maxPages),
  },
  requireClean: true,
});

await outbox.relay("drive-previews", previews.sink());
// or from a queue: queue.work("drive-previews", previews.job)
```

The sink renders the file behind every `attachment.uploaded` and `attachment.scanned` event on a drive node; `render(nodeId)` renders one file on demand, for example after `commit`. A renderer returns `undefined` for a type it doesn't handle. With `requireClean`, only files the scanner marked `clean` render; without it, `infected` and `failed` files are skipped. For images alone, the [attachments block's](/docs/blocks/attachments) `images()` transforms can serve a resized original instead of a preview, but they don't honor a download block.

## Labels and approvals

With the [tags block](/docs/blocks/tags) installed, `label(id, tagId)` puts a tag on a node and `label(id, tagId, false)` takes it off; it needs write access to the node. Every node the client returns carries its `labels` (`id`, `name`, `color`), and `labeled(organizationId, tagId)` lists the nodes with a tag that the caller may read. Tags of any kind work as labels. Purging a node deletes its labels.

With the [approvals block](/docs/blocks/approvals) installed, `requestApproval(id)` asks for approval of the file's current content, and `requestApproval(id, { attachmentId, reason })` asks for one earlier revision. The request records the attachment and the revision number in its payload, so a decision covers exactly those bytes. Add a policy for the `approve` action on the node subject:

```ts title="better-supabase.config.ts"
approvals: {
  options: {
    policies: {
      drive_node: {
        approve: { steps: [{ approvers: { permission: "approvals.manage" }, required: 1 }] },
      },
    },
  },
},
```

`approvals(id)` lists the file's requests, newest first, each with `attachmentId`, `revision` and `current` (whether that revision is still the file's content). Every node carries `approval`: the latest request for its current content, or `undefined`. Uploading a new revision clears it, and restoring an approved revision brings the approval back. A file has at most one pending request at a time, so a second request fails with `APPROVAL_PENDING`. Requests stay after the node is purged, as the record of what was decided.

Anyone who can read a node sees its labels and its approval state. Tagging, untagging and requesting approval need write access, and the tags and approvals functions check the same drive grants when they are called directly with the `drive_node` subject type.

## The bin

With trash installed, `trash(id)` moves a node and everything under it to the bin as one batch, and `bin(organizationId)` lists the batches. `restore(binId)` puts the batch back, applying the conflict policy if the name is taken again. A node whose folder is still in the bin can't come back until the folder does. `purge(binId)` deletes it for good and records `drive.node_purged` with the object paths. Run `prune()` from the service role to delete the purged objects from storage:

```ts
const drive = createDrive({ transport: serviceTransport, storage });
await drive.prune({ maxObjects: 500 }).orThrow();
```

## Stars, recent items and links

With share-links installed, `star(id)` and `star(id, false)` mark a node for the caller, `open(id)` records that the caller opened it, and `starred` and `recent` list them. A share link on a folder opens it and the nodes under it: `link(token)` returns the folder and its children, and `link(token, { nodeId })` returns one node under it with its stored object.

Creating a link on a node needs the share role. A `view` or `download` link opens the item. Its `downloadAllowed` is false, and the stored object is left out, when the link was created with `downloadAllowed: false` or a download block covers the item; the `previews` still come back. An `upload` link names a folder, and `link(token)` refuses it with `DRIVE_LINK_ROLE_INVALID`, since it takes files and opens nothing; [file requests](#file-requests) send files through one.

## With ReUI

`driveTree(nodes)` shapes the nodes you loaded for a tree view such as the [ReUI](https://reui.io) file tree on headless-tree: it returns `rootItemId`, `getItem`, `getChildren` and `isFolder`. `fileTypeCategory(mimeType, name)` and `nodeType(node)` name a file's kind (`image`, `pdf`, `spreadsheet`, `code` and others) to pick its icon.

```tsx
import { driveTree, nodeType } from "better-supabase/blocks/drive";

const data = driveTree(await drive.list(organizationId).orThrow());
const tree = useTree({
  rootItemId: data.rootItemId,
  getItemName: (item) => data.name(item.getId()),
  isItemFolder: (item) => data.isFolder(item.getId()),
  dataLoader: { getItem: data.getItem, getChildren: data.getChildren },
  features: [syncDataLoaderFeature],
});
```

Load a folder's children with `list(organizationId, { parentId })` as it opens, and build the tree again from all the nodes loaded so far.

## Comments, search and relations on nodes

`driveSubject()` describes the node table as a subject, so the [subject registry](/docs/blocks/sql#subject-registry) lets comments, reactions and other blocks attach to nodes with the drive's read and write rules. It also carries a `search` entry: with the [search block](/docs/blocks/search) installed, node names are indexed as they are created and renamed, trashed nodes drop out of the results, and [relations](/docs/blocks/relations) can link a node to any other subject:

```ts title="better-supabase.config.ts"
import { driveSubject } from "better-supabase/blocks/drive";

export default defineConfig({ records: { drive_node: driveSubject() } });
```

The entry follows the node's grants, not only the tenant keys. Its `read` action asks `drive.read` and `drive_node_readable(node)`, its `comment` action asks `drive_can_comment(node)` (the comment role), and its `fields` action asks `drive_node_writable(node)`, all through `check` functions (see [Actions granted per row](/docs/blocks/sql#actions-granted-per-row)). With `readAccess: "record"`, [custom fields](/docs/blocks/custom-fields) on a node are readable only by members who can read the node, and only editors can set them. `can_subject_for` can't run the check functions for another user, so it returns false for a node's `read`.

## Over your own tables

Map `tables.nodes` and `tables.grants` to run the drive on your own tree and grant tables. A grant table can name its principal with `principalType` and `principalId` columns (users, teams and roles), or with a `user` column and an optional `team` column (users and teams). With `drives` on, map `tables.drives`, `tables.driveGrants` and `tables.connections` too; a drive grant table takes the same principal columns as a node grant table. Set `attachment` to `null` when your files don't live in attachments: the tree, grants, sharing and checks still work, and uploads stay with your code.

The node columns `lockedBy`, `lockedUntil` and `lockNote` (check-out), `downloadBlocked` (download blocks) and `previewPages` (previews), and the drive column `downloadBlocked`, are optional. Map one to `null` when your table doesn't have it, and the block leaves that feature out; the block's own tables have them all.

The node `kind` and `source`, the `role` of node and drive grants, the drive `kind` and the connection `provider` and `status` may be enums of yours: the block casts what it writes into them and compares roles as text.

When your schema already has its own read policies, set `readPolicy` to `false` so the block leaves reads to them. Name `roleFunctions.node` or `roleFunctions.drive` to let your own functions decide the caller's role at that level, as the Access section describes.

```ts title="better-supabase.config.ts"
drive: {
  tables: { nodes: "public.file_node", grants: "public.file_node_grant" },
  columns: {
    nodes: { tenant: "organization_id", attachment: null, path: null, rank: null, deletedAt: null },
    grants: {
      tenant: "organization_id",
      node: "file_node_id",
      principalType: null,
      principalId: null,
      expiresAt: null,
      createdBy: null,
    },
  },
  options: { roles: ["viewer", "commenter", "editor"] },
},
```

## Errors

| Hint                         | When                                                                                                 |
| ---------------------------- | ---------------------------------------------------------------------------------------------------- |
| `DRIVE_NOT_FOUND`            | The node doesn't exist, or the caller may not read it                                                |
| `DRIVE_FORBIDDEN`            | The caller's role on the node doesn't allow the change                                               |
| `DRIVE_NAME_CONFLICT`        | The folder already has a node with that name and `conflict` is `fail`                                |
| `DRIVE_NAME_INVALID`         | The name isn't 1 to 255 characters, or holds a `/` or a control character                            |
| `DRIVE_CONFLICT_INVALID`     | `conflict` isn't `fail`, `rename` or `replace`                                                       |
| `DRIVE_PARENT_NOT_FOUND`     | The parent folder doesn't exist in the organization                                                  |
| `DRIVE_PARENT_NOT_FOLDER`    | The parent is a file                                                                                 |
| `DRIVE_PARENT_TRASHED`       | `restore` names a node whose folder is still in the bin                                              |
| `DRIVE_MOVE_CYCLE`           | The move puts a folder inside itself                                                                 |
| `DRIVE_RANK_INVALID`         | The rank isn't a rank key                                                                            |
| `DRIVE_ROLE_UNKNOWN`         | The role isn't one of `options.roles`                                                                |
| `DRIVE_PRINCIPAL_INVALID`    | The principal type isn't `user`, `team` or `role`, or the id is missing                              |
| `DRIVE_PRINCIPAL_NOT_FOUND`  | The user isn't a member, or the team or role isn't in the organization                               |
| `DRIVE_NOT_A_FILE`           | A file call names a folder                                                                           |
| `DRIVE_ATTACHMENT_NOT_FOUND` | `commit` or `requestApproval` names an upload that doesn't belong to the file, or isn't uploaded yet |
| `DRIVE_REVISION_NOT_FOUND`   | The revision doesn't belong to the file                                                              |
| `DRIVE_LINK_NOT_FOUND`       | The link is unknown, expired or revoked, or the node isn't under it                                  |
| `DRIVE_STORAGE_CLIENT`       | A file call ran on a client created without `storage`                                                |
| `DRIVE_READ_ONLY`            | The node mirrors an external account, so only the sync may change it                                 |
| `DRIVE_HELD`                 | The node or something under it is under a legal hold                                                 |
| `DRIVE_HOLD_INVALID`         | `hold` needs an end in the future                                                                    |
| `DRIVE_REQUIRED`             | A top-level node needs a drive                                                                       |
| `DRIVE_KIND_INVALID`         | The drive kind isn't one of `options.driveKinds`                                                     |
| `DRIVE_CONNECTION_NOT_FOUND` | `createDrive` names a connection that doesn't exist or isn't the caller's                            |
| `DRIVE_CONNECTION_EXISTS`    | The caller already connected this account under that name                                            |
| `DRIVE_PROVIDER_INVALID`     | The provider isn't one of `options.sources`                                                          |
| `DRIVE_NOT_CONNECTED`        | `drive_sync_batch` names a drive that doesn't mirror a connection                                    |
| `DRIVE_OWNER_NOT_MEMBER`     | The owner isn't an active member of the organization                                                 |
| `DRIVE_LOCKED`               | Someone else has the file, or a file under the folder, checked out                                   |
| `DRIVE_LOCK_INVALID`         | The lock doesn't end in the future within 30 days, or the note is over 500 characters                |
| `DRIVE_DOWNLOAD_BLOCKED`     | `download` names a file whose downloads are blocked for the caller                                   |
| `DRIVE_TARGET_INVALID`       | A download block names an unknown target type, or `blocked` isn't true or false                      |
| `DRIVE_LINK_ROLE_INVALID`    | An upload link names a file, `link` opens an upload link, or a view link takes a file                |
| `DRIVE_LINK_RATE_LIMITED`    | A file request took more files than its rate limit allows                                            |
| `DRIVE_PREVIEWS_INVALID`     | `drive_set_previews` got no page count or a negative one                                             |
| `TRASH_HELD`                 | `purge` names a batch with a subject under a legal hold                                              |

A read-only support session refuses every write with `ACTOR_READ_ONLY`. In a
writable [support session](/docs/auth/impersonation#storage-in-a-support-session),
`commit` first claims the uploaded object for the user the admin acts as,
which records the session on it. A claim Storage refuses returns `forbidden`
with the hint `DRIVE_FORBIDDEN`, and the upload stays uncommitted.

## Events and hooks

The drive records `drive.node_created`, `drive.node_renamed`, `drive.node_moved`, `drive.node_shared`, `drive.node_unshared`, `drive.node_purged`, `drive.node_hold_placed`, `drive.node_hold_released`, `drive.node_locked`, `drive.node_unlocked` and `drive.node_download_blocked_changed`; with `drives` on it also records `drive.created`, `drive.renamed`, `drive.deleted`, `drive.shared`, `drive.unshared`, `drive.download_blocked_changed`, `drive.connection_created` and `drive.connection_removed`. The [events page](/docs/extending/events) lists their payloads. Sharing, unsharing and download blocks also write an `access` audit entry. The `before_` and `after_` SQL hooks run around `drive_node_create`, `drive_node_move`, `drive_node_rename` and `drive_node_share`, and the client takes `withBlockHooks` hooks on every method.

## Without the client

`db.drive` is this client. Code that does not go through `bsb.db()` builds it with a transport and an organization id:

```ts
import { createAttachments } from "better-supabase/blocks/attachments";
import { createDrive, rpcTransport } from "better-supabase/blocks/drive";

const transport = rpcTransport(supabase);
const drive = createDrive({
  transport,
  storage: supabase.storage,
  attachments: createAttachments({ transport, storage: supabase.storage }),
});

const projects = await drive
  .createFolder(organizationId, { name: "Projects" })
  .orThrow();
const upload = await drive
  .upload(organizationId, {
    parentId: projects.id,
    name: file.name,
    mimeType: file.type,
    size: file.size,
  })
  .orThrow();
await supabase.storage
  .from(upload.attachment.bucket)
  .uploadToSignedUrl(upload.attachment.path, upload.token, file);
await drive.commit(upload.node.id, upload.attachment.id).orThrow();

await drive.share(projects.id, { type: "team", id: designTeam }, "editor");
await drive.share(projects.id, { type: "role", id: memberRoleId }, "viewer");
const { signedUrl } = await drive.download(upload.node.id).orThrow();
```
