title: Overview
description: Blocks for SaaS apps. Each one installs SQL into your schema and, when it has a TypeScript side, a client on db.
---

A block is a feature most SaaS apps build by hand: organizations and
invitations, background jobs, notifications, outgoing webhooks, plan
entitlements. `better-supabase add` installs its SQL into `supabase/schemas`
([what that SQL contains](/docs/blocks/sql)). An app calls an instance on
`db`, and `gen.hooks` writes the list and record hooks. Blocks with a
TypeScript side also export a client from `better-supabase/blocks/<name>`
for code that does not use `bsb.db()`.

```bash
pnpm better-supabase add organizations invitations
```

```ts
import { createOrganizations } from "better-supabase/blocks/organizations";
```

Every block also exports its manifest, such as `organizationsBlock`: its SQL
modules, options, events and the ports it provides and consumes. To build
several blocks with one set of options and wire them on their ports, pass
the manifests to [`createBlocks`](/docs/blocks/create-blocks) from
`better-supabase/blocks`.

A block can be extended without forking it: add your own columns and type
them with a Standard Schema, steer its methods with hooks in TypeScript or
SQL, wrap its transport with middleware and add methods. See
[Extending blocks](/docs/extending/blocks).

List the blocks to keep in sync in `blocks` in `better-supabase.config.ts`,
keyed by instance, with that instance's settings as the value. Core blocks,
such as `memberships`, `permissions` and `updated-at`, go there too. The
primitives that every app
uses, such as [list queries](/docs/platform/list),
[storage](/docs/platform/storage) and [realtime topics](/docs/platform/realtime),
are not blocks and keep their top-level subpaths.

## Instances

Each key in `blocks` is an instance. The key names the block by default; any
other key installs a second instance of the block in its `block` setting, with
its own tables and the same options as the first:

```ts
blocks: {
  pipelines: {},
  "hiring-pipelines": { block: "pipelines", on: ["candidates"] },
  tasks: { uses: { pipelines: "pipelines" } },
}
```

`on` lists the record types an attachable block attaches to. `uses` picks the
instance of a dependency a block works with; it is required when that
dependency has more than one instance, and its keys are the block's
dependencies. Core blocks, such as `memberships`, `permissions`, `outbox` and
`audit`, install once under their own name. The config check lists every
unknown block, repeated core block, unknown `uses` key and missing `uses`
together.

A second instance renders its own SQL files, named after the instance
(`900_better_supabase_031_hiring_pipelines.sql`). Its entity renames in
`entities` name its tables and functions; any table, function, trigger or
index name those renames leave unchanged gets the instance as a prefix, so
`taggings` in a `labels` instance of `tags` becomes `labels_taggings`. A
second instance has to rename its record entities, since two `pipelines`
tables can't share a schema. The instance writes its own row in
`better_supabase.blocks`, whose `block` column names the block it installs,
and `doctor` and `upgrade` follow each instance's version on its own.

On the TypeScript side, `blocks.generated.ts` has an entry for each instance
and a renamed client for a second one (`ticketsBlock` for `tickets: { block:
"tasks", entities: { work_item: "ticket" } }`), which calls the instance's
functions. Pass it under the instance key:

```ts title="lib/blocks.ts"
import { blockConfig, tasksBlock, ticketsBlock } from "./blocks.generated";

export const blockSet = defineBlocks(blockConfig, {
  tasks: tasksBlock,
  tickets: ticketsBlock,
});
```

When two blocks in a set provide one port, such as two `notifications`
instances providing `notifier`, a consumer takes the one its `uses` names.
`createBlocks({ ports: { notifier: "inbox" } })` picks one for every consumer
whose `uses` names none.

### Contributions

Seven generic blocks take work from the blocks around them: `approvals`
(subjects to approve), `bulk` (named actions), `numbering` (number
sequences), `pipelines` (record types with stages), `relations` (kinds of
link), `share-links` (subjects to share) and `subjects` (summary counts and
my-work rows). The block that has the records declares what it
gives in its definition's `contributes`, so the generic block never names its
consumers. `leave`, for example, contributes the `leave_request` subject and
its approve function to `approvals`.

The default instance of a block contributes to the default instance of the
generic block. A second instance contributes only when its `uses` names the
generic instance, so a `labels` instance of `tags` adds no second `tags.set`
bulk action unless you point it at one:

```ts
blocks: {
  "bulk": {},
  rowActions: { block: "bulk" },
  tags: {},
  labels: {
    block: "tags",
    entities: { tag: "label" },
    uses: { "bulk": "rowActions" },
  },
}
```

Two blocks that give one generic instance the same subject or action name
fail at render with the name and the fix.

### Record types

An attachable block, such as `tags`, `attachments`, `versions`, `trash` or
`sla`, works on the record types in `config.subjects`. Without `on` it
attaches to every registered type. `on` narrows it: a list names the types,
and an object keyed by type adds the block's settings for each one on top of
the registry entry:

```ts
blocks: {
  tags: { on: ["deal", "contact"] },
  attachments: { on: { contract: { bucket: "contracts" } } },
  "field-history": { on: { deal: { fields: ["amount", "stage_id"] } } },
}
```

`field-history` tracks only the types and columns its `on` names. The
block's SQL checks each `subject_type` against the types `on` resolves to,
and doctor (BS346) reports a type in `on` that `config.subjects` doesn't
register. `on` replaces `options.subjects` from 0.14; `better-supabase
upgrade` moves it.

## Connections

A block's TypeScript side runs its SQL functions through a connection you
pass in. It never opens a pool of its own.

| Connection                                                              | What it runs as                             | Blocks                                                        |
| ----------------------------------------------------------------------- | ------------------------------------------- | ------------------------------------------------------------- |
| `ctx.postgresAdmin` from `withPostgresAdminClient` (`@supabase/server`) | The connection-string role, bypassing RLS   | jobs, idempotency, webhook inbox, outbox, audit, webhooks out |
| `ctx.postgres` from `withPostgresClient`                                | The caller, with RLS                        | organizations, notifications (through `sqlTransport`)         |
| `createPostgres()` from `better-supabase/postgres`                      | `admin`, or a user through `asUser(claims)` | every block                                                   |
| `rpcTransport(supabase)` over PostgREST                                 | The client's session, or the secret key     | organizations, notifications, webhooks out                    |

Every function that takes a SQL client accepts `@supabase/server`'s Postgres
clients as they are, so an app that already composes `withPostgresClient` and
`withPostgresAdminClient` keeps one pool and one connection string
(`SUPABASE_DB_URL` by default, or `connectionString`). `withBlock` from
`better-supabase/server` builds a block on the pipeline context; see
[middleware](/docs/auth/middleware).

`@supabase/server` runs each query in its own transaction. A block call is
one SQL function, so that changes nothing for the blocks, but
`outbox.emit()` then commits on its own instead of with the writes before it.
Emit from SQL (`emit_event` inside the function that writes) when the event
must commit with the write.

A SQL connection needs TCP: Node, Deno, Bun and the Supabase Edge runtime have
it, Cloudflare Workers and other isolates without sockets do not. There, use
`rpcTransport` for the blocks that call only SQL functions (organizations,
notifications, outgoing webhooks, flags, announcements and the rest of the
blocks that take a `transport`, and `createOutbox`, which takes a transport in
place of the SQL client), and the `pgmq_public` RPCs for jobs. The
TypeScript helpers of the idempotency keys, the webhook inbox, incoming
webhooks, route rate limits and `exportAuditLog` still need a SQL connection,
but every function a module grants, the service-role ones of `queue`,
`idempotency`, `webhook-inbox` and `access` included, gets an entry point in
the API schema, so a server can call them over the Data API. Give
the module an API schema (`blocks.<module>.api`, see
[SQL modules](/docs/blocks/sql#calling-a-module-over-the-data-api)), expose
that schema, and pass it as `rpcTransport(supabase, { schema: "api" })`. Never
expose the module schema itself.

## How modules work together

`better-supabase add` installs a module with the modules it requires. The modules it
works with are optional: when one of them is installed too, the module calls
it (it queues a job, sends a notification, checks a plan), and without it the
module installs and runs without that step. Every module also writes its
events to the [outbox](/docs/blocks/outbox) when the outbox is installed.
`better-supabase blocks list --installed` prints both lists for each module.
