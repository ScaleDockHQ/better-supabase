---
title: scaffold
description: Write an API module, a REST resource per table and an OpenAPI route for Hono or Next.js, or list, create and detail pages for an app table.
---

`scaffold api` writes the files that serve your tables as REST
[resources](/docs/specs/resources) and serve the OpenAPI document for them,
for Hono or Next.js. Run [`gen`](/docs/cli/gen) first: the tables come from
the metadata module it writes.

```bash
pnpm better-supabase scaffold api
pnpm better-supabase scaffold api --framework hono --tables customers,tags
```

Side effects: Writes files.

## Options

| Option               | Default                                                | Effect                                                                  |
| -------------------- | ------------------------------------------------------ | ----------------------------------------------------------------------- |
| `--framework <name>` | The one framework (`hono` or `next`) in `package.json` | Which files to write. With both or neither installed, pass it           |
| `--tables <list>`    | Every table and view in the `public` schema            | The tables to serve, comma-separated or repeated                        |
| `--name <name>`      | `api`                                                  | The module name: `lib/<name>.ts` and `lib/<name>.generated.ts`          |
| `--base-path <path>` | `/api`                                                 | Where the resources are served                                          |
| `--dry-run`          |                                                        | Prints a diff of each file that would change and writes nothing         |
| `--check`            |                                                        | Writes nothing; exits 1 when a file would change                        |
| `--force`            |                                                        | Overwrites `lib/<name>.ts` and the routes, which are yours once written |

Each option falls back to the same key under `tooling.scaffold.api` in the config
(`framework`, `tables`, `name`, `basePath`) before its default. Without a
`tooling.scaffold.api` entry, the command prints one for the flags you passed.

## From gen

With `tooling.scaffold.api` set, [`gen`](/docs/cli/gen#tasks) runs scaffold as a
task after it writes the metadata, so a new table reaches the API without
another command:

```ts title="better-supabase.config.ts"
export default defineConfig({
  tooling: {
    scaffold: { api: { framework: "hono", tables: ["customers", "tags"] } },
  },
});
```

The task rewrites only `lib/<name>.generated.ts`, never the module you edit
or the routes, and `gen --check` fails when that file is out of date.

`--tables` names are checked against the metadata module
(`generated.meta.js`), and an unknown table fails with the list of known
ones. Without a metadata module, pass `--tables`; the names are used as
they are. `--name` is a file name without a folder.

## What it writes

Paths are under `src/` when the project has one, else under the project
root.

| File                            | Framework | Written                |
| ------------------------------- | --------- | ---------------------- |
| `lib/api.generated.ts`          | both      | On every run           |
| `lib/api.ts`                    | both      | Once; yours after that |
| `app/api/[...path]/route.ts`    | Next.js   | Once; yours after that |
| `app/api/openapi.json/route.ts` | Next.js   | Once; yours after that |
| `api-routes.ts`                 | Hono      | Once; yours after that |

`lib/api.generated.ts` holds `tableNames`, `resources` and `basePath`, and
starts with an `@generated` header. Each run rewrites it from the options,
and a file at that path without the header stops the command, so it never
overwrites your code. Every other file is written when it doesn't exist and
kept (`Kept <path> (yours)`) when it does.

`lib/api.ts` is the API model, the entry `spec emit` reads:

```ts title="src/lib/api.ts"
import { defineApi } from "better-supabase/spec";

import { betterSupabase } from "./supabase";
import { basePath, resources, tableNames } from "./api.generated";

export { basePath, resources, tableNames };

export const api = defineApi(betterSupabase, {
  info: { title: "API", version: "1.0.0" },
  basePath,
  resources,
});
```

Describe the resources, add list queries and custom routes there (see
[API documents](/docs/specs)).

### Next.js

A catch-all route serves every resource through `bsb.resources`, and a
second route serves the document with
[`specResponse`](/docs/specs#serve-the-document):

```ts title="src/app/api/[...path]/route.ts"
import { basePath, resources } from "../../../lib/api";
import { bsb } from "../../../lib/supabase/server";

export const { GET, POST, PATCH, PUT, DELETE } = bsb.resources(resources, {
  basePath,
});
```

```ts title="src/app/api/openapi.json/route.ts"
import { specResponse } from "better-supabase/spec";

import { api } from "../../../lib/api";

const { document } = api.openapi();

export const GET = (request: Request) => specResponse(document, request);
```

### Hono

`api-routes.ts` exports `apiRoutes(bsb)`: the document at
`<basePath>/openapi.json`, `bsb.middleware()` on `<basePath>/*`, and
`bsb.resource(table)` for each table. Mount it in `src/server.ts`:

```ts title="src/server.ts"
import { createHono } from "better-supabase/hono";

import { apiRoutes } from "./api-routes";
import { betterSupabase } from "./lib/supabase";

export const bsb = createHono(betterSupabase);

export const app = bsb.app().route("/", apiRoutes(bsb));
```

## Next steps

The command prints what is left to do:

- With Hono, mount the routes in `server.ts`.
- When `api.specs.entry` is not the new `lib/api.ts`, set
  `specs: { entry: "src/lib/api.ts" }` in `better-supabase.config.ts`, so
  [`spec emit`](/docs/cli/spec) reads the model.
- Describe the resources in `lib/api.ts`. A later `scaffold api` only
  rewrites `api.generated.ts`, so run it again with a new `--tables` list
  to add or remove a table.

## Screens

`scaffold screens <table>` writes Next.js pages for one of your
[app tables](/docs/blocks/app-tables): a list, a create form and a detail
page. They read and write through the generated repository with `bsb` from
`lib/supabase/server`, so the table's policies check every request.

```bash
pnpm better-supabase scaffold screens tasks
pnpm better-supabase scaffold screens tasks --base-path "(app)/work/tasks"
```

`--base-path` is the route under `app/`, `/<table>` by default. Route
groups such as `(app)` stay in the folder and leave the links; a dynamic
segment such as `[locale]` is refused, so move the pages under one
yourself.

| File                    | What it does                                                                  |
| ----------------------- | ----------------------------------------------------------------------------- |
| `<route>/page.tsx`      | The newest 100 rows of the caller's tenant (or user) in a table               |
| `<route>/new/page.tsx`  | Loads the rows each reference picker lists, then renders the form             |
| `<route>/form.tsx`      | The create form, a client component on `useActionState`                       |
| `<route>/actions.ts`    | The Server Action that parses the form, creates the row and opens it          |
| `<route>/[id]/page.tsx` | One row, or `notFound()` for an id that is malformed, missing or out of scope |
| `<route>/show.ts`       | Turns a column value into text for the list and detail pages                  |

Every file is written once. After that the command lists it as Skipped and
leaves it alone, unless you pass `--force`.

Each column gets the input its config calls for:

| Column                                       | Input                                        |
| -------------------------------------------- | -------------------------------------------- |
| `text` with `options`                        | A select of the options                      |
| `text` with `format` `email`, `url`, `phone` | An input of that type                        |
| `text` with `format` `long_text`             | A textarea                                   |
| A number type                                | A number input with `min` and `max`          |
| `boolean`                                    | A checkbox                                   |
| `date`                                       | A date input                                 |
| `timestamptz`                                | A date and time input, with the string codec |
| A reference to another app table             | A select of its rows, labelled by its title  |

The form leaves out identity columns, columns with a function default
(`now()`, `gen_random_uuid()`, `auth.uid()`), `jsonb` and `text[]`. The
action converts each value to the type the [`codecs`](/docs/cli/config)
generate and passes the tenant column itself.

The command stops for a table it can't serve: one that isn't in
`tables`, one with `scope: "none"` (only the service role writes it),
and one with a required column the form has no input for. It also needs
Next.js; pass `--framework next` when `package.json` doesn't list it.

For search, filters, saved views, a board, a calendar or a timeline, start
from the `record-*` [UI recipes](/docs/registry/ui-recipes#app-tables), which build
the same screens on ReUI.

Side effects: Writes files.
