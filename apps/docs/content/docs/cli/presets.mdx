---
title: apply, adopt, preset and blocks
description: Apply a preset to an existing project, map blocks onto tables it already has, read a preset code, and find the blocks to add.
---

These commands work with [presets](/docs/presets) and the block catalog. To
start a new project from a preset, use
[`init --preset`](/docs/cli/init#starting-from-a-preset).

## apply

```bash
pnpm better-supabase apply --preset crm
pnpm better-supabase apply --preset 1pWEF3d578B1iGt16 --dry-run
pnpm better-supabase apply --preset crm --only blocks
```

`apply` edits the config file you have. By default it sets `preset` to the
named preset or the code, replacing the one the config has, so
`defineConfig` expands it into `blocks` and the conventions while your own
keys keep winning. It prints the diff of the config file, then loads the
config again and writes the module files of every block it now holds, as
`better-supabase sql sync` does. `--dry-run` prints the diff and writes
nothing.

| `--only`      | What `apply` changes                                                                         |
| ------------- | -------------------------------------------------------------------------------------------- |
| unset         | `preset`: the preset's blocks and its conventions                                            |
| `blocks`      | `blocks`: the preset's blocks and what they require, listed by name; `preset` stays as it is |
| `conventions` | `preset`: a code with the preset's conventions and no blocks                                 |

With a Create URL that holds a design (`&design=`), `apply` also merges the
design into the config: each table in `appTables`, replacing a table of the
same name and keeping the others, and each block's extra columns over the
`options.extraColumns` it already has. Quote the URL. `--only conventions`
leaves the design out. See [init](/docs/cli/init#a-design-from-create) for
what a design holds and what to do when it's too large for a URL.

### Breaking changes

Before it writes a design, `apply` compares each of its tables with the one
of the same name in `appTables`. Adding a table or an optional column is
safe. Dropping or renaming a column, changing its type or the table's id
type, and making a column required without a default break rows already in
the database or app code that reads them. `apply` lists each breaking
change with the expand-and-contract steps that make it safe, writes
nothing and exits 1:

```txt
Breaking changes to app tables:
  Changes notes.body from jsonb to text.
    1. Add a text column next to body.
    2. Fill it from body with a cast in a migration, and write both columns.
    3. Move reads to the new column, drop body in a later migration and rename the new one if you need the name.
```

Pass `--allow-breaking` to write the design anyway, for example on a project
without data. `--dry-run` prints the list and the diff without it.
`diffAppTables` and `diffDesigns` from `better-supabase/preset` return the
same changes, and Create shows them on the Changes tab of Get code.
[Doctor's BS228](/docs/cli/doctor#bs228) reports a column whose type or
nullability in the database has drifted from `appTables`.

### Adopting existing tables

```bash
pnpm better-supabase apply --preset crm --only blocks --adopt --dry-run
```

With `--adopt`, `apply` reads the tables in the database and looks for each
block's tables under their default names (`teams` and `team_members` for
`teams`). For every block it finds there, it writes `blocks.<block>` in
[adopt mode](/docs/blocks/sql#existing-tables-managed-adopt-and-custom) instead of letting the managed block skip the
table: `tables` names the existing tables, `columns` the columns that differ
from the defaults, and an optional column the table lacks maps to `null`.
The proposed mapping of each block is printed before the diff, so
`--dry-run` shows both. Blocks with no existing table stay managed, and a
block whose config already sets a mode keeps it.

When a block has a table under a default name that can't be adopted as it
is, for example because a column the block needs is missing, `apply`
writes nothing and prints what is missing. Add the column, map the block
with `better-supabase adopt`, or leave the block out of the preset.
`--adopt` reads the tables where `introspect` does: the config's `source`,
`$DATABASE_URL`, `$SUPABASE_DB_URL` or the local stack, or `--snapshot`,
`--db-url-stdin` and `--project-ref`.

A preset that can't install stops `apply` with the reason. When the config
isn't an object literal `apply` can follow, it changes nothing and prints the
`preset` entry to set yourself. Without a config file, `apply` points to
`init --preset`.

## adopt

```bash
pnpm better-supabase adopt teams --from public.squads --dry-run
pnpm better-supabase adopt audit --from public.audit_logs
pnpm better-supabase adopt tags --from app.labels,app.label_links --json
```

`adopt` maps one block onto tables the app already has and writes the
proposed `blocks.<block>` entry in adopt mode. Each table in `--from`
(`table` or `schema.table`, comma-separated or repeated) goes to the block's
logical table whose columns it matches best; the block's other tables are
looked up by their default names. Each logical column then takes the column
of the same name, or a likely rename: `organization_id` for `tenant`,
`position` for `rank`, `recipient_user_id` for `user`. Those guesses are
marked in the output, so check them before you keep the entry. When the
tenant column is a `bigint`, `text` or `integer`, the entry sets `idType`
too.

The output lists every logical table and column with what it maps to, then
a report like doctor's: errors for what can't map (a missing table, a
required column the table lacks, a value the module refuses) and warnings
for the migration-only options the entry keeps. With an error `adopt` exits
1 and writes nothing. Otherwise it prints the diff of the config and writes
it; `--dry-run` writes nothing. Run `better-supabase sql sync` afterwards to
write the block's module over the adopted tables. `--json` prints the entry,
the mapping and the report as data. The tables are read like `introspect`
reads them, with `--snapshot`, `--db-url-stdin` and `--project-ref`.

Only blocks with an adopt mode can be adopted; `blocks view <name>` lists a
block's modes.

## preset

```bash
pnpm better-supabase preset decode 1pWEF3d578B1iGt16
pnpm better-supabase preset decode "https://bettersupabase.com/create?preset=1pWEF3d578B1iGt16"
pnpm better-supabase preset info
```

`preset decode` takes a name, a code or a `/create` URL and prints the
conventions, every block the preset installs with the reason it is there,
and anything that can't install, which exits 1. A code from an older
version also lists the fields it predates, which decode at their defaults.

`preset info` reads the `preset` of the config and prints the same, then
how the config differs from it: the blocks it adds (`+`), a casing that
differs, and the preset blocks it gives settings of its own (`~`).

## blocks

```bash
pnpm better-supabase blocks list
pnpm better-supabase blocks list --category crm
pnpm better-supabase blocks view comments
pnpm better-supabase blocks search invoice
```

`blocks list` prints every block by category, and `--category` keeps one
(`identity`, `tenancy`, `collaboration`, `messaging`, `growth`, `crm`,
`work`, `people`, `commerce`, `scheduling`, `content`, `ai`, `automation`,
`developer`, `admin` or `database`). `blocks view` prints one
block: what it requires, what it works with, its modes, its client
subpath, the `better-supabase add` command and its registry glue.
`blocks search` matches the name, the title and the description. Each one
reads the same catalog as [/blocks](https://bettersupabase.com/blocks) and
`--json` prints it as data.
