---
title: init and add
description: Scaffold the config, the data layer and framework glue for your project, start from a preset, and add blocks.
---

```bash
npx better-supabase init   # before better-supabase is installed
pnpm better-supabase init  # once it is a dependency
```

`init` reads your `package.json` and writes:

- `better-supabase.config.ts` with `casing` written out (`--casing snake|camel`,
  `snake` by default, as in a config without `gen.casing`) and the
  [conventions](#conventions) that differ from the defaults. It lists the integrations it set up under `adapters`, and
  carries commented `gen` and `tooling` entries for the options you
  would otherwise pass on every run (see [Flags and the config](/docs/cli/config#flags-and-the-config))
- `src/lib/supabase/index.ts`, which exports `betterSupabase` and the `Models` and `Functions` types
- glue for every framework it finds, the same files `add` writes

When `supabase/config.toml` exists and has no `[experimental.pgdelta]` table,
`init` adds one with `enabled = true`, so `supabase db schema declarative sync`
diffs your schema files with pg-delta, the engine `supabase init` uses for new
projects. A table that sets `enabled = false` stays as it is, and `init` prints
the steps to switch (see [BS316](/docs/cli/doctor#bs316)).

`--workflow` picks how the SQL modules reach the database (see
[Workflows](/docs/blocks/sql#workflows)):

```bash
pnpm better-supabase init --workflow migrations
```

| `--workflow`         | What `init` does                                                                                |
| -------------------- | ----------------------------------------------------------------------------------------------- |
| `pg-delta` (default) | Turns pg-delta on in `supabase/config.toml` and writes no `database.sql.workflow`               |
| `migra`              | Writes `sql: { workflow: 'migra' }` and leaves `config.toml` alone, for declarative schemas 1.0 |
| `migrations`         | Writes `sql: { workflow: 'migrations' }`: the `sql` commands write the modules into a migration |

It then prints the next steps: the install command for your package manager,
`supabase start`, `better-supabase env` and `better-supabase gen`. Files that
already exist are never overwritten unless you pass `--force` or confirm the
prompt. `--dry-run` shows what would be written, and `--check` exits 1 when a
file is missing or differs ([writing files](/docs/cli#writing-files)). The names and the layout are described in [Naming](/docs/concepts/naming).

In a terminal, `init` asks for the conventions (unless you pass a convention
flag), the integrations, with the detected ones checked (unless you pass
`--integration`), and whether to overwrite files that exist. `add` without names asks which
integrations to add. It never asks in CI, when stdin or stdout is not a
terminal, or with `--yes`, which takes the flags and the defaults.

| Found in `package.json` | Integrations           |
| ----------------------- | ---------------------- |
| `next`                  | `next` (and `client`)  |
| `hono`                  | `hono`                 |
| `@orpc/server`          | `orpc`                 |
| `vite`                  | `client`               |
| `expo`                  | `expo` (and `client`)  |
| `@tanstack/react-query` | `react` (and `client`) |

Add more with `--integration edge,mcp`. A project with only `edge` and `mcp` gets no
`src/lib/supabase/index.ts`: Edge Functions import `betterSupabase` from
`supabase/functions/_shared/supabase.ts`.

Side effects: Writes files.

## Conventions

The convention flags set what [Create](https://app.bettersupabase.com/create)
sets in its Conventions step, with the same names and defaults:

| Flag            | Config key                         | Values                                                             |
| --------------- | ---------------------------------- | ------------------------------------------------------------------ |
| `--casing`      | `casing`                           | `snake` (default), `camel`                                         |
| `--scope`       | `database.sql.owner`               | `tenant` (default), `user`, `none`                                 |
| `--tenant-name` | `blocks.tenant.names.organization` | `organization` (default), `workspace`, `team`, or a lowercase name |
| `--access`      | `blocks.access.model`              | `roles` (default), `catalog`, `provider`, `custom`                 |
| `--id-type`     | `blocks.access.idType`             | `uuid` (default), `text`, `bigint`, `integer`                      |
| `--api`         | `database.sql.api`                 | `none` (default), `api`                                            |

Without `--preset`, `init` asks for each one in a terminal, in Create's
order: Casing, Row ownership, Tenant name (for tenant scope only), Auth and
permissions, ID type and API schema. Once you pass a convention flag, it
asks for none of them and takes the defaults for the rest. It writes only
the values that differ from the defaults: `sql` for the scope, tenant name
and API schema, and `blocks.access` for the access model and id type, which
installs the access block. With `--access provider` it also writes a comment
that points you at the `authorization` key.

With `--preset`, each flag overrides that convention of the preset, and
`init` writes the changed preset code. A code stores the tenant names Create
offers (`organization`, `workspace`, `team`), so for another name leave
`--tenant-name` out and set `blocks.tenant.names.organization` in the config. `apply` takes
the same flags.

```bash
pnpm better-supabase init --scope user --api api
pnpm better-supabase init --preset saas --tenant-name workspace --access catalog
```

## Starting from a preset

```bash
npx better-supabase init --preset saas
npx better-supabase init --preset 1pWEF3d578B1iGt16
```

`--preset` takes a [named preset](/docs/presets), a code from
[Create](https://app.bettersupabase.com/create), its whole URL or the path of
a [design file](#a-design-from-create). `init` then
also:

- writes `preset` into `better-supabase.config.ts`, which `defineConfig`
  expands into `blocks` and the preset's conventions; the
  [convention flags](#conventions) override them
- adds the preset's integrations and its framework's integration to the
  ones it found
- writes the module files of every block the preset installs, as
  `better-supabase sql sync` does
- writes `lib/blocks.ts`, which wires the blocks that have a TypeScript
  client with `defineBlocks`
- prints the `npx shadcn@latest add @better-supabase/...` command for the
  [registry glue](/docs/registry) that fits the preset's framework and
  platforms

A preset that can't install, such as one whose blocks need tenants under
scope `user`, stops `init` with the reason. In a terminal without
`--preset`, a convention flag or `--integration`, `init` first asks for a preset; None
keeps the steps above out. To apply a preset to a project that already has
a config, use [`apply`](/docs/cli/presets#apply).

### A design from Create

When you add tables or extra columns on the Create canvas, its URL carries a
second code, `&design=`. Quote the whole URL so the shell keeps the `&`:

```bash
npx better-supabase init --preset "https://app.bettersupabase.com/create?preset=1pWEF3d578B1iGt16&design=0..."
```

`init` decodes the design locally, with no network call, and writes its
[app tables](/docs/blocks/app-tables) into `tables` and its extra columns into
each block's `options.extraColumns`, next to `preset`. The canvas positions
stay in the URL. A design that doesn't decode, or that adds columns to a
block the preset doesn't install, stops `init` with the reason.

A design is capped at 6000 characters so the URL stays usable. When Create
says a design is too large to share, download the design file instead and
pass its path to `--preset`:

```bash
npx better-supabase init --preset ./better-supabase.design.json
```

The file holds the preset code and the design as JSON, with no length limit,
and `init` reads it like a URL: the same checks, the same config keys and the
same module files. A path ending in `.json` is read as a design file, relative
to `--cwd`. [`apply`](/docs/cli/presets#apply) takes the same file. The format
is on [Preset codes](/docs/presets/codes#design-files).

## Supabase Lite

```bash
pnpm better-supabase init --lite
```

`--lite` sets the project up for [Supabase Lite](/docs/platform/lite). The
next steps install `@supabase/lite` as a dev dependency instead of `pg`, run
`npx lite init` and `npx lite dev` instead of `supabase init` and
`supabase start`, and ask you to set `jwt_secret = "env(SUPABASE_JWT_SECRET)"`
in `supabase/config.toml` with a secret of 32 or more characters in `.env`.
Pass `backend: 'lite'` to `createServer` (or the framework adapter) so the
server verifies Lite's HS256 tokens.

## Workspaces

At the root of a pnpm, npm, yarn or bun workspace (a `pnpm-workspace.yaml`,
or `workspaces` in `package.json`), `init` writes into one package instead of
the root. In a terminal it asks which package owns the runtime, with the one
that already depends on better-supabase (or else the first with a framework)
selected. Otherwise pass it:

```bash
pnpm better-supabase init --package packages/runtime
```

`init` then detects the frameworks and `tsconfig.json` of that package, writes
the config and the glue there, and prints next steps that target it:
`pnpm --filter @acme/runtime add ...` (or `npm install -w`, `yarn workspace`,
`bun add --cwd`) and `better-supabase gen --cwd packages/runtime`. Without
`--package` and without a terminal, `init` stops with an error that lists the
packages; `--package .` writes at the root as before.

On [Create](https://app.bettersupabase.com/create), turn on Monorepo and enter
the package path (`apps/web` by default): the install and apply commands then
end in `--package <dir>`. A Create URL carries it as `&package=`, so `init`
and `apply` take it from a URL you pass to `--preset`. The migrations stay in the root `supabase/` folder. See
[monorepos](/docs/guides/monorepo) for how to split the runtime from domain
packages.

## add

```bash
pnpm better-supabase add comments tags
pnpm better-supabase add --integration hono,mcp
```

`add` with block names is how you install blocks. It lists them in `blocks`
of the config and writes their module files and the modules they require
(`--allow-hook-overlap`, `--dry-run`, `--check` and `--tests-dir` work as in
[`sql add`](/docs/blocks/sql#low-level-sql-add), the low-level command that
stops after the SQL). It also wires the blocks that have a TypeScript client into
`lib/blocks.ts`: an import and an entry in the object passed to
`defineBlocks` (or `createBlocks`). When the file is missing or calls neither
with an object literal, `add` prints the lines to add instead. Last, it prints the
`npx shadcn@latest add @better-supabase/...` command for the registry glue
of those blocks that fits the frameworks in the config or `package.json`.
`better-supabase blocks list` shows the names. `--force` overwrites files
that exist.

`--integration` adds glue for integrations instead. `add` without an argument
or `--integration` sets up every integration in the config's
`adapters` list whose files are missing, which is how a fresh checkout
or a new package in a workspace gets its glue. When `--integration` names
integrations the config doesn't list yet, `add` prints the `adapters`
entry to paste.

| Integration | Writes                                                                                                                                  |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `client`    | `lib/supabase/client.ts` with the framework's public env variables                                                                      |
| `next`      | `lib/supabase/server.ts` (with `import "server-only"`) and `proxy.ts`                                                                   |
| `react`     | `providers.tsx` (`app/providers.tsx` in Next.js) and `lib/hooks.ts`                                                                     |
| `hono`      | `server.ts`, which creates `bsb` and adds the middleware and error handler                                                              |
| `orpc`      | `router.ts`, which creates `bsb` and adds the auth middleware                                                                           |
| `edge`      | `supabase/functions/api` (`server.ts` creates `bsb`) plus `supabase/functions/_shared/supabase.ts`                                      |
| `expo`      | `lib/supabase/expo.ts` (`bsb` for API routes), `lib/supabase/client.native.ts` (the session in secure storage) and `app/+middleware.ts` |
| `mcp`       | `supabase/functions/mcp`, an MCP server as an Edge Function (`server.ts` creates `bsb`)                                                 |

Relative imports follow your `tsconfig.json`: they keep `.ts` when
`allowImportingTsExtensions` or `rewriteRelativeImportExtensions` is on.
Edge Functions always use `.ts` and get a `deno.json` import map. CI
typechecks every template against the library, so the files compile as
written. The names and the layout are described in [Naming](/docs/concepts/naming).

Side effects: Writes files.
