---
title: better-supabase and PermDock
description: Use PermDock for authorization and better-supabase for authentication and data, with one hook and one claim contract.
---

[PermDock](https://github.com/ScaleDockHQ/PermDock) is an authorization layer
for Supabase apps. better-supabase follows PermDock's claim contract, so the two
share one access token hook and one set of claims. Neither package imports the
other: they compose through `@supabase/middleware` and plain claim shapes.

## Who owns what

| Area                  | better-supabase                                                                            | PermDock                                                                                                                                              |
| --------------------- | ------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tokens                | Verification through `@supabase/server`, sessions, refresh, `AuthSession`                  | Reads the verified claims into a subject                                                                                                              |
| Access token hook     | None when PermDock is installed                                                            | `permdock supabase hook generate`, the only hook                                                                                                      |
| Roles and permissions | None                                                                                       | `role_permissions`, `authorize()`, and from `permdock rls generate`: `permdock_has`, `permitted_<scope>_ids`, `member_<scope>_ids` and table policies |
| Data                  | Typed clients, repositories, typegen, jobs, webhooks                                       | None                                                                                                                                                  |
| Storage and Realtime  | `defineBucket`, `defineTopic`, with a `permdock` policy mode that calls PermDock's helpers | The helpers those policies call, from `permdock rls generate`                                                                                         |
| MCP                   | `createMcp`, its protected-resource metadata, and the `authorize` and `visible` hooks      | Tool permissions, through `createMcp`'s hooks or through `permdock/mcp` on the official MCP SDK                                                       |
| Lints                 | Token lifetime, refresh reuse, signing keys, splinter, claim size                          | Authorization lints                                                                                                                                   |

## Setup

<Steps>

<Step>

### Generate the helpers and table policies

`permdock rls generate` writes the SQL helpers (`permdock_has`, and per scope
one `permitted_<scope>_ids(p_grant)` and one membership-only
`member_<scope>_ids()`) and the table policies:

```bash
permdock rls generate --target sql --dialect supabase --out supabase/migrations/20260929_permdock_rls.sql
```

The helpers live in PermDock's `rls.schema` (`permdock` by default, a schema
the Data API does not expose). Buckets and topics in `permdock` mode call them
in `permdock` unless their `schema` option names another schema, and doctor
(BS214) reports a `schema` that differs from the manifest's.

</Step>

<Step>

### Use one hook

Generate the custom access token hook with PermDock and enable it in
`supabase/config.toml`:

```bash
permdock supabase hook generate --out supabase/migrations/20260929_permdock_hook.sql
```

It writes only the hook, its grants, the `permdock_authz_version` table and
its triggers, and the `config.toml` block. The helpers come from the previous
step.

The hook writes these claims:

| Claim                   | Value                                                                                           |
| ----------------------- | ----------------------------------------------------------------------------------------------- |
| `user_role`             | The user's global role, or an array when there are several                                      |
| `roles`                 | The user's global roles, always an array                                                        |
| `memberships`           | `[{ scope, id, roles }]`, the active tenant first, cut to the budget                            |
| `tenant_id`             | The active tenant, named by PermDock's `rls.tenantClaim`                                        |
| `attrs`                 | The attributes listed in `supabase.hook.attrs`, when there are any                              |
| `authz_ver`             | The user's authorization version from `permdock_authz_version`, bumped when their grants change |
| `memberships_truncated` | `true` when memberships were dropped to fit the budget                                          |
| `features`              | The plan features from `better_supabase.feature_claims`, when `supabase.hook.claims` names it   |

Claims better-supabase owns go through `supabase.hook.claims` in
`permdock.config.ts`. Each value is a schema-qualified function that takes the
user id and returns `jsonb`; the hook sets the claim to its result:

```ts title="permdock.config.ts"
import { fromJunction } from "permdock/supabase";

export default {
  supabase: {
    hook: {
      memberships: [
        fromJunction({
          table: "better_supabase.memberships",
          scope: "organization",
          id: "org_id",
          roles: "role",
        }),
      ],
      claims: { features: "better_supabase.feature_claims" },
    },
  },
};
```

Don't call better-supabase's `membership_claims()` from a hook next to it, and
don't write `roles`, `user_role`, `memberships` or the tenant claim yourself:
PermDock owns them, and `permdock supabase hook generate` refuses those names
in `supabase.hook.claims`. `better-supabase sql add tenant` stops when it finds
a `permdock.config.ts` (`--force` writes it anyway), and
[doctor](/docs/cli/doctor#bs407) reports BS407 for a hook that writes those
claims next to PermDock. The `entitlements` module is not a conflict: see
[Entitlements with PermDock](#entitlements-with-permdock).

</Step>

<Step>

### Name the same claims

The `claims` block in `better-supabase.config.ts` defaults to PermDock's
names. Set `scope` to the name of your first PermDock scope:

```ts title="better-supabase.config.ts"
export default defineConfig({
  claims: { tenant: "tenant_id", scope: "organization" },
});
```

The tenant plugin, storage and realtime policies and the generated schema then
read `tenant_id`, the same claim PermDock's policies read.

The tenant claim name must match on both sides. If you set a non-default
`claims.tenant`, set the same name as PermDock's `rls.tenantClaim` (which the
generated hook and policies use) and pass it to `subjectFromSupabase` or
`subjectFromSupabaseSession` as `{ tenant }`:

```ts
// better-supabase.config.ts
claims: { tenant: 'org_id', scope: 'organization' },
// permdock.config.ts
rls: { tenantClaim: 'org_id' },
// server code
subjectFromSupabaseSession(session, { tenant: 'org_id' });
```

Otherwise PermDock writes and reads `tenant_id` while better-supabase reads
`org_id`, and tenant checks on one side see no tenant.

</Step>

<Step>

### Validate the claims with PermDock's schema

`betterSupabase.claims(schema)` validates the claims on every request and types
`session.claims`. It takes any Standard Schema, so use the one PermDock
publishes for its claim contract. `supabaseClaims()` checks the claims the
hook writes and passes the rest through, so claims it doesn't name reach
PermDock unchanged. `extend(app)` adds your own hook claims, validated by your
schema library:

```ts title="src/lib/supabase/index.ts"
import { defineSupabase } from "better-supabase";
import { supabaseClaims } from "permdock/supabase";
import * as v from "valibot";
import { schema } from "./generated";

export const betterSupabase = defineSupabase(schema).claims(
  supabaseClaims().extend(
    v.object({
      datetime_preferences: v.optional(
        v.object({
          timezone: v.string(),
          week_start: v.picklist(["monday", "sunday"]),
          date_format: v.string(),
          time_format: v.picklist(["12h", "24h"]),
        }),
      ),
    }),
  ),
);
```

The server and the browser each create `bs` from that definition, so both
validate the claims the same way:

```ts title="src/lib/supabase/server.ts"
import "server-only";
import { createNext } from "better-supabase/next";
import { betterSupabase } from "./index";

export const bs = createNext(betterSupabase);
```

```ts title="src/lib/supabase/client.ts"
import { createClient } from "better-supabase/client";
import { betterSupabase } from "./index";

export const bs = createClient(betterSupabase, {
  env: {
    url: process.env.NEXT_PUBLIC_SUPABASE_URL!,
    publishableKey: process.env.NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY!,
  },
});
```

`session.claims` then has PermDock's `memberships`, `tenant_id`, `roles` and
`authz_ver`, plus `datetime_preferences`. A token whose claims fail either
schema resolves to `{ kind: 'invalid', reason: 'claims' }`. Pass
`supabaseClaims({ tenantClaim: 'org_id' })` when you renamed the tenant
claim. `hasEntitlement(session, ...)` keeps working, because `features` passes
through. Name the `features` claim in the app schema to type its keys
(`features: v.optional(v.record(v.string(), v.array(v.picklist(['exports', 'sso']))))`).

</Step>

</Steps>

## Servers

`withBetterSupabase(server)` verifies the caller and contributes `ctx.db` and
`ctx.jwtClaims`, and `withPermDock()` contributes `ctx.permdock` from those
claims:

```ts title="src/api/customers.ts"
import { pipeline } from "@supabase/middleware";
import { createServer, withBetterSupabase } from "better-supabase/server";
import { createPermDock } from "permdock/supabase/middleware";
import { subjectFromSupabase } from "permdock/supabase";

const { withPermDock } = createPermDock(policy, {
  subject: (ctx) => subjectFromSupabase(ctx.jwtClaims),
});

export const listCustomers = pipeline(
  [
    withBetterSupabase(createServer(betterSupabase), { allow: ["user"] }),
    withPermDock(),
  ],
  async (_req, ctx) => {
    if (!ctx.permdock.can(permissions.customers.read)) {
      return new Response(null, { status: 403 });
    }
    return Response.json(await ctx.db.customers.findMany().orThrow());
  },
);
```

### oRPC

PermDock's oRPC adapter reads the subject from the procedure's context, and
`bs.middleware()` has put the verified `AuthState` there as `context.auth`.
`subjectFromSupabaseSession` maps it, and anything but a user becomes an
anonymous subject that no grant matches.

Export one builder that takes a permission and keep `bs.middleware()` inside
it. A procedure built any other way has no `context.db`, so it can't reach the
database, and one built with `procedure()` can't compile without a
permission:

```ts title="src/router.ts"
import { os } from "@orpc/server";
import { createOrpc, type OrpcRequestContext } from "better-supabase/orpc";
import type { AuthState } from "better-supabase/server";
import type { Permission } from "permdock";
import { createPermDock } from "permdock/orpc";
import { subjectFromSupabaseSession } from "permdock/supabase";

export const bs = createOrpc(betterSupabase);

const authed = os.$context<OrpcRequestContext>().use(bs.middleware());
const pd = createPermDock<OrpcRequestContext & { readonly auth: AuthState }>(
  policy,
  { subject: ({ context }) => subjectFromSupabaseSession(context.auth) },
);

/** The only way to build a procedure: refused unless the caller holds `permission`. */
const procedure = (permission: Permission) =>
  authed.use(pd.protect(permission));

export const router = {
  customers: {
    list: procedure(permissions.customers.read).handler(({ context }) =>
      bs.unwrap(context.db.customers.findMany({ select: ["id", "name"] })),
    ),
  },
};
```

`protect` answers `FORBIDDEN` with PermDock's Problem Details as the error's
`data`, the same shape `bs.unwrap` gives a `DbError`.

### Hono

The Hono adapter works the same way, with `c.var.auth` as the session. Bundle
both middlewares into one helper and use it on every route, rather than
`app.use(bs.middleware())`, so a route that skips it has no `c.var.db`
and `bs.handler` answers 500 instead of running:

```ts title="src/server.ts"
import { createHono } from "better-supabase/hono";
import type { Permission } from "permdock";
import { createPermDock } from "permdock/hono";
import { subjectFromSupabaseSession } from "permdock/supabase";

const bs = createHono(betterSupabase);
const pd = createPermDock(policy, {
  subject: (c) => subjectFromSupabaseSession(c.get("auth")),
});

const guarded = (permission: Permission) =>
  [bs.middleware(), pd.protect(permission)] as const;

export const app = bs.app().get(
  "/customers",
  ...guarded(permissions.customers.read),
  bs.handler((_c, { db }) => db.customers.findMany({ select: ["id"] })),
);
```

Both recipes are written against PermDock's adapter types; `permdock` on npm
is still a name placeholder, so they aren't compiled in this repository's
type tests yet.

## MCP tools

`permdock/mcp` wraps the official MCP SDK's server, so it can't wrap
`createMcp`. On the official SDK, wrap the server with `protectServer` and then
with [`withBetterSupabase`](/docs/frameworks/mcp#official-mcp-sdk), so
PermDock refuses a tool before its repositories are built. With `createMcp`, use `createMcp`'s [`authorize` and `visible`
hooks](/docs/frameworks/mcp#authorizing-tools) instead: put the PermDock
permission in each tool's `meta`, answer `visible` with PermDock's `mayUse`
and `authorize` with `can`. `meta` is `unknown` to better-supabase, which
never imports PermDock, so narrow it with PermDock's `isPermission` first. A
tool without a PermDock permission in `meta` is hidden and refused, so a tool
someone forgot to annotate is never open to everyone:

```ts title="supabase/functions/mcp/index.ts"
import { createMcp } from "better-supabase/mcp";
import { createPermDock, isPermission, mayUse } from "permdock";
import { subjectFromSupabaseSession } from "permdock/supabase";

type Auth = { kind: string; claims?: unknown };
type Dock = Awaited<ReturnType<typeof createPermDock>>;

// One PermDock instance per request: `visible` runs once per tool.
const docks = new WeakMap<Auth, Promise<Dock>>();
function dockFor(ctx: { auth: Auth }): Promise<Dock> {
  let dock = docks.get(ctx.auth);
  if (!dock) {
    dock = createPermDock(policy, subjectFromSupabaseSession(ctx.auth));
    docks.set(ctx.auth, dock);
  }
  return dock;
}

const bs = createMcp(betterSupabase, {
  name: "crm",
  version: "1.0.0",
  scopes: ["openid"],
  // Table tools carry a permission per operation; one without stays hidden.
  resources: {
    customers: {
      operations: ["list", "get"],
      meta: {
        list: permissions.customers.read,
        get: permissions.customers.read,
      },
    },
  },
  authorize: async (ctx, tool) => {
    if (!isPermission(tool.meta))
      return { allowed: false, reason: "No PermDock permission in meta" };
    return (await dockFor(ctx)).can(tool.meta)
      ? { allowed: true }
      : { allowed: false, reason: "PermDock denied this tool" };
  },
  visible: async (ctx, tool) =>
    isPermission(tool.meta) && mayUse(await dockFor(ctx), tool.meta),
}).tool({
  name: "export_customers",
  description: "Export the organization’s customers as CSV.",
  meta: permissions.customers.export,
  run: (_args, { db }) => db.customers.findMany(),
});
```

Table tools from `resources` take their permission from the resource's
`meta`, keyed by operation (`list`, `get`, `create`, `update`, `delete`); an
operation without one is hidden and refused like any other tool.

To tell the client why PermDock refused, call `decide(tool.meta)` instead of
`can`: the decision's `denials` carry the reason (such as `no-grant` or
`approval`) to put in the refusal's `reason`.

Return `scopes` from `authorize` when the permission needs an OAuth scope the
token lacks, and the client gets an `insufficient_scope` challenge naming it.
`mayUse` lists a tool when some grant could apply to the subject, including a
grant with a row condition. `can` decides without a row, so `authorize` still
refuses a permission granted only on some rows; check those inside `run`,
where the row is known, or rely on RLS. A permission that needs human
approval is refused too, because `createMcp` has no approval store: serve
those tools through `permdock/mcp` and
[`withBetterSupabase`](/docs/frameworks/mcp#official-mcp-sdk) on the official
MCP SDK.

## Sessions in Next.js and React

`subjectFromSupabaseSession(session)` takes a better-supabase `AuthSession`
as it is. A `user` session becomes a PermDock subject from its claims; `anon`,
`service` and `invalid` sessions become the anonymous subject.

```ts title="src/lib/permissions.ts"
import { createPermDock } from "permdock";
import { subjectFromSupabaseSession } from "permdock/supabase";

export async function permdockFor() {
  const session = await bs.session();
  return createPermDock(policy, subjectFromSupabaseSession(session));
}
```

## Large membership lists

The hook keeps `memberships` plus `attrs` under its budget
(`supabase.hook.budget`, 1 KB by default) by dropping memberships and setting
`memberships_truncated`. The budget doesn't cover the rest of the token,
including the `supabase.hook.claims` such as `features`, so keep those small. Pass
your membership sources through PermDock's `claimsFirst(sources)`: it uses the
token's memberships and reads the sources only when the token says it dropped
some.

When it finds a `permdock.config.ts`, `better-supabase doctor --as <user id>`
measures `memberships` plus `attrs` against the same budget, and the whole
token against 2 KB, as separate [BS405](/docs/cli/doctor#bs405) warnings. It
also reports `memberships_truncated` for the sample user. Set
`doctor.claimsLimit` to match a different `--budget`.

## Storage and Realtime

Buckets and topics can call PermDock's helpers instead of comparing the
tenant claim. See [PermDock permissions for buckets](/docs/platform/storage#permdock-permissions)
and [for topics](/docs/platform/realtime#authorization).

The helpers check role and scope only. A permission's row conditions (for
example `ownerId = principal.id`) are applied by the table policies
`permdock rls generate` writes, so a bucket or topic in `permdock` mode ignores
them and grants every object in the scope. Use the mode only for permissions
whose grants have no row conditions beyond the scope:

```ts
// Wrong: documents.read is granted only for documents the member owns
policy: { permdock: { read: 'documents.read' }, scope: 'organization' }
// Right: documents.browse is granted per organization, with no row condition
policy: { permdock: { read: 'documents.browse' }, scope: 'organization' }
```

Keys PermDock splits by row condition (`documents.read#1`) are refused. To
find the rest, read `rowConditions` in `permissions.catalog.json`: it is `true`
for a permission with a grant the helpers don't check. `permdock doctor`
reports PD037 for a migration's `storage.objects` or `realtime.messages`
policy that calls a helper for such a key, and `permdock rls verify --db`
checks the same in `pg_policies`.

## Entitlements with PermDock

Plan entitlements are not a PermDock claim, so the
[entitlements module](/docs/blocks/entitlements#with-permdock) works next to
PermDock:

- `has_entitlement(tenant, key)` and `tenant_entitlements(tenant)` read the
  Stripe tables, so SQL and RLS need no claim. With `permdock.manifest.json`
  present, `has_entitlement` and `feature_claims` check membership through
  PermDock's `member_<scope>_ids` helpers, and the module no longer needs the
  `tenant` module.
- `hasEntitlement(session, ...)` reads the `features` claim. Add
  `claims: { features: 'better_supabase.feature_claims' }` to
  `supabase.hook` in `permdock.config.ts` (see [Use one hook](#use-one-hook))
  and PermDock's hook writes it.

`subjectFromSupabaseSession(session, { plans: 'features' })` reads the active
tenant's `features` into the subject's `principal.plans`, so PermDock
policies can grant by plan.

With `rls.memberships` in the manifest (the tables PermDock's
`member_<scope>_ids_for` reads), `entitlement_members()` reads the entries
for the module's scope from there, and falls back to the hook's membership
sources only for a manifest without it. Doctor (BS408) reports a scope with
no `rls.memberships` entry.

## The access block with PermDock

Set `sql.modules.access.model: 'permdock'` and the SQL modules' `can()`, the
organizations, invitations, audit, support-sessions, notifications and
webhooks modules check permissions through PermDock's helpers instead of a
role catalog of their own:

```ts title="better-supabase.config.ts"
export default defineConfig({
  sql: {
    modules: {
      organizations: {},
      invitations: {},
      audit: {},
      access: {
        model: "permdock",
        functions: {
          canAssign: "permdock.permdock_can_assign({role}, {tenant}::text)",
        },
      },
    },
  },
});
```

Then run `permdock supabase inspect --out` and `better-supabase sql add`.
The block reads `permdock.manifest.json` whether or not the entitlements
module uses PermDock:

- the schema is `rls.schema` (write it in `canAssign` too), the scope is the
  root scope (the `rls.scopes` entry without `within`) and the id type is
  that scope's `type`. A manifest with `rls.schema: "authz"` and a root scope
  `tenant` gets `authz.permitted_tenant_ids`;
- `sql add` stops on a missing manifest, no single root scope, a
  `sql.modules.access.permdock.scope` the manifest doesn't declare, or a schema or
  `sql.modules.access.idType` that disagrees with it;
- every permission key the SQL modules check must be `rowConditions: false`
  in `permissions.catalog.json`, because the helpers check role and scope
  only. `modulePermissionKeys` from `better-supabase/sql` lists the keys; map
  one to another key with `sql.modules.<module>.permissions`;
- `canAssign` names PermDock's assignment rule, `permdock_can_assign`, which
  PermDock writes when a role declares `assigns`. Without it only the
  service role assigns roles.

[Doctor](/docs/cli/doctor#bs411) (BS411) reports the same problems and checks
that the database has the helpers. PermDock's helpers read `auth.uid()`, so
`can_user()` and `member_can()` answer for the caller only and raise SQLSTATE
`0A000` for anyone else. The invitations module therefore doesn't check the
inviter's permission again when an invitation is accepted, and the
notifications module doesn't filter recipients by their read permission. See
[the access block](/docs/blocks/access#permdock) for the details.

## Support sessions and other actors

The `act` claim is part of the claim contract both packages read. A support
session marks it `kind: "support"` and `actingAs` marks it
`kind: "impersonation"`; an `act` without `kind` is an OAuth client or an
agent chain:

| `act`                                                     | `session.actor`                                | `session.impersonator` | `scopes` guard     |
| --------------------------------------------------------- | ---------------------------------------------- | ---------------------- | ------------------ |
| `{ kind: "support", sub, reason, session_id, read_only }` | `{ kind: "support", id, sessionId, readOnly }` | set                    | not limited        |
| `{ kind: "impersonation", sub, reason }`                  | `{ kind: "impersonation", id, reason }`        | set                    | not limited        |
| no `kind` (an OAuth client or agent chain)                | `{ kind: "oauth-client", id, chain }`          | not set                | limited to `scope` |

Another `kind` makes the session invalid. A support token minted by 0.5.0
(`session_id` without `kind`) still counts as a support session until 0.6.
`supabaseClaimFixtures` from `better-supabase/testing` has one token of each
kind, in the shape of PermDock's fixtures, so tests on both sides read the
same claims.

## Anonymous sign-ins

Users from `signInAnonymously()` pass a guard only when `allow` lists
`'anonymous'`; `'anon'` means a caller without a session and never admits
them (see [anonymous users](/docs/auth#anonymous-users)). On the PermDock
side, `rls.anonymousSignIns: 'deny'` in `permdock.config.ts` keeps an
`is_anonymous` token out of every policy branch except `anyone()`'s. Use the
two together, so neither the routes nor the policies serve a guest session:

```ts title="permdock.config.ts"
export default {
  rls: { anonymousSignIns: "deny" },
};
```

Routes then keep the default `allow: ['user']`, or `['user', 'anon']` for
public ones; neither admits an anonymous sign-in.

## What neither package does

- Read roles, memberships, the tenant or entitlements from `user_metadata`.
  Users can change it with `auth.updateUser()`.
  [`betterSupabase.userMetadata(schema)`](/docs/auth#profile) parses it into
  `session.profile`, which is for display only.
- Trust a tenant id from a URL or request body without a matching membership.
- Build a subject for `service_role`. The storage and realtime policies are
  only ever for `authenticated`.
