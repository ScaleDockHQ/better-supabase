```ts title="src/lib/supabase/client.native.ts"
import { PowerSyncDatabase } from "@powersync/react-native";
import { createNativeClient } from "better-supabase/client/native";
import { powersyncEngine } from "better-supabase/powersync";
import { connector } from "../powersync/connector";
import { betterSupabase } from "./index";
import { schema } from "../powersync/schema";

export const powersync = new PowerSyncDatabase({
  schema,
  database: { dbFilename: "app.db" },
});

export const bsb = createNativeClient(betterSupabase, supabase, {
  engine: powersyncEngine(powersync, { connector, local: ["customers"] }),
});
```

`powersyncEngine(db)` runs `bsb.db` and the generated
[data hooks](/docs/frontend/data-hooks) on the PowerSync database: each
repository call compiles to SQLite and runs on the device, online or not.
Rows come back the way PostgREST returns them: in the definition's casing,
with booleans, JSON and Temporal values decoded the same way. `local` lists
the tables PowerSync syncs; `bsb.db` reads and writes every other table
through PostgREST. Leave it out when every table syncs.

```tsx title="src/components/customer-list.native.tsx"
import { useCustomers } from "@/lib/supabase/hooks";

export function CustomerList() {
  const customers = useCustomers({
    where: { status: "active" },
    orderBy: { name: "asc" },
  });
  // ...
}
```

`@powersync/common` is not a dependency; the engine only needs `getAll`,
`execute` and `writeTransaction`, `onChange` for live reads and
`registerListener` with `currentStatus` for the sync state, so
`@powersync/react-native`, `@powersync/web` and a test double all work. To
run the repositories without the client, use
`betterSupabase.connect(powersyncExecutor(powersync))`.

## What runs on SQLite

Filters, search, sorting, offset and cursor pages, counts, aggregates,
includes (nested ones too, with their own `where`, `orderBy`, `limit` and
`required`), related counts and related aggregates, and inserts, updates,
upserts and deletes all run. A read with includes stays one SQL statement:
each include is a correlated subquery that returns JSON, and the executor
decodes its rows the same way as the top-level ones. Some things have no
SQLite form:

| Feature                                       | On SQLite                                 |
| --------------------------------------------- | ----------------------------------------- |
| full-text search (`fts`)                      | `unsupported` error                       |
| `db.$rpc` and function sources (`db.$search`) | `unsupported` error                       |
| writes to a table without a primary key       | `unsupported` error                       |
| `ilike`                                       | SQLite `like`: case-insensitive for ASCII |
| `like`                                        | `glob`: case-sensitive, like Postgres     |
| timestamps                                    | compared as UTC ISO text                  |

The error has kind `unsupported` (HTTP 501), the feature in `details`, and
nothing runs. To catch it before a screen does, check a list definition, or
a single read from `betterSupabase.spec`, in a test:

```ts title="src/lists.test.ts"
import { checkSqlite } from "better-supabase/powersync";

expect(await checkSqlite(betterSupabase, customerList)).toEqual({
  ok: true,
  data: undefined,
});

const detail = betterSupabase.spec.customers.list({
  include: {
    notes: { orderBy: { createdAt: "desc" }, limit: 5 },
    _count: { notes: true },
  },
});
expect(await checkSqlite(betterSupabase, detail)).toMatchObject({ ok: true });
```

`checkSqlite` compiles every query the list runs (the page, its count and the
facet counts), or the one read a spec describes, without a database. It
returns the first error; pass
`{ all: true }` to get every one as an array, empty when the whole list runs
on SQLite.

## Server fallback

What SQLite can't run goes to the server: a read that compiles to
`unsupported` (full-text search, a function source) runs on the client's
PostgREST executor, and so does `db.$rpc`. Everything else stays on SQLite.
Writes never fall back, so PowerSync's upload queue stays the only write path
for a synced table, and an unsupported write still returns `unsupported`.
When the device is offline, the read returns the server's error, usually kind
`network`. Pass `fallback: false` to keep every call on the device, or
another executor as `fallback`.

A hook that reads from the server is read again when one of its local tables
changes, and every hook is read again when PowerSync connects after it was
offline, so a fallback read catches up once the device is back.

## Porting a list from PostgREST

Most lists run locally as they are: filters, `ilike` search, facets, facet
counts, sorting, pages, aggregates, includes and related counts all compile
to SQLite, as long as the included tables sync too. The reads that don't are
usually full-text search and database functions that aggregate. For each, pick one:

- Sync what the screen needs. A summary table or view that a sync rule
  publishes (note counts per customer, a denormalized name) turns an RPC
  aggregate into a local table the hooks read.
- Search a synced text column with `search: ["name", "kvk"]` (`ilike`)
  instead of `{ fts: ... }`.
- Keep it on the server through the fallback, and accept that it needs a
  connection. It reads again when PowerSync connects.

To find the server-only reads, list them in a test:

```ts title="src/lists.test.ts"
import { checkSqlite } from "better-supabase/powersync";

it("runs every list on the device", async () => {
  for (const list of [customerList, noteList])
    expect(await checkSqlite(betterSupabase, list, { all: true })).toEqual([]);
});
```

The errors that test reports are the reads that go to the server; each has
the feature in `details`.

## Live results

The hooks read once and then follow their table: PowerSync reports every
local write and every synced row, at most once every 30 ms (`throttleMs`),
and each hook that reads a changed table reads again. A hook named after
something other than a table, such as a list definition wrapped in
`defineDataHooks("customer-pages", ...)`, names its tables in
`tables: { "customer-pages": ["customers"] }`. Writes through a hook apply
to the cached lists first, run on the device and roll back on an error.

### Sync state

`useSyncStatus()` and `useConflicts()` from `better-supabase/react` read the
provider's engine:

```tsx
import { useConflicts, useSyncStatus } from "better-supabase/react";

function SyncBanner() {
  const sync = useSyncStatus();
  const { changes, dismiss } = useConflicts();
  // ...
}
```

`useSyncStatus` returns `connected`, `connecting`, `hasSynced`, `uploading`,
`downloading` and the last sync `error`, re-renders only when one of them
changes, and returns `undefined` when the engine syncs nothing.
`useConflicts` reads the changes the engine's `connector` could not upload;
see [Offline-first](/docs/guides/offline-first#conflicts).

A read with a count (`page` with `count: "exact"`, a list query's total)
runs the rows and the count in one `readTransaction`, so the two agree while
PowerSync syncs.

## Table names and keys

PowerSync names each view after the table without its schema, and that is
the default. Pass `tableName` to `powersyncEngine` (or `powersyncExecutor`)
when your PowerSync schema renames a table. PowerSync tables key on a text
`id` that the client creates: an insert without one gets
`crypto.randomUUID()` (or `newId` when you pass it).

Writes go to the local database and PowerSync uploads them.
`createUploadConnector` replays them through repositories on PostgREST (a
client without the engine), and `uploadRoute(server.db.events, { put: "create" })`
inserts the rows of a write-once table, counting a conflict as already
applied. `onError` reports a failed session read and retried uploads. See
[Offline-first](/docs/guides/offline-first) for the routes, outcomes and
conflicts.

## Attachments

The [attachments](/docs/blocks/attachments#offline) block works offline with
`blocks.attachments.options.offline: true`. Without it, `authenticated` can't
insert a record's `id`, so a record created offline fails to upload.
`attachmentQueueRoute` replays the table: a `PUT` creates the record under
the id the client chose and counts a conflict as applied, a `DELETE` removes
the record first, which queues its files for deletion, and a `PATCH` is
refused. It sends only the columns an insert accepts, so the synced
`object_path` and `status` stay out of the upload; list your own columns in
`extraColumns`.

```ts title="src/lib/powersync/connector.ts"
import { bindClient } from "better-supabase/client";
import {
  attachmentQueueRoute,
  createUploadConnector,
} from "better-supabase/powersync";
import { betterSupabase } from "../supabase";
import { supabase } from "../supabase/supabase.native";

const server = bindClient(betterSupabase, supabase);

export const attachments = attachmentQueueRoute(server.db.attachments, {
  path: "{organization_id}/attachments/{id}.{ext}",
});

export const connector = createUploadConnector({
  endpoint: process.env.EXPO_PUBLIC_POWERSYNC_URL,
  supabase,
  tables: { attachments },
});
```

`attachments.path(row)` returns the object path the database generates for
the row (pass the block's `path` option when you changed it), so PowerSync's
`AttachmentQueue` uploads the file where the record expects it. A storage
trigger marks the record uploaded when the file lands, so the client never
has to call `confirm`.

## Offline-capable blocks

Five blocks work offline on PowerSync: attachments (above), notifications,
memberships (the organization switcher), teams and profiles. Every other
block calls its functions on the server, so on native it needs
the network. `better-supabase powersync streams` writes the Sync Streams, the
publication migration and the client schema for the instances you name; see
[`powersync streams`](/docs/cli/powersync).

With `gen.powersync` set, `gen` marks every other instance in the generated
`blocks` map with `/** Needs the network on native. */`, so the editor shows
which block calls fail offline. An app that doesn't own the database can set
`gen.tasks: ["types"]` to get the marks without writing the block SQL or the
publication migration; the `expo-powersync` example does this.

`powersyncNotificationsTransport` runs the notifications feed on the synced
tables: listing, paging, counts, marking read, unread or dismissed, and
listing and setting channel preferences. The local writes go into the upload
queue, and `notificationRecipientsRoute` and `notificationPreferencesRoute`
replay them through the server's functions, which check that the caller owns
the row. Sending, resolving and removing a preference (`enabled: null`) go to
`server`.

```ts title="src/lib/powersync/notifications.ts"
import {
  createNotifications,
  rpcTransport,
} from "better-supabase/blocks/notifications";
import {
  notificationPreferencesRoute,
  notificationRecipientsRoute,
  powersyncNotificationsTransport,
} from "better-supabase/powersync";
import { supabase } from "../supabase/supabase.native";
import { powersync } from "./database";

const remote = createNotifications({ transport: rpcTransport(supabase) });

export const notifications = createNotifications({
  transport: powersyncNotificationsTransport(powersync, {
    server: rpcTransport(supabase),
  }),
});

export const notificationRoutes = {
  notification_recipients: notificationRecipientsRoute(remote),
  notification_preferences: notificationPreferencesRoute(remote, powersync),
};
```

The upload routes take the client on `rpcTransport`, not the local one: the
local transport would write the change into SQLite again. A preference
update carries only `enabled`, so `notificationPreferencesRoute` reads the
type, channel and organization from `powersync`. Pass
`powersyncTopicPort(powersync)` as `ports.topic` to
`createNotificationsController`: the feed reloads when a sync or a local write
changes the notification tables, without a Realtime channel. Pass `functions`
and `tables` when the instance renames them.

### Care: progress notes, observations and doses

Care staff write offline in a client's home, so the `activities` (progress
notes), `observations` and `medications` blocks can sync too. Name them in
`gen.powersync.instances`; the streams need the roles access model
(`authorization: "roles"`), because PowerSync bypasses row level security and
the streams filter instead. A user syncs the rows of the organizations where
their role holds the block's `read` key (`observations.read`,
`medications.read`, `activities.read`), including system observation
definitions. Only progress notes (`type = 'note'`) open to the team sync, with
their record links, never a restricted engagement. Record-team limits are not
applied on the device.

The upload routes replay each write through the block's functions:

```ts title="src/lib/powersync/care.ts"
import {
  activityLinksRoute,
  careUploadOutcome,
  createUploadConnector,
  medicationAdministrationRoute,
  observationRoute,
  progressNoteRoute,
} from "better-supabase/powersync";
import { bsb } from "../supabase/supabase.native";
import { powersync } from "./database";

export const connector = createUploadConnector({
  classify: careUploadOutcome,
  tables: {
    activities: progressNoteRoute(bsb.activities, powersync),
    engagement_subjects: activityLinksRoute(),
    observations: observationRoute(bsb.observations, powersync),
    medication_administrations: medicationAdministrationRoute(bsb.medications),
  },
  // fetchCredentials, powersync, and so on
});
```

- A note is logged with its local id as `externalRef`, so a retried upload
  updates it instead of adding a second note. An edit of a note that locked
  on the server becomes an addendum, and a note is never deleted.
- A reading that the server already has (same definition, time and value) counts
  as applied, so a lost answer doesn't add a duplicate. An observation is
  corrected online, as a new observation.
- A dose is recorded with `recordAdministration` or, for an as-needed dose,
  `recordAsNeeded`. A dose that was already recorded, a missing second
  checker or a locked note is a conflict: with `careUploadOutcome` it lands in
  `connector.rejected` for the nurse to resolve and is never retried or dropped
  quietly.

The server assigns the ids of notes and observations, so the next sync
replaces the local row with the server's.

### Organizations, teams and profiles

The same pattern covers the organization switcher, teams and the user's
profile. Each transport answers some functions from SQLite and sends the rest
to `server`; each upload route replays the queued change through the server
client.

| Transport                       | Answers locally                                                                | Upload route                                              |
| ------------------------------- | ------------------------------------------------------------------------------ | --------------------------------------------------------- |
| `powersyncMembershipsTransport` | `organizations.mine()` and `leave()`                                           | `membershipsRoute(organizations)`                         |
| `powersyncTeamsTransport`       | `teams.list()`, `update`, `archive`, `restore`, `addMember` and `removeMember` | `teamsRoute(teams, powersync)`, `teamMembersRoute(teams)` |
| `powersyncProfilesTransport`    | `profiles.mine()` and `updateMine()`                                           | `profilesRoute(profiles)`                                 |

```ts title="src/lib/powersync/organizations.ts"
import {
  createOrganizations,
  rpcTransport,
} from "better-supabase/blocks/organizations";
import { createProfiles } from "better-supabase/blocks/profiles";
import { createTeams } from "better-supabase/blocks/teams";
import {
  membershipsRoute,
  powersyncMembershipsTransport,
  powersyncProfilesTransport,
  powersyncTeamsTransport,
  profilesRoute,
  teamMembersRoute,
  teamsRoute,
} from "better-supabase/powersync";
import { supabase } from "../supabase/supabase.native";
import { powersync } from "./database";

const server = rpcTransport(supabase);

export const organizations = createOrganizations({
  transport: powersyncMembershipsTransport(powersync, { server }),
});
export const teams = createTeams({
  transport: powersyncTeamsTransport(powersync, { server }),
});
export const profiles = createProfiles({
  transport: powersyncProfilesTransport(powersync, {
    server,
    userId: async () =>
      (await supabase.auth.getSession()).data.session?.user.id,
  }),
});

const remoteTeams = createTeams({ transport: server });

export const organizationRoutes = {
  memberships: membershipsRoute(createOrganizations({ transport: server })),
  teams: teamsRoute(remoteTeams, powersync),
  team_members: teamMembersRoute(remoteTeams),
  profiles: profilesRoute(createProfiles({ transport: server })),
};
```

The synced rows are the ones RLS lets the user read: their active
memberships (and their `membership_roles` rows with `roles.many`) with the
names of those organizations, every team in those organizations with its
members, and their profile. So offline, `teams.list()` returns the same teams
as online. `userId` lets the profiles transport read the signed-in user's
row by id, so a row another user left on the device before the next sync is
never returned.
Switching organizations, creating or deleting a team and changing another
member's role need the network, because the server picks ids, refreshes the
session claim or checks a permission the device can't. `teamsRoute` reads the
team's name from `powersync` when a queued change kept it, because a `PATCH`
carries only the changed columns.

### Following the session

`syncWithAuth(powersync, bsb.auth, { connector })` connects on sign-in, and
on sign-out or another user disconnects and clears the device database. It
also reconnects when a new token for the same user carries another tenant or
`authz_ver`, because the sync service reads the claims only when a client
connects; the reconnect makes it evaluate the streams again and remove the
rows the user lost. `sync.reconnect()` forces one, such as after a tenant
switch:

```ts title="src/lib/powersync/sync.ts"
export const sync = syncWithAuth(powersync, bsb.auth, { connector });

export async function afterSwitch(result: SwitchResult): Promise<void> {
  if (result.refresh) await supabase.auth.refreshSession();
  await sync.reconnect();
}
```

The connector's `fetchCredentials` must read the current session on every
call, as `createUploadConnector` does, or the reconnect sends the old token.
Pass `sync` to the native `SessionProvider` so a role change refreshes the
token and reconnects without waiting for the token to expire
([Authorization refresh on native](/docs/frontend/authorization-refresh-native)).

## Uploaded columns

A generated column is in the row you sync down, but Postgres rejects an
insert or update that sets it. `WritableColumnOf` lists the columns of a table
that accept writes, so a column list for the upload fails to compile when it
names a generated one:

```ts title="src/lib/powersync/connector.ts"
import type {
  GeneratedColumnOf,
  WritableColumnOf,
} from "../supabase/generated";

// With `casing: "snake"` the names are the database names PowerSync uses.
const uploadable = [
  "organization_id",
  "user_id",
  "role",
] as const satisfies readonly WritableColumnOf<"memberships">[];

// Dropped from the upload payload before it reaches PostgREST.
type Skipped = GeneratedColumnOf<"memberships">; // "tier_role"
```

Adding `"tier_role"` to `uploadable` is a type error.
