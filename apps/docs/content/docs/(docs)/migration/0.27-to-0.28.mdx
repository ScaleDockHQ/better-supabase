---
title: From 0.27 to 0.28
description: What to check when upgrading to better-supabase 0.28, where db diff plans with pg-delta, realtime tenant topics follow membership, and add and init work over an existing project.
---

0.28 changes how `db diff` plans and who receives realtime tenant topics. The
config is unchanged; the `tables` and `records` removal shipped in 0.29 (see
[From 0.28 to 0.29](/docs/migration/0.28-to-0.29)).

## `db diff` plans with pg-delta

On a pg-delta project (`database.sql.workflow: "pg-delta"`), `db diff` plans
with pg-delta's library (#424). Install its two optional peers first:

```sh
pnpm add -D @supabase/pg-delta @supabase/pg-topo
```

Doctor's BS239 reports when they are missing. Two behaviours are new:

- A rename is a rename only when a migration records it with
  `-- bsb: rename old -> new`. Without the comment, the plan drops the old
  name and creates the new one.
- A plan that drops tables or columns stops with a `check_failed` error until
  you pass `--allow-data-loss`.

The shadow database comes from the running stack, so `pg_dump`, `psql` and
`BSB_PG_BIN` are no longer used. The migra workflow and remote databases still
run through the Supabase CLI.

## Realtime tenant topics follow membership

A tenant topic of `realtime-tables` (`bsb:t:<table>:<tenant>`) now reaches the
members of that tenant at the time of the message, checked with
`member_organization_ids()` (#431). Before, it reached whoever carried the
tenant id in their token, so a removed member kept receiving until the token
expired. Run the upgrade and generate a migration:

```sh
npx better-supabase upgrade
npx better-supabase db diff
```

Without the `memberships` module, tenant topics stay closed. Unscoped and
own-user topics are unchanged.

## New in the CLI

- `add <block> --over <schema.table>` installs one block over a table you
  already have (#441). It proposes the `tables` and `columns` mapping, reports
  what can't map and writes `blocks.<block>` to the config.
- `init` recognizes a project that already has a `supabase` folder (#425): it
  lists the migrations, schema files and snapshot tables it found and leaves
  the database unchanged. `init --from` starts from a `postgres://` URL, which
  writes the schema to `supabase/snapshot.json`, or from a preset, design code,
  URL or file.
