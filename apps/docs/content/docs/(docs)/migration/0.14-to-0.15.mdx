---
title: From 0.14 to 0.15
description: What to change when upgrading to better-supabase 0.15, where the config is grouped, the runtime instance is bsb, the SQL engine says block and the CLI has one command per job.
---

0.15 groups the config file, renames the runtime instance to `bsb`, moves
the SQL engine's names from module to block and gives the CLI one command per
job. `better-supabase codemod 0.15` makes the changes below in your config,
source files, `package.json` scripts and GitHub workflows. Run it, review the
diff, then run `better-supabase upgrade` and generate a migration.

```sh
npx better-supabase codemod 0.15
```

## The config is grouped

`better-supabase.config.ts` groups its keys into `database`, `auth`, `gen`,
`api` and `tooling`. `preset`, `blocks`, `plugins`, `records`, `tables` and
`adapters` stay at the top level. A config that still uses a 0.14 key fails
to load, and the message names the key's new place.

```ts title="better-supabase.config.ts"
export default defineConfig({
  database: { schemas: ["public"], sql: { owner: "tenant", api: "api" } },
  auth: { organization: { claim: "tenant_id" } },
  gen: { casing: "camel", output: "src/lib/supabase/generated.ts" },
  tooling: { doctor: { strict: true } },
  records: { customer: { table: "customers", title: "name" } },
  tables: { notes: { owner: "user", columns: { body: { type: "text" } } } },
  adapters: ["next"],
  blocks: { tenant: { names: { organization: "workspace" } } },
});
```

| Group      | Keys                                                                                                                                                                                                                        |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `database` | `source`, `schemas`, `sql`, `seed`, `expose`, `buckets`, `realtime`, `topics`, `vectorSearch`                                                                                                                               |
| `auth`     | `organization`, `claims`, `authorization`, `entitlements`                                                                                                                                                                   |
| `gen`      | `output`, `casing`, `postgrestVersion`, `generateFeatures`, `tables` (the generator overrides), `json`, `codecs`, `relations`, `sensitive`, `storagePaths`, `functions`, `generators`, `readSets`, `tasks`, `watchInterval` |
| `api`      | `openapi`, `specs`                                                                                                                                                                                                          |
| `tooling`  | `doctor`, `env`, `keys`, `skills`, `scaffold`                                                                                                                                                                               |

Some keys take new names on the way:

| 0.14                           | 0.15                       |
| ------------------------------ | -------------------------- |
| `subjects`                     | `records`                  |
| `appTables`                    | `tables`                   |
| `appTables.<name>.scope`       | `tables.<name>.owner`      |
| `integrations`                 | `adapters`                 |
| `tables` (generator overrides) | `gen.tables`               |
| `sql.scope`                    | `database.sql.owner`       |
| `claims.tenant`                | `auth.organization.claim`  |
| `plugins.tenant.column`        | `auth.organization.column` |
| `blocks.<name>.mode`           | `blocks.<name>.ownership`  |
| `blocks.<name>.scope`          | `blocks.<name>.owner`      |
| `blocks.<name>.entities`       | `blocks.<name>.names`      |
| `blocks.<name>.hooks`          | `blocks.<name>.callbacks`  |

Environment blocks (`$env`, `$ci` and the others) take the same groups. A
`better-supabase.config.json` is regrouped the same way. Create designs keep
`appTables` and `scope` in this release.

`resolveConfig` returns the same resolved config as in 0.14, so code that
reads `config.claims.tenant` or `config.appTables` from a resolved config
keeps working. `flattenConfig` and `groupConfig` from `better-supabase/config`
turn one shape into the other.

## The runtime instance is bsb

The instance `createBetterSupabase` returns is called `bsb` in the docs, the
templates and the request contexts: `ctx.bsb`, `c.var.bsb`, `locals.bsb` and
`context.bsb`. The codemod renames `bs` where a file creates, imports or
destructures it. Database objects better-supabase installs use the `bsb_`
prefix; `upgrade` renames the old `bs_` ones.

## The SQL engine says block

`SqlModule` is `BlockSql`, `ModuleDefinition` is `BlockSqlDefinition`, and
the other `Module*` types from `better-supabase/sql` are `BlockSql*`.
`SubjectRef` is `RecordRef`, `entityForm` is `recordForm`, `ShipmentCarrier`
is `ShippingProvider` and `QueueBackend` is `QueueProvider`. Installed
versions live in `better_supabase.blocks`; `upgrade` copies the rows of
`better_supabase.modules` before the schema diff drops it.

## The CLI has one command per job

The CLI keeps one command for each job: `init`, `add`, `remove`, `upgrade`,
`gen`, `doctor`, `db`, `dev`, `blocks`, `spec`, `mcp` and the helpers. The
commands below moved. Running an old one exits 2 and names the new one, and
the codemod rewrites them in `package.json` scripts and GitHub workflows.

| 0.14                          | 0.15                                          |
| ----------------------------- | --------------------------------------------- |
| `apply --preset <p>`          | `add --preset <p>`                            |
| `adopt <block>`               | `add --adopt <block>`                         |
| `sql add <block>`             | `add <block>`                                 |
| `sql sync`, `sql upgrade`     | `upgrade`                                     |
| `sql data`                    | `add --adopt`                                 |
| `sql list`                    | `blocks list --installed`                     |
| `sql print <block>`           | `blocks view <block> --sql`                   |
| `preset decode <code>`        | `blocks list --preset <name or URL>`          |
| `preset info`                 | `config --preset`                             |
| `introspect`                  | `gen --save-snapshot`                         |
| `seed`                        | `db seed`                                     |
| `env`, `run`, `keys`, `stack` | `dev env`, `dev run`, `dev keys`, `dev stack` |

`gen --out <file>` now names the file `gen --save-snapshot` writes;
the generated code still goes to `--out-dir`. `add --force` overwrites
files that exist, so a block whose hooks overlap the authorization provider's
needs `--allow-hook-overlap`. `remove` is new: it
takes blocks out of the config and `lib/blocks.ts` and deletes their module
files, and [`db diff`](/docs/cli/db#diff) writes the migration that drops
their tables. See the [CLI reference](/docs/cli) for every command.

## Designs replace preset codes

Create URLs and the CLI carry the design JSON instead of a preset code. The
config's `preset` key takes a preset name or an object with the conventions
that differ from the defaults and the blocks:

```ts title="better-supabase.config.ts"
// 0.14
preset: "1pWEF3d578B1iGt16",

// 0.15
preset: { casing: "camel", scope: "user", blocks: ["profiles", "tags"] },
```

A Create URL is `/create?preset=<name>` for an unchanged named preset and
`/create?design=<code>` otherwise, with the preset inside the design. A design
file is the design JSON with its `version` and `preset` keys, without the
0.14 `design` wrapper. `init --preset`, `add --preset` and `blocks list
--preset` take a name, a URL, a design code or a file, and stop on a 0.14 code
with a message that names the codemod. The codemod turns a code in the
config's `preset` into the name or object it holds, and rewrites
`*.design.json` files.

`encodePreset`, `decodePreset`, `isPresetCode`, `defaultPresetCode`,
`withPresetField`, `PRESET_BLOCKS`, `PRESET_FIELDS`, `PRESET_VERSION` and the
`DecodedPreset` type are gone from `better-supabase/preset`. Use
`presetSpec`, `presetFromSpec` and `presetOfSpec` for the config value,
`createUrl` for a link and `presetAndDesignOf` to read one.
`designConfigSource`, `designInstallCommand` and `designApplyCommand` merge
into `presetConfigSource`, `presetInstallCommand` and `presetApplyCommand`,
which take an optional design and are now async.

## Blocks take plain names

26 blocks have new names. Each one changes in the config, the CLI, its
subpath, its exports, its operation names and its CloudEvent source:

```ts title="better-supabase.config.ts"
// 0.14
blocks: { tenant: {}, "work-items": {}, rules: {} },

// 0.15
blocks: { memberships: {}, tasks: {}, automations: {} },
```

| 0.14                 | 0.15               |
| -------------------- | ------------------ |
| `work-items`         | `tasks`            |
| `parties`            | `contacts`         |
| `engagements`        | `activities`       |
| `targets`            | `goals`            |
| `number-sequences`   | `numbering`        |
| `actor`              | `created-by`       |
| `ensure-rls`         | `rls-guard`        |
| `shared-signals`     | `security-events`  |
| `service-principals` | `service-accounts` |
| `support-sessions`   | `impersonation`    |
| `controls`           | `compliance`       |
| `ai-tasks`           | `ai-schedules`     |
| `ai-providers`       | `ai-keys`          |
| `workflow-builder`   | `workflow-editor`  |
| `jobs`               | `queue`            |
| `access`             | `permissions`      |
| `rules`              | `automations`      |
| `tenant`             | `memberships`      |
| `activity`           | `timeline`         |
| `workflow-sdk-world` | `workflow-sdk`     |

The codemod renames the `blocks` keys and lists, the `preset.blocks` list,
the operation names in `auth.authorization.operations`, the imports from
`better-supabase/blocks/<name>` and the exports named after a block. It
lists the event sources `better-supabase/<name>` it finds, so you can update
your subscribers. A 0.14 name in the config stops `add` and `gen` with a
message that names the codemod.

Table names, permission keys, event types, hint codes and queue names keep
their 0.14 values. Run `better-supabase upgrade`, then
[`db diff`](/docs/cli/db#diff): the migration moves the installed blocks to
their new names, and renames two tables whose names clashed with a renamed
block. Hiring's `jobs` table becomes `job_openings`, and catalog's
`collections` table becomes `product_collections`.

## More blocks register record types

The quotes, invoices, orders, bookings and forms blocks register their primary
noun as a record type, so `records.quote`, `records.invoice`, `records.order`,
`records.booking` and `records.form` now fail with `config_invalid`. Remove the
entry when it points at the block's own table. When it points at a table of
your own, keep it and turn the block's record type off:

```ts title="better-supabase.config.ts"
blocks: {
  bookings: { names: { booking: { subject: false } } },
},
```

Then run `better-supabase upgrade`. Every block that owns tables now declares
its nouns, so `blocks.<name>.names` renames them; see
[SQL blocks](/docs/blocks/sql).

## Plugins become block extensions

The built-in plugins live with the blocks that own their columns, and the
`plugins` config key goes. The codemod moves the config and the imports:

| 0.14                                                      | 0.15                                                                                            |
| --------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `plugins.timestamps`                                      | the `updated-at` block (`createdAt` and `updatedAt` options)                                    |
| `plugins.actor`                                           | the `created-by` block (`createdBy`, `updatedBy` and `impersonatedBy`)                          |
| `plugins.softDelete.column`                               | the `trash` block's `deletedAt` option                                                          |
| `plugins.tenant.column`                                   | `auth.organization.column`                                                                      |
| `timestamps()` from `better-supabase/plugins/timestamps`  | `updatedAtExtension()` from `better-supabase/blocks/updated-at`                                 |
| `actor()` from `better-supabase/plugins/actor`            | `createdByExtension()` from `better-supabase/blocks/created-by`                                 |
| `softDelete()` from `better-supabase/plugins/soft-delete` | `trashExtension()` from `better-supabase/blocks/trash`                                          |
| `tenant()` from `better-supabase/plugins/tenant`          | `membershipsExtension()` from `better-supabase/blocks/memberships`                              |
| `rules()`, `safe()`, `recommended()`, `strict()`          | `guards()`, `safeGuards()`, `recommendedGuards()`, `strictGuards()` from `better-supabase/lint` |
| `validation()` from `better-supabase/plugins/validation`  | `validation()` from `better-supabase`                                                           |

`gen` now installs the extensions of the installed blocks in the generated
schema, and `validation()` with the generated validators when a `zod()`,
`valibot()` or `standardSchema()` generator is configured. Remove the
`.use()` calls the codemod moved unless they pass options; a `.use()` of an
extension with options replaces the one the schema installed.

One default changed: a query on an organization table without an
organization is left to RLS (`onMissing: "skip"`). The codemod keeps the
0.14 behavior by writing `auth.organization.onMissing: "error"` for a config
that had `plugins.tenant`; set it yourself to fail closed.

## One data contract for tables and blocks

Repositories and block clients share the data verbs: `list`, `page`, `get`,
`count` and `aggregate` read, `create`, `update`, `upsert` and `delete`
write, and `attach` and `detach` link a row to a record. The codemod
rewrites the repository calls:

| 0.14                                           | 0.15                                                 |
| ---------------------------------------------- | ---------------------------------------------------- |
| `findMany(args)`                               | `list(args)`                                         |
| `paginate(args)`                               | `page(args)`                                         |
| `findById(id)`                                 | `get(id)`, or `get(id, { optional: true })` for null |
| `findUnique(key)`, `findOnly(args)`            | `get(key)`, or `get({ where })` for a filter         |
| `findFirst(args)`                              | `list({ ...args, limit: 1 })`, then the first row    |
| `exists(args)`                                 | `count(args)`, then compare with zero                |
| `createMany(rows)`, `upsertMany(rows)`         | `create(rows)`, `upsert(rows)` with an array         |
| `updateMany(where, patch)`                     | `update({ where }, patch)`                           |
| `deleteMany(where)`                            | `delete({ where })`                                  |
| `guards({ noUnboundedFindMany })`              | `guards({ noUnboundedList })`                        |
| `guards({ noDeleteManyWithoutWhere })`         | `guards({ noDeleteWithoutWhere })`                   |
| `better-supabase/no-unbounded-find-many`       | `better-supabase/no-unbounded-list`                  |
| `better-supabase/no-delete-many-without-where` | `better-supabase/no-empty-where`                     |

`get` takes the primary key, an object with one complete unique key, or
`{ where }`. With `{ where }` it fails with `multiple_rows` when more than
one row matches, so it replaces `findOnly`. Read sets and query specs have
no `.map`, so where the codemod wrote `findFirst` as a list with
`.map((rows) => rows[0] ?? null)`, use `get({ where }, { optional: true })`
or destructure the first row; the codemod lists those calls.

The lint rule `no-empty-where` reports an `update` or `delete` whose filter is
`{ where: {} }`, and `no-unbounded-list` reports a `list` without `limit`.

Block clients move to the same verbs. These calls are listed for review,
because the names are too common to rewrite safely:

| 0.14                                                   | 0.15                                                      |
| ------------------------------------------------------ | --------------------------------------------------------- |
| `tags.tag(record, tagId)`, `tags.untag(record, tagId)` | `tags.attach(record, tagId)`, `detach`                    |
| `tags.create(kind, name, color, description, fields)`  | `tags.create({ kind, name, color, description, fields })` |
| `tags.update(id, name, fields)`                        | `tags.update(id, { name, fields })`                       |
| `tags.list(kind)`                                      | `tags.list({ kind })`                                     |
| `forSubject(record)` on tags, channels and scores      | `list({ on: record })`                                    |
| `save(...)` on a block client                          | `upsert(...)` with the same arguments                     |
| `set(...)` on ai-cache and on ai-files `providerFiles` | `upsert(...)`                                             |

The rule builder and saved-view controllers keep `save`, the settings client
keeps `setUser` and `setOrganization`, and domain verbs such as `approve`,
`send` and `publish` stay.

## Blocks install as instances

Each key in `blocks` is now an instance. A config keyed by block name keeps
working unchanged. To install a block twice, add a key with `block` set to
the block's name; when a block depends on a block you installed twice, name
the instance it uses in `uses`. See [Instances](/docs/blocks#instances).
`resolveConfig` reports a core block, such as `memberships`, that is renamed
or installed twice.

## Every instance renders its own SQL

`better_supabase.blocks` has a new `block` column. The schema file creates it
for new installs, and the data file of a second instance adds it with
`alter table ... add column if not exists`, so an existing database needs no
manual step. Rows written before have `block` set to null, which means the
row's `name` is the block. Block markers keep their format; a second instance
adds its block after the mode (`-- @bsb-block tickets@1 managed tasks`).

## Blocks contribute to approvals, pipelines and the other generic blocks

`approvals`, `bulk`, `pipelines`, `share-links` and `subjects` no
longer list the blocks that use them. Each consumer declares its part in
`contributes`, so the rendered SQL keeps the same branches in a new order.
Run `better-supabase upgrade`, then `better-supabase db diff` to write the
migration; the functions change only in the order of their `case` branches.
A second instance contributes only when its `uses` names the generic
instance. See [Contributions](/docs/blocks#contributions).

## Blocks attach to record types through on

The blocks that took `options.subjects` (`attachments`, `tags`, `versions`,
`trash`, `sla`, `pipelines` and the others) read `on` on the block entry
instead. `better-supabase upgrade` moves the value; `field-history` lists also
become `{ fields }`:

```ts title="better-supabase.config.ts"
// Before
"field-history": { options: { subjects: { deal: ["amount"] } } },
tags: { options: { subjects: ["deal"] } },
// After
"field-history": { on: { deal: { fields: ["amount"] } } },
tags: { on: ["deal"] },
```

A config that still sets `options.subjects` fails to render with the key to
move. An unset `on` still means every type in `config.records`, and doctor
(BS346) reports a type in `on` that `config.records` doesn't register. The
rendered SQL changes only in its comments. See
[Record types](/docs/blocks#record-types).

## Block clients are keyed by instance

`blocks.generated.ts` has an entry for each instance, and a second instance
gets its own renamed client (`ticketsBlock` for `tickets: { block: "tasks" }`)
that calls the instance's functions. Pass it to `defineBlocks` or
`createBlocks` under the instance key; `createBlocks` reads the entry under
that key before the one under the block's name, and refuses an entry that
installs another block. `createBlockClient` takes `instance` for the same
lookup.

Two blocks in one set may now provide the same port (`notifier`, `files`,
`attachments`, `workflows`, `mailer`). A block that consumes it takes the
provider its `blocks.<instance>.uses` names, else the one
`createBlocks({ ports: { notifier: "inbox" } })` names, and fails with both
keys when neither picks one.

Block queries share the table key space: `blockQueries` keys a read
`["bsb", instance, method, ...args]` instead of `["bs-block", ...]`, and its
meta is `{ bsTables: [instance] }` instead of `bsBlock`. One matcher,
`invalidateTables`, makes table and instance queries stale, and it takes the
methods to narrow to. The 0.15 codemod rewrites `"bs-block"` literals and
lists `bsBlock` reads for review.

## Block instances live on db

`.blocks(blockSet)` on the definition puts every instance on `db`, so a
hand-written `blocks(supabase, tenant)` helper is no longer needed.
`db.comments` runs through the same executor as the tables and acts in the
active organization; `db.$with({ tenant })` switches it. An instance whose
name a table already uses stays reachable at `db.$blocks.<instance>`, and
`db.$api(fn, args)` calls a function in the API schema:

```ts
// Before
const comments = blocks(supabase, tenant).comments;
await blocks(supabase).call("archive_customer", { id });
// After
const comments = db.comments;
await db.$api("archive_customer", { id });
```

`blocks.generated.ts` now exports `blocks`, the block for each instance
under its key, so `defineBlocks(blockConfig, blocks)` lists them all. With
`gen.hooks` set, `gen` also writes `hooks.ts` with a list and a record hook
per table ([Data hooks](/docs/frontend/data-hooks)).

The `requireTenant` option of `bsb.action`, `bsb.blockAction` and the oRPC
guard is `requireOrganization`, and so is the helper. The 0.15 codemod
renames both, and doctor reports BS418 for a `requireTenant` that is left.

## Record sections become record bindings

A block has one `record` binding instead of a `sections` map, and the binding
takes the block's key in your config, so a second instance gets its own
binding. `gen` writes one framework-neutral file per record type,
`records/<type>.ts` with `<type>Record`, instead of the `features/<subject>/`
folder, and no longer writes `navigation.generated.ts` or
`commands.generated.ts`. `gen.generateFeatures` is now `gen.recordTypes`.

```ts title="src/features/customers/customer-record.ts"
// Before
import { customerRecord } from "@/lib/supabase/features/customer/customer-server";
export const removeAttachment = bsb.sectionAction(/* ... */);
// After
import { customerRecord } from "@/lib/supabase/records/customer";
export const customerPage = bsb.record(customerRecord);
export const removeCustomerAttachments =
  customerPage.actions.attachments.remove;
```

`recordServer` and `bsb.sectionAction` are gone: `bsb.record(type)` returns
`load`, `timeline`, `actions` and `tags`. `load` takes `bindings` instead of
`sections`, its view and the controller snapshot hold `bindings`, and a
timeline entry names its `binding`. Build the client provider with
`createRecordProvider(customerRecord)`, and pass the record type to
`recordQueries`, whose factories live under `bindings`.

`better-supabase codemod 0.15` renames `generateFeatures`, the section
exports (`defineSection` to `defineRecordBinding`, `commentsSection` to
`commentsBinding`, `loadSections` to `loadBindings`, `sectionTag` to
`bindingTag`, `testSection` to `testRecordBinding` and the rest), and lists
the feature imports, `recordServer` and `sectionAction` calls for review. A
config that still sets `generateFeatures` fails with the key to use. See
[Record bindings](/docs/repository/record-bindings).

## Copied tables become instances

Four blocks dropped a table that copied another block:

| Block       | Before                                   | After                                                                              |
| ----------- | ---------------------------------------- | ---------------------------------------------------------------------------------- |
| `leases`    | `maintenance_requests` and its functions | a `tasks` instance with `names: { work_item: "maintenance_request" }`              |
| `passes`    | `pass_credit_entries`                    | ledger accounts per pass; `credits(passId)` reads them                             |
| `inventory` | its own `inventory_locations`, always    | `tables: { locations: null }` keeps stock at the `assets` locations                |
| `donations` | receipt numbers counted by the block     | a `donation_receipt` sequence it contributes to `numbering`, which it now requires |

`better-supabase upgrade` moves the data: pass credits post onto the ledger,
each organization's receipt sequence starts after its highest receipt, and
the old maintenance table is renamed to `maintenance_requests_legacy`. Copy
the maintenance rows you keep into the tasks instance before you generate
the next schema migration, which drops the legacy table.
`better-supabase codemod 0.15` lists the calls to `fileMaintenance`,
`updateMaintenance`, `listMaintenance` and `maintenanceRequestInputSchema`
for review. See [Leases](/docs/blocks/leases#maintenance-requests).

## Presets write instances

A preset object takes `instances`: `blocks` entries with `block`, `names`,
`options`, `tables`, `on` and `uses`. The `helpdesk` and `itsm` presets now
name the tasks block's work items `ticket` and its projects `issue`, so their
tables, functions and generated hooks say tickets; `property` adds a
`maintenance` instance of tasks. To keep the 0.14 names on a project that
uses one of these presets, set the names back in your own entry, which wins
over the preset's:

```ts title="better-supabase.config.ts"
export default defineConfig({
  preset: "helpdesk",
  blocks: { tasks: { names: { work_item: "work_item", project: "project" } } },
});
```

A design with a preset object that has `instances` is format 8
([Designs](/docs/presets/designs)). See
[Instances in a preset](/docs/presets#instances-in-a-preset).

## Block hooks are registry items

The `better-supabase/blocks/<block>/react`, `/vue`, `/svelte` and `/solid`
subpaths and `better-supabase/chat-sdk/react` are gone. Install a block's
React hooks into the app, then import them from there:

```sh
npx shadcn add @better-supabase/use-notifications
```

```ts
// before
import { useNotifications } from "better-supabase/blocks/notifications/react";
// after
import { useNotifications } from "@/hooks/use-notifications";
```

The hooks keep their names, options and return values, and the file is
yours to change. Vue, Svelte and Solid call `useBlockController` with the
block's controller and the options the old hook took:

```ts
// before
import { useOnboarding } from "better-supabase/blocks/onboarding/vue";
const { state } = useOnboarding({ client, checklist });
// after
import { createOnboardingController } from "better-supabase/blocks/onboarding";
import { useBlockController } from "better-supabase/vue";
const { state } = useBlockController(createOnboardingController, {
  client,
  checklist,
});
```

See [Block controllers](/docs/frontend/block-controllers#vue-svelte-and-solid).

## `scaffold screens` is removed

better-supabase no longer writes pages. The files an earlier
`scaffold screens` wrote are yours and keep working. For new screens, use the
table's generated data hooks (`useTasks`, `useTask`) and start from the
`record-*` [UI recipes](/docs/registry/ui-recipes#app-tables). Running
`bsb scaffold screens` now exits with a message that points there.

## One API layer

`defineApi` now publishes every table and every block instance unless you
say otherwise. If you passed `resources`, only those tables stay published,
so nothing changes there; without it, every table appears. Each table also
gets the contract verbs `page`, `count`, `aggregate` and `upsert` as
`POST /<table>/<verb>`, and `defineResource` and `bsb.resource` serve them.
Pass `verbs: false` to a resource to keep the 0.14 routes, `resources: false`
or `blocks: false` to leave a whole group out, and an action path that
collides with a verb (such as `POST /count`) needs another path.

`bsb.blockRouter` is removed. Serve the same model the document describes
with `bsb.router(api)`:

```ts
// before
const tasks = bsb.blockRouter(({ db }) => db.tasks, {
  name: "tasks",
  methods: ["list", "create"],
  meta: (route) => openapi({ method: route.method, path: route.path }),
});

// after
const api = defineApi(betterSupabase, {
  info,
  resources: false,
  blocks: { tasks: { verbs: ["list", "create"] } },
});
const { procedures } = bsb.router(api, { meta: openapi });
```

A method that takes more than one argument still takes a JSON array. See
[Serve the API](/docs/frameworks/orpc#serve-the-api).

## `scaffold api` is removed

`bsb scaffold api`, the `scaffold` group, the `tooling.scaffold` config key
and the `scaffold` step of `gen` are gone, because `bsb.router(api)` serves
the API without a generated module. Delete `lib/api.generated.ts` and the
route files `scaffold api` wrote, serve the router instead, and delete the
`scaffold` key from `better-supabase.config.ts`; a config that still sets it
fails to load with that message.

## Spec renderers live in `better-supabase/spec`

The `better-supabase/openapi`, `better-supabase/asyncapi`,
`better-supabase/arazzo` and `better-supabase/overlay` subpaths are removed.
Import the same names from `better-supabase/spec`:

```ts
// before
import { createOpenApi } from "better-supabase/openapi";
import { createAsyncApi } from "better-supabase/asyncapi";

// after
import { createAsyncApi, createOpenApi } from "better-supabase/spec";
```

`better-supabase codemod 0.15` rewrites these imports.

## Local-first runs on engines

PowerSync, SQLite and TanStack DB are engines behind the generated data
hooks, so a native screen reads `useCustomers(...)` like a web screen. Pass
the engine to the client:

```ts title="src/lib/supabase/client.native.ts"
import { powersyncEngine } from "better-supabase/powersync";

export const bsb = createNativeClient(betterSupabase, supabase, {
  engine: powersyncEngine(powersync, { connector, local: ["customers"] }),
});
```

`bsb.db` then runs on the device database for the tables in `local` and on
PostgREST for the rest. The upload connector replays through a client
without the engine, `bindClient(betterSupabase, supabase)`.

| 0.14                                                              | 0.15                                                                                 |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `watch(powersync, query, { tables: sqliteTables(...) })`          | a generated hook on `powersyncEngine`                                                |
| `useWatch` from `better-supabase/powersync/react`                 | a generated hook, or `defineDataHooks` for a list definition                         |
| `useSyncStatus(db)`, `useConflicts(connector)`                    | `useSyncStatus()`, `useConflicts()` from `better-supabase/react`                     |
| `betterSupabase.connect(powersyncExecutor(powersync))` as `local` | `bsb.db` with `powersyncEngine`                                                      |
| `better-supabase/expo-sqlite`, `expoSqliteExecutor`               | `sqliteEngine(expoSqliteDatabase(db))` from `better-supabase/sqlite`                 |
| `supabaseCollection` from `better-supabase/tanstack-db/supabase`  | `collectionOptions` and `tanstackDbEngine` from `better-supabase/tanstack-db`        |
| `realtime: true` on a collection                                  | `live: realtimeChanges(betterSupabase, supabase)` on `memoryEngine` or `queryEngine` |

`@supabase-labs/tanstack-db` is no longer a peer. `where` on every hook and
repository also takes a filter tree from a list query or a saved view. See
[Data hooks](/docs/frontend/data-hooks#engines),
[PowerSync](/docs/frontend/powersync) and [SQLite](/docs/frontend/sqlite).

## Installed blocks work together

Run `bsb upgrade` after updating. The new migrations change behavior where
two blocks are installed together:

- With `usage`, `ai-chat` records run tokens on `ai.input_tokens` and
  `ai.output_tokens`. If the app already meters tokens with
  `meterTelemetry` or `usageEntries`, set `meterUsage: false` on ai-chat so
  they are not counted twice.
- With `invoices`, `orders` creates and pays an invoice for every paid
  order. Orders paid before the upgrade keep no invoice.
- With `employees`, time entries and leave requests gain an `employee_id`
  column, filled for existing rows by the upgrade.
- The attachments data file now sets each of its buckets' `public` flag on
  every apply. A bucket you made public by hand in the dashboard turns
  private again unless you list it in `publicBuckets`, which needs
  `requireScan: false`.

## Flows become default automations

`better-supabase/flows` is removed, with `createFlows`, `defineFlow` and the
built-in flows. The blocks that fed another now ship
[default automations](/docs/blocks/automations#default-automations), rows
every organization copies and may turn off, edit or reset:

| 0.14 flow                | 0.15 default automation               | Action to register              |
| ------------------------ | ------------------------------------- | ------------------------------- |
| `conversationToWorkItem` | Open a task for each new conversation | `taskFromConversationAction`    |
| `applicationToEmployee`  | Preboard each hired candidate         | `employeeFromApplicationAction` |
| `quoteToOrder`           | Order each accepted quote (off)       | `orderFromQuoteAction`          |
| `bookingToEngagement`    | none: the bookings trigger does it    | none                            |

Run `bsb upgrade` so the automations module creates `rule_defaults`, then
replace `createFlows` in the outbox consumer with one action registry:

```ts
const actions = createActionRegistry([
  notifyAction(notifications),
  taskFromConversationAction({ clients: (tenant) => blocksFor(tenant) }),
]);
const sink = createRuleSink({
  rules: rulesAdmin,
  dispatcher: createRuleDispatcher({ actions }),
});
await outbox.consume("rules", sink);
```

`createRuleDispatcher` takes `actions` instead of `handlers`: wrap a custom
handler in `defineAction({ kind, title, run })`. `RuleActionHandler` and
`RuleActionCall` are now `ActionHandler` and `ActionCall`, and the hints
`RULE_ACTION_UNKNOWN` and `RULE_ACTION_INVALID` are now `ACTION_UNKNOWN` and
`ACTION_CONFIG_INVALID`. A `load` that returns `undefined` no longer skips
the event; it falls back to `eventTarget(event)`, so return early in the
consumer for events you don't want rules to see. A block you uninstall
leaves its default automations behind; turn them off.

## Workflows start from automations

Workflow-editor triggers of kind `event` are gone, with `triggers.onEvent`,
`builder.sink()`, `triggerMatches` and `triggerWhenProblem`. `bsb upgrade`
deletes the event triggers. Recreate each one as an automation whose trigger
is the event type, whose conditions replace `config.when`, and whose action is
`{ kind: "workflow", config: { definition } }`; register
`workflowAction(builder)` in the action registry.

The timers of the SLA, sequences, AI schedules, workflows and content blocks
run from the queue: schedule them with
`jobs.ensureSchedules(blockSchedules(blocks), { prefix: BLOCK_SCHEDULE_PREFIX })`
and drain the `block_ticks` queue with `blockTickHandler`
([Block timers](/docs/blocks/queue#block-timers)). A cron route that already
calls `sla.check()` or `sequences.runDue()` keeps working. The content
block's `publishSchedule` option is removed: its pg_cron job gives way to the
`content.publish` timer, so add `"content.publish": () => content.publishDue()`
to the tick handler.

## Presets turn on their default automations

The presets whose blocks feed each other now install the automations block:
`helpdesk` opens a ticket for each new conversation, `people` preboards each
hired candidate, `erp` orders each accepted quote, and `automation` starts
its workflows from automations. The presets with block timers or file
ingestion (`crm`, `helpdesk`, `cms`, `itsm`, `claims`, `ai`, `ai-chat` and
`ai-agents`) now install the queue. Run `bsb upgrade` after the upgrade, and
register the actions the wiring checklist lists.

The automations block takes `enable` and `disable`, lists of default
automation keys that change whether a new organization's copy starts on:

```ts title="better-supabase.config.ts"
export default defineConfig({
  preset: "erp",
  blocks: { automations: { options: { disable: ["quotes.quote_to_order"] } } },
});
```

## Blocks declare their wiring

Block manifests now declare their env keys, providers, routes and workers,
and `add` and `init` write the wiring: missing keys at the end of
`.env.example`, commented provider stubs in `providers.ts` next to
`blocks.generated.ts`, and a numbered checklist for the routes, the crons,
the block timers and the actions to register.
`add` also renders installed blocks again when a new block changes their SQL.

Two new doctor checks fail on an app that was already missing wiring:

- BS504: a required env key, such as `CRON_SECRET` for the outbox or
  `STRIPE_WEBHOOK_SECRET` for billing, that no env file lists. Add the key to
  `.env.example` and set it.
- BS505: enrichment or mail-sync installed with no provider passed. Pass it
  where you build the blocks:

```ts title="src/lib/supabase/providers.ts"
import { peopleDataLabsEnrichment } from "better-supabase/blocks/enrichment";
import { gmailMail, outlookMail } from "better-supabase/blocks/mail-sync";

import { blocks } from "./blocks.generated.ts";

export const providers = {
  enrichment: blocks.enrichment.with({
    provider: peopleDataLabsEnrichment({
      apiKey: process.env["PDL_API_KEY"] ?? "",
    }),
  }),
  "mail-sync": blocks["mail-sync"].with({
    providers: [gmailMail(), outlookMail()],
  }),
} satisfies Partial<typeof blocks>;
```

Then spread it: `defineBlocks(blockConfig, { ...blocks, ...providers })`.
Run `bsb add <block>` for an installed block to have the stubs and keys
written for you.

## Doctor finds what is left

`better-supabase doctor` reports BS418 for app code that still imports a
renamed block subpath or plugin subpath, an export named after a renamed
block, a spec subpath, a `blockRouter` call, or a record feature, leases
maintenance, pass credit or local-first API that 0.15 removed. A config key that moved fails to load with its new place, so after
the codemod a clean doctor run means nothing from 0.14 is left.

## Upgrade order

Upgrade in this order, so each step starts from code that loads:

1. Install better-supabase 0.15.
2. Run `npx better-supabase codemod 0.15` and review the diff, with its list
   of calls to check by hand.
3. Run `npx better-supabase upgrade`, then generate and apply the migration
   (`supabase db schema declarative sync`, or `better-supabase db diff`).
4. Copy the rows you keep from `maintenance_requests_legacy` into the tasks
   instance before the next schema migration drops it.
5. Run `npx better-supabase gen`, which writes the record types and the
   instance-keyed `blocks.generated.ts`.
6. Run `npx better-supabase doctor` and fix each BS418 finding, then your
   typecheck and tests.

The same steps work as a prompt for a coding agent: give it this page, the
codemod's review list and the doctor output, and ask it to work through the
steps in order and stop when doctor and the typecheck are clean.
