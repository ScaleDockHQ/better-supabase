title: Naming
description: The names better-supabase uses for definitions, instances, files, types and block names, and the renames from earlier versions.

Every app has one definition and one runtime instance per side. The docs,
the examples and the files `better-supabase init` writes all use the same
names, so code copied from one place works in another.

## Glossary

Each concept has one name. The renames land in phases listed on the
[roadmap](/docs/roadmap#planned-block-instances-and-one-data-contract);
until a phase ships, the code still exports the name in the Replaces
column, and each phase ships a codemod for its renames.
[ADR 0093](https://github.com/ScaleDockHQ/better-supabase/blob/main/docs/decisions/0093-block-instances-and-one-data-contract.md)
records the decision.

| Term          | Meaning                                                                                | Replaces                           |
| ------------- | -------------------------------------------------------------------------------------- | ---------------------------------- |
| block         | the unit you install: tables, functions, a client and generated code                   | module, SQL module, kit            |
| core block    | a block installed once per project (memberships, permissions, outbox, queue, audit)    | foundation block                   |
| instance      | one named install of a block, with its own tables                                      | nothing                            |
| record type   | a kind of row other blocks attach to (`RecordRef`, config `subjects`)                  | subject, `SubjectRef`              |
| names         | the nouns an instance uses (`blocks.<name>.names`)                                     | entities                           |
| tables        | the app's own tables (SQL in `supabase/schemas`)                                       | `tables`                           |
| tenant        | the account that owns data, in every library name (`auth.tenant`, `requireTenant`)     | organization (0.15 to 0.31)        |
| organization  | what the examples and the `organizations` block call a tenant in the UI and its tables | nothing                            |
| preset        | a named selection of blocks                                                            | nothing                            |
| design        | the JSON document Create writes, the one format for presets                            | preset codes                       |
| registry item | an installable file: a page, widget, route or recipe                                   | screens, glue                      |
| provider      | a versioned interface your app implements (`ShippingProvider`)                         | carrier, backend                   |
| adapter       | a framework integration (config `adapters`)                                            | integration, bridge                |
| plugin        | the versioned repository extension interface for third parties                         | the built-in plugins               |
| controller    | headless state for a widget or a list                                                  | nothing                            |
| hook          | a framework wrapper around a controller or a query                                     | nothing                            |
| engine        | what runs the hooks: TanStack Query, the controllers, PowerSync, TanStack DB, SQLite   | separate client data layers        |
| client        | the one better-supabase client, named `bsb`; instances and tables are properties on it | `bs`, transport                    |
| callbacks     | the `before_*` and `after_*` functions of a block (`blocks.<name>.callbacks`)          | block hooks                        |
| owner         | who owns a row: `tenant`, `user` or `none` (`blocks.<name>.scope`)                     | mode                               |
| event         | an outbox CloudEvent; in-process `on` handlers are listeners                           | nothing                            |
| automation    | a trigger and actions an organization can edit                                         | rules, flows                       |
| workflow      | code that runs durably                                                                 | nothing                            |
| schedule      | a timer on the queue                                                                   | reminders, SLA and sequence timers |

The data verbs are the same on every table and every instance: `list`,
`page`, `get`, `count` and `aggregate` read; `create`, `update`, `upsert`
and `delete` write; `attach` and `detach` link a row to a record. "Feature"
only means a feature flag.

## Definition and instances

`betterSupabase` is the definition from `createSupabase`. It holds the schema
and the configuration, no secrets, and is safe to import anywhere.

`bsb` is the runtime instance an adapter creates from it: `createNext`,
`createServer`, `createClient`, `createHono`, `createOrpc`, `createEdge` or
`createMcp`. Each file that creates one exports it as `bsb`, so a call reads
the same in every framework:

```ts
const { db } = await bsb.context(); // Next.js Server Component
app.use("/api/*", bsb.middleware()); // Hono
Deno.serve(bsb.handler(fn)); // Edge Function
```

## Files

The definition and the instances live in `lib/supabase/`, the layout
Supabase uses for its own `utils/supabase/server.ts` and `client.ts`:

| File                        | Exports          | Runs on                                         |
| --------------------------- | ---------------- | ----------------------------------------------- |
| `lib/supabase/index.ts`     | `betterSupabase` | both, imported as `@/lib/supabase`              |
| `lib/supabase/server.ts`    | `bsb`            | the server; Next.js adds `import "server-only"` |
| `lib/supabase/client.ts`    | `bsb`            | the browser                                     |
| `lib/supabase/generated.ts` | `schema`         | both, written by `better-supabase gen`          |

Hono and oRPC starters create `bsb` in the app's entry (`src/server.ts`,
`src/router.ts`), which only runs on the server. Edge Functions import the
definition from `supabase/functions/_shared/supabase.ts` and create `bsb` in
the function's own `server.ts`.

## Types

- The adapter factories return `Better<Adapter>`: `createNext` returns
  `BetterNext`, `createClient` returns `BetterClient`, `createPostgres`
  returns `BetterPostgres`, `createQueries` returns `BetterQueries`.
- Options are `<Thing>Options`: `ClientOptions`, `SupabaseOptions`,
  `QueriesOptions`, `MiddlewareOptions`.
- Acronyms in names are written as words: `toOrpcError`, `createOpenApi`.
- Members that sit next to your table names start with `$` so a table can't
  shadow them: `db.$table(name)`, `repository.$tableName`, `queries.$key`.

Supabase's own cookie and header names keep their `sb-` prefix
(`sb-<project>-auth-token`); those belong to `@supabase/ssr`, not to the
library.

## Block names

Every block names its entities, tables, permission keys, events, hint codes
and functions by one convention, so you can guess a name from the block and
the noun.
[ADR 0130](https://github.com/ScaleDockHQ/better-supabase/blob/main/docs/decisions/0130-one-naming-convention-for-blocks.md)
records the decision. 0.46 renamed the permission keys and 0.47 the entity
keys, subject types, hint codes, functions and event types. 0.47 also renamed the module
tables (`work_items` becomes `tasks`, `rules` becomes `automations`): the
upgrade migration renames each table with its indexes, policies and
constraints, so no row moves. The foreign key columns that point at a task or
an activity (`work_item_id`, `engagement_id`) become `task_id` and
`activity_id` the same way.

1. Block names are kebab-case. Existing block names do not change.
2. An entity key equals its `singular`. Entity keys are unique across all
   blocks. When the noun is generic (`document`, `request`, `entry`,
   `policy`, `task`, `type`, `location`, `key`, `link`, `view`, `field`,
   `node`, `server`, `snapshot`, `definition`, `project`) or another block
   uses it, the block noun comes first: `knowledge_document`,
   `leave_request`, `drive_node`. The block that owns the plain noun keeps
   it (`documents` keeps `document`, `tasks` keeps `task` and `project`).
3. A table is the plural of its entity in snake*case (`compliance_policy`
   becomes `compliance_policies`). A table that is not an entity (a link,
   log or history table) starts with its entity's singular:
   `task_assignees`, `case_actions`. Uncountable nouns stay singular:
   `control_evidence`, `webhook_inbox`, `subject_user_state`,
   `chat_state_cache`, `scim_sync_log`, `ai_message_feedback`,
   `ai_model_catalog`, `attachment_cleanup`, `custom_emoji`. Acronym
   prefixes of a standard stay (`ssf*\_`, `scim\_\_`, `oauth\_\*`).
4. `subject` is the SQL term and `record` is the docs term. The columns
   `subject_type` and `subject_id`, the `subjects` block and the
   `subject.*` events keep their names.
5. A permission key is `<area>.<verb>`, where the area is the block name in
   snake_case. Exceptions: `messaging`, `comments` and `channels` share
   `messages.*` because they share one table (`channels` keeps `channels.*`
   for channel settings); `organizations` owns `organization.*`,
   `members.*` and `platform.*`; `platform.*` stays for platform-wide
   actions.
6. The permission verbs are `read` (see), `write` (create and change
   records), `delete` (only when deleting differs from writing), `manage`
   (configure the block, act on everyone's records), and domain verbs
   (`approve`, `submit`, `review`, `acknowledge`, `collect`, `assign`,
   `grant`, `assess`, `close`, `invite`, `record`). There is no `view`,
   `edit` or `admin`, and a key never has three parts:
   `custom_fields.read_sensitive`, not `custom_fields.read_sensitive`.
7. An event type is `<entity singular>.<past tense verb>`, where the entity
   is the one that changed, whichever block wrote it. The lifecycle verbs
   are `created`, `updated`, `deleted`, `archived`, `restored` and `purged`.
   No event is named `saved` (it is `created` or `updated`), `removed` (it
   is `deleted`), `upserted` or `<attribute>_set` (it is
   `<attribute>_changed`). Payload keys are camelCase and carry
   `organizationId` when the event has a tenant.
8. A hint code is `<ENTITY>_<REASON>` in upper snake case, from the entity
   singular: `CONTROL_FORBIDDEN`, `TASK_NOT_FOUND`.
9. SQL functions take the entity singular: `create_<entity>`,
   `update_<entity>`, `get_<entity>`, `list_<entities>`, `delete_<entity>`,
   and domain verbs (`close_case`, `assess_risk`). Hooks are
   `before_<entity>_<action>` and `after_<entity>_<action>`.
10. Exports are `create<Pascal>`, `<camel>Block` and `<camel>Events`, with
    acronyms written as words: `createOauthServer`.
11. A block's docs page is titled with its plain name in title case,
    sometimes with a short qualifier ("Audits and inspections", "Usage and
    quotas"), and its first sentence names the block by its block name. The
    URL is `/docs/blocks/<block-name>`.
12. The manifest's `category` decides which docs folder the page sits in.

When you rename a block's nouns with `blocks.<name>.names`, its tables,
functions, events and permission keys follow the new singular; see
[Typed blocks](/docs/blocks/typed-blocks).

## Renames

`packages/better-supabase/api/naming.json` is the source of truth for names.
It holds the rules and the rename table below, and
[ADR 0246](https://github.com/ScaleDockHQ/better-supabase/blob/main/docs/decisions/0246-one-naming-convention.md)
records the decision. `pnpm check:naming` fails when a renamed name returns or
when code breaks a rule, and the old names have no alias. Run
[`better-supabase codemod naming`](/docs/cli/codemod) to rename them in your
app, and `better-supabase doctor` (BS260) to find the ones left.

| env      | `BEFORE_USER_CREATED_SECRET`  | `BETTER_SUPABASE_BEFORE_USER_CREATED_SECRET`          | 0.54  |

The rules:

- Environment variables the library or CLI reads start with `BETTER_SUPABASE_`.
  The platform's own names (`SUPABASE_*`, `NEXT_PUBLIC_*`, `EXPO_PUBLIC_*`,
  `PUBLIC_*`, `VERCEL_*`, `DATABASE_URL`) keep theirs.
- An exported type ends in `Options`, `Config`, `Decision` or `Error`, never in
  `Settings`, `Args` or `Failure`. `naming.json` keeps an allowlist for a
  violation that is not renamed yet, and the check fails when a listed name
  stops violating. The type list is empty.
- A hint code is `<ENTITY>_<REASON>`, and a core hint carries its core noun
  (`AUDIT_CHAIN_SIGNER`, `TABLE_APPEND_ONLY`, `PERIOD_CLOSED`).
- The helper functions live in `better_supabase`. The `bsb` schema is gone.
- Doctor codes are `BS` and three digits, never lower case.
- A subpath is `better-supabase/<area>` or `better-supabase/<area>/<variant>`.
