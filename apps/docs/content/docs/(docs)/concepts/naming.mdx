Every app has one definition and one runtime instance per side. The docs,
the examples and the files `better-supabase init` writes all use the same
names, so code copied from one place works in another.

## Glossary

Each concept has one name. The renames land in phases listed on the
[roadmap](/docs/roadmap#planned-block-instances-and-one-data-contract);
until a phase ships, the code still exports the name in the Replaces
column, and each phase ships a codemod for its renames.
[ADR 0093](https://github.com/ScaleDockHQ/better-supabase/blob/main/docs/decisions/0093-block-instances-and-one-data-contract.md)
records the decision.

| Term          | Meaning                                                                                | Replaces                           |
| ------------- | -------------------------------------------------------------------------------------- | ---------------------------------- |
| block         | the unit you install: tables, functions, a client and generated code                   | module, SQL module, kit            |
| core block    | a block installed once per project (memberships, permissions, outbox, queue, audit)    | foundation block                   |
| instance      | one named install of a block, with its own tables                                      | nothing                            |
| record type   | a kind of row other blocks attach to (`RecordRef`, config `subjects`)                  | subject, `SubjectRef`              |
| names         | the nouns an instance uses (`blocks.<name>.names`)                                     | entities                           |
| tables        | the app's own tables (SQL in `supabase/schemas`)                                       | `tables`                           |
| tenant        | the account that owns data, in every library name (`auth.tenant`, `requireTenant`)     | organization (0.15 to 0.31)        |
| organization  | what the examples and the `organizations` block call a tenant in the UI and its tables | nothing                            |
| preset        | a named selection of blocks                                                            | nothing                            |
| design        | the JSON document Create writes, the one format for presets                            | preset codes                       |
| registry item | an installable file: a page, widget, route or recipe                                   | screens, glue                      |
| provider      | a versioned interface your app implements (`ShippingProvider`)                         | carrier, backend                   |
| adapter       | a framework integration (config `adapters`)                                            | integration, bridge                |
| plugin        | the versioned repository extension interface for third parties                         | the built-in plugins               |
| controller    | headless state for a widget or a list                                                  | nothing                            |
| hook          | a framework wrapper around a controller or a query                                     | nothing                            |
| engine        | what runs the hooks: TanStack Query, the controllers, PowerSync, TanStack DB, SQLite   | separate client data layers        |
| client        | the one better-supabase client, named `bsb`; instances and tables are properties on it | `bs`, transport                    |
| callbacks     | the `before_*` and `after_*` functions of a block (`blocks.<name>.callbacks`)          | block hooks                        |
| owner         | who owns a row: `tenant`, `user` or `none` (`blocks.<name>.scope`)                     | mode                               |
| event         | an outbox CloudEvent; in-process `on` handlers are listeners                           | nothing                            |
| automation    | a trigger and actions an organization can edit                                         | rules, flows                       |
| workflow      | code that runs durably                                                                 | nothing                            |
| schedule      | a timer on the queue                                                                   | reminders, SLA and sequence timers |

The data verbs are the same on every table and every instance: `list`,
`page`, `get`, `count` and `aggregate` read; `create`, `update`, `upsert`
and `delete` write; `attach` and `detach` link a row to a record. "Feature"
only means a feature flag.

## Block naming

Every block follows one convention, recorded in
[ADR 0129](https://github.com/ScaleDockHQ/better-supabase/blob/main/docs/decisions/0129-one-naming-convention-for-blocks.md).
The block name is the stem for everything a block installs, so one word
finds the tables, the permissions, the events, the errors and the docs.

| Thing            | Rule                                                                                     | Example                                 |
| ---------------- | ---------------------------------------------------------------------------------------- | --------------------------------------- |
| block            | kebab-case, unchanged                                                                    | `service-accounts`                      |
| entity key       | its singular, unique across blocks; a generic noun takes the block noun as a prefix      | `compliance_policy`, `drive_node`       |
| table            | the plural of its entity; a link, log or history table starts with the entity's singular | `compliance_policies`, `task_assignees` |
| permission key   | `<area>.<verb>`, area is the block name in snake_case                                    | `compliance.read`                       |
| permission verbs | `read`, `write`, `delete`, `manage`, plus domain verbs; never `view`, `edit` or `admin`  | `cases.close`, `risks.assess`           |
| event type       | `<entity singular>.<past tense verb>`                                                    | `compliance_policy.updated`             |
| hint code        | `<ENTITY>_<REASON>`                                                                      | `CONTROL_FORBIDDEN`                     |
| SQL function     | `create_<entity>`, `update_<entity>`, `get_<entity>`, `list_<entities>`                  | `create_task`                           |
| docs page        | the block's plain name in title case, at `/docs/blocks/<block-name>`                     | "Tasks"                                 |

Event verbs are `created`, `updated`, `deleted`, `archived`, `restored` and
`purged`; a save emits `created` or `updated`, a removal emits `deleted`,
and a changed attribute emits `<attribute>_changed`. `subject` is the SQL
word and `record` the docs word, and the columns `subject_type` and
`subject_id` keep their names.

## Definition and instances

`betterSupabase` is the definition from `defineSupabase`. It holds the schema
and the configuration, no secrets, and is safe to import anywhere.

`bsb` is the runtime instance an adapter creates from it: `createNext`,
`createServer`, `createClient`, `createHono`, `createOrpc`, `createEdge` or
`createMcp`. Each file that creates one exports it as `bsb`, so a call reads
the same in every framework:

```ts
const { db } = await bsb.context(); // Next.js Server Component
app.use("/api/*", bsb.middleware()); // Hono
Deno.serve(bsb.handler(fn)); // Edge Function
```

## Files

The definition and the instances live in `lib/supabase/`, the layout
Supabase uses for its own `utils/supabase/server.ts` and `client.ts`:

| File                        | Exports          | Runs on                                         |
| --------------------------- | ---------------- | ----------------------------------------------- |
| `lib/supabase/index.ts`     | `betterSupabase` | both, imported as `@/lib/supabase`              |
| `lib/supabase/server.ts`    | `bsb`            | the server; Next.js adds `import "server-only"` |
| `lib/supabase/client.ts`    | `bsb`            | the browser                                     |
| `lib/supabase/generated.ts` | `schema`         | both, written by `better-supabase gen`          |

Hono and oRPC starters create `bsb` in the app's entry (`src/server.ts`,
`src/router.ts`), which only runs on the server. Edge Functions import the
definition from `supabase/functions/_shared/supabase.ts` and create `bsb` in
the function's own `server.ts`.

## Types

- The adapter factories return `Better<Adapter>`: `createNext` returns
  `BetterNext`, `createClient` returns `BetterClient`, `createPostgres`
  returns `BetterPostgres`, `createQueries` returns `BetterQueries`.
- Options are `<Thing>Options`: `ClientOptions`, `SupabaseOptions`,
  `QueriesOptions`, `MiddlewareOptions`.
- Acronyms in names are written as words: `toOrpcError`, `createOpenApi`.
- Members that sit next to your table names start with `$` so a table can't
  shadow them: `db.$table(name)`, `repository.$tableName`, `queries.$key`.

Supabase's own cookie and header names keep their `sb-` prefix
(`sb-<project>-auth-token`); those belong to `@supabase/ssr`, not to the
library.

## Renames

In 0.36 the refresh options name what they check, the session provider
prop takes a session or a promise, and the server's client for an auth state
is named after `createContextClient`.
[`better-supabase codemod 0.37`](/docs/cli/codemod) renames them; the
[0.35 to 0.37 guide](/docs/migration/0.35-to-0.37) has the details.

| Before (0.35)                                 | After (0.36)                                  |
| --------------------------------------------- | --------------------------------------------- |
| `refresh: "navigation"`                       | `refresh: true`                               |
| `verifySession: "navigation"`                 | `verifySession: "document"`                   |
| `<SessionProvider sessionPromise={...}>`      | `<SessionProvider session={...}>`             |
| `cacheLife({ stale: sessionStale(session) })` | `bsb.cached()` (stale 300 seconds by default) |
| `bsb.supabaseFor(auth, headers?)`             | `bsb.contextClient(auth, headers?)`           |
| `clearVerifiedTokens()` (internal)            | `clearKeyCaches()` (internal)                 |

From 0.32 the auth names follow supabase-js and Next.js.
[`better-supabase codemod 0.32`](/docs/cli/codemod) renames them and lists the
lines it can't rename safely; the
[0.31 to 0.32 guide](/docs/migration/0.31-to-0.32) has the details.

| Before (0.31)                                    | After (0.32)                                            |
| ------------------------------------------------ | ------------------------------------------------------- |
| `auth.organization`, `requireOrganization`       | `auth.tenant`, `requireTenant`                          |
| `bsb.session()`, `bsb.getRequestSession()`       | `bsb.claims()`, `bsb.getClaims()`                       |
| `bsb.contextForSession()`                        | `bsb.contextFromSession()`                              |
| `session.profile`                                | `session.userMetadata`                                  |
| caller kinds `anon`, `service`                   | `none`, `secret`                                        |
| `bsb.signIn()`                                   | `bsb.signInWithPassword()`                              |
| `bsb.authorizeUrl()`, `bsb.exchangeCode()`       | `bsb.signInWithOAuth()`, `bsb.exchangeCodeForSession()` |
| `endedSession`, `checkSession`                   | `verifySession`                                         |
| `refreshSkewSeconds`, `expiredPrefetch`          | `leeway`, `onExpiredPrefetch`                           |
| `bsb.invalidateSession()`, `bsb.forgetSession()` | `bsb.evictSession()`                                    |
| `bsb.cacheTag()`, `bsb.cacheTags()`              | `bsb.tag()`, `bsb.tags()`                               |

From 0.15 the runtime instance is `bsb`, not `bs`, matching the CLI's short
name; [`better-supabase codemod 0.15`](/docs/cli/codemod) renames it.

These names changed in 0.4. There are no aliases:
[`better-supabase codemod 0.4`](/docs/cli/codemod) renames the imports,
members and the provider prop, lists the lines it can't rename safely, and the
compiler points out anything left.

| Before                                           | After                                           |
| ------------------------------------------------ | ----------------------------------------------- |
| `const sb = defineSupabase(schema)`              | `const betterSupabase = defineSupabase(schema)` |
| `const next = createNext(sb)`                    | `const bs = createNext(betterSupabase)`         |
| `const browser = createBrowser(sb)`              | `const bs = createClient(betterSupabase)`       |
| `src/lib/supabase.ts`                            | `src/lib/supabase/index.ts`                     |
| `src/lib/supabase.server.ts`                     | `src/lib/supabase/server.ts`                    |
| `src/lib/supabase.browser.ts`                    | `src/lib/supabase/client.ts`                    |
| `next.server()`                                  | `bs.context()`                                  |
| `next.serverFor(session, { token })`             | `bs.contextForSession(session, { token })`      |
| `BetterBrowser`, `BrowserOptions`, `BrowserAuth` | `BetterClient`, `ClientOptions`, `ClientAuth`   |
| `<BetterSupabaseProvider browser={browser}>`     | `<BetterSupabaseProvider client={bs}>`          |
| `client.sb`                                      | `client.betterSupabase`                         |
| `BetterEnv` (Hono)                               | `HonoEnv`                                       |
| `bs.handle()` (Hono)                             | `bs.handler()`                                  |
| `bs.toORPCError(error)` (oRPC)                   | `bs.toOrpcError(error)`                         |
| `HandlerOptions` (Edge)                          | `MiddlewareOptions`                             |
| `mcp.handler`                                    | `bs.endpoint`                                   |
| `Queries`, `CreateQueriesOptions`                | `BetterQueries`, `QueriesOptions`               |
| `queries.key`                                    | `queries.$key`                                  |
| `Postgres`                                       | `BetterPostgres`                                |
| `DefineSupabaseOptions`                          | `SupabaseOptions`                               |
| `repository.$table`                              | `repository.$tableName`                         |
| `{ sb }` in `testExecutor` and the test plugin   | `{ betterSupabase }`                            |

`createHono`, `createOrpc`, `createEdge` and `createMcp` now keep the claims
and profile types from `.claims()` and `.userMetadata()`, so `auth.claims`
is typed in those adapters too. Code that parsed the claims again to read a
role can drop the parse.

## Block subjects and tenants (0.14)

From 0.14, a block method names the record it works on with one
`SubjectRef`, `{ type, id }`, and reads the organization from the block's
`tenant` option. Rows name the record `subject`. The full list of calls is in
the [0.13 to 0.14 guide](/docs/migration/0.13-to-0.14).

| Old                                                         | New                                         |
| ----------------------------------------------------------- | ------------------------------------------- |
| `organizationId, subjectType, subjectId` method arguments   | `subject` (`{ type, id }`), first           |
| `organizationId` method argument                            | the block's `tenant` option                 |
| `row.subjectType`, `row.subjectId`                          | `row.subject.type`, `row.subject.id`        |
| `subjectIds` in batch methods, results keyed by id          | `subjects`, results keyed `type:id`         |
| `useComments({ organizationId, subjectType, subjectId })`   | `useComments({ subject })`                  |
| `useReactions({ organizationId, subjectType, subjectIds })` | `useReactions({ subjects })`                |
| `useTagInput({ organizationId, subjectType, subjectId })`   | `useTagInput({ subject, kind })`            |
| a `lib/blocks.ts` wrapper per block                         | `createBlockClient(ctx.db, block, options)` |
