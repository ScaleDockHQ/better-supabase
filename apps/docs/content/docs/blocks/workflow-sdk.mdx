---
title: Workflow SDK
description: Run the Workflow SDK on Supabase with a World over Postgres and Supabase Queues, and start runs, resume hooks and protect routes as the signed-in user.
---

The Workflow SDK (`workflow`) needs a World: the storage and queue its runs,
steps, hooks and events live in. `better-supabase/workflow-sdk/world` is a
World on your Supabase database. Its tables sit in a `workflow` schema that
only the service role reads, its messages wait in a
[jobs](/docs/blocks/jobs) queue, and every run is copied into the
[workflows](/docs/blocks/workflows) block's `workflow_runs`, so members
list and follow runs through RLS. `better-supabase/workflow-sdk` has the
helpers that start runs and resume hooks as the signed-in user.

```bash
better-supabase add workflow-sdk-world   # adds workflows and jobs as well
pnpm add workflow @workflow/world @workflow/world-postgres pg
```

The world entry imports `pg` and Node built-ins, so it runs on Node, not on
edge runtimes. The helpers in `better-supabase/workflow-sdk` import only
`workflow`.

## Selecting the World

```ts title="next.config.ts"
import { withWorkflow } from "workflow/next";

export default withWorkflow(nextConfig);
```

```bash title=".env"
WORKFLOW_TARGET_WORLD=better-supabase/workflow-sdk/world
SUPABASE_DB_URL=postgresql://postgres:postgres@127.0.0.1:54322/postgres
```

The entry's default export is `createWorld()`, which reads its options from
the environment, so the SDK and tools that select a World by package name
load it without code. To build one yourself, call `createSupabaseWorld`:

```ts title="lib/world.ts"
import { createSupabaseWorld } from "better-supabase/workflow-sdk/world";

export const world = createSupabaseWorld({
  connectionString: process.env.SUPABASE_DB_URL,
  delivery: "pg_net",
});
```

| Variable                                                   | Option                     | Default                                                                                     |
| ---------------------------------------------------------- | -------------------------- | ------------------------------------------------------------------------------------------- |
| `WORKFLOW_POSTGRES_URL`, `SUPABASE_DB_URL`, `DATABASE_URL` | `connectionString`         | the first one set                                                                           |
| `WORKFLOW_DELIVERY`                                        | `delivery`                 | `poll`                                                                                      |
| `WORKFLOW_FLOW_URL`                                        | `flowUrl`                  | `WORKFLOW_LOCAL_BASE_URL` or `http://localhost:$PORT`, plus `/.well-known/workflow/v1/flow` |
| `WORKFLOW_DELIVERY_SECRET`                                 | `deliverySecret`           | the Vault secret `workflow_delivery_secret`                                                 |
| `WORKFLOW_ENCRYPTION_KEY`                                  | `encryptionKey`            | the Vault secret `workflow_encryption_key`                                                  |
| `WORKFLOW_DELIVERY_QUEUE`                                  | `queue`                    | `workflow_deliveries`                                                                       |
| `WORKFLOW_POSTGRES_WORKER_CONCURRENCY`                     | `concurrency`              | 50                                                                                          |
| `WORKFLOW_POSTGRES_POLL_INTERVAL_MS`                       | `pollInterval`             | 250                                                                                         |
| `WORKFLOW_POSTGRES_MAX_CONNECTIONS`                        | `maxConnections`           | 10                                                                                          |
| `WORKFLOW_POSTGRES_CONNECTION_TIMEOUT_MS`                  | `connectionTimeout`        | 30000                                                                                       |
| `WORKFLOW_POSTGRES_IDLE_TIMEOUT_MS`                        | `idleTimeout`              | 10000                                                                                       |
| `WORKFLOW_POSTGRES_STATEMENT_TIMEOUT_MS`                   | `statementTimeout`         | 30000                                                                                       |
| `WORKFLOW_POSTGRES_IDLE_IN_TRANSACTION_TIMEOUT_MS`         | `idleInTransactionTimeout` | 15000                                                                                       |

The pool holds at most `maxConnections` connections. A delivery that finds
them all busy waits up to `connectionTimeout` for one, so a burst queues
instead of failing. `statementTimeout` ends a query that runs longer, and
`idleInTransactionTimeout` ends a transaction left open with no query, so a
stuck worker can't hold row locks. Pass `events` (`betterSupabase.events`)
or a `logger` to see errors of idle pooled connections; without either, the
World logs them to the console. They never throw, so a dropped connection
can't crash the process.

The World speaks the `@workflow/world` protocol in
`WORKFLOW_WORLD_PROTOCOL` and stores its tables in the shape of the
`@workflow/world-postgres` version in `WORLD_POSTGRES_VERSION`. It passes
the `@workflow/world-testing` suite.

## Delivery

The SDK hands each step and each workflow turn to the queue, and the queue
posts it to the flow route that `withWorkflow` adds.

| Mode             | Who posts                                                              | Use it on                                     |
| ---------------- | ---------------------------------------------------------------------- | --------------------------------------------- |
| `poll` (default) | the World, in the process that queues: it claims jobs and posts them   | a server, a container, `next dev`             |
| `pg_net`         | `dispatch_workflow_deliveries()` on a pg_cron schedule, through pg_net | serverless hosts with no long-running process |

For `pg_net`, set `blocks.workflow-sdk-world.options.delivery` to
`pg_net` (the data file then schedules the dispatcher every
`options.schedule`, `1 seconds` by default) and store the route and a
secret in Vault:

```sql
select vault.create_secret('https://app.example.com/.well-known/workflow/v1/flow', 'workflow_flow_url');
select vault.create_secret(encode(extensions.gen_random_bytes(32), 'hex'), 'workflow_delivery_secret');
```

In poll mode, the first message a process queues starts its poller, and
`world.start()` also queues the runs that were active when the last
process stopped. Call it once at startup, for example from
`instrumentation.ts`.

Each delivery is signed with the secret (`x-bs-signature`, an HMAC-SHA256
over the time, the job and the body). The World's queue handler refuses an
unsigned or stale request with a 401 Problem Details response, and
completes or fails the job itself, so a delivery whose response is lost runs
again after its lease. Leave the flow route out of your proxy's matcher: the
World checks the signature, not a session.

Poll mode needs the secret too, unless `NODE_ENV` is `development` or
`test`: without one, the flow route answers every delivery with 401. Store
it in Vault as above or set `WORKFLOW_DELIVERY_SECRET`. A secret or key that
isn't in Vault counts as not set; a Vault read that fails is not cached, so
the next delivery reads again, and until then the route answers 503 and run
data can't be read or written.

A poll delivery that the flow route doesn't answer within `deliveryTimeout`
seconds (300 by default, at least `lease`) is aborted and retried. The
poller extends the job's lease only while the request is open.

## Encryption

With a 32-byte master key (base64 or hex) in `encryptionKey` or the Vault
secret `workflow_encryption_key`, the World derives an AES-256 key per run
with HKDF-SHA256, and the SDK stores the run's inputs, outputs and step
data encrypted. Without one, they are stored as JSON in the `workflow`
schema. When Vault can't be read, the World doesn't fall back to
unencrypted data: the read fails, and the next one tries Vault again.

## Starting runs as the user

```ts title="app/invoices/actions.ts"
"use server";

import { startFor } from "better-supabase/workflow-sdk";

import { approveInvoice } from "@/workflows/approve-invoice";

export async function requestApproval(invoiceId: string) {
  const ctx = await server.context();
  const run = await startFor(ctx, approveInvoice, [invoiceId], {
    idempotencyKey: `approve:${invoiceId}`,
  });
  return run.runId;
}
```

`startFor` starts the run with the `bs.tenant` and `bs.actor` attributes
of the caller, which the World copies into `workflow_runs.tenant_id` and
`actor_id`. Pass `subject: { type: "deal", id }` to store the record the
run belongs to (the `bs.subject` attribute, copied into `subject_type` and
`subject_id`; see [runs on a record](/docs/blocks/workflows#runs-on-a-record)). With `idempotencyKey`, it returns the run that already has the
key instead of starting another. To act as the user inside a step, pass
`workflowContext(ctx)` as an argument and call `bs.forContext(context)` in
the step. It keeps the actor and tenant and drops the claims, so no token
ends up in the run's stored state. A delegated token's `client_id`,
`scope`, `authorization_details` and `act` chain are the exception: they
stay, so a run an OAuth or MCP client started keeps that client's scopes
(see [Actor and tenant](/docs/blocks/jobs#actor-and-tenant)).

### Tickets

`startFor(ctx, workflow, args, { ticket })` stores an opaque ticket from
your authorization provider as the `bs.ticket` attribute. Pass
`workflowContext(ctx, { ticket })` as an argument too: inside a step,
`bs.forContext` resolves the ticket through the provider's
`tickets.subject` hook and runs as the context it returns, or fails with
`forbidden` when the ticket is refused or nothing resolves it.
`startOnEvent` takes `ticket: (event) => string | undefined`, and its
`args` function gets the event's context with the ticket as a second
argument. The ticket is stored in plain text with the run, so make it an
id the provider looks up, never a bearer secret.

### Event and schedule starts run as a publisher

Nobody is signed in when an event or a schedule starts a run, so
`startOnEvent` and the schedules of `workflowStarter` need `runAs`: the
publisher, a user who holds the permissions the run needs, and the
permission keys its steps may use. The context the run starts with is the
publisher's, capped to those keys, so `bs.forContext(context)` in a step
runs as the publisher and refuses every other key. A publisher who loses a
permission fails the step that needs it. The event's actor or the
schedule's creator is recorded as `bs.trigger` for audit and grants
nothing; the publisher is recorded as `bs.publisher`. The run's `actor_id`
is the user who triggered it (none for an event without an actor), so they
see the run they caused, and `principal_kind` and `principal_id` record the
publisher. Set `principalKind: "service_principal"` in `runAs` when the
publisher is a [service principal](/docs/blocks/service-principals). The
World records the principal only from these trusted starts: `startFor`
drops `bs.principal_kind` and `bs.principal` from caller attributes.

```ts title="workflows/start.ts"
import { startOnEvent, workflowStarter } from "better-supabase/workflow-sdk";

const runAs = {
  publisher: automationUserId,
  permissions: ["invoices.read", "invoices.approve"],
};

outbox.consume(
  "invoice-approval",
  startOnEvent(approveInvoice, {
    types: ["invoice.paid"],
    runAs,
    args: (event, context) => [context, event.payload],
  }),
);

await workflows.schedules
  .tick({
    start: workflowStarter(
      { weeklyDigest },
      { runAs, args: (call, context) => [context, call.input] },
    ),
  })
  .orThrow();
```

`runAs` can also be a function of the event or the start call, for a
publisher per tenant; `null` starts nothing for that event and fails that
schedule start, which runs again once its lease ends. A schedule start
without `runAs` throws. Admission requests run as the actor that queued
them unless you set `runAs`. A
[service principal](/docs/blocks/service-principals) is the usual
publisher for work an organization owns.

| Helper                                      | Does                                                                                                              |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `workflowStarter({ name: workflow }, opts)` | The `start` callback for `schedules.tick` and `admission.tick`; schedules run as `runAs`                          |
| `startOnEvent(workflow, { types, runAs })`  | An outbox handler that starts the workflow as `runAs` per matching event (`invoice.paid`, `invoice.*`, `*`), once |
| `hookMetadata(ctx, permission?)`            | Metadata for `createHook`, naming the actor and the permission a tenant member needs to resume it                 |
| `authorizeHook(token, ctx, { can })`        | The hook, when the caller created it or holds its permission; `HookForbiddenError` (403) otherwise                |
| `protectWebHandler(handler, key, { can })`  | Answers 401 or 403 as `application/problem+json` before a workflow UI route or a run's stream                     |
| `approvalWaiter.wait` and `.wake`           | Pauses a run on an approval token until a deadline, and resumes it by token                                       |

## Approvals with hooks

```ts title="workflows/approve-invoice.ts"
import type { RequestContext } from "better-supabase";

import { hookMetadata } from "better-supabase/workflow-sdk";
import { createHook } from "workflow";

export async function approveInvoice(invoiceId: string, ctx: RequestContext) {
  "use workflow";
  const hook = createHook<{ approved: boolean }>({
    metadata: hookMetadata(ctx, "invoice.approve"),
  });
  const { approved } = await hook;
  // ...
}
```

```ts title="app/api/approvals/[token]/route.ts"
import { authorizeHook } from "better-supabase/workflow-sdk";
import { resumeHook } from "workflow/api";

export async function POST(request: Request, { params }) {
  const { token } = await params;
  const ctx = await server.context(request);
  await authorizeHook(token, ctx, {
    can: (tenant, permission) => canInTenant(ctx, tenant, permission),
  });
  await resumeHook(token, await request.json());
  return new Response(null, { status: 204 });
}
```

A hook token in a link or an email is not enough to resume the run:
`authorizeHook` also checks who is asking. `can` is your permission check,
for example a call to `member_can(auth.uid(), tenant, permission)`.

### Approvals that expire

`approvalWaiter` waits on an approval by a token you choose, such as the
approval request's id, until a deadline. `wait` runs inside the workflow
and races a hook against `sleep`; `expiresAt` is a `Temporal.Instant` or
an RFC 3339 timestamp, since workflow arguments are serialized.

```ts title="workflows/approve-invoice.ts"
import { approvalWaiter } from "better-supabase/workflow-sdk";

export async function approveInvoice(approvalId: string, expiresAt: string) {
  "use workflow";
  const outcome = await approvalWaiter.wait<{ approved: boolean }>(approvalId, {
    expiresAt,
  });
  if (outcome.status === "expired") return "expired";
  // outcome.payload.approved
}
```

The code that records the decision wakes the run once it has checked the
approver:

```ts
await approvalWaiter.wake(approvalId, { approved: true });
```

With the [approvals](/docs/blocks/approvals) block, use the request's id as
the token and let `wakeOnApproval(event)` do the waking from your outbox
consumer: it resumes the run for `approval.approved`, `approval.rejected`,
`approval.expired` and `approval.cancelled` with `{ approved, status,
requestId }`, and ignores a request no run waits on.

`wait` resolves `{ status: "resumed", payload }` or `{ status: "expired" }`,
and returns `expired` at once for a deadline that has passed. `wake`
sends `null` when you pass no payload.

## Graph workflows

`better-supabase/workflow-sdk/builder` runs the graphs of the
[workflow builder](/docs/blocks/workflow-builder) on the Workflow SDK.
`compileGraph` turns a graph into dynamic workflow source: each step node
calls its own step, sleep nodes call `sleep` and approval nodes wait on
`createHook`. Pass it as `compile`, and `graphStarter` as `start`, to
`createWorkflowBuilder`.

Pass `approval` to `graphStarter` (and `requestApproval` to the static
executor's runtime): a step that files an approvals request for the node
and returns its id. The node then waits on that id, and `wakeOnApproval`
resumes it once an eligible approver decides. Without it the token is
`<runKey>:<node>`, which anyone who knows the run key can guess.

```ts title="workflows/approval.ts"
import { createApprovals } from "better-supabase/blocks/approvals";
import type { GraphApprovalCall } from "better-supabase/blocks/workflow-builder";

export async function requestApproval(call: GraphApprovalCall) {
  "use step";
  const claims = await serviceBuilder.versions.runAs(call.version).orThrow();
  const approvals = createApprovals({
    transport: serviceTransport,
    tenant: String(claims.tenant_id),
  });
  const request = await approvals
    .request(
      { type: "workflow_run", id: call.runKey },
      {
        action:
          typeof call.config.action === "string"
            ? call.config.action
            : "approve",
        payload: { node: call.node },
      },
    )
    .orThrow();
  return request.id;
}
```

```ts title="workflows/graph.ts"
import {
  executeGraph,
  graphRunFields,
  type GraphStepCall,
  type WorkflowGraph,
} from "better-supabase/blocks/workflow-builder";
import { createHook, sleep } from "workflow";

import { requestApproval } from "./approval";
import { steps } from "./steps";

export async function graphExecutor(
  graph: WorkflowGraph,
  input: unknown,
  meta: unknown,
) {
  "use workflow";
  return executeGraph(graph, input, {
    ...graphRunFields(meta),
    step: (call: GraphStepCall) => steps[call.step](call),
    sleep: (ms) => sleep(ms),
    requestApproval: (call) => requestApproval(call),
    approval: (token) => createHook({ token }),
  });
}
```

`graphRunFields(meta)` passes the run key, version, tenant, subject, start
trigger node and, for a test run, the stubs. Pass `executorRunsTests: true`
to `graphStarter` once your executor spreads it; test runs on the static
executor are refused without it.

The executor imports `executeGraph` from the block rather than from
`workflow-sdk/builder`, so the workflow bundle doesn't load `workflow/api`,
which the workflow sandbox can't run.

```ts title="workflows/steps.ts"
import {
  nodeRunReporter,
  type GraphStepCall,
} from "better-supabase/workflow-sdk/builder";

const report = nodeRunReporter(serviceBuilder.nodeRuns);

export async function sendEmail(call: GraphStepCall) {
  "use step";
  return report(call, () => email.send(call.config));
}

export const steps = { "email.send": sendEmail };
```

Dynamic workflows are experimental in the Workflow SDK. With
`WORKFLOW_EXPERIMENTAL_DYNAMIC_WORKFLOWS=1`, `graphStarter` compiles the
published version's graph again on every start and runs that source; it
never runs the `compiled` form stored with the version. Source over 128 KiB
fails to publish. Node ids are 1 to 100 letters, digits, underscores or
hyphens, in `validateGraph` and in `validate_workflow_graph`. Without it, `graphStarter` starts `executor`, a static
`"use workflow"` function that walks the stored graph with `executeGraph`
and takes the same branches. Either way a run carries `bs.definition`,
`bs.version`, `bs.tenant`, `bs.actor` and `bs.key`, and a start with a key
that already ran returns the first run.

`nodeRunReporter` records each step node's status, output and error in
`workflow_node_runs` for the canvas. A record that fails never fails the
step.

## Analytics

`world.analytics` lists runs (by workflow name, status, attributes and a
time window), their steps, events, hooks and waits, and the attribute keys
in use. Pages hold at most 100 runs or 1000 steps and events. Each page
continues after the last row of the previous one (`created_at`, then the
id), so runs started while you page don't shift it. Pass back the `cursor`
the previous page returned. `startFor` uses it to find a run by its
idempotency key.
