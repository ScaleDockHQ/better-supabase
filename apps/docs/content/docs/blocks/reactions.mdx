---
title: Reactions
description: Emoji reactions on any subject, messages (comments included) and inbox messages, with custom emoji per organization, counts under each subject's read rules and a realtime topic per organization.
---

`reactions` stores one row per actor and emoji on a subject. A member reacts to a subject they can read; counts, whether the user reacted and the first actors come back in one call. Reading needs `reactions.read`, reacting needs `reactions.create`, and custom emoji need `reactions.manage`.

```bash
better-supabase add reactions
```

The block's entity is `reaction` (the `reactions` table). It isn't registered as a subject. Rename it with `blocks.reactions.entities`.

```ts
import { createReactions } from "better-supabase/blocks/reactions";

const reactions = createReactions({ transport, tenant: organizationId });
const doc = { type: "doc", id: docId };

await reactions.react(doc, "👍").orThrow();
const byDoc = await reactions
  .summary(docIds.map((id) => ({ type: "doc", id })))
  .orThrow();
byDoc[`doc:${docId}`]; // the doc's ReactionCount[]
await reactions.react(doc, "👍", { present: false }).orThrow();
```

Every call acts in the block's `tenant`, an organization id or a function that returns the current one; `createBlocks` and `createBlockClient` pass the request's tenant, and a call without one fails with `invalid_request` and the hint `TENANT_REQUIRED`. A subject is a `SubjectRef`, `{ type, id }`. `summary(subjects)` takes up to 200 subjects of each type and returns their reactions keyed `type:id` (`subjectKey(subject)` from `better-supabase/blocks`); a subject without reactions may be left out.

`react` returns the subject's reactions, most used first:

| Field     | What it holds                                               |
| --------- | ----------------------------------------------------------- |
| `emoji`   | The emoji, or a custom emoji's `:shortcode:`                |
| `count`   | How many actors reacted with it                             |
| `reacted` | Whether the signed-in user is one of them                   |
| `actors`  | The first ten actors: user ids, or names the service passed |

## Subjects

A reaction's subject is any [`config.subjects`](/docs/blocks/sql#subject-registry) type, a message (with the [messaging](/docs/blocks/messaging) module, which includes [comments](/docs/blocks/comments)) or an inbox message (`inbox_message`, with the [inbox](/docs/blocks/inbox) module). Messages are always included, under the message entity's name (`message`, or the name `blocks.messaging.entities.message` sets), even when `options.subjects` lists other types. `react` and the read policy check that the caller sees the subject: the functions run as the caller, so the subject table's own policies apply, and the caller also needs the subject's read permission (`messages.read` for a message). A subject with a `deletedAt` column, such as a message, must not be deleted. Without registry subjects every type is accepted for members of the organization.

The service role reacts for anyone and passes the actor's name:

```ts
await reactions
  .react({ type: "message", id: commentId }, "✅", { actor: "deploy-bot" })
  .orThrow();
```

## Inbox messages

With the inbox installed, `react_to_message` writes to the `reactions` table and keeps the message's `reactions` column as a copy, so `inbox.messages.react()` and the inbox client keep working. `react({ type: "inbox_message", id: messageId }, emoji)` goes through `react_to_message`, with the inbox's own rules. Installing the module copies the reactions messages already had.

## Custom emoji

An organization's custom emoji are shortcodes with an image: an attachment id from [attachments](/docs/blocks/attachments) or an `https://` URL. A reaction `:shortcode:` must name one of them, or `react` fails with `REACTION_INVALID`. Deleting a custom emoji deletes the reactions that used it.

```ts
await reactions
  .saveCustomEmoji({
    shortcode: "ship-it",
    url: "https://cdn.example.com/ship-it.png",
  })
  .orThrow();
const emoji = await reactions.customEmoji().orThrow();
```

## Realtime

Every change broadcasts `changed` with the `subjectType` and `subjectId` to `reactions:{organizationId}` (`options.topic` renames the prefix). Members with `reactions.read` can join it. `useReactions` from `better-supabase/blocks/reactions/react` loads the subjects on screen and loads them again when one of them changes. It reads the schema and the topic from the `blocks` config passed to the browser client (`createClient(betterSupabase, { blocks: blockConfig })`), so `topic` is only needed to override it (`null` loads without listening), and it acts in the client's tenant: the client's `tenant` option, then the session's tenant claim. It waits while there is no tenant.

```tsx
import { useReactions } from "better-supabase/blocks/reactions/react";

const { reactions, toggle } = useReactions({
  subjects: comments.map((comment) => ({ type: "message", id: comment.id })),
});

await toggle({ type: "message", id: commentId }, "🎉");
```

`reactions` is keyed `type:id`, like `summary`. When the subjects on screen change, the hook loads the new ones without building a new controller.

## Vue

`better-supabase/blocks/reactions/vue` exports `useReactions`. It takes the
options of `createReactionsController`: a client built with its `tenant`, the
same `tenant` for the topic, `subjects` and an optional `topic`; `auth` and `ports` come from
`app.use(betterSupabase(bs))` unless you pass them. `state` is a shallow ref
of the snapshot and `actions` are the controller's actions. The work starts
on mount, and the controller is disposed with the component.

```vue title="Component.vue"
<script setup lang="ts">
import { useSupabase } from "better-supabase/vue";
import { useReactions } from "better-supabase/blocks/reactions/vue";
import {
  createReactions,
  rpcTransport,
} from "better-supabase/blocks/reactions";

const { organizationId, commentIds } = defineProps<{
  organizationId: string;
  commentIds: string[];
}>();
const supabase = useSupabase();
const { state, actions } = useReactions({
  client: createReactions({
    transport: rpcTransport(supabase),
    tenant: organizationId,
  }),
  tenant: organizationId,
  subjects: commentIds.map((id) => ({ type: "message", id })),
});
</script>

<template>
  <p>{{ Object.keys(state.reactions ?? {}).length }}</p>
  <button @click="actions.refresh()">Refresh</button>
</template>
```

## Svelte

`better-supabase/blocks/reactions/svelte` exports `useReactions`. It takes
the options of `createReactionsController`; `auth` and `ports` come from
`setBetterSupabase(bs)` unless you pass them. The hook returns a readable
store of the snapshot, read with `$`, with the actions on `.actions`. The
work starts on mount, and the controller is disposed with the component.

```svelte title="Component.svelte"
<script lang="ts">
  import { getBetterSupabase } from "better-supabase/svelte";
  import { useReactions } from "better-supabase/blocks/reactions/svelte";
  import { createReactions, rpcTransport } from "better-supabase/blocks/reactions";

  let { organizationId, commentIds }: { organizationId: string; commentIds: string[] } = $props();
  const { supabase } = getBetterSupabase();
  const reactions = useReactions({
    client: createReactions({
      transport: rpcTransport(supabase),
      tenant: organizationId,
    }),
    tenant: organizationId,
    subjects: commentIds.map((id) => ({ type: "message", id })),
  });
</script>

<p>{Object.keys($reactions.reactions ?? {}).length}</p>
<button onclick={() => reactions.actions.refresh()}>Refresh</button>
```

## Solid

`better-supabase/blocks/reactions/solid` exports `useReactions`. It takes
the options of `createReactionsController`; `auth` and `ports` come from
`<BetterSupabaseProvider client={bs}>` unless you pass them. `state()` reads
the snapshot through `from`, and `actions` are the controller's actions. The
work starts on mount, and the controller is disposed with the owner.

```tsx title="Component.tsx"
import { useSupabase } from "better-supabase/solid";
import { useReactions } from "better-supabase/blocks/reactions/solid";
import {
  createReactions,
  rpcTransport,
} from "better-supabase/blocks/reactions";

export function Component(props: {
  organizationId: string;
  commentIds: string[];
}) {
  const supabase = useSupabase();
  const { state, actions } = useReactions({
    client: createReactions({
      transport: rpcTransport(supabase),
      tenant: props.organizationId,
    }),
    tenant: props.organizationId,
    subjects: props.commentIds.map((id) => ({ type: "message", id })),
  });
  return (
    <>
      <p>{Object.keys(state().reactions ?? {}).length}</p>
      <button onClick={() => actions.refresh()}>Refresh</button>
    </>
  );
}
```

## Events and hooks

The module records `reaction.added` and `reaction.removed` with `organizationId`, `subjectType`, `subjectId`, `emoji` and `actor`. `react` calls the `before_react` and `after_react` SQL hooks with the tenant, subject type, subject id, emoji and whether the reaction is added.

| Error                | When                                                                    |
| -------------------- | ----------------------------------------------------------------------- |
| `REACTION_FORBIDDEN` | The caller lacks the permission or can't see the subject                |
| `REACTION_INVALID`   | The emoji is empty, longer than 64 characters, has spaces or is unknown |

## With ReUI

Render the ReUI Emoji Picker for new reactions and one Bubble per `ReactionCount`, highlighted when `reacted` is true. `toggle(subject, emoji)` adds the emoji, or removes it when the user already reacted with it.
