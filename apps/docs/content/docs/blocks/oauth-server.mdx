---
title: OAuth server
description: Storage for your own OAuth 2.1 authorization server, with hashed client secrets, PKCE-bound authorization codes, device codes, grants and a revocation list.
---

`oauth-server` stores what an OAuth 2.1 authorization server needs:
registered clients (RFC 7591) with hashed secrets, one grant per user and
client, single-use authorization codes bound to a PKCE S256 challenge
(RFC 7636), device codes (RFC 8628) and a revocation list of access token
`jti`s. It issues no tokens. Sign them with
[signing keys](/docs/blocks/signing-keys) and accept them with
[`accessTokenResolver`](/docs/auth/access-tokens).

Use it when your app is the authorization server for its own clients, for
example a platform that lets third-party apps act for its users. When the
Supabase Auth OAuth server fits, use that instead; the
[OAuth consent page](/docs/auth/oauth-consent) covers it.

```bash
better-supabase add oauth-server
```

```ts
import {
  createOAuthServer,
  sqlTransport,
} from "better-supabase/blocks/oauth-server";

const oauth = createOAuthServer({ transport: sqlTransport(postgres.admin) });
```

Every function is service-role only, except `my_oauth_grants` and
`revoke_my_oauth_grant`, which a signed-in user calls for their own grants.
Clients can't read the tables. Secrets, codes and registration tokens are
generated in TypeScript and only their SHA-256 reaches the database.

## Clients

`registerClient(metadata)` registers a client and returns its
`clientSecret` and `registrationAccessToken` once. A client with
`tokenEndpointAuthMethod: "none"` is public and gets no secret. Redirect URIs
must be absolute, carry no fragment, and use `https` or `http` on a loopback
host (RFC 9700 section 2.1). Metadata without a column of its own, such as
`logo_uri`, goes in `metadata`.

```ts
const { client, clientSecret, registrationAccessToken } = await oauth
  .registerClient({
    name: "Acme CLI",
    redirectUris: ["http://127.0.0.1:8976/callback"],
    grantTypes: ["authorization_code", "refresh_token"],
    tokenEndpointAuthMethod: "none",
    scope: "contacts:read contacts:write",
  })
  .orThrow();
```

`verifyClient(clientId, secret)` returns the client when the secret matches
(`null` as the secret for a public client), and
`verifyRegistrationToken(clientId, token)` checks the RFC 7592 token before
`readClient` or `updateClient`. `rotateSecret` returns a new secret, and
`deleteClient` removes the client with its grants and codes.

### Client ids

`registerClient` generates a client id. To choose your own, such as `acme-cli`,
pass `{ clientId }` as the second argument. The database checks every id
against `clientIdPattern`, a block option. The default accepts
`[A-Za-z0-9._~-]{8,128}`, so existing clients keep working. The preset
`"slug"` accepts lower-case slugs (`^[a-z0-9][a-z0-9-]{2,63}$`), and any other
value is a regular expression:

```ts title="better-supabase.config.ts"
blocks: {
  "oauth-server": { options: { clientIdPattern: "slug" } },
},
```

## Authorization codes

After the user consents, store the code with the request's PKCE challenge.
Only `S256` is accepted:

```ts
const { code } = await oauth
  .createAuthorizationCode({
    clientId,
    userId: user.id,
    redirectUri,
    scope: "contacts:read",
    codeChallenge,
    codeChallengeMethod: "S256",
  })
  .orThrow();
```

At the token endpoint, `redeemAuthorizationCode` hashes the code, computes
S256 of the `codeVerifier` and compares both with the client and redirect
URI in one locked row. It returns who to issue tokens for, or `null` for any
mismatch. A code presented a second time also revokes its grant, so tokens
issued from a stolen code stop working (RFC 9700 section 4.5). Codes live 60
seconds (`codeSeconds`).

### Resource indicators

Pass `resource` (RFC 8707) to `createAuthorizationCode` with the APIs the
token may be used at. The code, the device code and the user's grant store
them. At the token endpoint, pass the request's `resource` to
`redeemAuthorizationCode`: it has to be a subset of the code's resources, and
anything wider returns `null` (the `invalid_target` case). The returned
`authorization.resource` is what you put in the token's `aud`; without a
`resource` in the exchange it is every resource of the code.

## Device codes

`createDeviceCode(clientId, scope, resource?)` returns a `deviceCode` for the client
and a `userCode` such as `BDFG-HJKL` for the user. The verification page
reads the request with `deviceRequest(userCode)` and calls
`approveDeviceCode` or `denyDeviceCode` with the signed-in user. The client
polls `pollDeviceCode(deviceCode, clientId, resource?)`. A `resource` that is
not a subset of the device code's resources answers `invalid_grant`.

| Status                  | Token response (RFC 8628 section 3.5)                   |
| ----------------------- | ------------------------------------------------------- |
| `authorization_pending` | keep polling every `interval` seconds                   |
| `slow_down`             | polled too soon; `interval` grows by 5 seconds          |
| `access_denied`         | the user denied                                         |
| `expired_token`         | the code expired (`deviceCodeSeconds`, 600)             |
| `invalid_grant`         | unknown code, another client, or already exchanged      |
| `ok`                    | issue tokens for `authorization`; the code is now spent |

`deviceRequest(userCode)` returns `null` for a code that is unknown, expired
or already decided, so the verification page can show "code not found" for all
three. A client that polls before `interval` has passed gets `slow_down` and
the stored interval grows by 5 seconds up to 300, so honor the `interval` of
the last response.

## Grants and revocation

A grant is a user's consent for a client. Approving a code or a device code
reuses the user's active grant for the client and widens its scopes. Put the
grant id in the tokens you issue as `grant_id`.

`revokeGrant(grantId)` ends every token and code issued under it. For the
RFC 7009 revocation endpoint, look up the token's `jti` and `grant_id`
claims, then call `revokeToken(jti, expiresAt, { grantId })` for one access
token, or `revokeGrant` when the client revokes a refresh token.
`revokeToken(jti, expiresAt)` puts one access token on the revocation list
until it would expire anyway. `isRevoked(jti, grantId)` checks both, and
treats an unknown grant as revoked, so deleting a client ends its tokens.
Pass the client to the resolver as `revocation`:

```ts
accessTokenResolver({ jwks, issuer, audience, revocation: oauth });
```

For a connected-apps page, `listGrants(userId)` returns a user's grants with
the client name. In the browser, the user calls `my_oauth_grants` and
`revoke_my_oauth_grant` over RPC for their own grants only; a read-only
support session can't revoke ([support sessions](/docs/blocks/sql#support-sessions)).

`purge()` deletes expired codes, device codes and revocation entries; run it
from a daily job.

## Hono

The [Hono example](https://github.com/ScaleDockHQ/better-supabase/tree/main/apps/examples/hono-api)
serves an authorization server on these calls. `POST /oauth/authorize` runs
behind `bsb.middleware({ allow: ["user"] })`, stores a code for the signed-in
user and returns the redirect. `POST /oauth/token` verifies the client
(`client_secret_basic`, `client_secret_post` or a public client), redeems the
code and signs an RFC 9068 access token (`typ: at+jwt`) with
[signing keys](/docs/blocks/signing-keys), carrying `grant_id` for
revocation. `GET /.well-known/jwks.json` publishes the keys.

```ts title="src/server.ts"
const app = bsb
  .app()
  .post("/oauth/token", (c) => token(c.req.raw))
  .get("/.well-known/jwks.json", () => jwks())
  .post("/oauth/authorize", bsb.middleware({ allow: ["user"] }), async (c) => {
    if (c.var.auth.kind !== "user") {
      return c.json({ error: "login_required" }, 401);
    }

    const params = new URLSearchParams(await c.req.text());
    const redirect = await authorize({ userId: c.var.auth.user.id, params });

    return c.json({ redirect: redirect.href });
  });
```

The token endpoint answers a refused request in the RFC 6749 format
(`{ "error": "invalid_grant" }`), which OAuth clients expect. Anything else,
such as a database error from an `.orThrow()`, reaches `bsb.onError`, which
`bsb.app()` installs, and answers as [Problem Details](/docs/auth/problems).
The [oRPC example](https://github.com/ScaleDockHQ/better-supabase/tree/main/apps/examples/orpc-api)
serves its router on Hono the same way, so both can share one app.

## One tenant shared by Hono and Next

The authorization server and your dashboard can run as two apps on one
database. Hono serves the token and authorize endpoints; Next.js serves the
consent page and the connected-apps page with `listGrants`. Both read the
same users, organizations and grants, so a grant the user revokes in the
dashboard ends the tokens Hono issued. Resource servers verify those tokens
with `accessTokenResolver` against the JWKS Hono publishes.
[Hono and Next.js](/docs/frameworks/hono-and-next) covers serving both from
one deployment.

## Events

| Event                                             | Data                            |
| ------------------------------------------------- | ------------------------------- |
| `oauth_client.registered`, `oauth_client.deleted` | `clientId`                      |
| `oauth_grant.created`, `oauth_grant.revoked`      | `grantId`, `userId`, `clientId` |

Each also writes an audit entry when the audit module is installed.
