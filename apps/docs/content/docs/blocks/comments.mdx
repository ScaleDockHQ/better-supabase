---
title: Comments and activity
description: Threaded comments on any record in a tenant, mentions that notify, comment events in the outbox and an activity feed built from outbox events.
---

The `comments` block adds threaded comments to any record in a tenant
(projects, tickets, invoices) and an activity feed. Mentions notify the
mentioned members through the [notifications](/docs/blocks/notifications)
block, and every comment writes a `comment.*` event to the
[outbox](/docs/blocks/outbox).

Comments run in every [scope](/docs/blocks/sql#scope-and-naming). In `user`
scope a thread is visible only to the user whose scope it is in, and mentions
of other users notify no one. In `none` scope every signed-in user reads and
writes every thread.

```bash
better-supabase sql add comments   # adds tenant and access as well
```

| Table              | Holds                                                                                                        |
| ------------------ | ------------------------------------------------------------------------------------------------------------ |
| `comments`         | `subject_type`, `subject_id`, `author_id`, `body`, `mentions`, `parent_id`, `edited_at` and `deleted_at`     |
| `activity_entries` | One row per outbox event: `type`, `actor_id`, `subject_type`, `subject_id`, `summary`, `data`, `occurred_at` |

| Permission          | Lets a member                       | Default roles          |
| ------------------- | ----------------------------------- | ---------------------- |
| `comments.read`     | read the comments in a tenant       | `member`, `admin`      |
| `comments.create`   | comment and edit their own comments | `member`, `admin`      |
| `comments.moderate` | delete other members' comments      | `admin` (`comments.*`) |
| `activity.read`     | read the tenant's activity feed     | `member`, `admin`      |

Only the author edits a comment. Deleting is a soft delete: the row stays
as a placeholder so replies keep their parent, and its body and mentions
are cleared.

## Subjects

Without options, a comment can name any `subject_type` and `subject_id`.
Map each subject type to its table so the policies also require that the
caller can read the subject row (the subject table's own policies apply)
and, optionally, hold a permission:

```ts title="better-supabase.config.ts"
export default defineConfig({
  blocks: {
    comments: {
      options: {
        subjects: {
          project: { table: "projects", permission: "projects.read" },
          ticket: {
            table: "support.tickets",
            id: "ticket_id",
            tenant: "team_id",
          },
        },
      },
    },
  },
});
```

`id` defaults to `id` and `tenant` to `organization_id`. A subject type not in
the map is refused. `maxBodyLength` (default 10000) caps the body.

`permissions` gives a subject type its own keys per action, in place of the
module's `comments.read`, `comments.create` and `comments.moderate`, so
comments on deals follow the deal permissions while other subjects keep the
defaults:

```ts
subjects: {
  deal: {
    table: "deals",
    permissions: { read: "deals.read", create: "deals.comment", moderate: "deals.manage" },
  },
},
```

`read` decides who sees the thread, `create` who may comment, and `moderate`
who may edit or delete other people's comments; authors always edit their
own.

### Access per record

With `blocks.access.model: "provider"`, `scope` names a scope your
[authorization provider](/docs/extending/authorization-providers) declares
whose ids are the subject ids, such as `project`. A member then reads,
writes or moderates the comments on a record when they hold the key in the
tenant or on the record itself: the policies add
`subject_id in (select ... from <idsWith at that scope>)` next to the tenant
check. A scope the provider doesn't declare, or the tenant scope itself, is
refused.

```ts
subjects: {
  project: { table: "projects", idType: "uuid", scope: "project" },
},
```

`cascade: true` on a subject writes an `after delete` trigger on its table
that deletes the subject's comments, which stands in for a foreign key, since
`subject_id` is text. The subject table must exist before the module file.

## Rich text

A comment can carry a `document` (any JSON, such as a block editor's
document) next to `body`, which stays its plain text for search, summaries
and notifications. `createComments({ mentionsOf })` reads the mentioned user
ids from the comment when a call passes no `mentions`, for editors that store
mentions as nodes instead of `@[Name](<user id>)` markup:

```ts
const comments = createComments({
  transport,
  mentionsOf: ({ document }) =>
    mentionNodes(document).map((node) => node.userId),
});

await comments.create({
  organizationId,
  subjectType,
  subjectId,
  body,
  document,
});
await comments.edit(id, { body, document: null }); // null removes the document
```

An edit without `document` keeps the current one. With the jsonb-schemas
module, `options.documentSchema` (a JSON Schema object) adds a pg_jsonschema
check on the column.

## Copying a thread

When the app duplicates a record (a quote into an invoice, say),
`comments.copy(organizationId, { type, id }, { type, id })` copies the
thread to the new subject with its authors, times and replies, and returns
the number of comments copied. `copy_comments` is for the service role only:
call it from the code that duplicates the record, after that code checked the
caller may read both. It works over `sqlTransport` and over `rpcTransport`
with a service-role client; PostgREST sessions on Supabase load
pg-safeupdate, which refuses a `delete` or `update` without a `where`
clause, and every statement the SQL modules run has one. The function
creates no temporary table, so `supabase db lint` checks it like any other.

## Comments

```ts title="app/projects/[id]/actions.ts"
import { createComments, sqlTransport } from "better-supabase/blocks/comments";

const comments = createComments({
  transport: sqlTransport(postgres.asUser(claims)),
});

await comments
  .create({
    organizationId,
    subjectType: "project",
    subjectId: projectId,
    body: "Ready for review @[Ada](8c5a3d3e-...)",
  })
  .orThrow();

const thread = await comments
  .list(organizationId, "project", projectId)
  .orThrow();
```

`create` and `edit` read the mentions from the body when you pass none:
`mentionsIn(body)` returns the user ids written as `@[Name](<user id>)`, the
markup most mention inputs produce. The module drops the author and repeats,
and notifies only mentioned members who hold `comments.read`. `list` returns
the thread oldest first; `cursor` (an instant) polls for new comments, and `offset` with
`limit` pages by number. `counts(organizationId, subjectType, subjectIds)`
returns how many comments each subject has that the caller can read
(`comment_counts`), deleted ones left out and 0 for a subject without any,
for a counter on each row of a list. `edit` returns
`not_found` for a comment the caller can't see, and `forbidden` with the hint
`COMMENT_NOT_AUTHOR` for someone else's comment.

With the notifications module installed, each new mention sends a
`comment.mentioned` notification with the subject, the first 140 characters
of the body as its `summary` and the commenter as the actor. Three more keys
of `options.subjects.<type>` shape it, each SQL on the subject's row
`{row}`:

```ts
subjects: {
  task: {
    table: "public.tasks",
    idType: "uuid",
    label: "{row}.title",
    path: "'/tasks/' || {row}.id",
    readableBy: "not {row}.private or {row}.owner_id = {user}",
  },
},
```

`label` fills the notification's `subject_label` and `path` its
`action_path`, which an adopted events table may require. A mentioned member
is notified only when they hold the subject type's read key
(`permissions.read`, else `comments.read`) and its `permission` in the
tenant, and `readableBy` holds for them (`{user}` is their id). The others
stay in the comment's `mentions` but get nothing.

`readableBy` also takes `{ sql, enforce: true }`. The read policy then
applies the same SQL to the caller (`{user}` becomes `auth.uid()`), so a
member who can't read a private task doesn't see its comments either:

```ts
subjects: {
  task: {
    table: "public.tasks",
    readableBy: { sql: "not {row}.private or {row}.owner_id = {user}", enforce: true },
  },
},
```

### Group mentions

`options.mentionGroups` expands a mention of a group, such as `@team`, into
its members. It names a table with one row per member of a group, the group
and member columns, and optionally a tenant column that must match the
comment's tenant:

```ts title="better-supabase.config.ts"
comments: {
  options: {
    mentionGroups: {
      table: "public.team_members",
      group: "team_id",
      member: "user_id",
      tenant: "organization_id",
    },
  },
},
```

The app writes the group id into `mentions` like a user id, for example as
`@[Support](<team id>)`. The trigger adds the members of every mentioned
group to the mentioned users, leaves out the author, and then applies the
read check above to each of them, so a group member who can't read the
subject gets nothing. On an edit, only members who were not already reached
through the old mentions are notified, and `comment.mentioned` carries the
expanded user ids in `mentionIds`. Both columns hold `uuid`s, and the
comment's `mentions` keep the group id as written.

`options.notify: false` sends no notification at all, for an app that sends
its own mention notifications. The outbox still gets `comment.mentioned`,
so that app can send from the event.

### Following a thread

With the notifications module installed, the author of a new comment and
every user it mentions (after group expansion) follow the subject: the
trigger adds a `participating` row to `notification_subscriptions` for each
of them. A user who already has a row for the subject keeps it, so someone
who chose `ignore` stays unsubscribed. An edit adds only the newly mentioned
users. `options.follow: false` turns this off.

## In the browser

`useComments` from `better-supabase/blocks/comments/react` loads one
subject's thread through the provider's client and keeps it current after
`add`, `edit` and `remove`. The same hook runs in React DOM and React Native.
The module broadcasts nothing, so the thread loads again after the caller's
own writes; pass `topic` (a private topic that hears of new comments, such as
a `realtime-tables` topic on the comments table) to load it again for
everyone's.

```tsx title="components/comment-thread.tsx"
import { useComments } from "better-supabase/blocks/comments/react";

const { comments, error, add, remove } = useComments({
  organizationId,
  subjectType: "project",
  subjectId: projectId,
  schema: "api",
});

await add("Ready for review");
```

`add`, `edit` and `remove` return a `Result` and keep a failure in `error`.
`schema` names the schema the calls go to: the module schema by default, or
the API schema from `blocks.comments.api`. The thread waits while
`organizationId` is `null`. `createCommentsController` from
`better-supabase/blocks/comments` is the same logic without React, and
`better-supabase/blocks/comments/vue`, `/svelte` and `/solid` export
`useComments` over it, taking the controller's options with `auth` and
`ports` from the provider. The [comment thread recipe](/docs/registry/ui-recipes)
shows it in the Next.js and Expo examples.

```vue title="CommentCount.vue"
<script setup lang="ts">
import { useSupabase } from "better-supabase/vue";
import { useComments } from "better-supabase/blocks/comments/vue";
import { createComments, rpcTransport } from "better-supabase/blocks/comments";

const { organizationId, projectId } = defineProps<{
  organizationId: string;
  projectId: string;
}>();
const supabase = useSupabase();
const { state, actions } = useComments({
  client: createComments({ transport: rpcTransport(supabase) }),
  organizationId,
  subjectType: "project",
  subjectId: projectId,
});
</script>

<template>
  <p>{{ state.comments?.length ?? 0 }} comments</p>
  <button @click="actions.add('Looks good')">Approve</button>
</template>
```

```svelte title="CommentCount.svelte"
<script lang="ts">
  import { getBetterSupabase } from "better-supabase/svelte";
  import { useComments } from "better-supabase/blocks/comments/svelte";
  import { createComments, rpcTransport } from "better-supabase/blocks/comments";

  let { organizationId, projectId }: { organizationId: string; projectId: string } = $props();
  const { supabase } = getBetterSupabase();
  const thread = useComments({
    client: createComments({ transport: rpcTransport(supabase) }),
    organizationId,
    subjectType: "project",
    subjectId: projectId,
  });
</script>

<p>{$thread.comments?.length ?? 0} comments</p>
```

```tsx title="CommentCount.tsx"
import { useSupabase } from "better-supabase/solid";
import { useComments } from "better-supabase/blocks/comments/solid";
import { createComments, rpcTransport } from "better-supabase/blocks/comments";

export function CommentCount(props: {
  organizationId: string;
  projectId: string;
}) {
  const supabase = useSupabase();
  const { state } = useComments({
    client: createComments({ transport: rpcTransport(supabase) }),
    organizationId: props.organizationId,
    subjectType: "project",
    subjectId: props.projectId,
  });
  return <p>{state().comments?.length ?? 0} comments</p>;
}
```

## Reactions

With the [reactions](/docs/blocks/reactions) module installed, a comment is
the subject type `comment`: `reactions.react(organizationId, "comment",
comment.id, emoji)` reacts to a comment the caller can read, and
`reactions.summary(organizationId, "comment", ids)` counts a thread's
reactions in one call.

## Your own columns

Add columns to the `comments` table with
`blocks.comments.options.extraColumns` (column name to SQL type), then pass
a Standard Schema for them as `fields`. `create` and `edit` validate the
`fields` you pass and write them after the insert or the update, so a
column you leave out keeps its default or its value, and an edit that sets
only `fields` still needs the `body`. `create`, `edit` and `list` return the
columns parsed under `fields`, keyed by column name, and `copy` copies them
to the new thread. Members write them with the same policies as the rest
of the comment: the author, or a member with `comments.moderate`.

```ts title="better-supabase.config.ts"
blocks: {
  comments: {
    options: {
      extraColumns: { visibility: "text not null default 'internal'" },
    },
  },
},
```

```ts title="lib/comments.ts"
import { createComments, rpcTransport } from "better-supabase/blocks/comments";
import { z } from "zod";

const comments = createComments({
  transport: rpcTransport(supabase),
  fields: z.object({ visibility: z.enum(["internal", "customer"]) }),
});

const comment = await comments
  .create({
    organizationId,
    subjectType: "project",
    subjectId: projectId,
    body: "Shipped",
    fields: { visibility: "customer" },
  })
  .orThrow();
comment.fields.visibility; // "internal" | "customer"
```

Without `extraColumns`, `create_comment` and `edit_comment` keep their
default signatures and stay `language sql`. The block also takes `hooks`
around its methods; see [extending blocks](/docs/extending/blocks).

## Events

With the outbox installed, the module writes these events with the tenant as
the partition key and `comments/<id>` as the subject:

| Event               | When                           | Data                                                                          |
| ------------------- | ------------------------------ | ----------------------------------------------------------------------------- |
| `comment.created`   | a comment or reply is added    | `commentId`, `subjectType`, `subjectId`, `authorId`, `parentId`, `mentionIds` |
| `comment.mentioned` | a create or edit adds mentions | the same, with only the new `mentionIds`                                      |
| `comment.deleted`   | a comment is deleted           | `commentId`, `subjectType`, `subjectId`, `authorId`                           |

## Activity feed

`activitySink` is an outbox sink that writes events into `activity_entries`.
Run it as a consumer with a service-role transport:

```ts title="app/api/cron/activity/route.ts"
import { activitySink, sqlTransport } from "better-supabase/blocks/comments";

await outbox.relay(
  "activity",
  activitySink({
    transport: sqlTransport(postgres.admin),
    types: ["comment.*", "organization.member_added", "billing.*"],
    describe: (event, type) =>
      type === "comment.created" ? { summary: "commented" } : {},
  }),
);
```

Events without a tenant are skipped, and the event id is unique, so a
replayed batch writes nothing twice. The actor is the event's `actorId`,
`authorId` or `userId`, and the subject its `subjectType` and `subjectId`
(or the CloudEvents `subject`). `describe` can set the summary, actor,
subject and data, or return `null` to skip an event.

`comments.history(organizationId, subject?, { before, limit })` reads the
feed through `list_activity`, which runs as the caller: the tenant's entries
newest first, or one subject's timeline when you pass `{ type, id }`. It works
over `rpcTransport` too, without exposing the module schema.

```ts
const timeline = await comments
  .history(organizationId, { type: "quote", id: quoteId }, { limit: 20 })
  .orThrow();
```

Each entry carries a `source`: `event` for a row of `activity_entries`, or
`audit` for an audit log entry (see below).

### Visibility per record

With the `subjects` module of the
[subject registry](/docs/blocks/sql#subject-registry) installed, the feed only
shows a caller the entries on records they can read. The read policy on
`activity_entries` checks `can_subject(subject_type, subject_id, 'read')` row
by row for every subject type in the registry, so the tenant feed, the
subject timeline and `activityListQuery` all leave out entries on records the
caller can't read, and entries on a deleted record. `list_activity` returns
an empty timeline for a subject the caller can't read. Entries without a
subject, or on a type the registry doesn't list, keep the tenant check alone.

### Audit entries in a timeline

With the [audit](/docs/blocks/audit) module installed with
`options.readPolicy: true`, a subject's timeline also returns the audit log
entries for the subject's row: the entries whose table is the type's
registry table and whose record id is the subject id. The audit read policy
gates them, so only callers who hold `audit.read` (by default `admin` and
`owner`) see them. An audit entry has `source: "audit"`, the audit entry id
as `id`, no `eventId`, the audit event type as `type` (`audit.<op>` when it
has none), and `op`, `changed` and `table` in `data`. The tenant feed and
`activityListQuery` list no audit entries.

Or read the feed with `activityListQuery`, a cursor-paged
[list query](/docs/platform/list) filtered by type, actor and
subject, newest first. Generate types for the `better_supabase` schema to
have the table in your models:

```ts
import { activityListQuery } from "better-supabase/blocks/comments";

export const activity = activityListQuery(betterSupabase, "activityEntries", {
  pageSize: 30,
});
```
