---
title: Tags
description: Tag definitions per kind, applied to subjects through one table or a link table per subject.
---

`tags` keeps definitions (`kind`, `name`, `slug`, `color`) and applies them to records. Applying or removing a tag needs `tags.apply` (or `tags.manage`) in the tenant, the subject's own read permission, and a tag kind the subject allows.

With the [drive](/docs/blocks/drive#labels-and-approvals) installed, `drive_node` subjects follow the node's grants: reading a node's tags needs read access, and tagging or untagging needs write access, which is how the drive's labels work.

| Permission    | Checked by                                                     | Default roles        |
| ------------- | -------------------------------------------------------------- | -------------------- |
| `tags.read`   | `list`, `forSubject`                                           | owner, admin, member |
| `tags.apply`  | `tag`, `untag`                                                 | owner, admin, member |
| `tags.manage` | `create`, `update`, `reorder`, `delete`, and every check above | owner, admin         |

```bash
better-supabase add tags
```

```ts
import { createTags } from "better-supabase/blocks/tags";
```

In managed mode every application lives in `taggings` (`subject_type`, `subject_id`). In adopt mode each subject can name its own link table.

Every call acts in the block's `tenant`, an organization id or a function that returns the current one; `createBlocks` and `createBlockClient` pass the request's tenant, and a call without one fails with `invalid_request` and the hint `TENANT_REQUIRED`. A record is a `SubjectRef`, `{ type, id }`.

```ts
const tags = createTags({ transport, tenant: organizationId });
const customer = { type: "customer", id: customerId };

const vip = await tags.create("customer", "VIP", "amber").orThrow();
await tags.tag(customer, vip.id).orThrow();
const onCustomer = await tags.forSubject(customer).orThrow();
```

`create(kind, name, color?, description?, fields?)` creates a tag of a kind. `tag(subject, tagId)` and `untag(subject, tagId)` put a tag on a record and take it off. `list(kind?)` returns the tenant's tags of a kind (every kind without one) in rank order, for a caller with `tags.read` or `tags.manage`. `forSubject(subject)` returns the tags on one record, for a caller who can also read the record. They call `list_tags` and `subject_tags`.

## In the browser

`useTagInput` from `better-supabase/blocks/tags/react` loads a record's tags and every tag of a kind for suggestions through the provider's client. `add(tagId)` and `remove(tagId)` show the change at once and take it back when the module refuses it. `create(name)` adds the tag of that kind with the same name (ignoring case), or creates it first, which needs `tags.manage`. The same hook runs in React DOM and React Native.

```tsx title="components/tag-input.tsx"
import { useTagInput } from "better-supabase/blocks/tags/react";

const { tags, available, add, remove, create } = useTagInput({
  subject: { type: "customer", id: customer.id },
  kind: "customer",
});
```

The hook calls the schema and function names in the `blocks` config passed to the browser client (`createClient(betterSupabase, { blocks: blockConfig })`), so it takes no `schema`, and acts in the client's tenant: the client's `tenant` option, then the session's tenant claim. It waits while there is no tenant or `subject` is `null`.

`createTagInputController` from `better-supabase/blocks/tags` is the same logic without React, and `better-supabase/blocks/tags/vue`, `/svelte` and `/solid` export `useTagInput` over it, taking the controller's options: a client built with its `tenant`, and `subject`. The [tag input recipe](/docs/registry/ui-recipes/tag-input) shows it in the Next.js and Expo examples.

```vue title="CustomerTags.vue"
<script setup lang="ts">
import { useSupabase } from "better-supabase/vue";
import { useTagInput } from "better-supabase/blocks/tags/vue";
import { rpcTransport } from "better-supabase/blocks";
import { createTags } from "better-supabase/blocks/tags";

const props = defineProps<{ organizationId: string; customerId: string }>();
const supabase = useSupabase();
const { state, actions } = useTagInput({
  client: createTags({
    transport: rpcTransport(supabase),
    schema: "api",
    tenant: props.organizationId,
  }),
  subject: { type: "customer", id: props.customerId },
  kind: "customer",
});
</script>

<template>
  <button
    v-for="tag in state.tags"
    :key="tag.id"
    @click="actions.remove(tag.id)"
  >
    {{ tag.name }}
  </button>
</template>
```

```tsx title="CustomerTags.tsx"
import { useSupabase } from "better-supabase/solid";
import { useTagInput } from "better-supabase/blocks/tags/solid";
import { rpcTransport } from "better-supabase/blocks";
import { createTags } from "better-supabase/blocks/tags";

export function CustomerTags(props: {
  organizationId: string;
  customerId: string;
}) {
  const supabase = useSupabase();
  const { state } = useTagInput({
    client: createTags({
      transport: rpcTransport(supabase),
      schema: "api",
      tenant: props.organizationId,
    }),
    subject: { type: "customer", id: props.customerId },
    kind: "customer",
  });
  return (
    <p>
      {state()
        .tags?.map((tag) => tag.name)
        .join(", ")}
    </p>
  );
}
```

Tags run in every [scope](/docs/blocks/sql#scope-and-naming). In `user` scope each user has their own tags, and in `none` scope every signed-in user shares one set.

## Adopt mode

```ts title="better-supabase.config.ts"
tags: {
  mode: "adopt",
  tables: { tags: "public.organization_tags" },
  options: {
    subjects: {
      task: {
        table: "public.tasks",
        kinds: ["task"],
        links: { table: "public.task_tags", subject: "task_id", tag: "tag_id" },
      },
    },
  },
},
```

`links` columns are `subject`, `tag` and optional `tenant` and `createdAt`.

The adopted `kind` and `subjectType` columns may be enums, such as `kind public.organization_tag_kind`: the module casts the text it writes and compares to the column's type, so an unknown kind fails with the enum's `invalid input value` error.

## Order

Tags of a kind are ordered by `rank`, a fractional key (see [Rank](/docs/blocks/rank)). `create` appends a tag after the last one of its kind, and `reorder(id, { previous, next })` moves it between the tags with those keys. Version 2 of the module replaced the integer `position` column with `rank`: the upgrade backfills keys in the old order and drops `position`. In adopt mode `rank` is optional; map it to `null` when the table has no such column.

## Your own columns

Add columns to the tag table with `blocks.tags.options.extraColumns`
(column name to SQL type), then pass a Standard Schema for them as `fields`.
`create` and `update` (the last argument) validates and writes them, and `create` return them parsed under
`fields`. The block also takes `hooks` around its methods; see
[extending blocks](/docs/extending/blocks).

```ts
import { createTags } from "better-supabase/blocks/tags";
import { z } from "zod";

const client = createTags({
  transport,
  fields: z.object({ priority: z.enum(["low", "high"]) }),
});
```
