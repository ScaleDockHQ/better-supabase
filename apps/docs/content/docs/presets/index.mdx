A preset is a block selection plus the conventions to install it with:
framework, platforms, casing, id type, scope, tenant name, access model, API
schema and integrations. Put a named preset or a code from
[Create](https://app.bettersupabase.com/create) in your config, and
`defineConfig` expands it into `blocks`, with the blocks they require:

```ts title="better-supabase.config.ts"
import { defineConfig } from "better-supabase/config";

export default defineConfig({
  preset: "saas",
  sql: { api: "api" },
  blocks: { comments: { options: { maxBodyLength: 5000 } }, tags: {} },
});
```

The keys you set win. A block you name joins the preset, and its entry is
merged over the preset's settings for that block. `casing`, `sql.api` and
`integrations` from the preset apply only when the config leaves them unset.
`npx better-supabase sql sync` then writes the files of every block the
preset expands to, and `supabase db schema declarative sync` turns them into
a migration ([SQL modules](/docs/blocks/sql)).

A new project starts from a preset with
`npx better-supabase init --preset saas`, which writes the config, the module
files and `lib/blocks.ts` in one step. `better-supabase apply --preset crm`
applies one to a project you have, and `better-supabase preset info` shows
how your config differs from its preset ([CLI](/docs/cli/presets)).

Each one also installs what its blocks require (`tenant`, `access`,
`updated-at`, ...). The named presets use the default conventions, except
`consumer`, which scopes rows to the user (`scope: "user"`) and so leaves out
the blocks that need tenants, such as billing and settings. The `/create`
preset picker and `init` list them in these groups.
`tests/validation-presets` renders each one, applies it to the local stack
as one migration, and typechecks the `lib/blocks.ts` it generates.

## Codes and Create

[Create](https://app.bettersupabase.com/create) builds a preset in the browser
and keeps it in the URL as `/create?preset=<code>`. The code also works as
`preset` in the config, with `init --preset` and with `apply --preset`, and
so does the whole URL. See
[Codes and the resolver](/docs/presets/codes) for the encoding and the
`better-supabase/preset` API.

Create runs in the better-supabase cloud app and needs no account for the
canvas, Get code and Deploy to Supabase. Signing in adds the AI chat, saved
projects with version history, designs too large for a link, deploy
history and the cloud MCP server at `https://app.bettersupabase.com/api/mcp`.
That server edits your saved designs; the docs MCP server at
`https://bettersupabase.com/mcp` answers questions about these docs. Old
`bettersupabase.com/create` links redirect to the app with their query
string, so codes and URLs you already shared keep working.

To skip the blank canvas, pick "Start from a template" under Preset. Each
template sets a named preset, adds the blocks its tables use and draws the
app tables with their relations and features. The templates are projects
and tasks, a content calendar, an asset register, event planning, a
feedback board and a course catalog. Starting from one replaces the canvas,
and Undo brings the previous design back.

The Data tab on the table inspector shows eight sample rows for an app
table. The values follow each column's format, options and bounds, a
reference shows a row title from the table it points to, and a nullable
column is empty in some rows. The rows are generated in the browser and
never reach a database.

The Computed section at the end of the Columns tab adds
[rollups and lookups](/docs/blocks/app-tables#rollups-and-lookups). A
rollup counts, sums or takes the min, max or average of the rows that link
to the table, optionally only the rows with one select value. A lookup
shows a column of the row the table links to. You pick each part from the
links the design already has, so there is no SQL to type, and the table's
node lists them under its columns. Deleting or retyping a column a rollup
reads removes the rollup.

The Changes tab in Get code lists what you changed in the app tables since
the page loaded the design in its link. Each change is marked safe or
breaking, and a breaking one (a dropped, renamed or retyped column, or a
column made required without a default) lists the expand-and-contract steps
that [`apply`](/docs/cli/presets#breaking-changes) prints before it refuses
to write the design.

## The shared wiring

Three pieces connect the blocks in every recipe.

The subject is declared once in `config.subjects`. Comments, tags, custom
fields, share links and reminders all read it from the
[subject registry](/docs/blocks/sql#subject-registry), and `rank` reads its `rank` entry.

A state machine is named after its subject (`deal`, `task`, `booking`). The
machine name is the `subjectType` of its history rows and of
`status.changed`, so a status change reaches the same watchers as a comment.

A cron route hands the outbox to the watchers. `watcherHandler` reads the
actor from each outbox row, so whoever acts is not notified of their own
change:

```ts title="app/api/cron/watchers/route.ts"
import { watcherHandler } from "better-supabase/blocks/notifications";

const watchers = watcherHandler(notifications, {
  types: {
    "comment.created": "subject.commented",
    "subject.tagged": "subject.tagged",
    "status.changed": "subject.moved",
    "share_link.created": "subject.shared",
    "field_value.set": "subject.field_changed",
  },
});

export const GET = outbox.relayRoute({
  secret: process.env.CRON_SECRET,
  consumers: { watchers },
});
```

Users follow a row with `notifications.subscribe({ subject, level })`.
Watchers at level `all` get every mapped event. See
[watchers](/docs/blocks/notifications#watchers) for rules with `activity`,
`recipients` and `summary`.

Reminders deliver through the `notifications` block, the `notifier` port,
when the reminders block has a `notification` type. The reminder's owner and the subject's watchers get
one notification per occurrence:

```ts title="lib/blocks.ts"
const { comments, reminders, stateMachine } = createBlocks(
  { transport, service },
  {
    notifications: notificationsBlock.using((options) =>
      createNotifications({ ...options, types }),
    ),
    comments: commentsBlock,
    reminders: remindersBlock.with({ notification: "reminder.due" }),
    stateMachine: stateMachineBlock,
  },
);
```

`reminders.job` runs as the handler of the `reminders.deliver` queue
([delivery](/docs/blocks/reminders#delivery)).
