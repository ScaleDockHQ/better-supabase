title: Notifications
description: In-app notifications with per-recipient state, subject subscriptions, channel preferences, email and push deliveries, and realtime updates on a private topic.
---

The `notifications` [SQL kit](/docs/kits/sql) module stores one event per
change and one row per recipient, with read, dismissed and resolved state
each user controls. `createNotifications` from `better-supabase/notifications`
sends and reads them with typed data, and `useNotifications` from
`better-supabase/react` keeps a list current over Supabase Realtime.

```bash
pnpm better-supabase sql add notifications
```

Sending goes through `notify(jsonb)`, a `security definer` function, so a
client can't write notification rows directly or pick another user as the
actor. With the [access contract](/docs/kits/access) installed, the sender
needs `notifications.send` in the organization and every recipient needs
`notifications.read`; the actor and non-members are left out. With the
[outbox](/docs/kits/outbox), every notification also emits
`notification.created`.

## Sending

Declare each kind with a Standard Schema for its data. `send` validates the
data before it reaches the database:

```ts title="lib/notifications.ts"
import "server-only";

import {
  createNotifications,
  sqlTransport,
} from "better-supabase/notifications";
import { z } from "zod";

export const kinds = {
  "task.assigned": z.object({ title: z.string() }),
  "approval.requested": z.object({ amount: z.number() }),
};

export const notificationsFor = (claims: Record<string, unknown>) =>
  createNotifications({
    transport: sqlTransport(postgres.asUser(claims)),
    kinds,
    actionable: ["approval.requested"],
    events: betterSupabase.events,
    render: (item) => ({ title: `${item.kind}: ${item.subject?.label ?? ""}` }),
  });
```

```ts
const ctx = await bs.context();
const notifications = notificationsFor(ctx.auth.claims);

await notifications
  .send("task.assigned", {
    tenant: orgId,
    recipients: [assigneeId],
    subject: { type: "task", id: task.id, label: task.title },
    actionPath: `/tasks/${task.id}`,
    data: { title: task.title },
    key: `task-assigned-${task.id}-${assigneeId}`,
  })
  .orThrow();
```

`send` returns the notification id, or `null` when nobody was left to notify.
With a `key`, sending again in the same organization returns the first id,
so a retried request never notifies twice. `rpcTransport(supabase)` calls the
same functions over the Data API instead, when the kit schema is exposed.

| Input          | Meaning                                                                                        |
| -------------- | ---------------------------------------------------------------------------------------------- |
| `recipients`   | User ids. Subject watchers and the `notification_audience` hook add more                       |
| `subject`      | What it is about, `{ type, id, label? }`. Watchers of the subject get it too                   |
| `activity`     | `participating` (default) reaches every watcher; `all` reaches only watchers at level `all`    |
| `priority`     | One of `options.priorities` (`low`, `normal`, `high`, `urgent`). Defaults to `normal`          |
| `channels`     | The channels to deliver on. Defaults to `options.channels`                                     |
| `includeActor` | Also notify the user who caused it                                                             |
| `resolved`     | Store it already resolved, for a record of something that needs no action                      |
| `actorId`      | The actor when the service sends for a user. A signed-in sender is always the actor themselves |

## Reading

The same client reads the signed-in user's notifications. `render` runs at
read time, so text follows the reader's locale and later copy changes:

```ts
const items = await notifications
  .list({ tenant: orgId, status: "unread", locale: "nl" })
  .orThrow();
const { unread, actionable } = await notifications
  .counts({ tenant: orgId })
  .orThrow();
await notifications.markRead({ ids: [items[0].id] });
await notifications.dismiss([items[0].id]);
await notifications.resolve({
  kind: "approval.requested",
  subject: { type: "invoice", id },
});
```

`list` pages with `before` (an instant) and `limit` (50 by default, at most
200), and filters with `status` (`all`, `unread`, `read`, `unresolved`) and
`kinds`. `resolve` marks every recipient's copy of a kind about one subject
as handled, for example when someone approves the invoice.

## Realtime

By default each new or changed recipient row is broadcast on the user's
private topic, `notifications:{userId}`. The payload carries ids only; the
client reloads through RLS. `useNotifications` joins the topic with the
user's token, reloads on each message and after a reconnect, and merges any
other sources you pass:

```tsx title="components/inbox.tsx"
"use client";

import { useNotifications } from "better-supabase/react";

export function Inbox({ userId, orgId }: { userId: string; orgId: string }) {
  const { items, count } = useNotifications({
    topic: `org:${orgId}:notifications:${userId}`,
    load: () =>
      fetch(`/api/notifications?org=${orgId}`).then((res) => res.json()),
  });
  return <Bell count={count} items={items ?? []} />;
}
```

| Option         | Default                  | Meaning                                                                  |
| -------------- | ------------------------ | ------------------------------------------------------------------------ |
| `realtime`     | `broadcast`              | `broadcast`, `changes` (adds the table to `supabase_realtime`) or `none` |
| `topic`        | `notifications:{userId}` | The topic template; `{tenantId}` adds the organization                   |
| `createdEvent` | `notification_created`   | The broadcast event for a new notification                               |
| `updatedEvent` | `notification_updated`   | The broadcast event for a read, dismissed or resolved one                |

The module adds a `realtime.messages` policy so each user can join only
topics that match the template with their own id.

## Subscriptions and preferences

Users watch a subject with `subscribe({ subject, level })`. Level `all` gets
routine activity too, `participating` only what involves them, and `ignore`
mutes the subject even when a sender names them. `null` removes the
subscription.

`setPreference({ kind, channel, enabled, tenant? })` turns a kind (or `*`)
on or off on a channel. The most specific row wins: the organization and
kind, the organization and `*`, everywhere and kind, everywhere and `*`,
then `options.channelDefaults` (email is off until a user turns it on).

## Email, push and other channels

Every channel except `in_app` gets a `pending` delivery row per recipient.
Pass a `NotificationChannel` per channel and call `deliver()` from a cron
route or a job, with a service connection:

```ts title="app/api/notifications/deliver/route.ts"
import "server-only";

import {
  createNotifications,
  sqlTransport,
} from "better-supabase/notifications";

import { kinds } from "@/lib/notifications";

const notifications = createNotifications({
  transport: sqlTransport(postgres.admin),
  kinds,
  channels: [
    {
      apiVersion: 1,
      name: "email",
      send: async ({ email, text, notification }) => {
        if (!email) return { status: "skipped" };
        const { id } = await resend.emails.send({
          to: email,
          subject: text?.title ?? notification.kind,
        });
        return { provider: "resend", providerMessageId: id };
      },
    },
  ],
});

export async function GET() {
  return Response.json(await notifications.deliver({ budgetMs: 50_000 }));
}
```

`deliver` claims pending rows with `for update skip locked` and leases them
(`lease`, five minutes by default), so two runs never send the same message.
A channel that throws leaves the row pending for the next run, until
`maxAttempts` (5) marks it `failed`. `testNotificationChannel` from
`better-supabase/testing` checks a channel against the contract.

## Extending it

| Hook or event                   | Use                                                                           |
| ------------------------------- | ----------------------------------------------------------------------------- |
| `notification_audience` hook    | A SQL function that adds recipients, e.g. everyone with a role on the subject |
| `after_notify` hook             | A SQL function that runs in the same transaction after the rows are written   |
| `onSent` option                 | Runs after `send` stores a notification, e.g. to call Next's `updateTag`      |
| `notification.*` kit events     | `created`, `delivered` and `failed` on `betterSupabase.events`                |
| `notifications.send` permission | Rename it with `kits.notifications.permissions.send`                          |

## Existing tables

The default names match a common layout (`notification_events` with `type`
and `metadata`, `notification_recipients`, `notification_deliveries`,
`notification_subscriptions` and `notification_preferences`, keyed on
`organization_id`). Adopt yours and rename what differs; map columns and
tables you don't have to `null`:

```ts title="better-supabase.config.ts"
export default defineConfig({
  kits: {
    notifications: {
      mode: "adopt",
      schema: "public",
      idType: "uuid",
      tables: { subscriptions: null },
      columns: { events: { key: null }, recipients: { resolvedAt: null } },
      options: {
        topic: "org:{tenantId}:notifications:{userId}",
        channels: ["in_app", "email"],
      },
    },
  },
});
```

Without a key column, keyed sends derive the event id from the organization
and key instead. A recipient with in-app off for a kind still gets a row,
stored as dismissed, so other channels can deliver it.

## Error codes

| `hint`                          | When                                                               |
| ------------------------------- | ------------------------------------------------------------------ |
| `NOTIFICATION_KIND_REQUIRED`    | `notify` without a kind                                            |
| `NOTIFICATION_KIND_UNKNOWN`     | `send` with a kind that isn't in `kinds` (checked in TypeScript)   |
| `NOTIFICATION_FORBIDDEN`        | The sender lacks `notifications.send` in the organization          |
| `NOTIFICATION_PRIORITY_UNKNOWN` | A priority that isn't in `options.priorities`                      |
| `NOTIFICATION_ACTIVITY_UNKNOWN` | An `activity` other than `participating` or `all`                  |
| `NOTIFICATION_LEVEL_UNKNOWN`    | A subscription level other than `participating`, `all` or `ignore` |
| `NOTIFICATION_STATUS_UNKNOWN`   | Completing a delivery with a status the kit doesn't know           |
