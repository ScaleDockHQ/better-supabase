---
title: db
description: Run SQL files and typed seeds against the local stack or another database, and diff the schema into a migration.
---

## query

```bash
pnpm better-supabase db query supabase/tests/seed.sql supabase/tests/more.sql
pnpm better-supabase db query --single-transaction a.sql b.sql
```

`db query` runs each file as one script, in the order you pass them. A file
can hold many statements, so a data migration or a fixture file runs as it
would in `psql -f`, without a `psql` install.

| Flag                   | Effect                                                                            |
| ---------------------- | --------------------------------------------------------------------------------- |
| `--single-transaction` | Wraps every file in one transaction, so a failure keeps none.                     |
| `--stack <name>`       | Uses the database of `supabase/stacks/<name>/config.toml` (default `$BSB_STACK`). |
| `--db-url-stdin`       | Reads the connection string from stdin, so it never reaches argv.                 |

Without `--db-url-stdin`, the command connects through `$DATABASE_URL`,
`$SUPABASE_DB_URL`, or the local stack. Against a database that is not local,
an agent needs the user's consent first. A failing file stops the run, and
the error names it. The JSON envelope lists the files that ran in `data.ran`.

Side effects: Writes to the database.

## diff

```bash
pnpm better-supabase db diff -f add_invoices
pnpm better-supabase db diff --in-stack
```

`db diff` turns the declarative schema files into a migration. On a local
database under pg-delta, it plans with pg-delta's library: it creates a shadow
database in the same Postgres as the stack, loads the files into it, and plans
the changes from the stack to the shadow. The shadow is dropped afterwards,
also when a step fails. The stack has to have applied every migration first
(`supabase migration up`), or the diff would repeat them.

Under migra, or on a database that isn't local, `db diff` runs the Supabase
CLI's command for the workflow (`supabase db diff`). When that command can't
start its shadow database, usually because every System V shared memory
segment is in use (macOS allows 32, and each running stack holds one), `db
diff` plans with the library on the stack you already run.

The plan is checked before anything is written:

- A table or column that looks renamed is never guessed. Record the rename in
  a migration as `-- bsb: rename old_name -> new_name` and the next diff plans
  a rename that keeps the data. Without it, the diff plans a drop and a create
  and tells you which rename it suspects.
- An action that destroys data (dropping a table or column, narrowing a
  column type) stops the diff with a `check_failed` error and writes nothing.
  Run it again with `--allow-data-loss` once you have read the list.

| Flag                | Effect                                                                                 |
| ------------------- | -------------------------------------------------------------------------------------- |
| `-f, --file`        | Saves the diff as `supabase/migrations/<timestamp>_<name>.sql` instead of printing it. |
| `--in-stack`        | Plans with the library on the running stack, without the Supabase CLI.                 |
| `--allow-data-loss` | Writes the migration even when it destroys data.                                       |
| `--stack <name>`    | Uses the database of `supabase/stacks/<name>/config.toml` (default `$BSB_STACK`).      |

A migration from the library plan starts with a comment that asks you to
review it: it compares two databases, so check the order of the statements
before you apply it. The JSON envelope names the engine in `data.engine`, lists
the plan's findings in `data.issues` and sets `data.fellBack` when the shadow
database failed. `better-supabase dev stack prune` frees the segments that idle
stacks hold.

Side effects: Writes to the database, writes files with --file.

## seed

Define fixtures once, in app casing, checked against your Insert types:

```ts title="supabase/seed.ts"
import { defineSeed } from "better-supabase/testing";
import { betterSupabase } from "../src/lib/supabase/index.ts";

export const ACME = "00000000-0000-4000-8000-000000000001";

export const seed = defineSeed(betterSupabase, {
  organizations: { acme: { id: ACME, name: "Acme", slug: "acme" } },
  customers: {
    first: {
      organizationId: ACME,
      name: "First customer",
      metadata: { tier: "pro" },
    },
  },
});
```

```bash
pnpm better-supabase db seed          # writes supabase/seeds/000_better_supabase.sql
pnpm better-supabase db seed --check  # fails in CI when the SQL is stale
pnpm better-supabase db seed --apply  # also inserts into the local database
```

`--entry <file>` and `--out <file>` override `database.seed.entry` and
`database.seed.output`. `--dry-run` prints the diff and writes nothing; neither it nor
`--check` runs `--apply`. `--apply` connects to `$DATABASE_URL` or `$SUPABASE_DB_URL`, or to the local stack;
to seed another database, pipe its connection string in with
`--db-url-stdin`.

- Tables are inserted parents first, following foreign keys.
- Missing columns use their defaults, and every insert is
  `on conflict do nothing`, so a seed can run twice.
- Unknown tables and columns are type errors. A column you leave out that
  has no default fails in the editor, not at `db reset`.
- Add the file to `[db.seed] sql_paths` in `supabase/config.toml`. `db seed`
  prints the line when it's missing, and it never overwrites a file it
  didn't write unless you pass `--force`.

Tests import the same rows: `seed.rows.customers.first`, and
`await seed.insert(sql)` in a `beforeAll`. Node loads `seed.ts` directly,
so use `.ts` extensions in its relative imports.

### Seeds per tenant

A tenant seed builds rows from a tenant, so every organization can start
with the same demo data. Put it in `database.seed.perTenant`
(`supabase/seed.tenant.ts` by default):

```ts title="supabase/seed.tenant.ts"
import { defineTenantSeed } from "better-supabase/testing";
import { betterSupabase } from "../src/lib/supabase/index.ts";

export const seed = defineTenantSeed(betterSupabase, (tenant) => ({
  customers: { demo: { organizationId: tenant.id, name: "Demo customer" } },
}));
```

```bash
pnpm better-supabase db seed --tenant acme  # one organization, by slug or id
pnpm better-supabase db seed --tenant '*'   # every organization
```

`--tenant` looks organizations up in the
[organizations block](/docs/blocks/organizations) and inserts the rows for
all of them in one transaction, so a failure leaves none behind. `--entry`
overrides `database.seed.perTenant`. The database and consent rules are the ones
`--apply` follows: the local stack needs no consent, any other database
does, and `--dry-run` connects to nothing. `tenant.slug` and `tenant.name`
are set when the organization has them. Every insert is
`on conflict do nothing`, so give rows a key when the seed may run twice
for the same tenant; a row whose id comes from a default is inserted again.

To seed each organization as it's created in development, register the
seed once on the server with a service-role client:

```ts title="src/lib/supabase/dev-seed.ts"
import { createPostgres } from "better-supabase/postgres";
import { seedTenantOnCreate } from "better-supabase/testing";
import { seed } from "../../../supabase/seed.tenant.ts";
import { betterSupabase } from "./index.ts";

const postgres = createPostgres({
  connectionString: process.env.SUPABASE_DB_URL,
});

seedTenantOnCreate(betterSupabase, seed, { sql: postgres.admin });
```

It listens for `organization.created` and runs only when `NODE_ENV` is
`development` (pass `enabled` to decide yourself). The seed runs after the
create call has returned, so it can't change its result; a failed seed goes
to `onError`, or to `console.error` by default.

Side effects: Writes files, writes to the database with `--apply`, writes to the database with `--tenant`.

## backfill

```bash
pnpm better-supabase db backfill invoices.organization_id --from projects.organization_id via project_id
pnpm better-supabase db backfill invoices.currency --value "'EUR'" --dry-run
```

`db backfill` fills the null values of a column that a migration added to a
table that already holds rows, the middle step of expand and contract. With
`--from`, it copies each value from the table a foreign key column points at:
`via project_id` names the column of the target table, and the command finds
the key it references (the foreign key, else the primary key of the source
table). With `--value`, it writes one SQL literal, such as `'EUR'`, `0`,
`true` or `'{}'::jsonb`, to every null row.

It updates `--batch-size` rows per statement, each in its own transaction,
and locks only those rows (`for update skip locked`), so the app keeps
writing while it runs. It prints a line per batch. It only touches rows where
the column is null, so a run that stops can start again, and a second run
fills nothing. Rows whose source value is null, or that have no source row,
stay null; the result counts them in `remaining`.

| Flag                 | Effect                                                                             |
| -------------------- | ---------------------------------------------------------------------------------- |
| `--from <table.col>` | Copies the value from this column, joined through `via <column>`.                  |
| `--via <column>`     | The foreign key column of the target table, the same as a trailing `via <column>`. |
| `--value <literal>`  | Writes this SQL literal instead of `--from`.                                       |
| `--batch-size <n>`   | Rows per statement (default 1000).                                                 |
| `--dry-run`          | Counts the rows it would fill and writes nothing.                                  |
| `--stack <name>`     | Uses the database of `supabase/stacks/<name>/config.toml` (default `$BSB_STACK`).  |
| `--db-url-stdin`     | Reads the connection string from stdin, so it never reaches argv.                  |

A table name without a schema means `public`. The command connects like
[`db query`](#query), and against a database that is not local, an agent
needs the user's consent first. The JSON envelope returns `data.filled`,
`data.batches` and `data.remaining`, or `data.pending` with `--dry-run`.

Each update fires the table's triggers, so audit, version and event triggers
record every backfilled row. When nothing is left null, add the not-null check
as `not valid` in a migration, then run
[`doctor --fix`](/docs/cli/doctor#bs236), which validates it. Then
`set not null` needs no scan:

```sql
alter table invoices
  add constraint invoices_currency_not_null check (currency is not null) not valid;
```

A `tables.<name>` entry that enriches a table you already have adds that check
to the scope column itself, so the order there is the other way round: new
rows must name an owner at once, and `db backfill` fills the existing rows
that [doctor reports as BS238](/docs/cli/doctor#bs238). See
[Your own schemas](/docs/blocks/own-schemas#fill-the-owner-with-db-backfill).

Side effects: Writes to the database.

## prune-workflows

```bash
pnpm better-supabase db prune-workflows --older-than 30d
pnpm better-supabase db prune-workflows --older-than 7d --status failed --dry-run
```

`db prune-workflows` deletes the [Workflow SDK](/docs/blocks/workflow-sdk)
runs that ended longer ago than `--older-than`, with their events, steps,
waits, stream chunks and hooks. It calls `workflow_purge_runs` in batches
until a batch comes back short, so each statement holds its locks only
briefly. Running runs are never deleted. Run it on a schedule when the
database has no pg_cron, or set the block's
[`retention`](/docs/blocks/workflow-sdk#retention) option instead.

| Flag                 | Effect                                                                            |
| -------------------- | --------------------------------------------------------------------------------- |
| `--older-than <age>` | `30d`, `12h`, `7 days` or `12 hours` (default `30d`).                             |
| `--status <list>`    | Comma-separated: `completed`, `failed`, `cancelled` (default all three).          |
| `--batch-size <n>`   | Runs per statement, 1 to 10000 (default 500).                                     |
| `--dry-run`          | Counts the runs it would delete and writes nothing.                               |
| `--stack <name>`     | Uses the database of `supabase/stacks/<name>/config.toml` (default `$BSB_STACK`). |
| `--db-url-stdin`     | Reads the connection string from stdin, so it never reaches argv.                 |

Against a database that is not local, an agent needs the user's consent
first. The JSON envelope returns `data.deleted`, or `data.pending` with
`--dry-run`.

Side effects: Writes to the database.
