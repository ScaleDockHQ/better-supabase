---
title: doctor
description: Security, performance and drift checks for your database, config.toml and env files.
---

```bash
pnpm better-supabase doctor
```

`doctor` introspects the database the same way [`gen`](/docs/cli/gen) does,
then reads `supabase/config.toml`, your `.env*` files and `.gitignore`. Every
finding has a code, a severity and a link to its section on this page. When a
finding is about a table, function or policy, doctor points at the file that
creates it: declarative schemas in `supabase/schemas` first, then the newest
migration.

It also runs Supabase's own [Security and Performance
Advisors](https://supabase.com/docs/guides/database/database-advisors) (BS100
and BS200), so the dashboard's findings show up locally and in CI. It exits
with 1 when there are errors, or with any warning under `--fail-on warning`.

| Option                     | Description                                                                                                                                                                                                                                                        |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `--format <f>`             | `text` (default), `sarif` or `github`; also `tooling.doctor.format`. The global `--json` prints the JSON report                                                                                                                                                    |
| `--out <file>`             | Write the report to a file; also `tooling.doctor.file`, which applies with `tooling.doctor.format`                                                                                                                                                                 |
| `--only <codes>`           | Run only these checks, e.g. `--only BS100,BS304`; also `tooling.doctor.only`                                                                                                                                                                                       |
| `--ignore <codes>`         | Skip checks. Adds to `tooling.doctor.ignore` in the config                                                                                                                                                                                                         |
| `--fail-on <level>`        | Exit 1 on findings at this level: `error` (the default), `warning` (the default with `tooling.doctor.strict`) or `never`                                                                                                                                           |
| `--snapshot <file>`        | Check a saved snapshot instead of the database                                                                                                                                                                                                                     |
| `--metadata <path\|->`     | Check a `GeneratorMetadata` document (`-` for stdin). Checks that need policies, grants, indexes, triggers or other data it lacks are skipped with an info finding; it exits 65 for a document it rejects ([gen](/docs/cli/gen#from-a-generatormetadata-document)) |
| `--db-url-stdin`           | Read the connection string of the database to check from stdin                                                                                                                                                                                                     |
| `--project-ref <ref>`      | Hosted project to read through the Management API (needs `SUPABASE_ACCESS_TOKEN`)                                                                                                                                                                                  |
| `--stats`                  | Report slow frequent statements from `pg_stat_statements` ([BS209](#bs209))                                                                                                                                                                                        |
| `--explain <tables>`       | Plan these tables, or functions such as `rs_customers_hub` and `order_payload`, under RLS ([BS212](#bs212))                                                                                                                                                        |
| `--explain-write <tables>` | Plan an insert (a copy of one row with fresh keys) and an update on these tables, with the time of each trigger ([BS212](#bs212))                                                                                                                                  |
| `--args <json>`            | With `--explain <function>`: the arguments, a JSON array (positional) or object (named)                                                                                                                                                                            |
| `--as <uuid>`              | With `--explain` or `--explain-write`: plan as this authenticated user. Also measures the claims the custom access token hook returns for them ([BS405](#bs405))                                                                                                   |
| `--claims <json>`          | With `--explain` or `--explain-write`: plan with these JWT claims                                                                                                                                                                                                  |
| `--fix-grants`             | Print the grant and revoke SQL that [BS404](#bs404) asks for, as one block for a schema file or migration                                                                                                                                                          |
| `--update-baseline`        | Rewrite the [baseline](#baseline) file to accept this run's errors and warnings                                                                                                                                                                                    |

Doctor never prints env values, only variable names and line numbers.

Side effects: Reads the database, writes to the database with `--yes`, calls the Supabase Management API with `--project-ref`, downloads from GitHub.

## In CI

`--format github` writes workflow annotations, so findings show up on the pull
request diff:

```yaml
- run: pnpm better-supabase doctor --format github --fail-on warning
```

The `github` and `sarif` formats write file paths relative to the repository
root (the directory that holds `.git`, else the Supabase project root), so
annotations land on the right files when the CLI runs from a package. The text
format keeps paths relative to the project directory.

For GitHub code scanning, upload SARIF:

```yaml
- run: pnpm better-supabase doctor --format sarif --out doctor.sarif
- uses: github/codeql-action/upload-sarif@v3
  if: always()
  with:
    sarif_file: doctor.sarif
```

To keep the workflow step to `better-supabase doctor`, put the CI settings in
the config's [`ci` environment](/docs/cli/config#environments), which the CLI
applies when `$CI` is set:

```ts title="better-supabase.config.ts"
export default defineConfig({
  $ci: {
    tooling: {
      doctor: { format: "sarif", file: "doctor.sarif", strict: true },
    },
  },
});
```

`doctor --json` puts the report in the envelope's `data`. The report follows
[`doctor-report-v1.json`](https://unpkg.com/better-supabase/schemas/doctor-report-v1.json),
and a run with errors has the `findings` error code.

## Ignoring checks

```ts title="better-supabase.config.ts"
export default defineConfig({
  tooling: { doctor: { ignore: ["BS204"], strict: true } },
});
```

`tooling.doctor.sources` lists the app files that checks such as BS210 scan, as globs
relative to the project root. The default is `['src/**/*.{ts,tsx}']`; at the
root of a pnpm or npm workspace, doctor also scans that glob in each package,
such as `apps/web/src/**/*.{ts,tsx}`. A `sources` you set is used as it is.
`tooling.doctor.claimsLimit` is a BS405 limit in bytes: the budget of the
[authorization provider's](/docs/extending/authorization-providers) hook when
it sets `tokenHook.budget`, otherwise the limit for the whole token (default
2048).
`tooling.doctor.policyHelperLimit` (default 5) is how many policies a security definer
helper may appear in before [BS206](#bs206) reports it.

## Baseline

A baseline accepts the findings an existing project already has, so CI fails
only on new ones. Point `tooling.doctor.baseline` at a JSON file and write it
once:

```ts title="better-supabase.config.ts"
export default defineConfig({
  tooling: { doctor: { baseline: "doctor-baseline.json" } },
});
```

```sh
pnpm better-supabase doctor --update-baseline
```

The file lists one entry per accepted finding, keyed by its code and target
(its title when it has none). Fill in each `reason` so a reviewer can see why
the finding stays:

```json title="doctor-baseline.json"
[
  {
    "code": "BS351",
    "target": "src/app/settings/actions.ts:12",
    "reason": "Moves to the credentials API in the next release"
  }
]
```

Doctor leaves out the findings the file lists. An entry that no finding matches
fails the run as an error with its code, so the baseline shrinks as you fix
findings: remove the entry, or run `--update-baseline` again. It only judges an
entry when its check ran, so a run without a database keeps the entries of the
checks that need one, and `--only` keeps the rest. `--update-baseline` keeps
each entry's reason, gives a new entry the reason of another entry with its
code, and leaves out info findings.

The full `doctor` block, generated from the `DoctorConfig` type:

## Supabase advisors

### BS100

**Security Advisor findings.** Each finding keeps the advisor's own severity
(error, warning or info), title and remediation link. The advisor covers RLS
disabled in exposed schemas, RLS without policies, security definer functions
anon or authenticated can call, mutable `search_path`, `auth.users` exposed
through views, `user_metadata` in policies and more. The message ends with the
lint name, for example `[rls_disabled_in_public]`.

Where the findings come from depends on what doctor reads:

- **Hosted projects** (`--project-ref` or `database.source.projectRef`): the Management
  API's `GET /v1/projects/{ref}/advisors/security`, the same data the dashboard
  shows.
- **A database on this machine** (the local stack or a loopback URL): `supabase db advisors`
  when the Supabase CLI is 2.81.3 or later. Doctor passes the URL with
  `--db-url`, `--type` and `--level info`, and reads the JSON output (a list, an
  object with `lints`, or one lint per line). A missing or older CLI, a remote
  database, a failed run or an output shape it doesn't know falls back to
  splinter.
- **Any other database, or the fallback** (`$DATABASE_URL`, `$SUPABASE_DB_URL` or `--db-url-stdin`): [splinter](https://github.com/supabase/splinter),
  the SQL behind the advisors. Doctor downloads `splinter.sql` at a pinned
  commit, checks its SHA-256, caches it in
  `node_modules/.cache/better-supabase` and runs it in a read-only transaction
  that is rolled back. splinter has no license, so it isn't bundled.
- **Saved snapshots:** there is no database to lint, so doctor reports an info
  finding saying the advisors were skipped.

If the advisors can't run (offline, no access token), doctor reports a warning
instead of failing silently. For `--project-ref`, use a scoped personal access
token limited to the project and the advisor and read-only query permissions
(see [Hosted projects](/docs/cli/gen#hosted-projects-without-a-database-password)),
not a classic token with access to your whole account.

### BS200

**Performance Advisor findings.** Same sources as BS100: unindexed foreign
keys, `auth.uid()` re-evaluated per row in policies, multiple permissive
policies, unused and duplicate indexes, tables without a primary key, table
bloat and more. Doctor's own [BS207](#bs207) and [BS216](#bs216) repeat
splinter's `multiple_permissive_policies` and `unindexed_foreign_keys`; when
BS200 runs and the advisor loads, they skip the tables splinter reports, so
each problem shows up once.

## Security

### BS103

**Error: policy allows anonymous writes.** A permissive `insert`, `update`,
`delete` or `all` policy for `anon` or `public` uses `true`. Anyone can change
rows. Restrict the policy to `authenticated` and check ownership.

### BS106

**Error: table not granted to the Data API.** Hosted projects grant new
tables to `anon` and `authenticated` unless the project turns default
privileges off (`auto_expose_new_tables = false` locally). Without a grant,
every request fails with
`42501` before RLS runs. Tables listed in [`expose`](/docs/guides/data-api-grants)
need exactly the privileges listed; other tables in the generated schemas need
`select` for `authenticated`, except tables with RLS on and no permissive
policy when
`blocks.grants.options.fromPolicies` is on: those are service-only, so
BS106 expects no grants for them ([BS115](#bs115)). Add the table to `expose`
and run `better-supabase add grants`. When `config.toml` sets
`[api] auto_expose_new_tables = false`, the finding says so.

A table that only the server reads, such as an audit log written with the
secret key, is kept off the Data API on purpose. Mark it
`tables: { audit_logs: { serviceRole: true } }`: BS106 then checks the
opposite, that `anon` and `authenticated` (directly or through `public`) have
no grant on it, and reports any they have. Its models are still generated, so
an admin client keeps its types. `exclude` also silences BS106, but leaves
the table out of the generated models.

### BS107

**Warning: tenant table without a policy for every command.** A table with
the tenant column (or whose policies call a membership or tenant helper) has
permissive policies for `authenticated` covering some of `select`, `insert`,
`update` and `delete`, but not all. RLS denies the missing commands without
an error, so an update or delete matches 0 rows and the UI looks like it
worked. Add the missing policies, or a restrictive `using (false)` policy to
make a read-only table explicit, and cover the table with
[`expectTenantIsolation`](/docs/testing#tenant-isolation). The tenant table
itself (the one the tenant column references) is skipped. On an app table a
block runs over, only your own policies decide whether the table is reported:
the block reads it through its `bsb_` policies and writes it through its own
functions, so a table with only block policies is left alone.

### BS108

**Error: policy reads `auth.mfa_factors` directly.** `authenticated` can't
select from `auth.mfa_factors`, so the policy fails every request with
`42501`. Use `(select better_supabase.mfa_satisfied())` from
`better-supabase add mfa`, a `security definer` function. See
[MFA and SSO](/docs/auth/mfa-sso).

### BS109

**Warning: `auth.role()` in a policy or function.** Supabase deprecated
`auth.role()`. Doctor reads every policy, the functions policies call and the
functions in the exposed schemas. Scope the policy with `to authenticated`
instead, or read the claim with `(select auth.jwt() ->> 'role')`.

### BS110

**Warning: update policy without a select policy or with check.** An update
finds its rows through the select policies first, so a role with an update
policy but no select policy updates nothing and gets no error. Add a select
policy for the same role. An update policy without `with check` is an info
finding: Postgres then checks the new row against `using`, which leaves
unstated whether a row may move to another owner or tenant. Write both:

```sql
create policy notes_update on public.notes for update to authenticated
  using (organization_id in (select better_supabase.member_organization_ids()))
  with check (organization_id in (select better_supabase.member_organization_ids()));
```

### BS111

**Warning: API roles hold privileges they don't use.** `anon` and
`authenticated` never need `truncate`, `references` or `trigger` on a table,
and `truncate` skips RLS. The finding lists the `revoke`. A grant to `anon`
on a table with RLS where no policy applies to `anon` is an info finding: it
lets no request through, but lists the table in the Data API schema that
anyone with the publishable key can read.

### BS112

**Warning: exposed security definer function that doesn't check the
caller.** A `security definer` function runs as its owner, past RLS. In an
exposed schema the Data API serves it at `/rpc/<name>`, so when `anon` or
`authenticated` may execute it and its body never reads `auth.uid()`,
`auth.jwt()` or the request claims, any caller gets the owner's access. Check
the caller in the body, revoke `execute` from the API roles, or move the
function to a schema the API doesn't expose. Trigger functions are skipped;
`/rpc` can't call them. Needs a snapshot taken with this version, which
records who may execute each function.

### BS113

**Info: storage upload policy without the upsert policies.** An upload with
`upsert: true` (the `x-upsert` header) needs `select` and `update` policies
on `storage.objects` besides `insert`. Without them, replacing a file that
exists fails with 403. Doctor reads the policies in `supabase/schemas` and the
migrations; add the missing ones with the same bucket and path check.

### BS114

**Error: policy helper reads `user_metadata`.** Users can change their own
`raw_user_meta_data` with `auth.updateUser()`, so a function that reads
`user_metadata` to decide access lets them grant themselves rights. Read
`app_metadata`, which only the service role can write. Splinter's
`rls_references_user_metadata` (BS100) covers the policy text; this check
covers the functions policies call, and the functions those call.

### BS115

**Warning: table without a policy still granted to the Data API.** A table
with RLS on and no permissive policy for `anon` or `authenticated` answers
every request with no rows or a denied write, yet a grant lists it in the API
schema. With `blocks.grants.options.fromPolicies`, `better-supabase upgrade`
revokes `anon`, `authenticated` and `public` on every table in `schemas` with
RLS on that no `expose` entry and no permissive policy reaches, and keeps the privileges
of `service_role`. Until the migration is applied, doctor reports the grants
that are still on the database. Tables in `expose`, `tables.<name>.exclude`
and `tables.<name>.serviceRole` are skipped.

### BS116

**Warning: security definer function open to the API roles but not
exposed.** Postgres grants `execute` on a new function to `public`, so a
`security definer` function in an exposed schema is callable at `/rpc` by
`anon` and `authenticated` unless it is revoked. When no
[`expose`](/docs/guides/data-api-grants) entry lists the function and no
policy calls it, nothing in the project says the API roles should reach it.
Doctor never revokes anything. Run
`revoke all on function schema.name(args) from public, anon, authenticated;`,
then grant `execute` to the roles that call it (or list the function in
`expose`). [BS112](#bs112) reports the same functions when they also skip a
caller check. Needs a snapshot taken with this version, which records who may
execute each function.

### BS117

**Warning: policy without a role.** A policy without `to`, or with
`to public`, applies to every role, `anon` included. Postgres evaluates it on
requests it was never written for, and a later edit to its expression can
open the table to signed-out users. Name the roles the policy is for:

```sql
create policy notes_read on public.notes for select to authenticated
  using (organization_id = (select better_supabase.current_tenant_id()));
```

Restrictive policies only narrow access, so doctor skips them.

## Performance

### BS204

**Warning: tenant column without an index.** With the
[memberships extension](/docs/blocks/memberships), every query filters on the tenant column. Add
an index that starts with it. Views are left out, because a query on a view
uses the indexes of its tables.

### BS205

**Warning: policy calls a slow function once per row.** A policy passes a
column of the row, such as `is_member(organization_id)`, to a function
Postgres can't inline: `plpgsql` or another non-SQL language, `volatile`,
`security definer`, or with any `set` option (`set search_path = ''`
included). The call runs once for every row the query reads. Doctor finds the
functions a policy calls in `pg_depend`, so helpers in private schemas count
too. Have the helper return the allowed values once and compare, which works
for security definer helpers as well:

```sql
create policy notes_member on public.notes for select to authenticated
  using (organization_id in (select private.user_organization_ids()));
```

### BS206

**Warning: security definer policy helper that cannot be inlined.** A
`security definer` function appears in more than `tooling.doctor.policyHelperLimit`
policies (default 5). Postgres never inlines a security definer function, even
one written in `language sql stable`, so a call that takes a column of the row
runs once per row. Call it as `(select helper(...))` when its arguments don't
come from the row, so Postgres evaluates it once per statement as an
InitPlan, or have it return the allowed ids as a set and compare with
`organization_id in (select helper())`. When the helper itself is slow, compute
its answer once per transaction with
[`better_supabase.memo_get` and `memo_set`](/docs/blocks/sql#memoize-a-value-for-one-transaction).
A policy whose every call to the
helper already reads `(select helper(...))` with constant arguments, such as
`(select tenant_ids_with('crm.read'))`, doesn't count.

### BS207

**Warning: several permissive policies for one command and role.** Postgres
evaluates every permissive policy that applies to a command and role, and ORs
the results, so each extra policy adds its cost to every row. The message
lists each command and role with its policies; a policy for `public` counts
for every role. Merge each group into one policy with `or`. When
[BS200](#bs200) runs, splinter's `multiple_permissive_policies` reports the
tables it covers and this check skips them; on a saved snapshot, or when the
advisor can't run, this check reports every table. On one of your tables that a
block runs over, one of your policies next to the block's `bsb_` policy for the
same command is left to [BS347](#bs347): it reports the pair when the block's
condition is wider. When your policy already covers the block's, the block
adds no policy there.

### BS208

**Warning: queries spill to temporary files.** Reads `temp_files` and
`temp_bytes` from `pg_stat_database` since the statistics were last reset,
with the current `work_mem`. When `pg_stat_statements` is installed, the
message lists the five statements that wrote the most temporary blocks.
Statements run by Supabase's service roles (PostgREST's schema cache query as
`authenticator`, Auth and Storage) are left out, and so are better-supabase's
own catalog reads from `gen` and `doctor`, which start with the
comment `/* better-supabase */`. When only those spilled, there is no finding. Add indexes so large sorts go away, or raise `work_mem`
for the role that runs them. Needs a database; saved snapshots skip it.

### BS209

**Warning: slow frequent statements.** With `--stats`, doctor reads
`pg_stat_statements` and reports statements with a mean time above 50 ms and
more than 1000 calls, slowest total first. When a statement names a table in
the exposed schemas, the finding points at the file that creates the table.
Without the extension, doctor reports an info finding with the
`create extension` command.

### BS210

**Warning: aggregates used while PostgREST disables them.** PostgREST
answers `aggregate()`, `_sum`, `_avg`, `_min` and `_max` includes and list
[`facetCounts`](/docs/platform/list#facet-counts) with PGRST123 unless `pgrst.db_aggregates_enabled` is on for the `authenticator`
role. Doctor reads the role's settings from the database and scans the files
in `tooling.doctor.sources` (default `src/**/*.{ts,tsx}`) for those calls. Turn
aggregates on in a migration:

```sql
alter role authenticator set pgrst.db_aggregates_enabled = 'true';
notify pgrst, 'reload config';
```

Saved snapshots from before this check carry no role settings, so they skip it.

### BS211

**Info: statement timeouts for the Data API roles.** PostgREST switches to
`anon` or `authenticated` for each request, so their `statement_timeout`
limits Data API queries; doctor reports the values set on `anon`,
`authenticated` and `authenticator`. A function's own
`set statement_timeout = ...` only applies to an RPC when PostgREST hoists
it into the transaction. When `pgrst.db_hoisted_tx_settings` is set without
`statement_timeout`, doctor warns for each exposed function that sets one.
It also reports each role's `idle_in_transaction_session_timeout`, which ends
a session that leaves a transaction open. A role setting applies to the role
a connection logs in as, not to `set role`, so for `better-supabase/postgres`
set it on the login role or with the pool's `idleInTransactionTimeout`.

### BS212

**Info: RLS plan for a table.** `--explain customers,notes` runs, for each
table, in a transaction that is rolled back:

```sql
set local track_functions = 'all';  -- skipped if the role may not set it
select set_config('request.jwt.claims', '<claims>', true);
set local role authenticated;       -- the claims' role, default anon
explain (analyze, buffers, format json) select * from public.customers limit 1000;
```

That is the query `list()` sends, capped at Supabase's default `max_rows`.
`--as <uuid>` plans as `{ "sub": uuid, "role": "authenticated" }`;
`--claims '{"role":"authenticated","tenant_id":"..."}'` sets any claims your
policies read. Qualify tables outside the exposed schemas, such as
`better_supabase.memberships`.

The finding lists node types, timings and loops, never row data, with the
number of InitPlans and each function's share of the execution time from
`pg_stat_xact_user_functions`. A SubPlan that runs more than once means a
policy is evaluated per row, and the finding becomes a warning: wrap the
policy's function calls in `(select ...)` so they run once as an InitPlan.
`--explain` needs a direct connection (local stack, `$DATABASE_URL`, `$SUPABASE_DB_URL` or `--db-url-stdin`); the
Management API's read-only endpoint can't switch roles.

`--explain-write customers` measures what a write costs, which a read plan can't show: audit, `updated_at` and
outbox triggers all run inside the write. It copies one existing row with fresh keys (a new uuid, a unique text
value, or the key's default) into an insert, and assigns one non-key column its own value in an update. Each
statement runs under `EXPLAIN (ANALYZE)` in a transaction that is rolled back, and the finding lists the time
of every trigger from the plan. The update assigns a column its own value, so a trigger that fires only when a
column changes (like an audit trigger with `ignore`) shows only its cheap exit. Compare the numbers with
`audit(..., statement => true)` for bulk writes.

`--explain` also takes a function in an exposed schema, such as a compiled read
set (`rs_customers_hub`) or a payload function (`order_payload`). Pass the
arguments with `--args`, as a JSON array (positional) or object (named), and
the user with `--as`:

```bash
better-supabase doctor --explain rs_customers_hub --as 0000…00ff \
  --args '{"p_customer":"c7d1…"}'
```

Each value is sent as a literal cast to the argument's declared type, and the
finding never prints rows. When a security definer helper ran, the finding adds
a policy time share: the helpers' self time over the execution time, next to
the calls each helper made in the statement.

```text
info    BS212 RLS plan for a table
        public.customers as authenticated 0000…00ff: 0.15 ms, 1 InitPlan.
        Plan: Limit 0.14 ms ×1 > InitPlan 1: Result 0.13 ms ×1 > Seq Scan on
        customers 0.14 ms ×1. Function time: better_supabase.current_tenant_id
        0.13 ms over 1 call (83%).
```

### BS213

**Warning: API roles can write the columns that grant access.** RLS helpers
decide who sees a row from other rows: `better_supabase.has_organization_role` reads
`memberships.user_id` and `memberships.role`, and a contact-scoped helper reads
`contacts.user_id` and `contacts.customer_id`. Doctor collects the columns
that the helpers your policies call read, including the helpers those call,
plus the `decidingColumns` of the authorization provider. It warns when `anon` or `authenticated` may insert or update one of
those columns and a policy lets them write the row: a member who can update
their own `role`, or a portal contact who can change `customer_id`, grants
themselves access.

Four kinds of column don't count. A single-column primary key doesn't, because
its uniqueness stops a write from taking over another row. A tenant column
doesn't when every policy for the write pins it without an `or`, to
`better_supabase.current_tenant_id()`, to `better_supabase.can('tenant', column, ...)`
or to `column in (select better_supabase.tenant_ids_with(...))` or
`column in (select better_supabase.member_organization_ids())`, so a write can
only name a tenant the caller is a member of or holds the permission in. A
subject's `deletedAt` column in `config.recordTypes` doesn't: `can_subject`
filters soft-deleted rows out of a check that the row's own policies already
pass, so clearing the column only shows a row again to someone who could
already write it. A block's soft-delete column that its triggers never let a
write clear, such as `comments.deleted_at`, doesn't either. A column the
provider lists in `decidingColumns` always counts.

A table-level grant counts even after a column-level revoke, because
Postgres checks the table grant first. A grant to `public` counts for both
roles, and the SQL then revokes it from `public` too. The finding lists the SQL that keeps
the other columns writable:

```sql
revoke insert, update on public.contacts from authenticated;
grant insert (id, name, email), update (id, name, email) on public.contacts to authenticated;
```

Helper bodies come from the database, or from your SQL files when the
snapshot doesn't have them. Column grants need a snapshot taken with this
version; older snapshots only show table grants.

### BS214

**Error: permission the provider's SQL functions don't fully answer in a
Storage or Realtime policy.** An access policy on a bucket or topic reaches
the [authorization provider's](/docs/extending/authorization-providers)
functions through its `sql` templates, or through the access contract under
the `provider` access model. Those functions decide by role and scope, so a
permission with other conditions (such as `ownerId = principal.id`) would grant
every object or topic in the scope. Doctor reports every key whose
`authorization.permissions` entry isn't `sqlComplete: true`: a key marked
`false`, a key without the flag, a key the provider doesn't list, and every
key when the provider lists no permissions. `better-supabase gen` refuses to
write those bucket policies.

Doctor checks the `buckets` in the config and the `bs_` policies on
`storage.objects` and `realtime.messages` in your SQL files, matching the
provider's `idsWith` and `isPlatform` templates. It also reports a scope the
provider doesn't declare, and a key checked at a scope its entry's `scopes`
doesn't list.

It warns when a bucket's `sql` templates differ from the provider's `idsWith`
and `isPlatform`, because a copy goes stale when the provider changes. Set
`sql: "provider"` so `better-supabase gen` writes the provider's templates.

### BS215

**Warning: policy calls a helper per row that could run once.** A call such
as `current_tenant_id()` takes no column of the row, so its result is the same
for every row. Written bare, Postgres may run it for each row; wrapped as
`(select current_tenant_id())`, it runs once per statement as an InitPlan.
Splinter's `auth_rls_initplan` (BS200) covers `auth.uid()` and `auth.jwt()`;
this check covers your own helpers. Immutable functions are skipped.

### BS216

**Info: foreign key without an index.** Deleting or updating a referenced row
scans the referencing table for each row, and joins on the key can't use an
index. Add an index whose leading columns are the key's columns, in any order.
A partial index counts when its `where` only skips rows whose key is null
(`where customer_id is not null`), because those rows reference nothing.
When [BS200](#bs200) runs, splinter's `unindexed_foreign_keys` reports the
tables it covers and this check skips them; on a saved snapshot, or when the
advisor can't run, this check reports every table.

### BS217

**Warning: tenant foreign key that can cross tenants.** With the
[memberships extension](/docs/blocks/memberships), a tenant table that references another tenant
table by `id` alone can point at a parent in another organization: RLS checks
each row, not the pair. Reference the tenant column as well, backed by a
unique key on the parent:

```sql
alter table public.customers add unique (id, organization_id);
alter table public.notes add foreign key (customer_id, organization_id)
  references public.customers (id, organization_id) on delete cascade;
```

### BS218

**Info: soft-delete table without a partial index.** A table with a nullable
`deleted_at` or `archived_at` column is mostly read for its live rows. A
partial index with `where deleted_at is null` stays small and matches those
queries:

```sql
create index customers_active_idx on public.customers (organization_id, created_at desc)
  where archived_at is null;
```

Snapshots from before index predicates were recorded accept any partial
index.

### BS219

**Warning: containment filter on a column without a GIN index.** `@>`, `<@`,
`?`, `?|`, `?&` and `&&` on `jsonb` and array columns, and the
`.contains()`, `.containedBy()` and `.overlaps()` filters, can only use a GIN
index; without one, every query reads the table. Doctor looks in the
policies, the functions in the exposed schemas and the files in
`tooling.doctor.sources`. Use `jsonb_path_ops` when you only filter with `@>`, which
makes the index smaller; leave it out for `?`:

```sql
create index notes_meta_idx on public.notes using gin (meta jsonb_path_ops);
```

### BS220

**Info: column type to avoid.** `timestamp` drops the time zone, `varchar(n)`
and `char(n)` only add a length limit that a check constraint on `text`
states as well, `money` rounds by locale, and `json` is parsed again on every
read. Use `timestamptz`, `text`, `numeric` and `jsonb`.

### BS221

**Warning: direct database connection in a serverless app.** Each serverless
or edge invocation opens its own connection, so through the direct host
(`db.<ref>.supabase.co`, which is also IPv6 only) or the session pooler on
port 5432 they run out of `max_connections`. Use the transaction pooler on
port 6543 (`postgres://postgres.<ref>:<password>@<region>.pooler.supabase.com:6543/postgres`).
Doctor checks the env files when the sources export route handlers, a
`runtime`, a `fetch` handler or `Deno.serve`, or an env file sets `VERCEL`
variables. The message names the variable, never its value.

### BS222

**Warning: column that can exceed a JavaScript number.** `int8` and `numeric`
decode as `number` by default, which matches `supabase gen types`, but a
`number` loses precision past 2^53 (about 15 to 17 significant digits). Doctor
reports `int8` identity and sequence columns, which keep growing toward that
limit, and `numeric` columns, which usually hold exact amounts. Set
`gen.codecs.int8` to `"bigint"` or `"string"`, or `gen.codecs.numeric` to `"string"`,
in `better-supabase.config.ts` ([codecs](/docs/cli/config#options)), or add BS222
to `tooling.doctor.ignore` when the values stay small.

### BS223

**Info: function returns an int8 or numeric scalar.** PostgREST sends a
function's scalar `int8` or `numeric` result, or an array of them, as a JSON
number, so a value past 2^53 (about 15 to 17 significant digits) loses
precision before any codec sees it. `db.$rpc` casts the codec columns of
table and record results to text ([function
results](/docs/concepts/casing#function-results)), but a scalar has no column
to cast. Return it as text (`returns text`, `select total::text`) when it can
grow that large, or add BS223 to `tooling.doctor.ignore` when it stays small. Doctor
can't see inside a `json` or `jsonb` result: cast large numbers to text when
you build it.

### BS224

**Warning: Data API role without a timeout.** Without `statement_timeout`,
one slow request holds a connection until the query finishes. Without
`idle_in_transaction_session_timeout`, a client that leaves a transaction
open keeps its locks and its connection. PostgREST applies the settings of
`anon` and `authenticated` to each request, and the login role's
(`authenticator`) apply when the request role sets none, so doctor reports a
setting only when neither sets it. A value of 0 turns the timeout off and
counts as unset. [BS211](#bs211) lists the current values. Set them in a
migration:

```sql
alter role authenticated set statement_timeout = '8s';
alter role authenticated set idle_in_transaction_session_timeout = '60s';
notify pgrst, 'reload config';
```

Saved snapshots from before role settings were recorded skip it.

### BS225

**Info: `pg_stat_statements` is not installed.** The extension records the
time and calls of each statement. `--stats` ([BS209](#bs209)), [BS208](#bs208)
and the Supabase query performance report read it, so without it nothing
shows which queries are slow. Doctor checks `pg_extension` on every run
against a database; with `--stats`, BS209 reports it instead. Install it in a
migration:

```sql
create extension if not exists pg_stat_statements with schema extensions;
```

### BS226

**Warning: prepared statements through the transaction pooler.** The
transaction pooler on port 6543 gives each transaction any server connection,
so a named prepared statement from one transaction doesn't exist in the next
and the query fails with `prepared statement does not exist`. When an env
file or a file in `tooling.doctor.sources` has a `:6543` URL, doctor reports each
source file that imports postgres.js without `prepare: false`, and, when the
sources use Prisma, each `:6543` URL without `pgbouncer=true`:

```ts
const sql = postgres(process.env.DATABASE_URL!, { prepare: false });
```

`pg`, which `better-supabase/postgres` uses, sends unnamed statements and
works through the pooler as it is. This is the reverse of [BS221](#bs221),
which asks serverless apps to use the pooler.

### BS227

**Info: offset pagination or exact counts.** `pagination: "offset"` on a
resource or list reads and skips every row before the page, so late pages get
slower as the table grows, and rows written between requests shift the pages.
`count: "exact"` counts every matching row on each request, and so does a
`.count()` call without a `mode`. Doctor reports each line in
`tooling.doctor.sources` that sets either. Use `pagination: "cursor"`
unless the UI needs page numbers, keep `[api] max_rows` set so no request
reads a whole table, and use `count: "planned"` or `"estimated"` on tables
that can grow large.

### BS228

**Warning: app table column drifted from `tables`.** A column of an app
table has a different type or nullability in the database than
[`tables`](/docs/repository/tables) gives it, usually after an edit by
hand or a migration that wasn't regenerated. `gen` types the column from
`tables`, so the app reads values the database doesn't hold. Change
`tables` to match the database, or run `better-supabase upgrade` and
apply the migration it generates. When rows depend on the old shape, follow
the expand-and-contract steps that `apply --preset` prints for a breaking
change. A table or column the database doesn't have yet is left out, since
that is a migration not applied.

### BS229

**Warning: index built without `concurrently`.** BS229 to BS235 read the
migrations that haven't run yet, statement by statement, and flag the ones
that lock a table that already holds rows. With `--db-url`, doctor checks the
migrations missing from `supabase_migrations.schema_migrations`. Offline, it
checks the migrations after `tooling.doctor.migrationSafety.since`, or only the newest
migration when `since` is unset; `init` and `add --adopt` set `since` to the latest
migration so older files aren't reported. Tables a migration creates are
skipped, since nothing reads them yet.

`create index` blocks every write to the table until the index is built. Use
`create index concurrently`, and put it in a migration of its own, because it
can't run inside a transaction.

### BS230

**Warning: foreign key or check validated in the same step.** Adding a foreign
key or a check scans the whole table while it holds a lock that blocks writes.
Add the constraint with `not valid`, then run
`alter table ... validate constraint ...` in a later statement, which scans
without blocking writes. A `references` or `check` written inline in
`add column` can't be `not valid`, so BS230 flags it too: add the column,
then the constraint. For a check, [BS236](#bs236) tells you when the rows
pass and `doctor --yes` validates it.

### BS231

**Warning: column change that rewrites or scans the table.**
`alter column ... type` rewrites every row under an exclusive lock, unless the
types are binary compatible. `set not null` scans the table under the same
lock. For a type change, add a new column, backfill it, and switch reads to
it. For `set not null`, first add `check (column is not null) not valid`,
validate it, and then set not null, which Postgres then accepts without a
scan. BS231 also flags `add column ... not null` without a default, which
fails once the table has rows: add the column nullable, fill it with
[`db backfill`](/docs/cli/db#backfill), and then add the check.

### BS232

**Warning: column added with a volatile default.** A default like
`gen_random_uuid()`, `random()` or `clock_timestamp()` makes Postgres write
the value into every existing row while it holds an exclusive lock. `now()`
and constants are stored once and don't rewrite. Add the column without a
default, backfill it in batches, and then set the default.

### BS233

**Warning: no `lock_timeout` before an exclusive lock.** A migration that
alters an existing table waits behind long-running queries for its lock, and
every query that arrives after it waits too. Start the migration with
`set lock_timeout = '5s';` so it fails fast and can be retried instead of
stalling the app. A statement that only runs `validate constraint` takes a
share update exclusive lock, which doesn't block reads or writes, so it
doesn't count.

### BS234

**Info: drop or rename.** Dropping or renaming a table or a column breaks the
deployed app until it ships the matching code. Rename in steps: add the new
name, write to both, move the reads, and drop the old name in a later release.
`apply --preset` prints these steps for a breaking change.

### BS235

**Warning: a `better_supabase` function dropped with a new signature.** When
a better-supabase release changes a function's arguments, a schema diff drops
the old function and creates the new one. 0.12 did this for `audit()`, which
went from 9 to 11 arguments. A call with positional arguments, or a grant that
names the old argument list, fails once the migration runs. Doctor flags a
`drop function better_supabase.<name>(...)` in an unapplied migration unless
the same file creates that function again with the same number of arguments.
Read the [upgrade notes](/docs/migration) for the release, call the function
with named arguments, and grant on the new signature in the same migration.

### BS236

**Info: not valid check ready to validate.** Expand and contract adds a
column nullable, adds `check (column is not null) not valid` so new rows must
fill it, backfills the old rows with [`db backfill`](/docs/cli/db#backfill),
and then validates the check. BS236 reads the checks the database holds as not
valid and tests each one against the rows. When no row fails it, the finding
carries the fix, and `doctor --yes` runs
`alter table ... validate constraint ...` without a statement timeout. That
scans the table but doesn't block reads or writes. After it, `set not null` on
the column needs no scan. When rows still fail, the finding names the
`db backfill` command for a not-null check; for the scope column of an
enriched app table, [BS238](#bs238) reports it instead. BS236 needs a
database, so a saved snapshot skips it.

Postgres checks a not valid constraint on every insert and update, so an
update of a row the backfill hasn't reached yet fails until it fills the
column. Add the check after the backfill when the app still writes those rows.

### BS237

**Warning: app table keeps permissive policies or grants of its own.** When a
`tables.<name>` entry enriches a table your schema already creates, your own
policies on it stay: the entry names its policies `bsb_<table>_<command>`, so it
never replaces one of yours, even one named `<table>_select`. Postgres ORs permissive policies, so each one widens what
the entry's scope allows. In `tenant` scope the restrictive `bsb_tenant_scope_*`
policies still keeps every row inside the member's tenants, so BS237 is a hint
(info): check that your policies need no role or permission the scope's
policies ask for. In `user` scope, or without `bsb_tenant_scope_*`, nothing
narrows them, and a signed-in user reaches every row they allow. Drop your
policies, or recreate them `as restrictive`.

Enriching never revokes your grants either; it only adds the ones the scope
needs. BS237 lists the select, insert, update and delete grants that `anon` and
`authenticated` hold beyond that. While row level security filters the rows
this is a hint (info). It is a warning when the entry restricts columns
(`access` or `encrypted`), because a table-level grant reaches every column:
revoke it in your schema and the entry's column grants take over. BS111 reports
truncate, references and trigger grants.

### BS238

**Warning: rows of an enriched app table without an owner.** Enriching a table
that already has rows adds the scope column (`organization_id`, or `user_id` in
`user` scope) nullable, with a not valid not-null check. The scope's policies
match nobody for a row without a value, so only the service role reads or
writes it, and updates to it fail the check. BS238 counts those rows and names
the [`db backfill`](/docs/cli/db#backfill) command that fills them; then
`doctor --yes` validates the check ([BS236](#bs236)). BS238 needs a database,
so a saved snapshot skips it. The check is `not valid` on purpose; see
[Your own schemas](/docs/blocks/own-schemas#why-the-check-is-not-valid).

### BS239

**Warning: pg-delta packages missing.** The project runs the pg-delta
workflow (`database.sql.workflow`, or the one doctor reads from
`supabase/config.toml`), but `@supabase/pg-delta` or `@supabase/pg-topo` is not
installed. [`db diff`](/docs/cli/db#diff) plans the migration with both and
stops until they are there. Install them as dev dependencies:

```bash
pnpm add -D @supabase/pg-delta @supabase/pg-topo
```

### BS240

**Warning: enum value renamed or removed.** A migration that isn't applied yet
runs `alter type ... rename value` or deletes from `pg_enum`. Rows and app code
that still use the old value break once it runs, and Postgres can't drop a
value from a type a column uses. Editing `pg_enum` by hand corrupts indexes and
stored data. Create the new type, move the column with
`alter column ... type ... using`, then drop the old type. The steps are in
[removing an enum value](/docs/cli/db#removing-an-enum-value).

### BS241

**Warning: embedding jobs read too often.** An app table with `embedding`
queues each changed row on the pgmq queue `<table>_embed`, and the drain reads a
message again after 60 seconds until the worker applies it. A message read five
times or more is a job the worker can't finish: the embedder refuses the text, or
the worker URL or token is wrong. The row keeps no vector. BS241 lists the queues
that hold such messages. Fix the cause, then delete the message with
`select pgmq.delete('<queue>', <msg_id>)`. BS241 needs a database, so a saved
snapshot skips it.

### BS242

**Warning: embedding worker requests fail.** The drain posts each batch to the
worker with pg_net, which keeps the answers in `net._http_response` for six
hours. BS242 counts the responses of the last hour that have an error or a
status of 400 or more, when an app table has `embedding` or
`blocks.knowledge.options.autoEmbed` is on. Check that the Vault secrets
`embedding_worker_url` and `embedding_worker_token` match the deployed worker.
BS242 needs a database, so a saved snapshot skips it.

### BS243

**Warning: security definer helper holds a large literal.** A
`security definer` function whose body holds a quoted literal above 1 KB, such
as a permission map or a JSON catalog. Postgres parses the literal again on
every call, and a policy helper runs once per table per statement. Store the
data in a table, or parse it once per transaction and keep it with
[`better_supabase.memo_get` and `memo_set`](/docs/blocks/sql#memoize-a-value-for-one-transaction).
BS243 reads the SQL files, so a saved snapshot works too. It measures the quoted literals inside a function body and ignores the quote that wraps the body itself (`$function$ ... $function$`), so a long body with short literals is not reported.

### BS244

**Warning: schema cache pressure.** PostgREST loads every table, function and
relationship of the exposed schemas into its schema cache at start and after
each `notify pgrst, 'reload schema'`. BS244 reports an exposed schema with more
than 1500 tables and functions, and generated module SQL above 2 MB.

Two changes keep the cache small. Set `gen.api.expose` to `"used"` so `gen`
writes API wrappers only for the block functions your code calls (list the
rest in `gen.api.exposeAlso`; see [gen](/docs/cli/gen#expose-only-the-functions-you-use)).
And run DDL in one batch per deploy: every migration that ends a statement with
a schema change makes PostgREST reload, so put all of a deploy's DDL in one
transaction and send one reload.

## Drift

### BS260

**Warning: code uses a name that `api/naming.json` renamed.** Doctor reads the
app sources in `doctor.sources` for an export, type, subpath
or environment variable named in the rename table, which the
[Naming page](/docs/concepts/naming) lists. The old names have no alias. Run `better-supabase codemod naming` to rename them.

### BS301

**Warning: soft delete hidden by a select policy.** After an update, PostgREST
reads the row back through the select policy. If that policy hides rows where
the soft-delete column is set, the trash extension's delete fails with an RLS error. Filter
deleted rows in queries instead; the trash extension already does.

### BS302

**Warning: bucket differs from the config.** A bucket in `buckets` is missing
from the database, or its `public`, file size limit or MIME types differ.
When the Storage version has the columns, `versioning` and `lifecycle` are
compared too (generated lifecycle rule ids are ignored). Update the config,
or run `bucket.apply(client)` to set the bucket through the Storage API.

### BS303

**Error: generated code is out of date.** The generated module doesn't match
the database, so types and metadata are wrong. Run `better-supabase gen`. This
is the same check as `gen --check`.

### BS304

**Warning: SQL module files are out of date.** A module in `blocks` differs from
the version this release ships. Doctor renders the files with the same layout
as `upgrade` (grants from policies, session policies, audited tables and the
vector schema), so the two agree on what is out of date. Run `better-supabase upgrade`, then
`supabase db schema declarative sync` (`supabase db diff` on migra) to create
a migration. Under `database.sql.workflow: 'migrations'`, doctor compares against the
newest `*_better_supabase_modules.sql` migration instead, and `upgrade`
writes the new one; apply it with `supabase migration up`.

A file whose `@bsb-hash` line no longer matches its SQL was edited by hand.
`upgrade` leaves that file alone. Move the change into your own schema file
or a SQL hook, or pass `--force` to overwrite it. A block file that no
installed block renders any more is reported too, and `upgrade` removes it
unless it was edited by hand.

For the `read-sets` module, doctor imports the modules in `readSets` and
compares the functions they compile to. If a module can't be imported,
doctor skips that file instead of reporting it.

### BS305

**Warning: live query table without change broadcasts.** A table in
`database.realtime.tables` has no `bsb_realtime` trigger, so
[live queries](/docs/frontend/live-queries) never hear about its changes. Run
`better-supabase add realtime-tables`, then
`supabase db schema declarative sync`.

### BS306

**Warning: Realtime delete events without keys.** A table in the
`supabase_realtime` publication has replica identity `nothing`, or `default`
without a primary key, so `postgres_changes` delete events carry no keys. Add a
primary key, or run `alter table ... replica identity full`.

### BS307

**Error: custom SQL module without its contract.** A module in `blocks` uses
`ownership: "custom"`, so the app writes the functions other modules and the
TypeScript APIs call. With a database connection, doctor compares each
function's argument and return types with the contract; without one, it looks
for a `create function` in `supabase/schemas` and the migrations. Write the
function, or switch the module to `managed`, which also runs over tables you
already have. `better-supabase blocks
view <module> --sql` lists the signatures.

### BS308

**Warning: tenant claim the hook does not write.** With the `memberships` module and
`blocks.permissions.activeTenant: 'claim'`, `current_tenant_id()` and the
memberships extension read the active tenant from the `auth.tenant.claim` claim, at the
top level or in `app_metadata`. With `--as <user id>`, doctor calls the custom
access token hook for that user and warns when neither is in the claims it
returns. Write the claim in the hook, or, for apps that pick the tenant from
the URL or a profile, use the default `'resolver'` (with
`ServerOptions.tenant`) or `{ profileColumn }`.

### BS309

**Warning: deprecated SQL module symbol.** A file in `supabase/schemas` or a
policy uses a function, table, column or claim that a SQL module in `blocks`
deprecated or removed, such as `better_supabase.current_org_id()` or the
`org_id` claim. A deprecated symbol keeps a compatibility wrapper for at least
one minor release; a removed one fails at run time. The message names the
replacement. A renamed column such as `memberships.org_id` also counts
unqualified (`m.org_id`) in a statement that names its table. Block files and
migrations are skipped, and so is a claim the config maps in `claims`. Tables
and columns a block maps onto the app's own, and those of a module in custom
mode, are the app's names and are never reported.

### BS310

**Warning: duplicate block trigger.** A table has `bsb_updated_at` and another
trigger whose function looks like `updated_at`, `moddatetime` or `touch`, or
`bsb_audit` and another audit trigger, so both run on every write. Drop the
older trigger, or call `track_updated_at()` or `audit()` with
`replace_trigger => true` in a migration.

### BS311

**Warning: SQL module behind its current version.** A module file's
`@bsb-block` line, or its row in `better_supabase.blocks` on a live database,
records an older version than this release ships. Run `better-supabase sql
upgrade`, which writes the forward steps into a migration and rewrites the
files, then create the schema migration. BS304 skips files this check reports.

### BS312

**Error: block schema exposed through the Data API.** `[api] schemas` in
`supabase/config.toml` lists `better_supabase` or a schema a module in `blocks`
sets. Block schemas hold internal tables and helpers that `authenticated` can
execute so policies can call them; exposing the schema makes them callable over
REST and RPC as well. Remove the schema from `[api] schemas` and from the
exposed schemas in the dashboard, and set `blocks.<module>.api` to an
exposed schema such as `api`: `add` writes `security invoker` entry points
there for the module's client functions, and `rpcTransport(supabase, { schema:
"api" })` calls them. Doctor reads `[api] schemas` for every exposure check and falls
back to `schemas` in `better-supabase.config.ts` without a `config.toml`.

### BS313

**Warning: rate limits not wired to PostgREST.** The `rate-limit` module is in
`blocks`, but on the live database `pgrst.db_pre_request` for the
`authenticator` role is unset, or names a function whose body doesn't call
`better_supabase.check_request()`, so Data API writes are never counted. Apply
the migration `better-supabase add --adopt` writes, which sets the hook when no
other one is set, or call `check_request()` from your own pre-request
function. Doctor needs a database connection for this check. With
`blocks["rate-limit"].options.preRequest` set to `false`, the app calls
`check_request()` itself and BS313 does not run.

### BS314

**Warning: migration-only block option.** A module in `blocks` sets an option
that only exists to match a schema the app already has: `tokenStorage: "plain"`
for invitations, `secretStorage: "column"` for credentials,
`secretStorage: "column"`, `statuses` or an `eventIdType` or `runIdType`
other than `text` for webhooks-out, a `blockSource` or `defaultSource` for
the outbox, or `values` or `metadataColumns` for the audit log. The config
only accepts them when the block runs over a table the app already has.
Move the data to the managed default (hash the tokens, move the secrets into
Vault), then remove the option.

### BS315

**Error: table without an audit trigger.** The `audit` module is in
`blocks`, and a table in `schemas` has no `bsb_audit` trigger, nor another
trigger that calls `better_supabase.audit_row_change()`, so its inserts,
updates and deletes are not in the audit log. Register it with
`select better_supabase.audit('public.customers')` in a schema file. Doctor
skips the block schemas and the app's tables that blocks run over; list other tables in
`blocks.audit.options.exempt` as `{ table, reason }` entries, where `table` is
a `schema.table` glob (`*` matches any run of characters) and `reason` says why
its changes need no audit entry. `{ class: "no-tenant-column", reason }` leaves
out every table that has no tenant column, which the audit helpers can't
register. A bare glob string still works, but doctor reports it as an error and
asks for the reason. Doctor only checks tables in `schemas`, and
a partition counts through its parent.

```ts title="better-supabase.config.ts"
export default defineConfig({
  blocks: {
    audit: {
      options: {
        exempt: [
          { table: "public.*_archive", reason: "read-only copies" },
          { table: "public.sessions", reason: "high volume, no user data" },
        ],
      },
    },
  },
});
```

The same rule runs in pgTAP with
`select tests.every_table_audited('public', array['sessions', '%_archive'])`
(see [testing](/docs/testing#pgtap)).

### BS316

**Warning: legacy migra diff engine.** The project keeps declarative schemas
in `supabase/schemas` or lists `blocks`, but `supabase/config.toml` has
no `[experimental.pgdelta] enabled = true`, so the Supabase CLI diffs the
schema with migra. Migra drops grants, comments and `security_invoker` on
views, and runs only while the stack is stopped. Projects from `supabase init`
and `better-supabase init` use pg-delta. To switch, add the table, remove
`[db.migrations] schema_paths` (pg-delta orders files by dependency), and
create migrations with `supabase db schema declarative sync` instead of
`supabase db diff`:

```toml title="supabase/config.toml"
[experimental.pgdelta]
enabled = true
```

BS316 fires when `database.sql.workflow` is unset and the CLI detects migra (see
[Workflows](/docs/blocks/sql#workflows)), or when the workflow is pg-delta and
`config.toml` doesn't turn it on yet. To stay on migra, set
`sql: { workflow: 'migra' }`; that and `workflow: 'migrations'` silence it.

### BS317

**Warning: bulk grant in a pg-delta schema file.** Under pg-delta, a
`grant ... on all tables in schema`, `on all routines in schema` or `on all
sequences in schema` statement in `supabase/schemas` that reaches `anon`,
`authenticated` or `public` has no dependency position. pg-delta can run it after the per-object revokes that narrow a
function or table, which re-opens them to `anon` and `authenticated`. Grant
each object by name next to its definition:

```sql
revoke execute on function public.recalculate_totals(uuid) from public, anon;
grant execute on function public.recalculate_totals(uuid) to authenticated;
```

For objects created later, use Supabase default privileges instead of a bulk
grant: `alter default privileges in schema public grant select on tables to
authenticated;`. The [`grants` module](/docs/guides/data-api-grants) writes
per-table grants from `expose`.

### BS318

**Warning: catalog loop in a pg-delta schema file.** A `do` block in
`supabase/schemas` that reads `information_schema` or `pg_catalog` (`pg_class`,
`pg_tables`, ...) and executes statements runs, under pg-delta, before the
tables it looks for exist. It creates nothing, and the diff never sees the
triggers, grants or policies it was meant to add. Write the statements as
static SQL, one per table, or call a per-table function once per table, such
as `select better_supabase.audit('public.invoices');` or
`select better_supabase.track_updated_at('public.invoices');`.

### BS319

**Error: SQL alters a reserved role.** A schema file, SQL module or migration
alters, drops or changes the memberships of a role that supautils reserves on
Supabase: `supabase_admin`, `supabase_auth_admin`, `supabase_storage_admin`,
`supabase_functions_admin`, `supabase_read_only_user`,
`supabase_realtime_admin`, `supabase_replication_admin`, `supabase_etl_admin`,
`dashboard_user` and `pgbouncer`. The statement works on a local superuser
connection and fails on a hosted project. `authenticator`, `authenticated`,
`anon` and `service_role` accept `alter role ... set` and `reset`, such as
`alter role authenticator set pgrst.db_pre_request = '...'`, and nothing
else. Granting privileges on objects to a reserved role
(`grant usage on schema auth to supabase_auth_admin`) is not flagged. Create
your own role for anything else.

### BS320

**Warning: table without the session policy.** The `sessions` module is in
`blocks`, and a table with RLS in `schemas` has no restrictive policy
that calls `better_supabase.session_active()`, so a token whose session was
signed out, or whose user was banned or deleted, keeps reaching the table
until it expires. Set `blocks.sessions.options.policies` to `true` and

### BS321

**Warning: extension missing from the migrations under pg-delta.** A
`create extension` in `supabase/schemas`, a SQL module's file included, that
no migration in `supabase/migrations` repeats. pg-delta can leave an
extension that owns its own schema, such as `pgmq`, out of the generated
migration, so a database built from the migrations (a branch, CI or
production) lacks it. For a module that owns such an extension, run
`better-supabase upgrade`: it writes the extension into a migration that
runs before the schema migration. For your own schema files, add
`create extension if not exists <name>;` to a migration that runs before the
one that uses it. The rule stays quiet until the project has a migration.

### BS322

**Warning: audit registration of a dropped table.** The `audit` module is in
`blocks`, and `better_supabase.audited_tables` on the live database has
a row whose table no longer exists. Since the module installs the
`bsb_audit_forget_dropped` event trigger, dropping a table deletes its row,
but a table dropped before that keeps it. Run `better-supabase upgrade`
and apply the migration `better-supabase add --adopt` writes: the module's data
file deletes registrations whose table is gone. Doctor checks this only
against a database.

### BS323

**Warning: module event trigger missing.** A module in `blocks`
creates an event trigger (`bsb_audit_forget_dropped` for `audit`,
`bsb_ensure_rls` for `rls-guard`) that the live database lacks, or, without
a database, that no migration in `supabase/migrations` creates. Event
triggers belong to no schema, so a schema diff limited to some schemas
(`supabase db schema declarative sync -s ...`) leaves them out of the
migration, and dropped tables keep their audit registrations or new tables
get no RLS. Run `better-supabase upgrade`, then `better-supabase add --adopt`:
the module's data file repeats its event triggers, so the data migration
creates them. Run the declarative sync without `-s` from then on.

### BS324

**Error: shared roles table without a role condition.** Under the
`provider` model, the tenant module's `roleThrough` and the invitations

### BS325

### BS330

**Error: app table without a column a block uses.** A block runs over a
table of the app's, and the live database lacks a column the block's SQL
names, so the block's functions fail until that column exists. Doctor reads
every column the module's SQL names: the ones in `blocks.<name>.columns`
and the defaults for the unmapped ones, leaving out the columns mapped to
`null`. Tables that a block uses only when `blocks.<name>.tables` maps them

`blocks.<name>.on` names isn't added by the block: map it or add it yourself.
Needs a database.

### BS331

**Error: subject registry names a missing table or column.** An entry in
`config.recordTypes` names a table that the snapshot lacks, or a column the

### BS332

**Warning: subject table without RLS.** A table in `config.recordTypes` has row

visible, so every signed-in user passes the visibility half of the check for
every row. Enable RLS and add the policies that scope the table.

### BS333

**Warning: `admin()` inside a workflow-editor executor.** A source file that
runs workflow-editor steps (it uses `executeGraph`, `nodeRunReporter` or

### BS334

**Info: a policy checks a role name instead of a permission.** An app policy
or a function in `schemas` calls `member_organization_ids()`,

### BS335

**Warning: partitioned table created unpartitioned.** A block's
`options.partitioned` is on, but its table was created before it: the primary

| -------------------------------- | ------------------------------ |
| `audit`                          | `audit_events`                 |

### BS336

**Warning: flag past its expiry.** The flags table has an `expires_at` column

### BS337

**Warning: broadcast trigger sends whole rows.** A trigger function calls

### BS338

**Info: `gen.functions.notNull` entry a comment tag could replace.** `gen` reads

### BS339

**Warning: `expose` excludes a column the table doesn't have.** An `expose`

### BS340

**Info: a tenant foreign key has no same-tenant trigger.** With the `memberships`

### BS341

**Warning: a data export includes a column that looks like a secret.** A
data export writes every column of the tables it reads, except the ones in
`omit`. Doctor reports each column of an exported table, including the ones
`autoTables` finds, whose name contains `token`, `secret`, `_hash`,
`password`, `api_key` or `license_key`, when no `omit` and no `omitPattern`
leaves it out. Add the column to the table's `omit`, keep the table out of

`blocks.data-lifecycle.options.omitPattern`. See
[data lifecycle](/docs/blocks/data-lifecycle).

### BS342

**Error: an enum column of the app's that a module writes as text.** A
module writes a text parameter or a computed text value into a column of a
table the app already has, and the snapshot declares that column as an enum;
string literals are fine. Postgres has
no implicit cast from text to an enum, so the module's functions fail when
they run. Change the column to text with a check constraint on its values.
The columns the module casts to their declared type may stay enums or
domains: status columns, the tags `kind` and `subjectType`, the numbering
`entity` and the profiles `locale`. `upgrade` and
`better-supabase add --adopt` refuse the same columns when the schema files declare
the enum. See
[existing tables](/docs/blocks/sql#over-your-own-tables).

### BS343

**Error: a partition without row level security.** A table in `schemas` is a
partition of a table that has RLS on, but RLS is off on the partition itself.
Policies belong to the parent, so a query that names the partition (for
example `select * from decision_events_default`) never applies them, and a
role with a grant on it reads every row. The default partition counts too.

(ADR 0038).
In pgTAP, `tests.partitions_have_rls('schema')` checks the same thing.

### BS344

**Warning: app webhook endpoints without a format.** `webhooks-out` runs
over an endpoints table of the app's, that table maps no `format` column, and
`blocks.webhooks-out.options.defaultFormat` isn't set. Every endpoint then
gets `defaultFormat`, whose default changed from the 0.8 body (`standard`)
to `cloudevents` in 0.9, so receivers built for the old body break with no
change to the config. The message says whether the table has no `format`
column or has one the config doesn't map. Set `defaultFormat` to the body
your receivers expect, or map `columns.endpoints.format`. `upgrade` refuses
the same config; doctor reports it for configs it loads without that check.
See [connectors](/docs/blocks/webhooks#connectors).

### BS345

**Warning: attachments subject on block-wide keys with stricter RLS.** An
`attachments` subject has no `read` or `upload` key of its own, so its files
are checked with the block-wide `attachments.read` and `attachments.upload`
keys. The subject table's own policies check more than tenant membership: a
permission key of their own, an owner or `auth.uid()` comparison, or another
condition. Any member of the tenant then reads and uploads the files of rows
they can't open. Doctor counts `current_tenant_id()`, `tenant_ids_with`,
`member_<tenant>_ids` (and an authorization provider's own `*_ids_with` and
`*member_*ids` helpers), `can('tenant', ...)` and `member_can` with the
block's key as tenant membership, and a soft-delete `is null` as neutral. A
policy with an `or` branch that needs only membership is wider, not
stricter, and a table with no insert or update policy for clients doesn't
count against `upload`. A subject with its own read key (`permission`, or
`permissions.read` in the registry) passes for `read`, since the block checks
that key on top of `attachments.read`.
Set `subjects.<type>.permissions.upload` in the registry, or
`blocks.attachments.on.<type>.permissions` for `read`, to the keys the table
checks. See
[permissions per subject](/docs/blocks/attachments#permissions-per-subject).

### BS346

**Warning: block on names an unknown record type.** A block entry's `on`
lists a type, or has a key, that `config.recordTypes` doesn't register. The
block's SQL refuses such a type when `gen` renders the migration, so doctor
reports it first. Register the type in `config.recordTypes`, or remove it from
`on`. See [record types](/docs/blocks#record-types).

### BS347

**Warning: block policy widens an app table's access.** A block that runs
over one of your tables adds its own permissive policies there, named
`bsb_<table>_<command>` (such as `bsb_teams_select`), so they never replace
one of yours. Postgres ORs permissive policies, so when you have policies for
that command and none has the same condition, or `true`, for the same roles,
the block's policy can let a user reach rows yours keep closed. A block
condition that is yours with more `and` operands (such as the block's
`authz_actor_may_write()` check) is narrower, so it isn't reported either,
and so is the block's condition when it is one of the `or` operands of yours. A
command you have no policy for is the block's to grant, so doctor doesn't
report it. Doctor compares the conditions as text, so it also reports a
condition that means the same thing written differently. If the block's
condition is what you mean, repeat
it in your policy. Otherwise narrow the permission key the block checks, or
drop the `bsb_` policy in a schema file that runs after the block's. Your
policy and the block's for the same command don't also count as an overlap
under [BS207](#bs207). When one of your policies covers the block's in this
sense, `upgrade` leaves the block's policy out of its file and says so in a
comment, so Postgres doesn't evaluate two policies for the same rows. When
your policies should govern the table on their own, set `ownTablePolicies:
"app"` on the block or in `database.sql`: the block then adds no `bsb_`
policy there, and doctor doesn't report the table (see
[keeping your own policies](/docs/blocks/own-schemas#keeping-your-own-policies)).

### BS348

**Info: app table keeps its own updated_at trigger.** A block that runs over

### BS349

**Warning: block writes through a view Postgres can't update.** A block table
is mapped to one of your views, and the block's TypeScript API inserts,

### BS350

**Warning: app table governs its policies but lacks one for a command.** A
block runs over one of your tables with `ownTablePolicies: "app"`, so it adds
none of its `bsb_` policies there, and the table has no permissive policy for

### BS351

**Warning: app code writes a block's table directly.** A source file matched
by `doctor.sources` calls `.from("x").insert()`, `.update()`, `.upsert()` or
`.delete()` with supabase-js, or `create()`, `insert()`, `update()`, `upsert()`
or `delete()` on the typed client's repository (`db.webhookEndpoints.create()`),
on a table a block creates, the tables `blockTables(config).byBlock` lists. The

reported. The write skips the block's functions,
so its events, hooks and the checks it runs before a write don't run, and the

### BS352

**Warning: plain secret column next to a block that encrypts it.** One of
your tables has a `text`, `varchar`, `char`, `json` or `jsonb` column whose
name ends in `credentials`, `token`, `secret` or `header_value`
(`access_token`, `client_secret`, `auth_header_value`), and [`field-encryption`](/docs/blocks/field-encryption) or
the [`credentials`](/docs/extending/credentials) module is installed. The
value sits in the row as written, so every role that reads the row, and every

then stores it as ciphertext under a Vault data key.
With credentials, move the secret to Vault and store a `credential_ref jsonb`

tell which ones it fills.

### BS360

**Warning: secret column outside Vault.** One of your tables has a `text`,
`varchar`, `char`, `json` or `jsonb` column whose name ends in `credentials`,
`token`, `secret` or `header_value`, and neither
[`field-encryption`](/docs/blocks/field-encryption) nor the
[`credentials`](/docs/extending/credentials) module is installed. The value
sits in the row as written, so every role that reads the row, and every

returned id in a `uuid` column such as `access_token_secret_id`, and read it

### BS361

**Warning: an app table's check rejects values a block writes.** A block runs
over one of your tables, and the check constraint or enum on a column the block
writes rejects a value the block writes into it. The module's own table declares
the values it writes in a `check (column in (...))` constraint, and the block
writes them through the column your config maps. A narrower check, such as one
that predates a new delivery status, makes the block's inserts and updates fail.
Widen the check constraint to accept every value the block writes, or add the
values to the enum. Doctor reads simple membership checks (`in (...)` and `=
any (array[...])`), and leaves a check that also constrains another column, a
negation or an expression alone. A column with no check accepts every value and
is not reported. For the notifications block, the delivery `status` check must
accept `pending`, `sent`, `failed`, `skipped`, `held` and `digested`; see
[digests](/docs/blocks/notifications#digests).

### BS362

**Warning: update policy checks a read permission.** A permissive policy for
`update` (or `all`) calls `better_supabase.can(...)` or
`better_supabase.tenant_ids_with(...)` with a key that ends in `.read` or
`.view`. Anyone who may read the row can then change every column of it. Check
a write permission in the policy. When only some columns need a stricter
permission, list them in
[`tables.<name>.columnGroups`](/docs/repository/tables#column-groups): the generated
trigger raises `42501` when a caller without the group's permission changes one
of them.

### BS363

**Warning: a partial index differs from the module's definition.** `create index
if not exists` never changes an index that already exists. When a module now
writes another `where` predicate for an index, such as the mapped status values
in the `webhooks-out` delivery indexes, a database set up earlier keeps the old
one. Doctor compares the string literals of each partial index in the module
files with the live index of the same name and table, and lists the ones that
differ. Drop the index, run `better-supabase sql upgrade` and apply the
migration. Needs a database; saved snapshots skip it.

### BS364

**Warning: an API wrapper is volatile around a stable function.** A `language
sql` wrapper without `stable` is volatile, so Postgres can't inline it into a
policy or cache it for the statement. The wrappers `gen.api` writes copy the
volatility of the function they wrap. Doctor lists a volatile `security invoker`
SQL function with the same name and arguments as a `stable` or `immutable`
function in another schema, which is how a wrapper from an older release looks.
Run `better-supabase sql upgrade` to rewrite it.

### BS365

**Warning: an update policy has no select policy.** Postgres only updates rows the
caller can also select, so a table with a `for update` policy and no `for select`
or `for all` policy updates zero rows and reports no error. Add a select policy
with the same condition. Doctor reads the app's own schema files.

### BS366

**Error: a policy decides on `user_metadata`.** `raw_user_meta_data` and
`user_metadata` are editable by the signed-in user, so a policy that reads them
lets anyone grant themselves access. Put authorization data in `app_metadata` or
in the authorization provider. A trigger may read `raw_user_meta_data` for
display fields; a policy never does.

### BS367

**Warning: a view skips the caller's row level security.** A view runs with its
owner's rights unless it sets `security_invoker = true`, so it returns rows the
caller's policies would hide. Create the view `with (security_invoker = true)`.

### BS368

**Info: a column uses `timestamp` or `serial`.** `timestamp` has no time zone and
`serial` is the legacy form of an identity column. Use `timestamptz` and
`generated always as identity`.

### BS383

**Warning: a storage policy set has insert but no select and update.** A storage
upload with `upsert: true` reads the existing object and then updates it, so it
needs `insert`, `select` and `update` policies on `storage.objects`. With
`insert` alone the first upload works and every overwrite fails. Add the select
and update policies, or turn upsert off. Doctor reads the app's own schema files.

### BS384

**Warning: a policy calls `auth.uid()` once per row.** `auth.uid()`,
`auth.jwt()` and `auth.role()` called bare in a policy run for every row the
policy checks. Written as `(select auth.uid())`, Postgres evaluates the call
once per statement. Wrap each call in `select`.

### BS385

**Info: a policy column has no index.** A policy that filters on
`user_id = (select auth.uid())` runs that filter in every query on the table, so
the column needs an index that starts with it. A composite index puts the tenant
column first. Without one, Postgres reads the whole table. Doctor counts an
index, a primary key or a unique constraint that starts with the column.

### BS386

**Warning: a policy calls a volatile or PL/pgSQL function per row.** A policy
that calls a volatile function, or one written in PL/pgSQL, outside
`(select ...)` runs it once for every row the statement reads, and Postgres
can't hoist a volatile call. Wrap the call in `(select fn(...))` so it runs once
per statement, or replace a per-row check with a set helper such as
`tenant_id in (select tenant_ids_with('key'))`. A helper called inside
`(select ...)` is accepted even when it is volatile. Policies named `bsb_*`
belong to a block module and are left to `upgrade`. Doctor reads the policy
expressions and the functions they call from the catalog.

### BS387

**Info: many row-level triggers on one table.** Every row-level trigger runs
once per row a statement writes. A table with six or more `bsb_*` row triggers
(search, audit, events, totals) multiplies the cost of each import or bulk
update. Use the statement-level form where a block offers one, such as
`audit.statement`, or skip the triggers an import doesn't need.

### BS388

**Warning: a search trigger on an import target has no import guard.** An import
writes thousands of rows in one transaction. A search trigger whose function
neither checks `better_supabase.import_run() is not null` nor calls
`better_supabase.search_enqueue` (which defers the refresh to the end of the
transaction) rebuilds the search entry after every row. Run `better-supabase upgrade` so the search module skips
per-row refreshes while an import runs. Doctor reads the trigger function's
source in the schema files, so a function it can't find is left alone, and the
tables are the record types that `blocks.imports.options.targets` names.

### BS389

**Info: the audit log has no scheduled purge.** `better_supabase.audit_events`
grows with every audited write until something calls
`better_supabase.purge_audit_log()`. Schedule it nightly with pg_cron or call
`purgeAuditLog` from the jobs drain route. Doctor accepts a call in the schema
files, the seeds, the app sources or a pg_cron job (it reads `cron.job` when it
has a database), and skips projects without an audit table.

### BS390

**Info: a redundant index.** A non-unique btree index whose columns are the
start of another index on the same table, with the same predicate, answers no
query the longer index doesn't, and only slows writes. Drop it. Primary keys,
unique indexes and expression indexes are left out.

### BS391

**Info: a parameter that is null or matched with `any()`.** A function that
filters with `param is null or col = any(param)` can't use an index on `col`
once Postgres caches a generic plan, because the plan has to cover both
branches. Split the statement by whether the parameter is null, or set
`plan_cache_mode = force_custom_plan` on a PL/pgSQL function so the planner
folds the null. Doctor reads the functions in the app's schema files, not the
block modules'.

### BS392

**Info: a searched table has no trigram or sort index.** A table with the search
option (`@bsb search` or a `search_tsv` column) has a GIN index on the tsvector,
which only serves full-text queries. A list that matches with `ilike '%text%'`
needs a GIN trigram index on the searched column, and a newest-first list needs
a btree index that contains `created_at` or `updated_at`. Add both in the schema
file.

### BS393

**Warning: import batches run close to the statement timeout.** With `--stats`,
doctor reads `import_upsert_batch` from `pg_stat_statements` and compares its
mean time with the `statement_timeout` of the `service_role`, else the
`authenticator`, else the server. A mean above half of it fails once the table
grows or another job holds a lock. Send smaller batches, or raise the timeout of
the role that imports.

### BS394

**Warning: an app override of a block function has drifted.** An app file that
replaces a block function marks it with `-- @bsb-override-of schema.fn <hash>`
above its own `create function`. The hash is the first twelve hex digits of the
SHA-256 of the block's function statement with its whitespace collapsed, and
doctor prints the current one in its message. When the block module's function
changes, `upgrade` leaves the override behind and it keeps the old behavior, so
doctor reports a recorded hash that no longer matches, and a tag whose target no
module declares. Diff the module's function against your copy, merge what
changed, then write the new hash. BS369 skips a tagged function. Doctor reads
every schema file.

### BS395

**Error: verify_jwt is off for a function that expects a user.**
`[functions.<name>] verify_jwt = false` turns off the gateway's JWT check. A
function written with `auth: 'user'` relies on that check to refuse requests
without a token before any code runs. Turn `verify_jwt` back on, or verify the
token in the function and drop `auth: 'user'`. The `mcp` function is the
documented exception: it verifies the OAuth token itself, because the gateway
would reject the MCP client first. Doctor reads `supabase/config.toml` and the
files under `supabase/functions`.

### BS396

**Info: a seed file inserts one row at a time.** A file under `supabase/seeds`
with ten or more single-row `insert ... values (...)` statements for one table
is slow to parse and run, because each statement is planned and sent on its own.
Write one insert with several value tuples, or `insert ... select` from
`generate_series`. Files that `db seed --sample` wrote are left out.

### BS397

**Warning: a schema file changes rows a data migration holds.** A schema file in
the declarative layout holds structure. An `insert`, `update` or `delete` in it
runs on every sync, and when a migration or block data file writes the same
table, the rows have two owners. Remove the statement from the schema file and
keep the rows in the data migration or a seed. Files a block module wrote are
left out.

### BS398

**Warning: an app trigger replaces the same-tenant check without the tenant.**
`sameTenant.auto` emits no check for a foreign key column that an app trigger
(any trigger not named `bsb_*`) reads or writes through `new.<column>` or
`old.<column>`, because the app is taken to guard it, and BS340 accepts that
column for the same reason. A trigger that touches the column but never mentions
the tenant column guards nothing about the tenant, so nothing checks the
referenced row. Compare the tenant of the referenced row in the trigger, or list
the reference in `blocks.memberships.options.sameTenant` so the block emits the
check. Doctor reads the trigger functions in the schema files.

### BS369

**Warning: an app file declares an object a block module declares.** A table,
view, function or type that both a block module file and one of the app's files
create is defined twice, so the declarative diff keeps whichever file it reads
last. Declare the object once: let the app file alter the block's table, or map
the block to another name.

### BS370

**Error: a schema file asks for `transaction=false`.** The line
`-- pg-delta: transaction=false` runs a file's statements outside a transaction,
so a failure halfway leaves the schema partly applied. Create the index
concurrently in a hand migration with a `lock_timeout` instead.

### BS371

**Warning: two schema files declare the same object.** A function, policy,
trigger, index, table, view, type or sequence that two schema files both create
has two definitions, and the declarative diff keeps whichever file it reads
last. The helpers every block calls (`actor_may_write`, `import_run`, the memo
functions and the rest) live once in the prelude file, so a copy of one in a
module file means the file is older than the prelude: run
`better-supabase upgrade`, which `upgrade --check` also reports.

### BS372

**Warning: a `do` block in an app file creates objects.** A `do` block that
runs `create` or `execute` builds objects at run time, so a schema diff can't
see them and reports them missing. Write the statements out as plain DDL.

### BS373

**Warning: an app file creates an object with `if not exists`.** `create table
if not exists` and `create index if not exists` skip the statement when an
object of that name exists, so a changed definition never applies. Write
`create table` and let the diff change the table.

### BS374

**Warning: a block module file inserts rows.** A schema diff reads tables, not
rows, so a top-level `insert` in a block module file never reaches the database
from the sync. Rows belong in the module's data file, which `upgrade` writes into
a migration. The generator writes none; this finds a hand edit.

### BS375

**Warning: two policies decide the same way.** Two policies on one table have
the same command, roles and expressions under different names. Postgres ORs
permissive policies, so the second adds nothing, and a restrictive pair checks
the same condition twice. Delete one.

### BS376

**Warning: a migration creates an object no schema file declares.** Under
pg-delta, `supabase db schema declarative sync --strict-coverage` fails for a
table, view, type or function that the migration history creates and the schema
files don't, because the next diff would drop it. Declare it in
`supabase/schemas`, or drop it in a migration. Objects in Supabase's own
schemas and objects a later migration drops or renames are left out. A history
with a `do` block reports nothing, because the block can rename or create an
object by name.

### BS377

**Warning: a schema file declares an object no migration creates.** The other
direction of BS376: a table, view, type or function in `supabase/schemas` that no
migration creates is a change the sync has not turned into a migration yet. Run
`supabase db schema declarative sync` and review the migration.

### BS378

**Warning: a trigger aimed at a view.** A `before` or `after` trigger on a view
never fires for the rows of the table under it. Put the trigger on that table, or
use an `instead of` trigger that writes it. Reads every schema file.

### BS379

**Error: a columns entry the render refuses.** `blocks.<name>.columns.<table>.<column>`
is `null` for an optional column the view the block runs over lacks anyway, or
`columns.<table>.tenant` repeats `sql.tenantColumn`. The block already leaves out
a column its view lacks, and `sql.tenantColumn` fills every tenant column, so the
entry says nothing. Run `better-supabase codemod config` to remove the entries.
A `null` for a column the view has, or for a table you own, is fine.

`better-supabase upgrade --check` runs the checks of BS369 to BS375 that apply to
the installed block files (a helper two files define, an object two block files
declare, `transaction=false`, a top-level `insert` and duplicate policies) and
fails with a line for each.

## Auth config

### BS380

**Warning: a check constraint mixes `between` with `and` or `or`.** Postgres
rewrites `x between a and b` into two comparisons, so a check that joins a
`between` to other conditions reads back in another shape than the file declares,
and the next diff proposes the same constraint again. Write the comparisons out.
Reads the app's schema files.

### BS381

**Warning: a call names a block table that the app projects through a view.** An
app view over a block table (`public.job_attachments` over
`better_supabase.attachments`) is what clients read: it names the columns they
may see, and `better-supabase powersync streams` syncs the same columns.
`createNativeClient`, `powersyncEngine`, `attachmentQueueRoute` or `queryEngine`
given the block table's name skips the view. The qualified name always counts;
the bare name counts when the view is called something else. Name the view
instead. Reads the app's schema files and the files in `doctor.sources`.

### BS382

**Error: a subject's config entry and its table comment disagree.** The
`@bsb subject` tag on a table is the registry of the app's subjects, and a
`subjects.<type>` entry can set the same options. When both give an option
(`table`, `id`, `idType`, `tenant`, `title`, `url`, `scope`, `deletedAt`,
`cascade`) and the values differ, `gen` keeps the config's and the comment says
something else. Remove one, or make them agree.

### BS353

**Warning: declared link needs the relations block.** A block declares a
conversion or relation link to another block, such as an order created from a
quote, and both blocks are installed, but [`relations`](/docs/blocks/relations)
is not. The conversion still runs through the source row's `origin_type` and
`origin_id` columns, but no `created_from` or `converted_to` link is written,
so lineage reads find nothing. Run `better-supabase add relations`.

### BS354

**Warning: declared defaults are not applied to new organizations.** An
installed block declares tenant defaults, such as the tax codes of a country,
but the `seeds` block is not installed, `database.seed.defaults` is `false` or
has `onCreate: false`, or `organizations` is not installed. Nothing calls
`seed_tenant_defaults` when an organization is created, so new organizations
start without the defaults. Run `better-supabase add seeds`, turn the config key
back on, or run `better-supabase db seed --defaults` for each organization.

### BS355

**Warning: seed variant is not declared.** `database.seed.defaults.variants`
names a block that doesn't exist, or a variant the block doesn't declare.
`better-supabase blocks` lists the variants each block offers. Use one of them
or remove the entry.

### BS356

**Info: sample data file outside `database.seed.sample.output`.** A file under
`supabase/seeds` starts with the comment `better-supabase db seed --sample
--out` writes, but `database.seed.sample.output` points at another path. The
next run writes a second file instead of replacing it, and `supabase db reset`
loads both. Set `database.seed.sample.output` to the file, or delete it.

### BS357

**Error: a data file insert has no key.** A block data file runs again in every
data migration that changes it, so each `insert` in
`supabase/better-supabase-data` ends with `on conflict (...)` or guards itself
with `not exists`. Without a key a second run adds the rows again.

### BS358

**Warning: an app seed writes a table a block seeds.** A file under
`supabase/seeds` inserts into a table that a block data file also inserts into,
so both own its rows. Let the block seed the table, or keep the rows in your
seed and remove the block's. Files from `db seed --sample` are left out.

### BS359

**Warning: a seed function takes no locale.** A function named
`seed_<name>_defaults` has no `p_locale` parameter. Defaults that depend on a
country need it, and `seed_tenant_defaults` passes it to every seed function.
Reads every schema file.

### BS401

**Warning: refresh token reuse interval is 0.** With refresh token rotation,
server instances that refresh the same session at the same time need a reuse
interval, or all but one of them sign the user out. Use `10`, the Supabase
default.

### BS402

**Info: long access token lifetime.** better-supabase verifies tokens locally
instead of calling the auth server, so a revoked session stays valid until its
token expires. Keep `jwt_expiry` at 3600 or less; the proxy refreshes sessions
for you.

### BS403

**Info: local stack signs tokens with a shared secret.** Hosted projects sign
with asymmetric keys. Run [`better-supabase dev keys`](/docs/cli/dev#keys) so
local tokens verify through JWKS, the same as in production.

### BS404

**Error: Auth hook function grants.** For every enabled
`[auth.hook.<name>]` in `supabase/config.toml` with a
`pg-functions://postgres/<schema>/<function>` URI, doctor introspects the
function, even in a schema outside `schemas`. Auth calls it as
`supabase_auth_admin`, which needs `usage` on the schema and `execute` on the
function. Nobody else should be able to call it: through the Data API, a
client could call the custom access token hook for any user id and read the
claims it adds. The finding lists the SQL that fixes it:

```sql
grant usage on schema rbac to supabase_auth_admin;
grant execute on function rbac.custom_access_token_hook(event jsonb) to supabase_auth_admin;
revoke execute on function rbac.custom_access_token_hook(event jsonb) from authenticated, anon, public;
```

Add the statements to the schema file that defines the function and run
`supabase db schema declarative sync`: pg-delta carries function grants into
the migration. `better-supabase doctor --fix-grants` prints the block for
every hook at once, ready to paste into that file.

On the legacy migra engine ([BS316](#bs316)), `supabase db diff` drops
function grants, so append the block to the migration it wrote:

```bash
supabase db diff -f auth_hook
better-supabase doctor --fix-grants >> supabase/migrations/<timestamp>_auth_hook.sql
```

Under `database.sql.workflow: 'migrations'` there is no schema file, so the finding
says to put the block in a new migration and apply it:

```bash
supabase migration new auth_hook_grants
better-supabase doctor --fix-grants >> supabase/migrations/<timestamp>_auth_hook_grants.sql
supabase migration up
```

When the function is the authorization provider's hook
(`authorization.tokenHook.function`, or a file with its `markers.hook` line),
the finding lets the provider write the grants instead, with its
`grantsCommand` when it sets one.

When a file already grants the function, the database is behind, and the
finding names that file. On migra only a migration with the provider's
`markers.grants` line counts, and the finding says to run
`supabase migration up`. With pg-delta the declarative schema file that
defines the hook counts too, and the finding says to run
`supabase db schema declarative sync`, then `supabase migration up`.

Doctor reads the declarative schemas, then the migrations newest first, and
points findings at the first file that declares the object. With pg-delta it
reads every file in `declarative_schema_path` (default `supabase/schemas`) in
name order. On migra it follows `[db.migrations] schema_paths`, then the files
no entry matches.

A hook whose function doesn't exist is reported at its `config.toml` line,
because every sign-in fails until it does. Snapshots taken before the hook
was configured skip it; run `better-supabase gen --save-snapshot` again.

### BS405

**Warning: custom access token hook shape.** Auth runs the hook on every
sign-in and token refresh. Declare it `stable` and give it
`set search_path = ''`, qualifying every table it reads.

The claims it returns travel with every request, in the session cookie and in
the `Authorization` header. With `--as <uuid>`, doctor calls the hook for that
user the way Auth does, as `supabase_auth_admin` with the user's standard
claims, in a transaction that is rolled back. Two limits apply:

| Limit                      | Measures                                            | Default                                                           |
| -------------------------- | --------------------------------------------------- | ----------------------------------------------------------------- |
| Whole token                | `octet_length` of all the claims                    | 2048 bytes, or `tooling.doctor.claimsLimit` without a hook budget |
| The provider's hook budget | `octet_length` of each of `tokenHook.budget.claims` | `tokenHook.budget.bytes`, or `tooling.doctor.claimsLimit`         |

Each one is a separate warning, so a token of 1.5 KB whose budget claims fit
the budget passes. When the hook sets `tokenHook.budget.truncatedClaim`,
doctor also reports that the token lists only some entries, so server checks
for that user need a database lookup. Keep ids and roles in the token and
look everything else up. This needs a direct connection (local stack,
`$DATABASE_URL`, `$SUPABASE_DB_URL` or `--db-url-stdin`).

### BS406

**Warning: foreign key to `auth.users` blocks account deletion.** A key with
`no action` or `restrict` makes `auth.admin.deleteUser`, and
[`deleteAccount`](/docs/auth/account-deletion), fail with "Database error
deleting user" while the user still has rows. Use `on delete cascade` for data
the user owns (profiles, memberships, notifications) and `on delete set null`
for records that outlive them (`created_by` on shared documents, audit rows).

### BS407

**Error: two authorization hooks.** The authorization provider's hook
(`authorization.tokenHook`) owns the claims in `ownedClaims`, plus its
`tenantClaim`. A custom access token hook that also calls
`better_supabase.membership_claims` (when `memberships` is owned) or
`better_supabase.permission_claims` (when `permissions` is owned), or writes
one of those claims itself through `jsonb_set` or `jsonb_build_object`, gives
them two sources that drift apart. Use the provider's hook and remove the
extra writes.

The provider's own hook is not reported: doctor recognizes it by
`tokenHook.function` or by its `markers.hook` line in the file that creates
it. Claims in `registeredClaims`, such as `features` from
`better_supabase.feature_claims`, are sources of the provider's hook and are
not a second writer. A hook that wraps the provider's hook and then writes one
of those claims again is reported, with the function that already fills it.

### BS408

**Warning: the entitlements module can't read the provider's memberships.**
With `auth.entitlements.memberships: "provider"` (the default when the config has
`authorization`), the [`entitlements` block
module](/docs/blocks/entitlements) reads memberships through the provider's
`memberIds` template in `has_entitlement`, which runs as `authenticated`, and
`memberIdsFor` in `feature_claims`, which the provider's hook calls as
`supabase_auth_admin`. When `entitlements` is in `blocks`, doctor warns
when:

- the provider can't back the mode: `tenantScope` is not one of its scopes,
  the scope has no `idType` or one other than `uuid`, `text`, `bigint` or
  `integer`, or `memberIds` or `memberIdsFor` is missing. `sql add
entitlements` refuses to render the module then; set
  `auth.entitlements.memberships: "tenant"` to use the tenant module's memberships;
- the provider's hook doesn't fill `auth.claims.features` from
  `better_supabase.feature_claims` (`tokenHook.registeredClaims`), so
  `hasEntitlement()` would never see the plan features. With
  `auth.entitlements.claim: false` the token carries no features, so doctor skips
  this check;
- no `authorization.memberships` table covers the tenant scope, so
  `entitlement_members()` finds no users to sign out after a plan change (an
  info finding when the provider lists no memberships at all);
- a function those templates call is missing from `authorization.requires`,
  isn't executable by the role that calls it, or isn't in the database.

### BS409

**Warning: the authorization provider and the better-supabase config
disagree.** The provider's hook writes the active tenant to
`tokenHook.tenantClaim`. Doctor warns when `auth.tenant.claim` names another
claim, because the memberships extension, the guards and the module's RLS would then
read a claim the hook never writes. It also warns when the provider's
`tokenHook.activeOrganizationFrom` (the app_metadata claim, a profile column or
the request) differs from `blocks.permissions.activeTenant`, where
`switch_organization` writes the active organization, since switching would
then never change the token. It notes when `auth.claims.scope` is neither
`tenant` nor the provider's `tenantScope`, notes when the provider sets
`suspension` or `roleSources` while `blocks.permissions.model` is not
`provider` (only that model reads them), and reports every entry of the
provider's `problems`, such as a file version it can't read.

### BS410

**Warning: HTTP auth hooks.** Auth calls an `[auth.hook.<hook>]` with an
`http://` or `https://` URI by sending a request signed with the Standard
Webhooks secret in `secrets` (`v1,whsec_<base64>`, several joined with `|`).
Doctor can't read the endpoint's code, so it reports each HTTP hook as an info
finding; verify the request there with `authHook` from
[`better-supabase/blocks/webhooks`](/docs/standards/webhooks). It also reports:

- an error when `secrets` is missing, or when a secret is not
  `v1,whsec_<base64>` or decodes to fewer than 24 or more than 64 bytes. The
  message never quotes the secret;
- a warning when the secret is written in `config.toml` instead of read with
  `secrets = "env(BETTER_SUPABASE_AUTH_HOOK_SECRET)"`. A value read from `env()` is checked
  only when `@supabase/config` interpolated it;
- a warning when a non-local endpoint uses plain `http`.

### BS411

**Error: the provider access model can't use the authorization provider.**
With `blocks.permissions.model: "provider"`, `can()` and the SQL modules fill
the provider's `idsWith` template for tenant checks and `isPlatform` for
platform checks, at its `tenantScope`. Doctor reports, and `add` refuses:

- a config without `authorization`;
- a `tenantScope` the provider doesn't declare, a scope `idType` other than
  `uuid`, `text`, `bigint` or `integer`, or a `blocks.permissions.idType`
  that differs from it;
- a function those templates call that `authorization.requires` doesn't list,
  doesn't let `authenticated` execute, or the database lacks;
- a permission key a SQL module checks (`modulePermissionKeys` from
  `better-supabase/sql` lists them) that the provider doesn't mark
  `sqlComplete: true`. Its functions decide by role and scope only, so a key
  with other conditions would be granted everywhere in the scope. Map the
  action to another key in `blocks.<module>.permissions`.

It warns when neither `blocks.permissions.functions.canAssign` nor the
provider's `canAssign` is set, because only the service role then assigns
roles. See [the permissions block](/docs/repository/permissions) for the recipe.

It also warns for each optional template an installed module calls that the
provider doesn't set, and names the modules:

| Template        | Modules                                                                                  | Without it                                                                |
| --------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| `idsWithFor`    | `invitations`, `inbox`, `comments`, `sso`, `notifications`, `connectors`, `workflow-sdk` | checks of another user's tenant permissions raise `0A000` or are skipped  |
| `isPlatformFor` | `invitations`                                                                            | checks of another user's platform permissions answer false or are skipped |
| `canAssignFor`  | `invitations`                                                                            | the inviter's right to assign the role is not checked again at acceptance |
| `memberIds`     | `usage`                                                                                  | membership checks read the tenant module's `memberships` table instead    |

`blocks.permissions.functions.canAssignFor` silences the `canAssignFor`
warning.

### BS412

**Info: the session cookie encoding differs between server and browser.**
`@supabase/ssr` needs the same `cookies.encode` on both sides. Doctor reads
the files in `tooling.doctor.sources`: a file that imports `better-supabase/client` or
calls `createBrowserClient` is the browser side, and a file that imports
`better-supabase/server`, `next`, `ssr`, `hono`, `orpc`, `edge` or `expo`, or
calls `createServerClient`, is the server side. When a file on one side sets
`encode: 'tokens-only'` and a file on the other side doesn't, the other side
uses the default `user-and-tokens`: it writes the user object back into the
cookie, or reads a session without one and `session.user` throws. Set the same
`encode` in `createClient` and on the server. See
[Encoding](/docs/auth/sessions#encoding).

### BS413

**Warning: support sessions are not tied to the provider's read-only check.**
Support sessions are installed, `blocks.permissions.model` is `provider`, and
`authorization.functions.actorMayWrite` is not set. Writes still refuse a
read-only `act` through the built-in check. Set `actorMayWrite` to the
provider's read-only helper so that helper is the only check.

### BS414

**Warning: the access contract answers from built-in roles next to a
provider.** The config sets `authorization`, but `blocks.permissions.model`
names another model, so `better_supabase.can()` and
`better_supabase.tenant_ids_with()` answer from the built-in roles. Doctor
reports each policy and each function in `schemas` that calls them. Remove
`model` to use the provider (the default with `authorization`), or call the
provider's own function in that policy.

### BS416

**Warning: `isApprover` has no branch for support sessions.** Under the
provider access model, the `impersonation` module asks
`authorization.functions.isApprover` who may approve a support request, with
`{kind}` set to `'support-session'` and `{subject}` the request id. A
template written only for `'ai-tool'` answers false, so no admin can approve
and every start that needs a second admin stays pending. Doctor reads the
template and the live definition of each function it calls. Add a
`'support-session'` branch, or set `blocks["impersonation"].options.approval`
to `"none"`.

### BS417

**Warning: the provider declares teams but sets no `teamIdsOf` template.**
Under the provider access model, `team_ids_of()` and the team sharing in
`saved-views` and `collections` call `authorization.functions.teamIdsOf` for
the caller's teams. Without it, `team_ids_of()` reads the teams block's own
`team_members`, which a provider that keeps its own teams never fills, and
`saved-views` and `collections` without the teams block share with no team.
Doctor warns when the provider declares a `team` (or `teams`) scope, one of
those blocks is installed, and the template is unset. Set `teamIdsOf` to a
set-returning call with `{user}`, such as `provider.team_ids_of({user})`.

### BS419

**Warning: `permissionsAuthorizer` checks keys the token leaves out.** The
`permissions` claim carries only the keys the authorization provider marks
`sqlComplete: true`, because the SQL functions can't decide the others.
Doctor reports app files in `doctor.sources` that call
`permissionsAuthorizer(` while `authorization.permissions` is missing or has
keys without `sqlComplete`. A check for such a key is denied unless the
authorizer's `load` option reads `my_permissions`. Mark the keys
`sqlComplete` when the SQL functions answer for them, or pass `load`.

### BS420

**Error: a second authorization version source.** When the authorization
provider keeps the versions (`authorization.versions`), the sessions
module's `authzVersions` option renders no table, trigger or broadcast and
reads the provider's function instead. Doctor reports a
`better_supabase.user_authz_versions` table still in the database, and a
custom access token hook other than the provider's that reads
`better_supabase.authz_version(`. Either one gives tokens and the bootstrap a
version nothing bumps, so a role change never looks newer. Drop the table
with a migration (`better-supabase db diff` writes it), and use the
provider's hook or read its versions function.

### BS421

**Error: access token hook behind the tenant scope.** Auth runs the custom
access token hook as `supabase_auth_admin`, where `auth.uid()` is null. The
restrictive `bsb_tenant_scope_*` policies are `to public`, so they apply to
that role too and let it see no rows. Doctor reports a `security invoker` hook
whose body reads a table with a restrictive `bsb_tenant_scope_select` policy
that doesn't let `supabase_auth_admin` through. Every token then misses the
claims the hook reads from that table. Add the role to the tenant scope:

```ts title="better-supabase.config.ts"
export default defineConfig({
  database: { sql: { tenantScope: { exemptRoles: ["supabase_auth_admin"] } } },
});
```

The exemption only lifts the restrictive scope. The hook still needs the grant
and the permissive policy for `supabase_auth_admin` that the Supabase hook guide
describes. Or make the hook `security definer`, owned by a role that bypasses
row level security.

### BS426

**Info: a config value the authorization provider already supplies.**
`blocks.invitations.options.platformRoles`,
`blocks.memberships.options.roleThrough`, the memberships `disabledAt` column
and `blocks.permissions.disabled` (`tenant`, `user` and `userKey`) default to
what the provider declares in `platformRoles`, a role source's `through`, a
membership's `disabledAt` and `suspension`. A config value equal to
the provider's is a second copy that goes stale when the provider changes.
Remove it.

## Env files

### BS501

**Error: secret in a browser variable.** A variable with a public prefix
(`NEXT_PUBLIC_`, `VITE_`, `EXPO_PUBLIC_`, `PUBLIC_`, `NUXT_PUBLIC_`) holds a
secret key. Bundlers inline these into client code. Rename the variable and
rotate the key.

### BS502

**Warning: env file with secrets isn't ignored by git.** An env file holds a
secret key or database URL but no `.gitignore` pattern matches it. Add the
file, for example `.env*.local`, to `.gitignore`. `.example` files are skipped.

### BS503

**Warning: exported Supabase variable differs from the running stack.** A
`SUPABASE_*` variable exported in your shell, such as a `SUPABASE_URL` left
over from another worktree, has another value than the local stack. The app
then talks to the wrong stack, because frameworks never override a variable
that is already set. The finding names the variable and both values, redacted:
the host and port for a URL, and a SHA-256 fingerprint for a key. Unset the
variable, or start the app with `better-supabase dev run -- <cmd>`, which sets the
stack's values over the shell's. Doctor only checks this when the shell
exports a `SUPABASE_*` variable and the local stack is running.

### BS504

**Error: env key a block needs is missing.** An installed block declares an env
key, such as `CRON_SECRET` for the outbox relay or `STRIPE_WEBHOOK_SECRET` for
billing, and no env file lists it and the shell doesn't set it. The route or
worker that reads it then fails at runtime. `better-supabase add` and `init`
append the keys to `.env.example`; set them in `.env.local` and in every
deployed environment. Optional keys, like `AI_GATEWAY_API_KEY` (the OIDC token
works on Vercel), are never reported.

### BS505

**Error: required provider is not wired.** A block that can't run without an
implementation is installed: enrichment needs an `EnrichmentProvider` and
mail-sync needs its `MailProvider`s. No app source passes the instance one with
`.with(...)` or `.using(...)`. `add` writes a commented stub for it in
`providers.ts`, next to `blocks.generated.ts`. Fill in the stub, then spread
`...providers` into `defineBlocks(blockConfig, { ...blocks, ...providers })`.
Comments don't count, so the finding stays until the stub is real code.

### BS507

**Warning: block actions are not registered.** An installed block ships
automation actions, such as the conversions `tasks.from_conversation` or
`quotes.from_deal`, but no app source calls `blockActions(...)` or
`createActionRegistry(...)`. A default automation that you turn on then names an
action the rules consumer can't run. Build the registry with
`createActionRegistry([...blockActions(blocks, { clients })])` from
`better-supabase/blocks/automations` in the outbox route.

### BS508

**Warning: block timers have no handler.** An installed block declares timers,
such as an SLA check, but no app source calls `blockTickHandler(...)`, so the
timers never fire. Call
`jobs.ensureSchedules(blockSchedules(blocks), { prefix: BLOCK_SCHEDULE_PREFIX })`
once and drain the `block_ticks` queue with `blockTickHandler`.

### BS510

**Warning: maintenance jobs have no scheduler.** The schema files install the
`housekeeping` module (the `maintenance_jobs` view), but no schema file calls
`maintenance_schedule()` or schedules `maintenance()` with `cron.schedule`, and no
source calls `maintenanceTick(...)`. The purges and expiries the installed blocks
contribute never run. Run `select better_supabase.maintenance_schedule()` once,
which registers pg_cron, or drain the `block_ticks` queue with `maintenanceTick`
when pg_cron is not available. The check is static: it cannot see whether a job
is due in the live database, so it does not replace reading `maintenance_jobs`.

### BS511

**Warning: a client component reaches the server block wiring.** A module with
`"use client"` imports `blocks.generated` or `providers.ts`, or calls
`defineBlocks`, so every installed block client ends up in the browser bundle.
Import `blockConfig` from `blocks.config.ts`, which holds data only. When the
browser needs a few block clients, list those instances in `gen.clientBlocks`
and import `clientBlocks` from `blocks.client.ts`.

### BS506

**Warning: server and browser Supabase URLs differ.** An env file sets
`SUPABASE_URL` and a browser spelling such as `NEXT_PUBLIC_SUPABASE_URL` to
different URLs. The session cookie name comes from the URL
(`sb-<project-ref>-auth-token`), so the server and the browser client then
read different cookies, and a sign-in on one side is invisible to the other.
The finding shows each URL's host and port. Use one URL, or when the split
is intended (a custom domain in the browser, the project URL on the server),
set `auth.cookie.name` on `createNext` and on the browser client to the same
name.

## Dependencies

### BS601

**Warning: peer outside its range.** An optional peer of better-supabase is
installed at a version outside the range better-supabase declares, for
example `@supabase/postgrest-typegen@0.7.0` against `>=0.6.0 <0.7`. With
`strictPeerDependencies` the install fails, and the subpath that needs the
peer can break at runtime. Doctor reads the version from the nearest
`node_modules` above the project root and skips peers that aren't installed.
Install a version in the range, or remove the package if nothing imports it.
[Peers](/docs/getting-started/peers) lists which subpath needs which peer.

### BS602

**Error: content mapper not set up.** `gen.contentMapper` is on, so `gen`
writes `schema.bsb` instead of the type files, but `tsc` can't load the
[content mapper](/docs/content-mapper) that serves its types. The finding
names each missing piece: `tsconfig.json` has no `contentMappers` entry for
`better-supabase`, the project resolves TypeScript older than 7.1, or the
`typecheck` script in `package.json` runs `tsc` without `--runExternalCode`.
Doctor skips the script check when there is no `typecheck` script.
`better-supabase init --content-mapper` adds the entry and the flag. To go
back to the type files, turn `gen.contentMapper` off and run `gen`.

### BS607

**Warning: installed better-supabase differs from the lockfile or the
database.** Doctor compares three records of which release the project runs.
The finding names the one that differs:

- The `better-supabase` in `node_modules` is not a version the nearest
  lockfile at or above the project resolves (`pnpm-lock.yaml`,
  `package-lock.json`, `yarn.lock` or `bun.lock`), which happens after a pull
  that changed the lockfile. Run the install command the finding prints.
  Workspace links and file paths are skipped.
- A block file in `supabase/schemas`, or the module migration under the
  migrations workflow, carries a `@bsb-block` version newer than this release
  ships.
- A `better_supabase.blocks` row in the database records a newer version,
  read when doctor checks a live database.

The last two mean a newer release wrote the SQL, so `gen`, `add` and
`upgrade` would render the blocks of an older release. Install the release
your lockfile and teammates use, then run `better-supabase upgrade --check`.
[BS311](#bs311) reports the opposite case, SQL older than the release.

### BS608

**Warning: remote cache scope without a remote cache handler.** A source file
uses `bsb.remote()`, `bsb.cached({ scope: "remote" })` or
`"use cache: remote"`, the project has no `vercel.ts`, `vercel.json` or
`.vercel/project.json`, and `next.config` sets no `cacheHandlers.remote`.
Next.js then keeps remote entries in each instance's memory, so instances
never share them and every deploy starts cold. Set `remoteCacheHandler` in
`createNextConfig()` (or `cacheHandlers.remote`) to a shared handler such as
Redis. See [remote cache scope](/docs/frameworks/next-cache-components#remote-scope).

### BS609

**Info: three or more database reads in one `Promise.all`.** A source file
awaits at least three repository, block client or `$rpc` calls in one
`Promise.all`. They run in parallel, but each is its own request to
PostgREST. A read set compiles the same reads into one stable database
function, so the page waits on one round trip: `defineReadSet(db, "name", ...)`
and `db.$many(readSet, params)`, or `bsb.bootstrap` for a page's first load.
See [read sets](/docs/repository/read-sets).

### BS610

**Warning: nested private cache scopes.** A function with
`"use cache: private"` calls another function in the project that has the same
directive. Next.js doesn't nest private scopes, and each scope resolves the
session again. Call the inner function from the page and pass its result down,
read both in one scope, or give every scope the same
[session handle](/docs/frameworks/next-cache-components#skip-the-request-read-with-a-session-handle).
The check reads source text, so it follows function declarations and arrow
functions that carry the directive as their first statement.

### BS611

**Warning: service-role client in a private cache scope.** A function with
`"use cache: private"` calls `bsb.admin()` or `createAdminClient`. The service
role skips the user's policies, so what it returns is cached under the user's
key but isn't their data, and each call adds a verification. Read as the user,
or move the admin read out of the cached function.

## Shims

These checks read the app's source text, matched by `doctor.sources`, for code the library now covers. Each one reports once per file and only in files that name better-supabase. The shim registry in `src/cli/doctor/shims.ts` lists them, so one entry adds a check.

### BS621

**Warning: a client file imports a generated barrel.** A file with
`"use client"` imports `generated-schema`, `blocks.generated` or
`blocks.config`. Each one lists every table or every installed block, so the
page ships all of them. Import the table modules (`tables/<table>`) and block
slices (`blocks/slices`) the page uses, and build the browser's client over
`clientSchema`. The check is off with `gen.tableModules: false` and in content
mapper mode.

### BS622

**Warning: a block adds a column to a table your files create.** A block runs
over a table you create and adds an optional column to it with `add column if
not exists`, and your own schema files don't declare that column. Blocks no
longer add columns to tables you own and turn the feature that needs the column
off instead. Run `better-supabase codemod owned-columns` to
declare the columns in your schema files, or map the column to `null` in
`blocks.<name>.columns` to keep the feature off.

### BS623

**Warning: a block's unique index repeats one of yours.** A block creates a
unique index on a table where your own files already have a unique index over
the same columns, or over a subset of them. Your index is the stricter key, so
the block's adds write cost and storage and guarantees nothing more. Drop the
block's index, or narrow the block's key to the columns your index covers.

### BS624

**Warning: a block's trigger repeats one of yours.** A block creates a trigger
that keeps `updated_at` current on a table where your files already call
`track_updated_at()`, so both run on every write. Keep one of them.

### BS612

**Info: the proxy re-syncs session cookies with `setAll`.** Since 0.40 the library's own cookie handling in `bsb.proxy` writes them. Remove the callback.

### BS613

**Info: an extra Auth call follows `bootstrap`.** `auth.getUser()` or `auth.getClaims()` next to a bootstrap call. Since 0.44, `Bootstrap.endReason` says why a session ended without a second Auth call.

### BS614

**Info: the authorization version is seeded by hand after `bootstrap`.** The bootstrap already seeds the live version.

### BS615

**Info: comment paging filters `deletedAt` in the app.** Use `includeDeleted` on the comments client.

### BS616

**Info: comment authors are read again after a comment list.** With `profiles` installed, `Message.author` is `{ id, name, avatarUrl }`.

### BS617

**Info: `withPublicPolicyRoles`.** The catalog query maps empty policy roles to public itself.

### BS618

**Info: a unique violation is detected by `code === "23505"` or by a message search.** Use `isConflict(error, constraint)`.

### BS619

**Info: a support caller is built as an `AuthState` by hand.** Pass `{ token, claims }`, a `SupportCaller`, to the support API.

### BS620

**Info: settings are merged into one JSON blob by hand.** The `settings` block validates each key against a Standard Schema and writes one key at a time.

## Local stacks

These checks read the machine's System V shared memory with `ipcs`, so they
report on every stack the Supabase CLI runs, not only this project's. They
skip on Windows.

### BS700

**Warning: shared memory segments almost used up.** At least 80% of the
System V shared memory segment limit is in use. Every running Postgres keeps
one small segment as an interlock, even with `shared_memory_type = mmap`, and
macOS allows 32 (`kern.sysv.shmmni`). When they run out, the next stack or
shadow database fails with `could not create shared memory segment: No space
left on device`, which is how `supabase db diff` and `declarative sync` fail
on a machine with many worktrees. The finding names the stacks that hold
segments. Run [`stack prune --stop-idle`](/docs/cli/dev#prune) to destroy
the stacks of deleted worktrees and branches and stop the others, or raise
the limit. [`db diff`](/docs/cli/db#diff) needs no shadow database.

### BS701

**Warning: local stack uses System V shared memory.** A stack holds more than
the one small interlock segment, so its Postgres sets `shared_memory_type` or
`dynamic_shared_memory_type` to `sysv`. Its shared buffers and parallel query
memory then take segments of their own and fill the limit faster. The
defaults on macOS and Linux are `mmap` and `posix`; remove the override from
the stack's Postgres settings.
