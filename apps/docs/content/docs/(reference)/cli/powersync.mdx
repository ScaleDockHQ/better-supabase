---
title: powersync
description: Write PowerSync sync streams, the PowerSync schema and the publication migration for the blocks that work offline.
---

`powersync streams` writes the files PowerSync needs to sync block tables to a
device: the sync streams for the PowerSync service, the client `Schema`
tables, and a migration that adds the tables to the `powersync` publication.
Set `gen.powersync` and `gen` runs it as the `powersync` task.

```ts title="better-supabase.config.ts"
export default defineConfig({
  blocks: {
    memberships: {},
    organizations: {},
    notifications: {},
    attachments: {},
  },
  gen: {
    powersync: { instances: ["notifications", "attachments", "memberships"] },
  },
});
```

```bash
pnpm better-supabase powersync streams           # write the files
pnpm better-supabase powersync streams --check   # exit 1 when a file is out of date
```

| Command             | Side effects  |
| ------------------- | ------------- |
| `powersync streams` | Writes files. |

## Options

| Option            | Default                               | What it does                                                 |
| ----------------- | ------------------------------------- | ------------------------------------------------------------ |
| `--instance keys` | `gen.powersync.instances`             | The block instances to sync, comma separated                 |
| `--out dir`       | `gen.powersync.out`, then `powersync` | The folder for `sync-streams.yaml` and `schema.ts`           |
| `--check`         |                                       | Writes nothing; exits 1 with a diff when a file would change |
| `--dry-run`       |                                       | Prints what would change and writes nothing                  |
| `--force`         |                                       | Overwrites files the CLI did not write                       |

`gen.powersync.import` sets the module `schema.ts` imports `column` and
`Table` from. It defaults to `@powersync/common`; React Native apps can use
`@powersync/react-native`.

## What it writes

| File                                                    | What it holds                                                                                   |
| ------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `powersync/sync-streams.yaml`                           | One auto-subscribed stream per table, filtered to the signed-in user                            |
| `powersync/schema.ts`                                   | A PowerSync `Table` per synced table, and `blockTables` to spread into `Schema`                 |
| `supabase/migrations/<stamp>_powersync_publication.sql` | Creates the `powersync` publication with the synced tables, or adds the new ones                |
| `supabase/schemas/powersync_publication.sql`            | Declares the publication with every synced table, when the repo has a `supabase/schemas` folder |

Each block syncs only the rows the user can read:

| Block           | Tables                                             | Rows                                                                                                     |
| --------------- | -------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `notifications` | `notification_recipients`, `notification_events`   | The user's recipients and the events they point at                                                       |
| `attachments`   | `attachments`                                      | The files of the organizations where the user may read them                                              |
| `memberships`   | `memberships`, `membership_roles`, `organizations` | The user's active memberships, every member's roles in the user's organizations, and those organizations |
| `teams`         | `teams`, `team_members`                            | Every team in the user's organizations and its members                                                   |
| `profiles`      | `profiles`                                         | The user's own profile                                                                                   |

`attachments` reads the user's organizations from the `memberships` block, so
the config needs it. `memberships` adds the `organizations` table when the
config has the organizations block, so the organization switcher can show the
names offline. Other blocks can't sync yet; the command names the instance it
refuses.

A block that runs over the app's own table (`blocks.<name>.tables`, such as
`memberships: { tables: { memberships: "public.memberships" } }`) syncs that
table: the stream selects from `public.memberships`, the publication adds it,
and the client `Table` takes its columns from the snapshot `gen` saves. Save a
snapshot first (`better-supabase gen --save-snapshot`); without one the command
can't read the app table's columns and refuses the instance.

PowerSync replicates past the column grants and RLS policies, so each stream
selects only what the block lets the user read: the organizations stream lists
its columns instead of `*`, a disabled membership (`disabled_at` set) stops
syncing, and profiles sync only the user's own row. With the `roles` access
model, files sync only from the organizations where one of the user's roles
holds the attachments `read` key. Columns that a later `alter table ... add
column` adds sync too. Rows without an `id` column (`memberships`,
`membership_roles`, `team_members`) get one that joins their keys, such as
`<organization>:<user>`, `<organization>:<user>:<role>` and `<team>:<user>`;
the upload routes read it back.

The command reads your schema files. A table that one of your views projects
(`create view public.job_attachments as select id, tenant_id as organization_id,
name from better_supabase.attachments where subject_type = 'job'`) streams the
view's columns under the view's names and only the rows its `where` keeps, and
`schema.ts` takes the same columns, because the client reads the view. A view
with a join, an aggregate or an expression in its select list isn't a
projection. A table keyed by two columns still streams the composite `id`,
because PowerSync needs one on every row, and a table with its own `id` streams
that one, as text when it is a bigint. The authorization provider's version
column (`authz_version`, `permissions_version`) never syncs: the native client
refreshes on the provider's broadcast. The `membership_roles` stream covers every
member of the user's organizations, with no filter on the user or on disabled
members, so a role list on the device matches the server's. Doctor BS381 flags a
`createNativeClient`, `powersyncEngine`, `attachmentQueueRoute` or `queryEngine`
call that names a projected table instead of its view. The command syncs only the
instances in `gen.powersync.instances` or `--instance`, so installing a block
adds no stream.

### Files of a subject, and child tables

When a projection keeps one `subject_type` (`where subject_type = 'job'`) and
a table tagged `@bsb subject type=job` has a tenant column, the attachments
stream also keeps only the files whose `subject_id` is a row of that table in
the user's organizations (and, with `deleted-at`, one that is not deleted). A
file whose job is gone does not sync.

A view that names several subject types (`where subject_type in ('job', 'quote')`,
or the same types joined with `or`) gets one branch per type: a file syncs when
its `subject_type` is that type and its `subject_id` is a row of that type's table
in the user's organizations. A type no table registers with a tenant column keeps
only its `subject_type` and the organization bound. When no named type has a
registered table, or the view names no type, the stream keeps the view's `where`
alone.

An app table that belongs to a parent subject syncs with `gen.powersync.children`:

```ts title="better-supabase.config.ts"
gen: {
  powersync: {
    instances: ["memberships", "attachments"],
    children: [{ table: "public.job_parties", parent: "job", column: "job_id" }],
  },
},
```

The stream selects the rows of `job_parties` whose `job_id` is a `jobs` row in
the user's organizations, takes the child's columns from the snapshot
(`better-supabase gen --save-snapshot`), and adds the table to the publication
and the client `Schema`. The child needs an `id` column, and `parent` needs a
tenant column. Without the memberships instance the command has no
organizations to bound the stream by and refuses it.

The streams use Sync Streams edition 3, with a `with:` CTE for the user's
organizations. The first migration runs `create publication powersync for
table ...`. A later run reads the tables every earlier
`*_powersync_publication.sql` added and writes a new migration with one `alter
publication powersync add table ...` per new table, so a pushed migration is
never rewritten. If you created the publication yourself (`for all tables`),
delete the first generated migration.

Upload the streams with the PowerSync dashboard or CLI, then spread the tables
into the client schema:

```ts title="src/powersync/schema.ts"
import { Schema } from "@powersync/react-native";

import { blockTables } from "../../powersync/schema";

export const schema = new Schema({ ...blockTables });
```
