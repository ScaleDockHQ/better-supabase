---
title: codemod
description: Rewrite imports, subpaths and environment names for renamed better-supabase APIs after an upgrade.
---

`better-supabase codemod` rewrites your source for the renames in a release,
so an upgrade is a command and a review instead of a search through the
codebase. Run it after you update the package:

```bash
pnpm better-supabase codemod naming --dry-run
pnpm better-supabase codemod naming
```

Pass files or directories after the name to limit it (`codemod naming src app`).
Without them it walks the project and skips `node_modules`, build output
(`dist`, `build`, `.next`, `.turbo`, `.vercel`, `coverage`) and `.d.ts` files.
`--dry-run` prints a unified diff of each file it would change and writes
nothing. `--check` writes nothing and exits 1 when a file still needs the
codemod, so CI can tell the upgrade is done ([writing files](/docs/cli#writing-files)).

The codemod runs even when the config file fails to load, because the config
it migrates is often the one the new version rejects. It then walks the
directory that holds the discovered config file, or `--cwd` when there is none.

This release upgrades from 0.53 only. An app on an older version upgrades to
0.53 first with that release ([ADR 0245](https://github.com/ScaleDockHQ/better-supabase/blob/main/docs/decisions/0245-upgrades-start-at-0-53.md)).

| `naming`         | Applies the rename table of `api/naming.json`: renamed exports and types in imports and where they are used, renamed `better-supabase/<subpath>` specifiers, renamed environment variables in source, `.env*` files and `turbo.json`, one hand migration for renamed SQL objects of installed blocks (`alter ... rename`, `-- destructive: reviewed`, no data moves), the renamed block column names in your schema files and seeds (only in statements that name a `better_supabase` table, never in migrations), and a `columns` entry in the config that keeps the old name of a column your own table already has (`drive_nodes.deleted_at`, the actor columns of scorecards and status history).                                                                                                |
| `extra-columns`  | Moves each `blocks.<name>.options.extraColumns` (and `*ExtraColumns`) column into your schema files and drops the option from the config. A column goes beside the `alter table` statements of an app file that already alters the block's table, or into `<table>.ext.sql` next to your schema files when none does. The block then reads the column as a field because your file adds it. Files a block wrote (`@bsb-block`) are never edited. For a table you create yourself, the codemod lists the columns in the table comment as `@bsb fields`, adding the comment when the table has none. A column whose table the block does not have in your project stays in the config and is listed after the summary. The options are rejected at render time with a message that names this codemod. |

The statements are the blocks' own, so a database that has the columns changes nothing. Running it again finds nothing.                                                                                                                                                                                                                                                                                                                                                   |
| `config`         | Removes the `columns` entries the render refuses: a `null` for an optional column the view the block runs over lacks anyway, and a `tenant` that repeats `sql.tenantColumn` (doctor BS379). Other `null` entries stay. It edits the config file only.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| `read-many`      | Rewrites nothing. A `queries.<table>` read is listed for a hand change. It does nothing when `gen.tableModules` is `false` or `gen.contentMapper` is on.                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| `account-calls`  | Rewrites `bsb.deleteAccount(id)` to `deleteAccount(bsb, id)`, and the same for `suspendAccount`, `endSessions` and `lastSignIns`, and imports them from `better-supabase/server/account` (ADR 0604). Only a call on a plain identifier is rewritten.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `server-imports` | Splits each import from `better-supabase/server` so the account helpers (`deleteAccount`, `suspendAccount`, `endSessions`, `lastSignIns`, `supportSessions`, `supportStorage`, `sessionStatusRoute`, `claimsFingerprint`), the CSV helpers and the rate-limit header helpers import from `better-supabase/server/accounts`, `/csv` and `/rate-limit` (ADR 0450). Names that stayed keep their import.                                                                                                                                                                                                                                                                                                                                                                                                |

## What it rewrites

Each codemod makes narrow, mechanical renames. It reads the source with a
small scanner that skips strings, template literals and comments, so a name
in a message or a comment stays as it is.

- **Imports.** A renamed export imported from `better-supabase` or one of its
  subpaths is renamed in the import and wherever the file uses it. An aliased
  import (`Postgres as PG`) keeps the alias, and imports from other modules
  are left alone.
- **Subpaths.** A `better-supabase/<subpath>` specifier in a string is renamed.
- **Environment variables.** A renamed variable is renamed wherever a source
  file, an `.env*` file or `turbo.json` names it, as a whole word.
- **SQL.** A renamed table, column or policy of an installed block gets one
  migration of `alter ... rename` statements, each behind an existence check.

## What it leaves for you

Some renames depend on what a variable holds. The codemod doesn't guess: it
lists those lines after the summary, as `path:line: message`, so you can change
them by hand.

```text
Updated 3 of 41 files:
  src/lib/supabase/client.ts
  src/app/providers.tsx
  src/app/api/mcp/route.ts

Check these by hand:
  src/app/page.tsx:12: the message the codemod lists
```

Run your type checker afterwards; a rename the codemod missed shows up there.
With `--json`, the envelope's `data` is `{ codemod, dryRun, changed, review }`.

SQL module renames of the block SQL itself are not source rewrites:
`better-supabase upgrade` handles them. Doctor BS260 reports source that still
uses a renamed name.
