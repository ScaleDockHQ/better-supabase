---
title: gen
description: Generate database types, typed models, relation metadata and validators.
---

```bash
better-supabase gen [--only <list>] [--check] [--snapshot <file>] [--db-url-stdin | --project-ref <ref>]
better-supabase gen --metadata <path|-> [--only <file> | --out <dir> [--check]]
```

`gen` is the one command to run after a schema or config change. It writes
the typed client from the database, then every other generated file the
config sets up, so the config holds the options instead of each command line.

Side effects: Writes files, reads the database, calls the Supabase Management API with `--project-ref`.

## Tasks

| Task        | Runs by default when                                   | Does what                                                                                                     |
| ----------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| `types`     | always                                                 | Writes the files this page describes                                                                          |
| `sql`       | `blocks` lists a module, or `realtime.policies` is set | [`upgrade`](/docs/blocks/sql): rewrites the SQL module files                                                  |
| `powersync` | `gen.powersync` is set                                 | [`powersync streams`](/docs/cli/powersync): writes the sync streams, the schema and the publication migration |
| `spec`      | the `api.specs.entry` file exists                      | [`spec emit`](/docs/cli/spec), with `api.specs.failOn` and `api.specs.manifest`                               |
| `seed`      | the `database.seed.entry` file exists                  | [`seed`](/docs/cli/db#seed): renders the fixtures to SQL                                                      |
| `env`       | never; list it to run it                               | [`env`](/docs/cli/dev#env): writes the local stack's keys to `env.output`                                     |

The tasks run in that order, since later ones read what earlier ones write.
Pin the list in the config with `gen.tasks`, or pass `--only` for one run:

```ts title="better-supabase.config.ts"
export default defineConfig({
  gen: { tasks: ["types", "sql", "spec"], watchInterval: 1000 },
});
```

```bash
better-supabase gen --only spec,seed
```

A listed task always runs, even when the config doesn't set it up, so a
missing entry file fails loudly instead of being skipped. A run that writes
stops at the first task that fails. `--check` runs every task and reports
everything that is out of date, and leaves `env` out because it writes local
keys rather than a committed file. With one task, the output is that task's
own; with several, each gets a section headed by its name.
`gen --metadata` reads the schema from a document and runs no other task.

`gen` introspects your database with
[`@supabase/postgrest-typegen`](https://github.com/supabase/postgrest-typegen),
the same generator behind `supabase gen types typescript`, and writes:

1. `database.types.ts`, what `supabase gen types` prints for the same schema
   (CI checks this against the Supabase CLI), so `createClient<Database>()`
   works as usual;
2. the main module (`output`), with models in your casing, enum and CHECK
   constants, typed constraint names, and the `schema` object;
3. the runtime metadata next to it (`generated.meta.js`, with
   `generated.meta.d.ts`): tables, columns, relations with foreign key
   actions, and functions. Relations follow each foreign key to the table it
   references; the copies PostgREST lists for views over that table are
   left out, so adding a view never renames another table's relations. It is plain JavaScript typed as `SchemaMeta`, so
   TypeScript doesn't check a large object literal in every program that
   imports the main module. Each table and function is one line of JSON, which
   keeps the module small to load and a schema change visible per entry in a
   diff. Commit both files with the main module;
4. with `blocks` configured, `blocks.config.ts` next to the main module: each
   installed block's schema, API schema and the options its SQL and TypeScript
   halves share, with the module defaults filled in, as data only, for
   [`defineBlocks(blockConfig, ...)`](/docs/blocks/create-blocks#the-generated-config)
   and `createClient(app, { blocks: blockConfig })`. Browser code imports it
   without pulling in any block client. `blocks.generated.ts` re-exports
   `blockConfig` and adds `blocks`, each instance's manifest under its key, for
   [`betterSupabase.blocks()`](/docs/blocks/create-blocks#block-instances-on-db):
   import it from server code only. With `gen.clientBlocks` set, `blocks.client.ts`
   holds `clientBlocks`, `defineBlocks` over just the listed instances, so the
   browser bundle carries those clients and no others. With `gen.serverBlocks` set
   (`{ shell: ["permissions", "organizations"] }`), `blocks.shell.ts` holds `shellBlocks` and
   `shellInstances` the same way for the server, so a route that builds its server from the
   set (`createNext(app.blocks(shellBlocks))`) bundles those blocks and no others. The `reads` constant
   lists, next to each table a read touches, the typed key of every view your schema
   files project over it (`job_attachments` over `attachments`), so a cached read
   served from the view is invalidated by a write to the table. None of this needs a
   database, only the config;
5. with blocks that have a record binding installed, a
   [record type](/docs/repository/record-bindings#generated-record-types) per type in
   `config.recordTypes`, in `records/<type>.ts` next to the main module, unless
   `gen.records` is `false`;
6. with `gen.hooks` set, `hooks.ts` next to the main module: a list hook and a
   record hook per table (`useCustomers`, `useCustomer`) for the
   [data hooks](/docs/frontend/data-hooks) of that framework. A block table that
   one of your views projects gets no hooks; its view's hooks read it;
7. one file per configured generator (`zod()`, `valibot()`, `jsonSchema()`,
   `standardSchema()`);
8. with `readSets` configured, the `read-sets` SQL module file: one function per
   [read set](/docs/repository/read-sets). `gen` imports those modules after
   writing the main module, since they import it.

It doesn't need Docker or the Supabase CLI: it only needs a way to run SQL.
Files are only rewritten when their contents change, so watchers and bundlers
don't rebuild for nothing. Line endings don't count as a change: a checkout
with `core.autocrlf` keeps its `\r\n` files, and `--check` passes on them.

`database.types.ts` is formatted with [oxfmt](https://oxc.rs/docs/guide/usage/formatter),
an optional peer. Without it, `gen` writes the file unformatted and says so;
install it with `pnpm add -D oxfmt`. better-supabase accepts any oxfmt from
0.66.0 up to, but not including, 1.0. `@supabase/postgrest-typegen` pins exactly 0.66.0 as its
peer, the version that formats like `supabase gen types`, so pnpm
warns about a newer oxfmt until you allow it in `pnpm-workspace.yaml`:

```yaml title="pnpm-workspace.yaml"
peerDependencyRules:
  allowedVersions:
    "@supabase/postgrest-typegen>oxfmt": "0.71.0"
```

Names are sorted by code point, not by locale, so every machine writes the
same files.

## Introspection cache

Before reading a database, `gen` runs one query that hashes the system
catalogs (tables, columns, constraints, policies, functions, grants, comments,
role memberships and role settings; planner statistics are left out). When the hash, the
schemas, the better-supabase version and the pinned typegen version match the
last run, it reuses the
snapshot cached in `node_modules/.cache/better-supabase` and skips
introspection. Deleting that folder clears the cache.

[`dev`](/docs/cli/dev#watching) keeps one connection open and runs that query
whenever a file changes or the polling interval passes, so it reads the full
schema only after a change. `gen --watch` was removed in favor of `dev`;
`--no-cache` skips the cache for one run and
[`cache purge`](/docs/cli/cache) deletes it. Connecting gives up after 10
seconds, and each introspection query after 2 minutes.

## Content mapper

With `gen.contentMapper: true`, `gen` writes `schema.bsb` and a
`generated.ts` that re-exports its types, and no `database.types.ts`;
TypeScript 7.1 gets the types from the
[content mapper](/docs/content-mapper). The `types` task also writes the
mapper's cache, and when the types change, a stamp file in
`node_modules/.cache/better-supabase` that the editor watches, so [`dev`](/docs/cli/dev#watching)
reloads the types in the editor too. `--check` checks the mapper-mode files.

## Enum and column constants

`gen.constants: true` writes two modules next to the generated module, and
neither imports anything. `enums.ts` holds every enum and every CHECK value
list as a constant array and its union type (`noteKindValues`, `NoteKind`), so a
browser form or a script reads them without the runtime package. `columns.ts`
holds one constant per table that maps each column's row name, in the
configured casing, to its database name (`customersColumns.createdAt` is
`"created_at"`), for `$client`, `queryRaw` and SQL. It is off by default.

## Table modules

By default `gen` writes one module per table, `tables/<table>.ts`, next to the
generated module (`gen.tableModules: false` writes the single module instead). Each one exports the table's runtime metadata as
`<key>Table` (`customersTable`), and `generated.meta.js` lists no table. A page
that imports one table module does not load the others. `gen.types.tables.only`
lists the relations `database.types.ts` includes; the rest are omitted, and
`gen.types.also` lists more files that get a copy of it, for a monorepo whose apps share the types. The
server's schema moves to `generated-schema.ts`, which imports every table. The
generated module keeps the types, `buckets`, the extensions and `clientSchema`,
a schema with no tables for a browser client.

A client on `clientSchema` registers the tables it uses. Pass the module to
`bsb.table`, which returns the repository, or to a generated hook, which reads
through it. A table you embed with `with` is registered the same way before the
query.

```ts
import { createSupabase } from "better-supabase";
import { createClient } from "better-supabase/client";

import { clientSchema } from "./generated";
import { customersTable } from "./tables/customers";

const bsb = createClient(createSupabase(clientSchema), { env });

const customers = bsb.table(customersTable);
await customers.list({ where: { status: "active" } });
```

A route that only signs in and subscribes can use `better-supabase/client/lite`.
It builds Auth and Realtime and leaves out PostgREST, storage and functions.
Install `@supabase/auth-js` and `@supabase/realtime-js`. Cookie sessions stay on
`better-supabase/client`.

```ts
import { createLiteBrowserClient } from "better-supabase/client/lite";

const bsb = createLiteBrowserClient(url, key);
```

The generated `hooks.ts` does this for every `gen.hooks` framework (React, Vue,
Solid and Svelte): each hook is made with the table module and reads through
`client.table`. The file also exports `AppDb`, an interface over the app's
`db`, so each hook resolves one named type. Doctor reports a `"use client"` file
that imports `generated-schema`, `blocks.generated` or `blocks.config`
([BS621](/docs/cli/doctor#bs621)).

`defineListQuery` takes a table module in place of a table name, so a module
that defines a list for a client component loads one table. Keep server code on
`schema` from `generated-schema.ts`: a page that imports it loads every table.
`tests/next-build` in this repository holds the Next.js example to that rule.

`--metadata` output and the content mapper write the single-module output. An
existing project moves to this layout with `better-supabase codemod table-modules`:
it imports `schema` from `generated-schema` and, in a `"use client"` file,
rewrites `bsb.db.customers` to `bsb.table(customersTable)` with the import.

## Block modules

By default `gen` writes `blocks/slices.ts`, one export per
installed block instance (`commentsConfig`, `customFieldsConfig`), and
`blocks/permissions.ts` with `permissions` and `PermissionKey`. A slice is the
instance's schema, API schema, function names and options as plain data.
`blocks.config.ts` composes the slices into `blockConfig` for server code, and
each `records/<type>.ts` imports only the slices of the blocks it binds, so a
record no longer carries the config of every installed block.

Client code imports the slices it uses and passes them to the client:

```ts
import { commentsConfig, tagsConfig } from "@/lib/supabase/blocks/slices";

export const bsb = createClient(clientApp, {
  env,
  blocks: { comments: commentsConfig, tags: tagsConfig },
});
```

A client component that imported `blockConfig` loads every slice, so import the
slice instead (`commentsConfig.api`). A record's own slices fill in the blocks
the client's `blocks` option leaves out. The slices live in one module because a
bundler drops the exports a page doesn't import, and a module per instance adds
a wrapper to the chunk for each one. `gen.blockModules: false` writes
`blockConfig` as one object.

The slices are plain data. The block API types stay in `blocks.generated.ts`
as aliases over the block packages, because writing a concrete interface per
instance needs a type extraction step that `gen` does not have. Import those
types with `import type`, which costs nothing at runtime.

## Permission catalog

With `gen.permissionCatalog: true` and `blocks.permissions.model: "catalog"`,
`gen` writes `<stamp>_better_supabase_permission_catalog.sql`, a migration that
inserts a row for every permission key the installed blocks check or declare on
their entities, and the default grants of the `owner`, `admin` and `member`
roles. A new block's pages no longer answer 403 for the owner until you write a
catalog migration by hand. When the installed blocks or their keys change, the
next `gen` writes a new migration that holds every statement again, and
`gen --check` reports the file as stale. Every statement skips rows that exist,
and the migration runs again whole, so it grants a key's defaults again after
you removed one. Change a role's grants in your own migration only for keys the
generated one does not hold.

The same run writes `permission-scopes.ts` next to `blocks.config.ts`:

| Export         | Holds                                                                            |
| -------------- | -------------------------------------------------------------------------------- |
| `apiKeyScopes` | Every tenant permission key, for `scopes` of an API key                          |
| `oauthScopes`  | The same keys without the `manage` keys, for the scopes an OAuth client requests |

Platform keys get a catalog row and no default grant. The command needs the
managed catalog tables; it stops with `config_invalid` when
`blocks.permissions.tables` or `columns` rename them.

## Options

| Option                 | Effect                                                                                                                                                           |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--only <list>`        | The [tasks](#tasks) to run, comma-separated. Defaults to `gen.tasks`, then every task the config sets up.                                                        |
| `--check`              | Writes nothing; exits 1 when a generated file is out of date and prints a diff of each one. Use it in CI.                                                        |
| `--dry-run`            | Prints a diff of each file that would change, and writes nothing.                                                                                                |
| `--offline`            | Never connects: reads the saved snapshot (`--snapshot` or `source.snapshot`) and fails without one, so `gen --check --offline` runs in CI without a database.    |
| `--force`              | Overwrites a generated file that lost its `Generated by better-supabase` header.                                                                                 |
| `--snapshot <file>`    | Reads a saved snapshot instead of connecting.                                                                                                                    |
| `--db-url-stdin`       | Reads the connection string from stdin; overrides the config, `$DATABASE_URL` and `$SUPABASE_DB_URL`.                                                            |
| `--project-ref <ref>`  | Reads a hosted project through the Management API.                                                                                                               |
| `--metadata <path\|->` | Reads a `GeneratorMetadata` document (`-` for stdin) and prints one file on stdout. See [From a GeneratorMetadata document](#from-a-generatormetadata-document). |
| `--only <file>`        | With `--metadata`, the file to print: `schema` (default), `types`, `zod`, `valibot`, `json-schema` or `standard-schema`.                                         |
| `--out <dir>`          | With `--metadata`, writes every generated file into this directory instead of printing one.                                                                      |

With `--json`, the envelope's `data` is `{ "tables", "written" }` for `gen`
and `{ "upToDate", "stale" }` for `gen --check`. When several tasks run,
`data` is `{ "tasks": { "<task>": { "code", "data" } } }` instead, with each
task's result under its name.

A connection string holds the database password, so no command takes one as
an argument, where it would land in shell history and the process list. Set
`$DATABASE_URL` or `$SUPABASE_DB_URL`, or pipe it in:

```bash
printf %s "$PROD_DB_URL" | better-supabase gen --check --db-url-stdin
```

## Expose only the functions you use

With `sql.api` or a block's `api`, every function a role may execute gets a
wrapper in the API schema, and PostgREST loads each one into its schema cache.
Set `gen.api.expose` to `"used"` to keep a wrapper only for the functions your
sources name, plus the functions a block's own TypeScript client calls.

```ts title="better-supabase.config.ts"
export default defineConfig({
  gen: {
    api: {
      expose: "used",
      // Functions that only a database job or another service calls.
      exposeAlso: ["purge_rate_limits"],
    },
  },
});
```

`gen` reads the words in the files matched by `doctor.sources`, leaves the
generated folder out and keeps the wrappers whose names appear. The default,
`"all"`, keeps every wrapper. Each change to the list is a DDL batch, so ship it in one
migration per deploy. Doctor rule BS244 warns when the schema
cache grows past the point where this pays off.

## Where the schema comes from

In order:

1. `--snapshot`, `--db-url-stdin` or `--project-ref`;
2. `database.source.snapshot` in the config, when none of those flags is passed;
3. `database.source.dbUrl` or `database.source.projectRef` in the config;
4. a [Supabase Lite](/docs/platform/lite) project's `[db] driver` in
   `supabase/config.toml` (turn this off with `database.source.lite: false`);
5. `$DATABASE_URL`;
6. `$SUPABASE_DB_URL`, the name the Supabase CLI and `better-supabase dev env`
   use;
7. the local stack, on the `[db] port` from `supabase/config.toml`. When
   `config.toml` sets no port, as on the CLI's stack engine
   (`[experimental] stack = true`), the `DB_URL` from `supabase status`. When
   neither answers, the command fails with `not_found` and names both, instead
   of guessing port 54322, which could be another project's stack.

On a Lite project, the `postgres` driver reads its `[db] url`. The `pglite`
and `sqlite-postgres` drivers replay `supabase/migrations` and then the
declarative schema files into an in-memory PGlite with Lite's auth schema,
and introspect that, so `gen` needs no running server. The bare `sqlite`
driver takes native SQLite DDL, which `gen` can't read: switch to
`sqlite-postgres`, or save a snapshot.

### Hosted projects without a database password

`database.source.projectRef` (or `--project-ref`) runs the introspection queries
through the Management API's read-only SQL endpoint
(`POST /v1/projects/{ref}/database/query/read-only`). You need a
[personal access token](https://supabase.com/dashboard/account/tokens) in
`SUPABASE_ACCESS_TOKEN`, not the database password, and the queries run as a
read-only role.

Create a scoped token for this: limit it to the project and the read-only
query permission the
[personal access tokens guide](https://supabase.com/docs/guides/platform/personal-access-tokens)
lists for that endpoint. A classic token carries your whole account, on every
organization and project, which is more than CI or an agent needs. A scoped
token that lacks the permission answers "You do not have permission to
perform this action".

```ts title="better-supabase.config.ts"
export default defineConfig({
  database: { source: { projectRef: "abcdefghijklmnopqrst" } },
});
```

```bash
SUPABASE_ACCESS_TOKEN=sbp_... better-supabase gen --check
```

`SUPABASE_API_URL` points it at another Management API host.

## What the metadata knows

The generated `schema` carries what the runtime needs to stay correct without
extra round trips:

- **Read-only columns.** Generated columns, `identity always` columns and
  view columns Postgres marks as not insertable or updatable are left out of
  the `Insert` and `Update` types, and writes to them fail before a request is
  sent.
- **Unique keys and constraint names.** `get` accepts the primary key
  or any named unique key, and `UniqueConstraint`, `CheckConstraint` and
  `ForeignKeyConstraint` types narrow `isConflict(error, 'customers_kvk_key')`.
  See [unique keys and errors](/docs/repository/unique-and-errors).
- **Foreign key actions.** `on delete cascade`, `set null` and `set default`
  are recorded on relations, so a delete invalidates the tables it changes.
  See [caching](/docs/concepts/caching).
- **Codecs.** With `codecs` in the config, `int8`, `numeric` and
  `timestamptz` columns are read exactly (as `bigint`, `string` or
  `Temporal.Instant`; `timestamp` becomes `Temporal.PlainDateTime`), and the
  generated validators match. See [Temporal](/docs/concepts/temporal).
- **Columns a CHECK makes not null.** A nullable column with
  `check (slug is not null)`, alone or as a term of a top-level `and`, is
  typed and validated as not null. It is required on insert unless it has
  a default or a row-level `before insert` trigger fills it before the
  CHECK runs. `gen` reads the trigger's PL/pgSQL body: the column counts as
  filled when the body assigns it (`new.slug := …`, `new.slug = …` or
  `select … into new.slug`). A trigger that only validates leaves it
  required. When `gen` can't tell (another language, or the body replaces
  the whole row with `new := …`), the column stays optional. A term under
  `or` or `not`, and a `not valid` constraint, change nothing. Prefer
  `not null` on the column itself when you can.
- **Columns the database fills on insert.** A not-null column without a
  default is required in `InsertOf` and the insert validators. When a
  trigger or another database rule fills it, list its database name in
  `tables.<table>.insertOptional` and `gen` makes it optional on insert
  while the row type stays not null:

  ```ts title="better-supabase.config.ts"
  export default defineConfig({
    tables: { invoices: { insertOptional: ["number"] } },
  });
  ```

  `gen` fails when a listed name is not a column of the table. The `column`
  and `sequenceColumn` of each [numbering](/docs/blocks/numbering)
  entity with a `table` are optional on insert without being listed, unless
  the block is in `custom` mode.

- **Generated columns.** A generated column (`generated always as (...)
stored`) or an identity column `always` is in `Row` and typed `?: never` in
  `Insert` and `Update`. `WritableColumnOf<"table">` is the union of the
  columns the database lets you write, and `GeneratedColumnOf<"table">` is the
  rest. The generic forms, `WritableColumns<Models, T>` and
  `GeneratedColumns<Models, T>`, come from `better-supabase`. Use them to
  check a column list against the table, for example the columns an offline
  client uploads (see [PowerSync](/docs/frontend/powersync#uploaded-columns)).

- **Function arguments and results.** Every argument in `Functions` accepts
  `null`, since Postgres passes `null` to any function, and arguments with a
  default are optional. Functions that return rows of a table or a
  `returns table (...)` record get a `result` entry, so `db.$rpc` returns them
  in your [casing](/docs/concepts/casing#function-results).
- **Overloaded functions.** A function with several signatures gets a union
  of `{ Args; Returns }` in `Functions`, one member per overload in
  signature order, as in `database.types.ts`. PostgREST picks an overload by
  the argument names, so `db.$rpc` does too: a call type-checks against any
  overload, returns the type of the overload whose names it passes, and
  decodes the result with that overload's `result`. Overloads with the same
  argument names (`pick(value integer)` and `pick(value text)`) return the
  union of their types, and PostgREST can't choose between them at runtime
  either. An overload without arguments is typed `Record<PropertyKey, never>`,
  so it never matches a call that passes one.
- **Nullable function results.** Postgres can't promise that a function
  returns a value: a `strict` function returns `null` for a `null`
  argument, a SQL function returns `null` when its query finds no row, and
  an aggregate in a `returns table` column is `null` over no rows. So a
  scalar result, each element of a `setof` scalar, a single table row and
  each `returns table` column are typed `| null`. Rows of `returns setof`
  a table are not, and neither is `void` or `Json`, which already includes
  `null`. When you know a result is never null, say so in the config:

  ```ts title="better-supabase.config.ts"
  export default defineConfig({
    functions: {
      open_ticket_count: { notNull: true },
      customer_note_counts: { notNull: ["customer_id", "note_count"] },
    },
  });
  ```

  `notNull: true` covers the whole result, and a list names the
  `returns table` columns (database names) that are never null. `gen` fails
  on a function or column it can't find.

  You can also keep the promise next to the SQL. `gen` reads an `@notNull`
  tag from the function's comment, and `@notNull(a, b)` names the columns:

  ```sql
  comment on function public.customer_note_counts(uuid[])
    is 'Notes per customer. @notNull(customer_id, note_count)';
  ```

  A config entry for the same function wins over its tag, and a tag that names
  a column the function doesn't return fails `gen` the same way. Doctor's
  [BS338](/docs/cli/doctor#bs338) lists the config entries a tag could
  replace.

  A function that returns `json` or `jsonb` takes its result type from the
  config too, the way `gen.json` does for a column. `returns: { schema:
"./invoice.ts#InvoiceTotal" }` names a Standard Schema export: the result is
  typed from it and checked at runtime, as the `@bsb returns` comment tag does.
  `returns: { import: "./types.ts#InvoiceTotal" }` imports a type, and
  `returns: { type: "{ total: number }" }` writes one. The config wins over the
  tag.

  Postgres has no syntax for `not null` on a `returns table` column, and the
  catalog records none, so `gen` can't infer it from the function body. Two
  things do carry it: a function that `returns setof` a table gets that
  table's column nullability, and a column whose type is a domain declared
  `not null` is typed without `| null`:

  ```sql
  create domain public.customer_ref as uuid not null;

  create function public.customer_note_counts(customer_ids uuid[])
  returns table (customer_id public.customer_ref, note_count bigint)
  ...
  ```

  When a `returns table` function still has a nullable column and neither a
  tag nor a config entry covers it, `gen` prints a notice that names the
  function. `notNull: []` in the config keeps every column nullable and
  silences the notice.

- **Nullable arguments.** Every argument type includes `| null`, because
  Postgres passes `null` to any argument. This only widens what you may pass
  to `$rpc`; it never changes a result type. A `strict` function returns
  `null` for a `null` argument, which is why its result stays `| null`.

## Documentation in the validators

The `zod()`, `valibot()`, `jsonSchema()` and `standardSchema()` generators carry what the
database says about a table into the schemas, so an OpenAPI document or an MCP
tool built from them describes each field:

- Each table schema gets a title from the table name (`customer_tags` becomes
  `Customer tags`, then `Customer tags insert` and `Customer tags update`) and
  a description from `comment on table`.
- Each field gets a description from `comment on column`. A comment line that
  starts with `@example` adds an example: JSON when it parses (`@example 42`,
  `@example "Acme B.V."`), text otherwise. Examples the column's type rejects
  are left out.
- Simple CHECK constraints become bounds the validators enforce. Comparisons
  of a numeric column with a constant (`price >= 0`, `rating between 1 and 5`)
  become `minimum`, `maximum` and their exclusive forms, and comparisons of
  `length` or `char_length` with a constant become `minLength` and `maxLength`.
  Terms joined by `or`, other functions and comparisons between columns are
  left out.

```sql title="supabase/schemas/customers.sql"
create table public.customers (
  name text not null check (char_length(name) between 1 and 200)
  -- ...
);

comment on table public.customers is 'Companies the organization sells to.';
comment on column public.customers.name is 'Trading name.
@example "Acme B.V."';
```

```ts title="src/lib/supabase/generated.zod.ts"
export const customersInsert = z
  .object({
    name: z
      .string()
      .min(1)
      .max(200)
      .meta({ description: "Trading name.", examples: ["Acme B.V."] }),
    // ...
  })
  .meta({
    title: "Customers insert",
    description: "Companies the organization sells to.",
  });
```

Valibot gets the same through `v.title`, `v.description`, `v.examples`,
`v.minLength` and `v.minValue` in a pipe, and the JSON Schema through
`title`, `description`, `examples`, `minLength` and `minimum`. The
`standardSchema()` output carries them in each field spec.

The generated metadata carries the comments too, so the API documents that
[`defineApi`](/docs/specs) and `createOpenApi` render describe each table
and column without a validator. A table or column comment becomes
`description` in the metadata (without its `@example` lines), and a comment
line that starts with `@deprecated` sets `deprecated: true`. In the
document, the table's description goes on its schemas and its tag, each
column's on its property, and a deprecated table marks its schemas and
operations deprecated. A tag description set on the resource wins over the
table comment.
Examples stay in the validators; pass `examples` to `defineApi` to put rows
in the document.

### Coming from supabase-to-zod

`supabase-to-zod` converts the `database.types.ts` file into zod 3 schemas
through `ts-to-zod`. The `zod()` generator writes zod 4 schemas from the
database catalog instead, so they carry the CHECK bounds, comments and codecs
above, and it keeps separate `Row`, `Insert` and `Update` schemas per table.
Replace the `supabase-to-zod` script with `generators: [zod()]` and import
`<table>Row` from `generated.zod.ts`.

## Schemas for functions and blocks

The `zod()`, `valibot()`, `jsonSchema()` and `standardSchema()` generators
also write a schema for each database function's arguments and result, and
for the inputs of every installed entity block, next to the table schemas:

| Export                               | From                                                   |
| ------------------------------------ | ------------------------------------------------------ |
| `<function>Args`, `<function>Result` | each function: `listTasksArgs`, `customerStatsResult`  |
| `<entity>Input`, `<entity>Change`    | a block entity's create and update inputs: `taskInput` |
| `<entity>ListFilter`                 | a block entity's list options: `taskListFilter`        |

Block schemas carry the names the config gives the entities, so with
`work_item: "task"` the file has `taskInput` with a `taskId` field. An
overloaded function gets no schema, because one schema can't pick a
signature. Use them as action inputs or in forms.

### Form metadata

`fieldMeta: true` adds a `fieldMeta` export: for each writable table and
each input schema, a label, a `required` flag, the enum `options` and the
bounds of every field.

```ts title="better-supabase.config.ts"
generators: [zod({ fieldMeta: true })],
```

```ts title="src/lib/supabase/generated.zod.ts"
export const fieldMeta = {
  customers: {
    name: {
      label: "Trading name",
      required: true,
      minLength: 1,
      maxLength: 200,
    },
    status: {
      label: "Status",
      required: false,
      options: ["active", "churned"],
    },
  },

```

The label is the column's comment when it is short, one line of at most 60
characters; otherwise it comes from the column name.

## Search params for nuqs

`nuqs()` from `better-supabase/generators/nuqs` writes `<output>.nuqs.ts`, with
search-param parsers for a list of each table: a filter for every column
with a closed set of values, `orderBy` over the sortable columns,
`direction`, `cursor` and `limit`. Each set comes with a cache for Server
Components, a loader and a serializer for links. The file imports
`nuqs/server`, an optional peer the app installs.

```ts title="better-supabase.config.ts"
import { defineConfig } from "better-supabase/config";
import { nuqs } from "better-supabase/generators/nuqs";

export default defineConfig({
  gen: { generators: [nuqs({ tables: ["tasks", "customers"], limit: 50 })] },
});
```

A Server Component reads the params through the cache, and a Client
Component writes them with nuqs' own hooks:

```tsx title="app/tasks/page.tsx"
import { tasksSearchParamsCache } from "@/lib/supabase/generated.nuqs";

export default async function TasksPage({ searchParams }: PageProps<"/tasks">) {
  const { state, orderBy, direction, limit } =
    await tasksSearchParamsCache.parse(searchParams);
  // ...
}
```

```tsx title="app/tasks/task-filters.tsx"
"use client";

import { useQueryStates } from "nuqs";

import { tasksSearchParams } from "@/lib/supabase/generated.nuqs";

export function TaskFilters() {
  const [params, setParams] = useQueryStates(tasksSearchParams);
  // ...
}
```

| Option   | What it does                                                                        |
| -------- | ----------------------------------------------------------------------------------- |
| `tables` | The table keys to write parsers for; defaults to every table, block tables included |
| `limit`  | The default page size; defaults to 25                                               |
| `output` | The file path; defaults to `<output>.nuqs.ts`                                       |

Block tables appear under their final names, such as `tasksSearchParams`.
`load<Name>` parses a URL, a `Request` or `searchParams`, and
`serialize<Name>` writes the params into a link.

## Standard Schema without a validation library

`standardSchema()` writes `<output>.standard.ts`: a schema per table for its
Row, Insert and Update shapes that needs no zod or valibot install. Each one
implements [Standard Schema](https://standardschema.dev) (`~standard.validate`)
and Standard JSON Schema (`~standard.jsonSchema`), so it works anywhere a
Standard Schema does: the [validation extension](/docs/repository/validation),
`validate()`, form libraries, oRPC and MCP tool inputs.

```ts title="better-supabase.config.ts"
import { defineConfig } from "better-supabase/config";
import { standardSchema } from "better-supabase/generators/standard-schema";

export default defineConfig({
  gen: {
    file: "src/lib/supabase/generated.ts",
    generators: [
      standardSchema({
        json: { "customers.metadata": "./schemas.ts#metadata" },
      }),
    ],
  },
});
```

```ts title="src/lib/supabase/generated.standard.ts"
import { type TableSchema, tableSchema } from "better-supabase";

export const customersInsert: TableSchema<InsertOf<"customers">> = tableSchema({
  title: "Customers insert",
  fields: {
    name: { kind: "string", minLength: 1, maxLength: 200 },
    status: {
      kind: "enum",
      values: ["lead", "active", "archived"],
      optional: true,
    },
    metadata: {
      kind: "json",
      nullable: true,
      optional: true,
      schema: metadata,
    },
  },
});

export const validators = {
  customers: { insert: customersInsert, update: customersUpdate },
};
```

The checks match the `zod()` output: uuid, integer and ISO date formats,
enum values, CHECK bounds, `null` only on nullable columns, and Temporal
values on `instant` and `plainDateTime` codec columns. A present key never
accepts `undefined`, and unknown keys are dropped from the validated value.
`json` takes a Standard Schema per typed jsonb column; its issues keep their
path under the column, and its JSON Schema is used when it has one.

`~standard.jsonSchema.input()` and `output()` return the same JSON Schema the
`jsonSchema()` generator writes for that shape, for the `draft-2020-12`,
`draft-07` and `openapi-3.0` targets:

```ts
const schema = customersInsert["~standard"].jsonSchema.input({
  target: "draft-07",
});
```

## Saving a snapshot

```bash
better-supabase gen --save-snapshot
better-supabase gen --save-snapshot --check
better-supabase gen --snapshot supabase/snapshot.json
```

`gen --save-snapshot` reads your database the way `gen` does and writes what
it found to `supabase/snapshot.json` instead of generating code. Commit the
file, set `database.source.snapshot` in the config, and CI and contributors
can run `gen` and `doctor` without a database.

| Option          | Effect                                                                                       |
| --------------- | -------------------------------------------------------------------------------------------- |
| `--out <file>`  | Where to write. Defaults to `supabase/snapshot.json`, or `supabase/generator-metadata.json`. |
| `--kind <kind>` | `snapshot` (the default) or `generator-metadata`, postgrest-typegen's input on its own.      |
| `--check`       | Writes nothing; exits 1 when the file no longer matches the database.                        |
| `--dry-run`     | Prints a diff of the file and writes nothing.                                                |

`--snapshot <file>` reads a saved snapshot instead of the database, to
convert it with `--kind`, and `--db-url-stdin` and `--project-ref` work as
they do for `gen`. With `--json`, the envelope's `data` is
`{ "tables", "files" }`, plus `upToDate` for `--check`. It always reads the
full schema, without the [introspection cache](#introspection-cache).

The snapshot stores postgrest-typegen's own metadata plus the extras
better-supabase reads (policies, indexes, triggers, buckets, realtime), and
follows
[`snapshot-v2.json`](https://unpkg.com/better-supabase/schemas/snapshot-v2.json).
Row counts are left out so the file stays stable; tables Postgres estimates
at 10,000 rows or more only get `large: true`, which the
[`unbounded-read`](/docs/repository/lint#unbounded-read) lint rule reads.

The output is the same after `supabase db reset` and on every machine:
object ids come from names, and the arguments of each function keep their
declaration order. That matters for extension functions with unnamed
arguments, such as pgvector's distance functions and citext's casts, whose
argument order the catalog query alone does not fix. The snapshot leaves out
`rpcFunctions`, which postgrest-typegen derives from `functions`; the
generator resolves it again from the stable, ordered functions. A
`GeneratorMetadata` document passed to `gen --metadata` is treated the same
way, so `rpcFunctions` never names a schema `gen` doesn't generate.

## From a GeneratorMetadata document

`gen --metadata` generates from the JSON document that
`@supabase/postgrest-typegen` defines (`GeneratorMetadata`, versioned by
`GENERATOR_METADATA_VERSION`), the same document
[`@supabase/typegen`](https://github.com/supabase/sdk/tree/main/packages/typegen)
pipes to out-of-process generators. Pass a file, or `-` to read stdin:

```bash
better-supabase gen --metadata - < metadata.json > src/lib/supabase/generated.ts
```

It follows the registry's contract for an out-of-process tool:

- stdout holds only the generated file. Notices, warnings and the oxfmt
  notice go to stderr.
- It exits 0 on success, 1 when generation fails (for example without
  `@supabase/postgrest-typegen` installed), 2 on a usage error, and 65 (the code the registry
  maps to `MetadataRejectedError`, as for Dart's `supabase_typegen`) when it
  can't read the document, the document is not JSON, its `version` is not the
  `GENERATOR_METADATA_VERSION` this release reads, or the schema rejects it.
  The reason is on stderr.
- It reads `better-supabase.config.ts` from the working directory when there
  is one (`casing`, `schemas`, `tables`, `codecs`, generator options), and the
  defaults otherwise.

`--only` picks the file:

| `--only`          | Prints                                                                                                                                                    |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `schema`          | The `defineSchema` module, with the metadata written into it instead of a separate `generated.meta.js`. It imports `Database` from `databaseTypesOutput`. |
| `types`           | `database.types.ts`, formatted when oxfmt is installed.                                                                                                   |
| `zod`             | The `zod()` generator's file, with the options from the config when it lists `zod()`.                                                                     |
| `valibot`         | The `valibot()` generator's file, likewise.                                                                                                               |
| `json-schema`     | The `jsonSchema()` generator's document, likewise.                                                                                                        |
| `standard-schema` | The `standardSchema()` generator's file, likewise.                                                                                                        |

`--out <dir>` writes the usual files (`database.types.ts`, the main module,
its metadata module and each configured generator's file) into one directory
instead, and `--check` compares them there. A generator with its own `output`
keeps that path. It leaves the read-set SQL module
and the files an earlier `gen` wrote alone.

The document carries no more than the Data API types need, so a few things
the database connection adds are missing. Relations, primary keys, enums,
single-column unique keys and single-column CHECK unions stay typed; unique
keys and checks get the names Postgres gives them by default
(`<table>_<column>_key`, `<table>_<column>_check`). Multi-column unique keys
and checks, foreign key actions, indexes, triggers, policies, grants, buckets
and the realtime publication are absent, and a notice on stderr says so. Run
`gen` against the database for the full model.

`doctor --metadata` reads the same document. Checks that need what it lacks
are skipped with an info finding, and the advisors and live checks are
skipped as for a saved snapshot.

### As a `@supabase/typegen` language

The registry runs an out-of-process language in the project directory with
the sorted document on stdin. An `externalLanguage` entry for better-supabase
runs `npx better-supabase gen --metadata -`:

```ts title="packages/typegen/src/languages/better-supabase.ts"
import { externalLanguage } from "./external.ts";

export const betterSupabase = externalLanguage(
  "better-supabase",
  [
    {
      name: "emit",
      audience: "user",
      kind: "choice",
      choices: [
        "schema",
        "types",
        "zod",
        "valibot",
        "json-schema",
        "standard-schema",
      ],
      default: "schema",
      help: "The file to generate: the defineSchema module, database.types.ts or a validator file",
    },
  ],
  {
    command: "npx",
    args: (_metadata, options) => [
      "--no-install",
      "better-supabase",
      "gen",
      "--metadata",
      "-",
      "--only",
      String(options.emit),
    ],
    installHint:
      "Install Node.js, then run `npm install -D better-supabase @supabase/postgrest-typegen` in the project.",
    classify: (result) => {
      if (
        result.stderr.includes("could not determine executable to run") ||
        result.stderr.includes(
          'needs the "@supabase/postgrest-typegen" package',
        )
      ) {
        return {
          kind: "not-installed",
          tool: "the better-supabase package",
          installHint:
            "Run `npm install -D better-supabase @supabase/postgrest-typegen` in the project that should receive the types, then generate from that directory.",
        };
      }
      if (result.exitCode === 65) return { kind: "metadata-rejected" };
      return undefined;
    },
  },
);
```

Once the entry is in the registry's `languages`, `user` options become flags
of `supabase gen types`, so `supabase gen types --lang better-supabase --only zod`
prints what `better-supabase gen --metadata - --only zod` prints for the same
database. The upstream registry doesn't ship this entry, so without it, pipe
the document to `better-supabase gen --metadata -` yourself.
