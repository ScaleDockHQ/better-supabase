```ts
const off = betterSupabase.on("mutation", ({ table, kind, rows, context }) => {
  metrics.increment(`db.${table}.${kind}`, rows.length);
});

off();
```

`betterSupabase.on` returns a function that unsubscribes. Handlers are observers: they
can't change a result, and an error they throw goes to the
[`Logger`](/docs/extending/interfaces#logger) instead of the caller.

Subscribe once, at module scope or when a long-lived service starts. A
handler registered per request or per component render is never removed
unless you call `off()`, so the hub grows with every call. Outside
production, the logger warns once when one event has more than 50 handlers.

| Event      | Payload                                                                                                                                 |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `query`    | `table`, `operation`, `ok`, `durationMs`, `rows`, `truncated` (an unbounded read hit [`maxRows`](/docs/repository/pagination#row-caps)) |
| `mutation` | `table`, `kind` (`insert`, `upsert`, `update`, `delete`), `intent`, a copy of the app-cased `rows`, `keys`, `tenant`, `context`         |
| `error`    | `table`, the `DbError`                                                                                                                  |
| `auth`     | `source` (`bearer`, `cookie`, `none`), `ok`, `userId`, `rawSource` (a custom resolver's name), `reason` (why there is no user)          |
| `refresh`  | `ok`, `shared` (joined an in-flight refresh), `durationMs`                                                                              |
| `block`    | `type` (`support.started`, `organization.created`, ...), a copy of `data`, `subject`, `tenant`, `actorId`, `time`, `context`            |

`mutation` rows are a copy of what the database returned, so a listener
cannot change the caller's result. `delete(id)` returns the primary key, so
row-level cache tags and `row.deleted` CloudEvents work for deletes too.

`intent` is what the caller asked for: a soft delete runs as an `update`
(`kind`) with `intent: "softDelete"`. `keys` holds the primary keys of the
changed rows when they are known, from the returned rows or from a `where` on
the primary key, so writes that return nothing (soft deletes,
`returning: false`) still invalidate the right rows. `tenant` is
`context.tenant` or the tenant the memberships extension resolved from the claims.

Listeners are per runtime: register them once, next to `defineSupabase`, not
per request. Cache invalidation (`betterSupabase.cache`), CloudEvents
(`forwardMutations`) and OpenTelemetry metrics are built on these events.

## Diagnostics

`diagnostics: true` writes one debug record to the
[`Logger`](/docs/extending/interfaces#logger) for every `query`, `error`,
`refresh` and `auth` event, following the Supabase SDK
[diagnostic logging capability](https://github.com/supabase/sdk/blob/capability-matrix/v1.14.0/packages/capability-matrix/specs/client/observability/diagnostic_logging.md):

```ts
const betterSupabase = defineSupabase(schema, {
  diagnostics: process.env.NODE_ENV !== "production",
  logger: pino(),
});
// debug: "select customers ok in 14ms" { table, operation, ok, durationMs, rows, truncated }
// debug: "conflict error on contacts" { table, kind, status, code }
```

The records carry names, outcomes, timings and counts only. They never
contain tokens, keys, user ids, row values, filters, query strings, headers
or database error messages (a constraint message can quote the conflicting
value). The option is off by default, and with it off no handler is
registered. A logger that throws is caught like any other handler, so it
never changes a result.

## Block events

The blocks and the SQL modules report what they did as `block` events. Each
block declares its own events in its manifest, and exports them next to it:
`messagingEvents` from `better-supabase/blocks/messaging`, `impersonationEvents`
from `better-supabase/server`, `credentialsEvents` from
`better-supabase/credentials`. `onBlockEvent` from `better-supabase/events`
listens to one type or to every type with a prefix, and types the data for the
match from the events you pass:

```ts
import { onBlockEvent } from "better-supabase/events";
import { impersonationEvents } from "better-supabase/server";

onBlockEvent(
  betterSupabase,
  impersonationEvents,
  "impersonation.*",
  (event) => {
    // event.type is "support.started" | "support.ended" | "support.denied"
    auditTrail.write({ type: event.type, admin: event.data.adminId });
  },
);
```

[`defineBlocks`](/docs/blocks/create-blocks#typed-events-with-defineblocks)
merges the events of every block you use, so `app.on(betterSupabase,
"message.*", handler)` types them without listing each block's events. The
union comes from the manifests you pass, never from `declare module`.

### App events

`defineEvents` declares your own events with their data, for
`defineBlocks(blockConfig, blocks, appEvents)` and `onBlockEvent`. `emitBlockEvent` sends
one, typed by the same map:

```ts
import {
  defineEvents,
  emitBlockEvent,
  event,
  type EventMapOf,
} from "better-supabase/events";

export const appEvents = defineEvents({
  "invoice.sent": event<{ readonly invoiceId: string }>(),
});

emitBlockEvent<EventMapOf<typeof appEvents>>(
  betterSupabase.events,
  "invoice.sent",
  { invoiceId },
  { subject: `invoices/${invoiceId}`, tenant: organizationId },
);
```

Every type is `<entity>.<past_verb>` in snake case. A payload with a tenant
carries `organizationId`, and the subject is `<collection>/<id>` with a
kebab-case plural collection, such as `organizations/<id>` or
`impersonation/<id>`. Each SQL module declares the events it writes, with
their subject and payload keys, and rendering fails when a module writes
anything else. Events from writers that a job, a webhook or an engine may
call again carry an idempotency key, so the outbox keeps one row.

Every event about one subject (`subject.tagged`,
`subject.untagged`, `status.*`, `field_value.set`, `field_value.deleted`,
`share_link.created`, `subject.viewed`, `reminder.sent`, `subject.linked`,
`subject.unlinked`, `version.*`, the trash events, `reaction.*`,
`approval.*`, `drive.*`, `form_submission.*`, `signature.*`,
the `acknowledgement_assignment.*` and `acknowledgement.*` events,
`template.applied`, `segment.entered`, `segment.left`, `subject.assigned`, `party.enriched`,
the `sequence_enrollment.*` events, `stock.reorder_point_reached`, the `order.*`, `fulfillment.*` and
`return.*` events, and every `notification.*` event except
`notification.created`) carries the same three keys, typed as `SubjectEventData`
from `better-supabase/events` (`CollaborationEventData` adds the version,
trash, reaction and approval keys):
`organizationId`, `subjectType` and `subjectId`. A sink that handles one of
them, such as the [watcher sink](/docs/blocks/notifications#watchers),
handles them all. `status.changed` also names the previous status in `from`
and the `reason` passed to `transition()`, or `null`.

`attachment.uploaded`, `.replaced` and `.restored`, `time_entry.*` and
`workflow_run.completed`, `.failed` and `.cancelled` carry `subjectType` and
`subjectId` only when the row belongs to a record: a file or run without a
subject has `null` there.
They are not part of `SubjectEventType<M>`, the types in an event map `M`
whose keys are never `null`, so a sink that wants them checks `subjectType`
first.

`BLOCK_EVENT_RENAMES` from `better-supabase/events` maps the 0.5 names to the
current ones (`BLOCK_EVENT_RENAMES[type] ?? type`), for consumers that still
receive both.

Block events follow the same rules as the others: the data is a copy, and a
handler can't change what the block does. To decide something, pass the module's
policy callback instead (below).

`forwardBlockEvents(betterSupabase, sink, { source, types })` sends them to an
[`EventSink`](/docs/extending/interfaces#eventsink) as CloudEvents
(`dev.better-supabase.organization.created`, the tenant as `partitionkey`, the actor as
`data.actorId`), and `traceBlockEvents(betterSupabase)` from `better-supabase/otel`
records them on the active span. These events are in-process: when one must
not be lost, install the `outbox` module, and the SQL modules write the same
event in the transaction that caused it.

`dataschema` sets the CloudEvents `dataschema` attribute, the URI (or `$id`)
of the JSON Schema the event's `data` conforms to. It is accepted by
`forwardBlockEvents`, `blockCloudEvent`, `forwardMutations` and
`toCloudEvents`. A string applies to every event; a function receives
`{ type, table }` (`type` with the configured prefix, `table` set for row
events) and returns a URI, or `undefined` to leave the attribute out.
Without the option, events carry no `dataschema`:

```ts
forwardBlockEvents(betterSupabase, sink, {
  source: "/crm",
  dataschema: ({ type }) => `https://crm.example.com/schemas/${type}.json`,
});
```

## Policy callbacks

Where a block has a decision the app may want to make (who may start a support
session, who may invite, whether to deliver a notification, which webhook
URLs are allowed), it takes a policy callback such as `authorize`,
`canInvite`, `shouldDeliver` or `allowUrl`. Every policy follows the same
rules:

- It can be sync or async.
- Only `true` allows. `false`, any other value, a throw or a rejection
  denies, so a bug in a policy fails closed.
- Without the callback, the module's documented default applies.
- A denial emits the module's `*.denied` or `*.failed` event with the reason.

## SQL hooks

SQL modules call optional app functions around their work, for example
`after_organization_create(organization uuid, user_id uuid)`. A hook runs in the same
transaction when a function with that name and argument list exists in
`public`, and is skipped otherwise. Raise an exception in a `before_*` hook
to refuse the operation. Point a module at another schema or function with
`blocks.<module>.callbacks`:

```ts title="better-supabase.config.ts"
export default defineConfig({
  blocks: {
    organizations: {
      callbacks: {
        schema: "app",
        functions: { after_organization_create: "private.seed_organization" },
      },
    },
  },
});
```

Hooks are named `before_<entity>_<action>` and `after_<entity>_<action>`;
`notification_audience` and `after_notify` keep the names they shipped with.
Each module's page lists its hooks and their arguments, and
[Extending blocks](/docs/extending/blocks#hooks-in-sql) lists them for
organizations, profiles and notifications. With the `outbox`
module installed, modules also write their events with `emit_event` in the
same transaction; `blocks.<module>.events: false` turns that off for one
module.
