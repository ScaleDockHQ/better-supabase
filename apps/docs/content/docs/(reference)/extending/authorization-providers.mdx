---
title: Authorization providers
description: Let another authorization system answer permission checks in the SQL modules, bucket and topic policies, API keys and doctor, through one versioned config key.
---

An authorization provider is a plain object in the `authorization` key of
`better-supabase.config.ts`. It tells better-supabase which SQL functions
answer "does this user hold this permission", which scopes exist, which
membership tables the provider reads, and which claims its access token hook
writes. better-supabase never imports the provider: the object is data, and
the provider's own package builds it, usually from the files that package
generates.

```ts title="better-supabase.config.ts"
import { defineConfig } from "better-supabase/config";
import { authorizationProvider } from "your-authorization-package";

export default defineConfig({
  auth: { authorization: authorizationProvider() },
  blocks: { permissions: {}, organizations: {} },
});
```

With `authorization` set, `blocks.permissions.model` defaults to
`"provider"`, so `can()`, `tenant_ids_with()` and every module check answer
from the provider's templates.

[PermDock](https://permdock.com/docs/adapters/better-supabase) builds one
from its manifest and catalog.

The provider covers the database side. Permission checks in your server
code (a resource's `permissions`, an action's or MCP tool's `permission`, a
route guard) go to a runtime [authorizer](/docs/extending/authorizers)
instead, passed as `authorizer` to the server. An authorization package can
ship both: the provider for the config, and an authorizer for the server
that answers with the same permission keys.

A package that audits the tables it creates, or the app's tables, calls
`better_supabase.audit()` like the app does. Each call replaces the table's
settings, so pass the app's `ignore` and `redact` from `audit_settings(table)`
instead of calling it with defaults. See the
[audit log](/docs/blocks/sql#audit-log).

## What reads it

| Feature                                                                                    | What it takes from the provider                                                   |
| ------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------- |
| `blocks.permissions.model: "provider"`                                                     | `can()` and the modules' checks call `functions`, at `tenantScope`                |
| `auth.entitlements.memberships: "provider"`                                                | `has_entitlement` and `entitlement_members()` call `memberIds` and `memberIdsFor` |
| Bucket and topic `access` policies with `sql`                                              | the `idsWith` and `isPlatform` templates, for any scope in `scopes`               |
| `on.<type>.scope` in attachments and comments                                              | `idsWith` at that scope, for grants on a single record                            |
| [API keys](/docs/blocks/api-keys) with `claim`                                             | nothing at runtime; the claim names follow the provider's functions               |
| `better-supabase add memberships`                                                          | refuses when `tokenHook.ownedClaims` has `memberships` (`--force` writes it)      |
| `better-supabase gen`                                                                      | refuses a bucket or topic key that isn't `sqlComplete: true`                      |
| [Doctor](/docs/cli/doctor) BS107, BS213, BS214, BS324, BS404, BS405, BS407 to BS409, BS411 | `requires`, `decidingColumns`, `permissions`, `memberships`, `tokenHook`          |

`auth.entitlements.memberships` and `blocks.permissions.model` both default to
`"provider"` when `authorization` is set. Set another access model to keep
the built-in roles; doctor BS414 then reports each policy and function that
calls `can()` or `tenant_ids_with()`, because those answer from roles the
provider never sees.

The config key covers SQL. Server code reads the same decisions from
[runtime hooks](#runtime-hooks), passed to `createServer`.

## The contract

```ts
interface AuthorizationProvider {
  apiVersion: 1;
  name: string;
  scopes: { name: string; idType?: string; parent?: string }[];
  tenantScope: string;
  functions: AuthorizationFunctions;
  requires?: { function: string; args?: string; role: string }[];
  permissions?: { key: string; sqlComplete?: boolean; scopes?: string[] }[];
  memberships?: {
    table: string;
    userColumn: string;
    scope: { column: string } | { value: string };
    idColumn: string;
    rolesTable?: string;
  }[];
  suspension?: { user?: DisabledRow; tenant?: DisabledRow };
  roleSources?: AuthorizationRoleSource[];
  decidingColumns?: string[];
  tokenHook?: AuthorizationTokenHook;
  approvals?: { distinctApprover?: boolean };
  operations?: Record<string, AuthorizationOperation>;
  problems?: string[];
}
```

`AuthorizationProvider` and its parts are exported from
`better-supabase/config`. A scope name is lower case (`[a-z][a-z0-9_]*`),
because it goes into templates unquoted. `problems` lists what the provider
found wrong while building the object; doctor reports each one.

The CLI validates the object when it loads the config. Every scope name in
`tenantScope` and `parent` must be declared, parents must not form a cycle,
the tenant scope needs an `idType`, and `idType` is `uuid`, `text`, `bigint`
or `integer`. Each `decidingColumns` entry is `schema.table.column`, and
`tokenHook.budget.bytes` is a positive integer. An object with another
`apiVersion` gets one message naming both versions instead of a list of field
errors.

### Nested tenancy

The built-in tenancy has one level: a row belongs to an organization, and
`tenant_ids_with()` returns organization ids. An app that splits each
organization into environments (or projects, or workspaces) models the extra
level as provider scopes. Each scope names its `parent`, and `tenantScope`
picks the level the modules treat as the tenant:

```ts
scopes: [
  { name: "organization", idType: "uuid" },
  { name: "environment", idType: "uuid", parent: "organization" },
],
tenantScope: "environment",
functions: {
  idsWith: "authz.{scope}_ids_with({permission})",
  isPlatform: "authz.is_platform({permission})",
  memberIds: "authz.member_{scope}_ids()",
},
```

With `tenantScope: "environment"`, the modules' `organization_id` columns
hold environment ids, and `can()` asks the provider for the environments
where the caller holds a permission. The provider decides how a role on an
organization reaches its environments, so `authz.environment_ids_with()`
returns the environments of every organization where the caller holds the
key, plus those granted one by one. Keep `tenantScope: "organization"` when
the modules work per organization and only your own tables have an
environment column; your policies then call the provider's environment
function directly.

### Functions

Each function is a SQL template. better-supabase fills the placeholders and
puts the result into a policy or a module function:

| Template         | Placeholders                                                | Returns                                                                                    |
| ---------------- | ----------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `idsWith`        | `{permission}`, `{scope}`                                   | a set of the `{scope}` ids where the caller holds the key                                  |
| `isPlatform`     | `{permission}`                                              | `boolean`: the caller holds the key platform-wide                                          |
| `idsWithFor`     | `{user}`, `{permission}`, `{scope}`                         | as `idsWith`, for another user                                                             |
| `isPlatformFor`  | `{user}`, `{permission}`                                    | as `isPlatform`, for another user                                                          |
| `memberIds`      | `{scope}`                                                   | the `{scope}` ids the caller is a member of                                                |
| `memberIdsFor`   | `{user}`, `{scope}`                                         | as `memberIds`, for another user                                                           |
| `teamIdsOf`      | `{user}`                                                    | a set of the team ids `{user}` belongs to                                                  |
| `canAssign`      | `{role}`, `{roles}`, `{tenant}`, `{scope}`                  | `boolean`: the caller may give `{role}` in `{tenant}`                                      |
| `canAssignFor`   | `{user}`, `{role}`, `{roles}`, `{tenant}`, `{scope}`        | as `canAssign`, for another user                                                           |
| `permissionsFor` | `{user}`, `{tenant}`, `{scope}`                             | `text[]`: the permission keys `{user}` holds in `{tenant}`                                 |
| `isApprover`     | `{kind}`, `{subject}`, `{tenant}`, `{requester}`, `{scope}` | `boolean`: the caller may approve request `{subject}` of kind `{kind}`                     |
| `canApprove`     | `{tool}`, `{tenant}`, `{scope}`                             | deprecated: `isApprover` with `{kind}` `'ai-tool'`                                         |
| `holdersOf`      | `{permission}`, `{tenant}`, `{scope}`                       | a set of user ids that hold `{permission}` on `{tenant}`                                   |
| `actorMayWrite`  | none                                                        | `boolean`: the caller's session may write                                                  |
| `permitted`      | `{permission}`, `{id}`, `{tenant}`, `{resource}`, `{scope}` | `boolean`: the caller holds `{permission}` on instance `{id}` of `{resource}`              |
| `rowsWith`       | `{permission}`, `{resource}`, `{ids}`                       | a set of the ids (text) of `{resource}` rows the caller holds `{permission}` on            |
| `rowsWithFor`    | `{user}`, `{permission}`, `{resource}`, `{ids}`             | as `rowsWith`, for another user                                                            |
| `portalSubjects` | `{action}`                                                  | a set of `(tenant, subject_type, subject_id)` the caller reaches as a guest for `{action}` |
| `portalParties`  | none                                                        | a set of `(tenant, party_type, party_id)` the caller acts for as a guest                   |

`rowsWith` answers a `config.subjects.<type>.permissions.<action>` entry with
`rows` ([Actions granted per row](/docs/blocks/sql#actions-granted-per-row)).
`{resource}` is that entry's `rows`, unquoted, so it can be part of a
function name (`app.rows_{resource}({permission})`), and `{ids}` is a `text[]`
of the ids being checked, which a provider may use to limit its work.

`{roles}` is the same role as a `text[]` (`array[role]::text[]`), for a
function that checks a set of roles at once. A `memberships` entry's
`rolesTable` names the table of a member's roles when a member can hold
several, one row per scope id, user and role; better-supabase's own is
`better_supabase.membership_roles`
([`roles.many`](/docs/blocks/memberships#several-roles-per-member)). Doctor
(BS411) warns when `roles.many` is on and no entry sets it.

`idsWith` and `isPlatform` are required. A template that leaves out a `For`
variant makes the module function answer for the caller only: called for
another user, it raises SQLSTATE `0A000`. Without `canAssign`, only the
service role assigns roles: the `permissions` module's `can_assign` answers false
for every member, owners included.

Some modules call the optional templates under the `provider` model:
`invitations` calls `idsWithFor`, `isPlatformFor` and `canAssignFor` to check
the inviter again when an invitation is accepted; `inbox`, `comments`, `sso`,
`notifications`, `connectors` and `workflow-sdk` call `idsWithFor`; and
`usage` reads memberships through `memberIds`; `approvals` checks that a
delegate is a member through `memberIdsFor`. Doctor (BS411) warns for each
installed module whose template the provider doesn't set.

`teamIdsOf` is for a provider that keeps its own teams. `team_ids_of()` in
the `teams` block returns its set instead of reading `team_members`, and
`saved-views` and `collections` share with those teams even without the
`teams` block. Doctor (BS417) warns when the provider declares a `team`
scope and leaves it unset.

`permissionsFor` fills `better_supabase.member_permissions` and
`permission_claims`, so the access token hook can carry permission keys. The
claims cover the tenants `memberIdsFor` returns; without `memberIdsFor` they
stay empty. Without `permissionsFor`, both functions return nothing, as
before.

```ts
functions: {
  idsWith: "authz.{scope}_ids_with({permission})",
  isPlatform: "authz.is_platform({permission})",
  memberIds: "authz.member_{scope}_ids()",
  canAssign: "authz.can_assign({role}, {tenant}::text)",
},
requires: [
  { function: "authz.organization_ids_with", args: "text", role: "authenticated" },
  { function: "authz.is_platform", args: "text", role: "authenticated" },
  { function: "authz.member_organization_ids", role: "authenticated" },
  { function: "authz.can_assign", args: "text, text", role: "authenticated" },
],
```

`requires` lists every function the templates call, with `{scope}` filled,
and the role that must be able to execute it. Doctor (BS411) checks the
database has each one, and the conformance block checks the list is complete.
`idType` is the Postgres type of a scope's ids: `uuid`, `text`, `bigint` or
`integer`.

### Permissions

`permissions` lists the keys the provider knows. `sqlComplete: true` says its
SQL functions answer the key completely: a grant has no row condition beyond
the scope. Bucket and topic policies and the SQL modules check by role and
scope only, so `gen`, `add` and doctor (BS214, BS411) refuse a key that
isn't marked. Leave row-conditioned keys to the provider's table policies.

### Token hook

`tokenHook` describes the custom access token hook the provider generates:

| Field                    | Used for                                                                                     |
| ------------------------ | -------------------------------------------------------------------------------------------- |
| `function`               | BS404 checks its grants, BS405 its shape                                                     |
| `tenantClaim`            | BS409 compares it with `auth.organization.claim`                                             |
| `activeOrganizationFrom` | BS409 compares it with `blocks.permissions.activeTenant`, where `switch_organization` writes |
| `ownedClaims`            | BS407 reports another hook that writes them; `add memberships` stops on them                 |
| `registeredClaims`       | BS407 accepts these claims from the functions named, such as `features`                      |
| `budget`                 | BS405 measures the claims it lists against `bytes` for `doctor --as`                         |
| `markers`                | comment lines in the provider's files, so doctor recognises its hook and grants migration    |
| `grantsCommand`          | the command BS404 suggests                                                                   |

### Approvals

`isApprover` is the one eligibility check for every request that waits for
someone else: AI tool calls in the [ai-chat block](/docs/blocks/ai-chat)
(`{kind}` `'ai-tool'`, `{subject}` the tool's name) and support sessions
(`{kind}` `'support-session'`, `{subject}` the request id). `{tenant}` is
required. `{requester}` is optional: the uuid of the user who asked (the
approval's `requested_by`, the support admin, the chat's owner). A provider
that resolves out-of-office covers inside `isApprover` reads it so a cover
never lets the requester's own delegator approve. Under the `provider` model,
`decide_ai_tool_approval` lets the service role and any caller `isApprover`
allows decide the call. `approvals.distinctApprover: true` keeps the
requester from deciding their own request, for four-eyes approval. Without
`isApprover`, the chat's owner decides a tool call.

`canApprove` still works in 0.9 and is read when `isApprover` is unset;
`better-supabase codemod 0.9` points at each use. Doctor BS415 warns while a
provider sets it.

`holdersOf` is the audience for `notifications.send({ permission })`: the
user ids that hold that key on the tenant. A provider sets it from its
manifest when the tenant scope lists `permitted_<scope>_users`, for example
`permdock.permitted_organization_users({permission}, {tenant})`. Grant
execute on that function to the role that owns `send_notification`, and
never to `authenticated`. Without the template, a notification that names
`permission` fails with `NOTIFICATION_PERMISSION_AUDIENCE_UNAVAILABLE`.

`actorMayWrite` replaces the built-in read of the `act` claim. A provider
sets it to `permdock.permdock_actor_may_write()` when the manifest lists
that helper. Write functions and write policies call the template and not
the built-in as well. Doctor BS413 warns when support sessions are installed
under the provider model and this template is missing.

```ts
functions: {
  // ...
  isApprover: "authz.is_approver({kind}, {subject}, {tenant}::text, {requester})",
},
approvals: { distinctApprover: true },
```

#### Out-of-office covers

The approvals block's `delegate(id, userId)` hands one approver's place on
one step of one request to someone else. A standing cover ("Ana approves for
Ben until Friday") is a different thing, and it belongs to the provider when
the provider has one: its `isApprover` answers true for the cover as well as
for Ben, so every module that waits for an approval (the approvals block, AI
tool calls, support sessions) sees it without a configuration of its own.
Configure covers in one place only. An app without such a provider calls
`delegate` per request instead.

PermDock keeps covers in its `approval_delegations` table and resolves them
in `permdock_is_approver`, one hop deep, never for the requester's own
delegator. Its [better-supabase adapter](https://permdock.com/docs/adapters/better-supabase#approval-delegation)
passes `{requester}` for that check.

### Delegated tokens

`delegation.scopes` maps an OAuth scope to the permission keys a delegated
token (an OAuth client or an agent) may use. The access functions narrow
every check to those keys, and `blocks.permissions.scopes` is merged over it.
See [Access](/docs/repository/permissions#delegated-tokens).

```ts
delegation: {
  scopes: { "invoices:read": ["invoices.read"], "invoices:write": ["invoices.read", "invoices.update"] },
},
```

### Share links as guests

The [share-links block](/docs/blocks/share-links#guest-pages) resolves a
token in `security definer` functions. A provider can instead turn the row
`resolve_share_link` returns into a link principal and exchange it for a
short-lived anonymous session, so a guest page reads the subject under the
provider's row-level security. PermDock's `subjectFromShareLink` does this:
it builds a link capability from the row, caps its lifetime at the row's
`expiresAt`, and denies when the row is missing, revoked or expired.

### Guests and portals

`portalSubjects` and `portalParties` let a provider's external users (a
client, a contractor) into comments, attachments, invoices and bookings
without making them members. `{action}` is `'read'`, `'comment'` or
`'upload'`, and every column is read as text:

```ts
functions: {
  portalSubjects: "authz.guest_records({action})",
  portalParties: "authz.guest_parties()",
},
```

`access` wraps them in `better_supabase.portal_subjects(action)` and
`portal_parties()`, which policies read through `ctx.scope.guest` and
`ctx.scope.guestParty`. With the [guests block](/docs/blocks/guests)
installed, its own grants are added to the provider's sets. Without either,
the checks render `false` (ADR 0070).

### Operations

`operations` maps an operation name to the permission it needs, so one table
names the permission for every workflow-editor node, MCP tool, AI tool and
inbox command. A module looks up `<prefix><name>` and falls back to its own
key, after the `blocks.<module>.permissions` rename:

| Prefix           | Operations            |
| ---------------- | --------------------- |
| `workflow.node.` | workflow-editor nodes |
| `mcp.tool.`      | MCP tools             |
| `ai.tool.`       | AI tools              |
| `inbox.command.` | inbox commands        |

```ts
operations: {
  "mcp.tool.search_invoices": { permission: "invoices.read" },
  "ai.tool.refund": {
    permission: "invoices.refund",
    meta: { risk: "high", effects: ["write", "external"] },
  },
},
```

An MCP tool's `operation`, an agent's `toolOperations` and a
workflow-editor step's `operation` name an entry in place of the prefixed
one. Under the access module, `better_supabase.operation_permission(op)`
answers the key of any operation in SQL: the installed modules' operations
(`<module>.<action>`, such as `audit.view`) after renames, with this table
over them, and `null` for a name nobody declared.

Each `permission` must be in `permissions` when the provider lists them; the
conformance block checks it. `meta.risk` and `meta.effects` describe the
operation for approval prompts and tool listings.

## Bucket and topic policies

An `access` policy calls the access contract (`tenant_ids_with`,
`is_platform`) by default. Give it the provider's templates in `sql`, and it
calls those instead, for any scope they take. `sql: "provider"` uses the
provider's `idsWith` and `isPlatform`: `better-supabase gen` writes them into
the generated bucket meta, and `better-supabase upgrade` passes them to each
topic's `sql()`. A copy of the templates also works, so the bucket module
doesn't import the config; doctor (BS214) warns when the copy differs from the
provider.

```ts title="src/storage/documents.ts"
import { defineBucket } from "better-supabase/storage";

export const documents = defineBucket({
  id: "documents",
  path: "{organizationId}/{documentId}/{name}",
  policy: {
    access: { read: "documents.browse", write: "documents.write" },
    scope: "organization",
    sql: "provider",
  },
});
```

A topic with `sql: "provider"` throws when its `sql()` runs without
templates. Pass them yourself outside `upgrade`:

```ts
topic.sql({ functions: config.authorization.functions });
```

The scope id is compared as text, so a path or topic segment must be the id's
lowercase form. `segment` picks another path segment than `{organizationId}`.

## Runtime hooks

The config key is plain data for SQL. `AuthorizationHooks` is the runtime
half: functions that decide the same things in server code, so one provider
can own automations, support sessions, delivery, identity links, chat
actions, approvals and delegated tokens end to end. Build it with `defineAuthorizationHooks`
from `better-supabase/server` and pass it to `createServer`:

```ts title="src/server.ts"
import { createServer, defineAuthorizationHooks } from "better-supabase/server";
import { betterSupabase } from "./supabase";

const authorization = defineAuthorizationHooks({
  apiVersion: 1,
  name: "your-provider",
  support: { authorize: async (input) => policy.supportStart(input) },
  delivery: { subscribers: policy.subscribers, audience: policy.audience },
  approverOf: (approver, request) => policy.mayApprove(approver, request),
});

export const bsb = createServer(betterSupabase, { authorization });
```

Every hook is optional. A slot passed to a block directly wins over the hook.

| Hook                             | Decides                                                                                   | Owner page                                              |
| -------------------------------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------- |
| `automation.mayPublish`          | whether the publisher may publish a version whose nodes need the stored permissions       | [Workflow builder](/docs/blocks/workflow-editor)        |
| `automation.runAs`               | the claims each step of a published version runs with; `null` fails the step              | [Workflow builder](/docs/blocks/workflow-editor)        |
| `support.authorize`              | a support session start: `true` still needs a second approver, `{ approvedBy }` names one | [Support sessions](/docs/auth/impersonation)            |
| `delivery.subscribers`           | which webhook endpoints, outbox consumers and realtime members may read an event          | [Outgoing webhooks](/docs/blocks/webhooks-out)          |
| `delivery.audience`              | which notification recipients may read a notification                                     | [Notifications](/docs/blocks/notifications)             |
| `identities.principalByIdentity` | the user or contact a verified email address or chat user links to                        | [Identities](/docs/blocks/identities)                   |
| `chat.onAction`                  | a button a linked chat user pressed, such as an approval                                  | [Chat SDK](/docs/chat-sdk)                              |
| `approverOf`                     | whether a user may approve a request; the server side of `isApprover`                     | [Approvals](#approvals)                                 |
| `tickets.subject`                | the context an opaque run ticket stands for, for jobs and workflow steps                  | [Jobs](/docs/blocks/queue)                              |
| `delegation.permissions`         | the permission keys a delegated token's scopes grant, as the cap `forContext` runs with   | [Access](/docs/repository/permissions#delegated-tokens) |

Without `delivery.subscribers` or `delivery.audience`, delivery still fails
closed on records: webhooks, notifications and reminders fall back to
`subjectReaders`, which keeps a subscriber only when
`can_subject_for(user, type, id, 'read')` is true for an event about a
registered subject, and realtime fan-out refuses such an event without a
policy.

Each hook fails closed. A throw or rejection refuses, `null` from `runAs`,
`principalByIdentity` or `tickets.subject` refuses, and no hook falls back to
the service role. better-supabase refuses a requester as their own approver
before it calls `approverOf`.

`createServer` throws when the hooks target another `apiVersion`, with a
message naming both versions.

### Test the hooks

`testAuthorizationHooks` from `better-supabase/testing` runs the hooks a
provider sets against cases every provider must refuse: subscriber and
audience policies return a subset of their input, an unlinked identity is
`null`, a requester never approves their own request, a forged ticket is
`null`, an unknown publisher may not publish and gets no claims, an
unlinked chat author is refused, an admin with no claims cannot start a
support session, an admin is never named as their own support approver,
and a delegated token with no scopes maps to no permissions.

```ts title="tests/provider.test.ts"
import { testAuthorizationHooks } from "better-supabase/testing";
import { it } from "vitest";

it("fails closed", () => testAuthorizationHooks(authorizationHooks()));
```

## Version cache

A provider that caches decisions per user can key them on an authorization
version: a number the database bumps whenever a user's roles or grants
change. An access token hook copies it into the token as `authz_ver`, and
`session.authzVersion` (on `AuthSession` and `SessionSnapshot`) reads it, or
`null` without the claim. `issuedAt` reads `iat` the same way.

The provider's library owns the cache. better-supabase types it
structurally as `AuthzVersionCache`, which only needs `evict(userId)`.
Create it once at module scope, never per request or per cache scope, and
hand it to the server:

```ts title="src/lib/supabase/server.ts"
import "server-only";
import { createNext } from "better-supabase/next";
import { betterSupabase } from "./index";
import { versions } from "./authz";

export const bsb = createNext(betterSupabase, { versions });
```

Every authorizer call then gets `{ versions, memo }` as its runtime
(`AuthorizerRuntime`): `versions` is the shared cache, and `memo` is a
`RequestMemo` for reads that several checks in one scope share. Create a
memo with `requestMemo()` from `better-supabase/server`; nothing request-specific lives in module state.
`bsb.invalidateSession(userId)` calls `versions.evict(userId)` next to
expiring the user's cache entries.

To evict on other instances too, have the database broadcast each change on
a private Realtime channel, and subscribe from the module that creates the
cache:

```sql
perform realtime.send(
  jsonb_build_object('user_id', new.user_id, 'version', new.version),
  'changed',
  'authz-versions',
  true
);
```

```ts title="src/lib/supabase/authz.ts"
import { subscribeAuthzVersions } from "better-supabase/server";

export const versions = createVersionCache();

subscribeAuthzVersions({
  client: serviceClient,
  topic: "authz-versions",
  event: "changed",
  userIdKey: "user_id",
  versions,
  onError: (error) => console.warn(error),
});
```

The subscriber joins with the service-role client, so the channel needs no
`realtime.messages` policy and no user can listen. Each message evicts one
user; a malformed message goes to `onError`. A second call with the same
`versions` returns the first subscription; its `ready` promise settles once
the channel joined, and `close()` leaves it. Start it from that module, not from `instrumentation.ts`, so the
cache and its subscription live and die together.

The subscriber keeps a Realtime channel open for as long as the process
runs, so it only evicts reliably in a long-lived process, such as a Node
server or a container. Serverless instances (Vercel Functions, AWS Lambda,
Cloudflare Workers) freeze between requests and miss the broadcasts sent
in the meantime. There, don't call `subscribeAuthzVersions`. Give the
provider's cache a short maximum age instead, so each instance reads a
user's version again once it is older than that, and keep calling
`bsb.invalidateSession(userId)` where the change happens, which evicts the
user on that instance right away:

```ts title="src/lib/supabase/authz.ts"
export const versions = createVersionCache({ maxStaleMs: 30_000 });
```

`maxStaleMs` is the provider cache's option, not a better-supabase one; check
your library for its name. It bounds how long another instance can decide
with an old version.

## Test a provider

`testAuthorizationProvider` from `better-supabase/testing` checks API v1,
plain JSON, valid scopes (known names, no parent cycle, a tenant scope with an
`idType`), the placeholders of each template (each uses its `{permission}`,
`{user}`, `{tenant}` and `{role}`, and `idsWith` and `idsWithFor` use
`{scope}` when there is more than one scope), that templates are safe to
inline (a tokenizer reads strings, quoted identifiers and comments whole, then
refuses a function call without a schema, a dollar-quote tag such as `$$` or
`$tag$`, a `;`, a comment, an unterminated string and a stray `{`), that
`requires` lists every function the templates call, the permission list, and
the shapes of
`memberships`, `suspension`, `roleSources`, `decidingColumns` and
`tokenHook`: `ownedClaims` is not empty, a `registeredClaims` entry is not also
owned, `budget.claims` are owned or registered, and `budget.bytes` is a
positive integer. See [conformance blocks](/docs/extending/conformance).

```ts title="tests/provider.test.ts"
import { testAuthorizationProvider } from "better-supabase/testing";
import { it } from "vitest";

it("conforms", () => testAuthorizationProvider(authorizationProvider()));
```

A provider for a new contract version sets another `apiVersion`; this release
refuses anything but `1` with a message naming both versions.
