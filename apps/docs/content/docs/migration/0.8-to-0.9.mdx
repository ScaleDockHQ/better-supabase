---
title: From 0.8 to 0.9
description: What to change when upgrading to better-supabase 0.9, which routes permission checks through the authorization provider, caps delegated tokens, runs workflows as their publisher, approves support sessions by a second admin and sends CloudEvents webhooks.
---

0.9 closes places where work ran with more rights than the caller had: jobs
queued by an OAuth client, published workflows, support sessions and fan-out
to subscribers. Most changes are behaviour, not names, so
`better-supabase codemod 0.9` moves the one renamed config key, renames the
config types, rewrites the CLI calls in your scripts, and lists each call to
review:

```bash
pnpm better-supabase codemod 0.9 --dry-run
```

Then run `better-supabase sql sync` and create a migration. Every installed
module file changes, because the read-only check each one carries now knows
the agent actor. Beyond that, `access`, `tenant`, `subjects`, `support-sessions`,
`webhooks-out`, `workflow-builder`, `notifications`, `actor`, `approvals`,
`ai-chat`, `share-links`, `versions`, `promotions`, `time-tracking`,
`state-machine`, `comments`, `workflows`, `workflow-sdk-world` and
`saved-views` changed, and `identities`, `service-principals` and `templates`
are new.

## Config key

Blocks moved out of `sql` to a top-level `blocks` key. A config that still
sets `sql.modules` fails to load with `config_invalid` and
``sql.modules: moved to the top-level `blocks` key in 0.9``. The codemod
moves the key in `better-supabase.config.ts` (or `.mts`, `.js`, `.mjs`,
`.json`), with its comments, and drops `sql` when nothing else is left in it.
`blocks` goes right after `sql`, or in sorted position when the top-level
keys are already sorted. The codemod runs even though the config fails to
load:

```ts title="better-supabase.config.ts"
// 0.8
sql: { dir: "supabase/schemas", modules: { tenant: true, access: { model: "roles" } } },

// 0.9
sql: { dir: "supabase/schemas" },
blocks: { tenant: true, access: { model: "roles" } },
```

It also renames the config types: `ModulesConfig` to `BlocksConfig`,
`ModuleConfig` to `BlockConfig`, `AccessModuleConfig` to `AccessBlockConfig`
and `ModuleMode` to `BlockMode`. A config that sets both `sql.modules` and
`blocks`, keeps `sql.modules` in an environment block, or builds `sql` in
another module is listed for review: move the entries into `blocks` by hand.
Code that reads `config.sql.modules` from a loaded config reads
`config.blocks` instead.

## CLI commands and flags

`sql`, `blocks`, `preset`, `skills`, `spec`, `scaffold` and `codemod` are
command groups now: each subcommand has its own help, and the spelling of
`sql add tenant` or `blocks list` stays the same. A flag has one meaning
across the CLI (`--out` is a file, `--out-dir` a directory, `--only` narrows
what runs, `--force` only overwrites), so these calls changed:

| 0.8                              | 0.9                                |
| -------------------------------- | ---------------------------------- |
| `openapi emit`                   | `spec emit openapi`                |
| `spec check`                     | `spec emit --check`                |
| `init --with <name>`             | `init --integration <name>`        |
| `add --framework <name>`         | `add --integration <name>`         |
| `adopt --from <tables>`          | `adopt --tables <tables>`          |
| `gen --tasks <list>`             | `gen --only <list>`                |
| `gen --out <dir>`                | `gen --out-dir <dir>`              |
| `introspect --format <kind>`     | `introspect --kind <kind>`         |
| `doctor --strict`                | `doctor --fail-on warning`         |
| `env --print`                    | `env --out -`                      |
| `env --from <file>`              | `env --status-file <file>`         |
| `skills install --from <source>` | `skills install --source <source>` |
| `sql add --force` (hook overlap) | `sql add --allow-hook-overlap`     |

The old forms exit with code 2 and a `command_moved` error whose
`suggestion` is the new call, until 1.0. The codemod rewrites them in
`package.json` scripts and `.github/workflows/*.yml`, and lists the ones in
other shell scripts, Makefiles and YAML files for review. The package also
installs a short `bsb` bin, so `pnpm bsb doctor` runs the same CLI.

## Access model

With `authorization` in the config, `blocks.access.model` now defaults to
`"provider"`. `can()`, `tenant_ids_with()` and every module check answer from
the provider's templates. To keep the built-in roles, set the model:

```ts title="better-supabase.config.ts"
blocks: { access: { model: "roles" } },
```

Doctor BS414 then reports each policy and function that calls the access
contract, because those answer from roles the provider never sees. See
[Access](/docs/blocks/access#provider).

`authorization.functions.canApprove` is deprecated. Set `isApprover`, which
every module that waits for an approval reads:

| 0.8                        | 0.9                                                                  |
| -------------------------- | -------------------------------------------------------------------- |
| `canApprove` with `{tool}` | `isApprover` with `{kind}` `'ai-tool'` and `{subject}` the tool name |

0.9 still reads `canApprove` when `isApprover` is unset; doctor BS415 warns
while a provider sets it.

Under the provider model, `member_organization_ids()`,
`has_organization_role()` and `organization_member_role()` take membership
from the provider's `memberIds` and `memberIdsFor` templates, so a user the
provider no longer lists stops counting as a member even while a
memberships row remains. Their role arguments still compare role names the
provider may not use. Doctor [BS334](/docs/cli/doctor#bs334) lists your own
policies and functions that call them; replace each with
`better_supabase.tenant_ids_with('<permission>')` or `member_can()`, which
the delegation cap below also narrows.

### Delegated tokens are narrowed everywhere

A token that carries a `client_id`, or an RFC 8693 `act` chain that is not a
support or impersonation session, is now narrowed
inside `member_can`, `member_can_while_deleting`, `platform_can` and
`tenant_ids_with`, in every access model: a permission passes only when one
of the token's scopes maps to it. In 0.8 only the policies that called
`token_scope_allows` narrowed it. Map each scope your OAuth clients and MCP
servers grant to the permission keys it covers, or those clients lose
access to every key whose name differs from a scope:

```ts title="better-supabase.config.ts"
blocks: {
  access: {
    scopes: { "posts:write": ["posts.*"], "mcp:admin": ["*"] },
  },
},
```

`authorization.delegation.scopes` is the provider's form of the same map, and
a provider that maps scopes at runtime sets the `delegation.permissions`
hook. The `token_scope_allows` checks you added to write policies can stay,
but the cap already covers them. `forContext(context, { permissions })` caps
the work to a list of keys the same way. See
[Delegated tokens](/docs/blocks/access#delegated-tokens).

### One operations table

Every action a module checks is now an operation named `<module>.<action>`
(such as `audit.view`), and `better_supabase.operation_permission(op)`
answers its permission key in SQL, after your renames in
`blocks.<module>.permissions` and with the provider's `operations` over
them. An MCP tool's `operation`, an agent's `toolOperations` and a
workflow-builder step's `operation` name an entry in place of the prefixed
`mcp.tool.<name>`, `ai.tool.<name>` or `workflow.run`. The permission keys
themselves don't change, so this needs no edit unless you want a tool to
share an operation with the module it wraps. See
[Operations](/docs/extending/authorization-providers).

## Jobs and workflows

A job or workflow queued by an OAuth or MCP client now carries the client's
`client_id`, `scope`, `authorization_details` and `act` chain, and
`forContext` runs it with those claims. A job that used to run with the
user's full rights now runs with the client's scope, which the delegation
cap applies to every permission check. An invalid `act` chain is refused with
`forbidden` instead of being dropped. `claimsFor` can no longer set the four
delegation claims. `delay` must be a whole number of seconds. See
[Jobs](/docs/blocks/jobs).

Published workflow-builder versions record who published them and the
permissions their nodes need. A publisher must hold every one of those
permissions, or the publish returns `WORKFLOW_PUBLISHER_FORBIDDEN` with the
missing keys in `permissions`, and each step runs with the publisher's current claims through
`versions.runAs`. A demoted or removed publisher fails the step instead of
falling back to the service role. Versions published before 0.9 have no
publisher and fail with `WORKFLOW_PUBLISHER_REVOKED` until someone publishes
them again. See
[Workflow builder](/docs/blocks/workflow-builder#publisher-rights).

A version an organization owns (published by the service, with no member as
publisher) runs as the organization's default
[service principal](/docs/blocks/service-principals), capped to the
permissions the version stored. Create one with `default: true` before you
publish such versions, or set an `automation.runAs` hook; without either,
their steps fail.

Code workflows started by an event or a schedule need `runAs`, the publisher
the run starts as and the permission keys its steps may use. A schedule
start without it throws. The run's context is the publisher's, capped to
those keys, and the event's actor or the schedule's creator is only recorded
as `bs.trigger`. Admission requests keep running as their actor:

```ts
await workflows.schedules
  .tick({
    start: workflowStarter(
      { weeklyDigest },
      { runAs: { publisher: automationUserId, permissions: ["digest.send"] } },
    ),
  })
  .orThrow();
```

`startOnEvent` takes the same `runAs`, which can also be a function of the
event or the start call for a publisher per tenant. See
[Event and schedule starts run as a publisher](/docs/blocks/workflow-sdk#event-and-schedule-starts-run-as-a-publisher).

## Support sessions

`supportSessions` refuses every start unless `authorize` (or the server's
`authorization.support.authorize`) allows it. `authorize` returns `true`,
`false` or `{ approvedBy }`. A start also needs a request approved by a
different admin unless `policy.approval` is `"none"`:

```ts
supportSessions({
  store,
  authorize: ({ admin }) => admin.claims["role"] === "support",
  policy: { approval: "distinct" },
});
```

`authorize: "store"` keeps the 0.8 behaviour, where the store's SQL policy
alone decides. To start sessions without a second admin, set both
`policy.approval: "none"` and the module's
`blocks.support-sessions.options.approval: "none"`. See [Support sessions](/docs/auth/impersonation).

In a writable support session, `ctx.storage` now writes: `upload`, `update`,
`remove`, `copy`, `move` and `purgeCache` run as the target after a dry run
against the policies on `storage.objects`, where 0.8 refused them with
`SUPPORT_STORAGE_WRITES`. Signed uploads are still refused with that code.
`attachments.put` no longer creates a signed upload URL before it uploads. A
direct `supportStorage` call needs `adminSql` and `session` for writes. See
[Storage in a support session](/docs/auth/impersonation#storage-in-a-support-session).

## Webhooks and problems

Outgoing webhooks send CloudEvents 1.0 (`application/cloudevents+json`) in
place of `{ type, timestamp, data }`, signed per Standard Webhooks. A
`transform` returns only the event's `data`. Receivers read `data`, `type`
and `id` from the CloudEvent. `publish_webhook_event` takes `subject` and
`read_permission`, and delivers only to endpoints whose owner may read the
event. See [Outgoing webhooks](/docs/blocks/webhooks-out).

`sql upgrade` keeps endpoints created before 0.9 on the 0.8 body: they get
`format = 'standard'`, and new endpoints get `cloudevents`
(`blocks.webhooks-out.options.defaultFormat`). Move each endpoint to
`cloudevents` once its receiver reads CloudEvents:

```sql
update better_supabase.webhook_endpoints set format = 'cloudevents' where id = $1;
```

An adopted endpoints table keeps its own column. When it doesn't map
`format`, or a row holds `null`, deliveries use `defaultFormat`.

Generic problems use `type: "about:blank"` and the HTTP status phrase as
`title`:

| 0.8 `title`         | 0.9 `title`             |
| ------------------- | ----------------------- |
| `Invalid request`   | `Bad Request`           |
| `Not found`         | `Not Found`             |
| `Too many requests` | `Too Many Requests`     |
| `Unexpected error`  | `Internal Server Error` |

Match problems on `kind` or `code`, which did not change. See
[Problems](/docs/auth/problems).

## Delivery fails closed

Under an authorization provider without `delivery.subscribers` or
`delivery.audience`, webhooks, notifications and reminders now deliver an
event about a [registered subject](/docs/blocks/sql#subject-registry) only to
the users and service principals who may read it
(`can_subject_for(user, type, id, 'read')`). In 0.8 every subscriber got it.
A share link never counts. Events without a subject, or about a type the
registry doesn't list, keep the 0.8 checks.

Realtime `fanOut` goes further: under a server with authorization hooks and
no subscriber policy, an event with a `subject` goes to no one and returns
`forbidden` with the hint `REALTIME_SUBSCRIBER_POLICY_REQUIRED`. Pass the
subject's readers as the policy:

```ts
import { subjectReaders } from "better-supabase/realtime";

await inbox
  .fanOut(admin, {
    ...options,
    policy: subjectReaders(sqlTransport(postgres.admin)),
  })
  .orThrow();
```

See [Realtime](/docs/platform/realtime) and
[Outgoing webhooks](/docs/blocks/webhooks-out).

## Agent actors

An RFC 8693 `act` level may now be `{ kind: "agent", sub, tools, read_only }`,
which `agentClaims(claims, { agent, tools, readOnly })` from
`better-supabase/server` builds. In 0.8 an unknown `kind` made the chain
invalid. An agent writes with the user's row level security unless its
level sets `read_only: true`, and a token that carries a `scope` limits it
like an OAuth client. Pass `agentClaims(claims, run.act)` to `asUser` or
`forContext` in agent tools so the audit log names the agent. A level with
`kind: "agent"` whose `tools` is not a list of names, or whose `read_only`
isn't a boolean, is refused. A level without `tools` delegates every tool and
`tools: []` none; `createAgentRuntime({ actor })` refuses a tool the actor
wasn't delegated with `AGENT_TOOL_NOT_DELEGATED`. See
[Impersonation](/docs/auth/impersonation).

`actor_may_write()` now decides by `kind` first. An impersonation token is
read-only even with `read_only: false`, which 0.8 let write; use the
provider's `authorization.functions.actorMayWrite` template to allow those
writes. An unknown `kind`, or a `read_only` that is a string, can't write.

## Realtime triggers

Topic triggers no longer send the whole row. The default message is
`{ operation, schema, table, id, values }`: the primary key and the topic
values. A 0.8 trigger sent every column to every subscriber of the topic,
including columns their grants hide.

- `triggerSql(betterSupabase, table, options)` is deprecated. Call
  `trigger(table, { ...options, betterSupabase })`, which takes the same
  options plus `topics` for fan-out. The alias stays for 0.9.
- Subscribers that read the row with `rowChange` switch to `rowKeys` and
  refetch the row through the Data API, so policies and column grants apply.
- A table whose subscribers need the whole row passes `payload: "row"`, or
  `payload: "row"` in its `realtime.triggers` entry. Read
  [Row changes](/docs/platform/realtime#row-changes) first: it bypasses column
  grants.
- A topic value with characters topics don't allow now raises a warning and
  skips that send instead of failing the write.
- `broadcast_topic()` refuses to run as a `before` trigger.
- The trigger function's name now includes the schema
  (`bs_broadcast_<topic>_<schema>_<table>`), so tables with the same name in
  two schemas no longer replace each other's function. The trigger keeps its
  name. Drop the old `bs_broadcast_<topic>_<table>` functions in the
  migration; grants on them don't carry over.

Regenerate the triggers (`sql sync` for `realtime.triggers`, or rerun the
code that writes them) and create a migration. Doctor reports trigger
functions that still send whole rows without the opt-in
([BS337](/docs/cli/doctor#bs337)).

## Pagination

`defineListQuery` and the default list of `defineResource` and `defineApi`
now page by cursor. A cursor page reads the same number of rows however deep
it is, and rows inserted between requests don't shift it. It has no page
number and no total:

| 0.8 (offset, the old default)              | 0.9 (cursor, the new default)                               |
| ------------------------------------------ | ----------------------------------------------------------- |
| `?page=3&size=50`                          | `?after=<nextCursor>&size=50`                               |
| `page.page.number`, `.total`, `.pages`     | `page.hasMore`, `page.nextCursor`                           |
| `ListPage<R, F, C>` is an `OffsetPage`     | `ListPage<R, F, C>` is a `CursorPage`                       |
| `list.args(query)` returns `page`, `count` | `list.args(query)` returns `after`                          |
| OpenAPI and MCP list `page`                | OpenAPI and MCP list `after`; Arazzo adds a paging workflow |

A request that still sends `page` fails with "This list pages with `after`".
To keep page numbers, set `pagination: "offset"`:

```ts title="lib/lists.ts"
export const customers = defineListQuery(betterSupabase, "customers", {
  sorts: { name: [{ name: "asc" }, { id: "asc" }] },
  defaultSort: "name",
  pagination: "offset",
});
```

The codemod adds `pagination: "offset"` to `defineListQuery` and
`defineResource` calls that set no pagination, in files that read page
numbers (`.page`, `pageCount`, `totalPages`, a `page` key or URL param). It
lists the other calls, and every `defineApi` `resources` map, for review:
add the key where a UI in another file shows page numbers or a total. A list
that sorts by a relation (`{ organization: { name: "asc" } }`) needs
`pagination: "offset"` too, since a cursor can only follow the table's own
columns. Give each cursor list a unique column last in every sort, as the
example does, so rows with the same name don't skip a page.

The default list of a table or view without a primary key stays on offset,
because it has no unique column to continue after.

The World's `world.analytics` lists return keyset
cursors instead of offsets. Treat a cursor as opaque and pass back the one
the previous page returned; an offset number from 0.8 now fails with "not an
analytics cursor".

## Blocks

`create_share_link` takes two more arguments: `version_id`, which pins the
link to a version of its subject and must belong to it, and `expires_at`,
which must be in the future. Calls with four arguments still work, but
grants or revokes your SQL wrote on the four-argument signature
`create_share_link(uuid, text, text, text)` no longer exist after the sync:
write them for `(uuid, text, text, text, uuid, timestamptz)`.
`revoke_share_link` now accepts only the link's creator or a member with
`share_links.create`, `list_share_links` returns only links the caller may
read, and `record_view` refuses non-members.
An adopted links table needs a `version_id uuid` column, or map
`columns.links.versionId` to `null` and links are never pinned.
`shareLinks.resolve(token)` returns `versionId`. See
[Share links](/docs/blocks/share-links).

`promotions` calls `before_promotion_activate(promotion uuid)` when you
define it, after every write that leaves a promotion active, including an
edit to one that already is. A function of that name that you wrote for
another purpose now runs on each such save; rename it. See
[Promotions](/docs/blocks/promotions#hooks).

With `config.subjects` set and no `subjects` option on `comments`, comments
now accept only the registered subject types and require that the caller can
read the subject row. In 0.8 a comment could name any type. Register the
types you comment on, or give `comments` its own `subjects`. See
[Comments](/docs/blocks/comments#subjects).

Tagging a record needs `tags.apply` (or `tags.manage`). In 0.8 any member
could add or remove a tag on any record of their organization. The
`role_permissions` defaults give `tags.apply` to members; apps with their own
roles grant it to the roles that tag. See [Tags](/docs/blocks/tags).

`calendar_attendees.role` accepts only `chair`, `required`, `optional` and
`non-participant`. The check is added `not valid` and validated in the same
migration; rows with another role leave it unvalidated with a warning, so fix
them and run `validate constraint attendees_role_check`.

`list_comments` takes an `after_id` after `after`, so rows with the same
`created_at` no longer repeat or skip between pages. Pass the last comment's
id as `cursorId` with `cursor`. Grants on the six-argument signature no longer
exist after the sync. See [Comments](/docs/blocks/comments).

## Money in the sales blocks

Every amount with a currency in the deals, quotes, invoices, pipelines and
employees blocks is a `Money` value from `better-supabase/commerce` instead of
a bare `bigint`. Build one with `money(amount, currency)` and read `.amount`
for the `bigint`. Target goals and progress stay `bigint`.

| 0.8                                                                  | 0.9                                                                           |
| -------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| `deals.create(org, { amount: 4_800_000n, currency: "EUR" })`         | `deals.create(org, { amount: money(4_800_000n, "EUR") })`                     |
| `{ description, unitAmount: 9_500n }`                                | `{ description, unitAmount: money(9_500n, "EUR") }`                           |
| `invoices.recordPayment(id, { amount: 137_940n })`                   | `invoices.recordPayment(id, { amount: money(137_940n, "EUR") })`              |
| `deals.forecast(org, { currency: "EUR", target: 60_000_000n })`      | `deals.forecast(org, { currency: "EUR", target: money(60_000_000n, "EUR") })` |
| `employees.addContract(id, { salary: 5_400_000n, currency: "EUR" })` | `employees.addContract(id, { salary: money(5_400_000n, "EUR") })`             |

An amount in another currency than its record returns an `invalid_request`
error with hint `CURRENCY_MISMATCH` before any database call, and an unknown
ISO 4217 code returns `CURRENCY_INVALID`. The SQL enforces the same rule, and
`record_invoice_payment` takes a `currency` after the amount: grants your SQL
wrote on the five-argument signature no longer exist after the sync.

The block functions return every `int8` as text, so amounts past 2^53 survive
the round trip, and the clients reject a missing or malformed amount instead
of reading `0n`. Code that calls these functions through `$rpc` or `queryRaw`
gets strings where it got numbers. `db.$rpc` also casts the `int8` and
`numeric` columns of a typed table function to text and decodes them with the
column's codec. Doctor BS223 lists exposed functions that return a bare
`bigint` or `numeric`, which PostgREST sends as a JSON number. See
[ADR 0037](https://github.com/ScaleDockHQ/better-supabase/blob/main/docs/decisions/0037-money-on-the-wire.md).

### Time tracking rates

A time entry's `rate` is `Money` too, and the timesheet totals return
`amounts`, one `Money` per currency, instead of `amount`:

| 0.8                                              | 0.9                                                                |
| ------------------------------------------------ | ------------------------------------------------------------------ |
| `time.start(org, { billable: true, rate: 120 })` | `time.start(org, { billable: true, rate: money(12_000n, "EUR") })` |
| `entry.rate` is `120`                            | `entry.rate` is `money(12_000n, "EUR")`                            |
| `sheet.totals.amount` is `480`                   | `sheet.totals.amounts` is `[money(48_000n, "EUR")]`                |

The `rate` column becomes `bigint` in minor units, next to a new
`rate_currency`. `start_timer` and `log_time` take `rate bigint` and
`rate_currency text`, and the `numeric` signatures are dropped, so grants
your SQL wrote on them no longer exist. `time_entry.*` events carry `rate` as
text and `rateCurrency`. The upgrade multiplies existing rates by 100, which
is right for a currency with two decimals, and leaves `rate_currency` empty.
Set it in the migration:

```sql
update better_supabase.time_entries
set rate_currency = 'EUR'
where rate is not null and rate_currency is null;
alter table better_supabase.time_entries
  validate constraint time_entries_rate_pair_check;
```

An adopted entries table needs a `rate_currency text` column. See
[Time tracking](/docs/blocks/time-tracking#timers-and-entries).

## AI SDK and notifications

`gatewayOptions` ignores a `user` in its second argument; the AI Gateway
`user` only comes from `context.userId`. With `authorizeTool` set on
`createAgentRuntime`, a tool without a declared permission is denied. See
[Agents](/docs/ai-sdk/agents).

`deliver()` in the notifications block counts suppressed and audience-denied
deliveries in `skipped`. A hand-written realtime `Topic` needs a `fanOut`
method. See [Notifications](/docs/blocks/notifications).

## Records, workflows and state

These changes come with record-bound workflows. New SQL arguments all have
defaults, so existing calls keep working, but `sql sync` drops the old
signatures. Rewrite any grants, revokes or `comment on function` statements
your own SQL wrote on them for the new argument lists.

### State machine transitions run as the caller

`better_supabase.transition()` is no longer a security definer function. The
subject table's row level security decides who may move a record, and a
caller who can't update the row gets `STATE_SUBJECT_NOT_FOUND` (a `not_found`
error from `createStateMachine().transition()`) instead of `true`. In 0.8 any
signed-in user could change the status of any record of a machine. Give
members an update policy on each machine's table, or call `transition()`
with the service role where a server action moves records on their behalf. A
`bulk` row the caller can't update now fails instead of moving. See
[Who may transition](/docs/blocks/state-machine#who-may-transition).

### Comments activity per record

With the `subjects` module installed, the `activity_entries` read policy and
`list_activity` check `can_subject(subject_type, subject_id, 'read')`, so
members no longer see entries on records they can't read. Entries without a
subject, or on an unregistered type, keep the tenant check. `ActivityEntry`
has a required `source` field (`"event"` or `"audit"`): code that builds
entries by hand, such as test fixtures or a custom feed, sets it. See
[Visibility per record](/docs/blocks/comments#visibility-per-record).

### Notification delivery tracking

`complete_notification_delivery` takes a seventh argument, `template_key`,
and the six-argument signature is dropped. `resendWebhook` records every
Resend status through `record_delivery_event`, which ships in notifications
module version 6: run `sql sync` and apply the migration before you deploy
the new handler, or it answers 500. See
[Delivery tracking](/docs/blocks/notifications#delivery-tracking).

### Workflow runs on records

`record_workflow_run`, `workflow_runs_list` and `request_workflow_start` gain
`subject_type` and `subject_id`, and the first two gain `mode`.
`record_workflow_run` also takes `principal_kind`, `principal_id` and
`trigger_node`. `workflow_runs_list` defaults to `mode => 'live'`, so test
runs are left out unless you ask for them.

Runs that `startOnEvent` and `workflowStarter` start with `runAs` now record
the user who triggered them as `bs.actor` and `actor_id`. In 0.8 that was the
publisher; the publisher is now in `principal_kind` and `principal_id`, and
`runAs` takes `principalKind`. Reports or policies that read `actor_id` as
"who the run acted as" read `principal_id` instead. `startFor` no longer
accepts `bs.principal_kind` or `bs.principal` from caller attributes. See
[Runs on a record](/docs/blocks/workflows#runs-on-a-record).

### Workflow builder

`save_workflow_definition` takes `subject_types`, `scope` and `restricted`,
`workflow_definitions_list` takes `subject_type`, `workflow_start_target` and
`workflow_run_principal` take a `tenant`, and `save_workflow_draft` takes
`input_schema`. `versions.runAs(version, tenant)` needs the tenant when the
version belongs to a system definition, because the run's organization isn't
on the definition. `validateGraph` no longer reports a second trigger node as
an error: a graph may have several, and a trigger picks one with
`config.node`. An editor that relied on the error to block a second trigger
checks the count itself. See
[Runs on a record](/docs/blocks/workflow-builder#runs-on-a-record) and
[System workflows](/docs/blocks/workflow-builder#system-workflows-forks-and-opt-outs).

### Saved views

The `save` callback passed to `useSavedViews` also receives `state`, the
view state `savedViews.save()` stores. A callback that forwards its whole
argument to an API that rejects unknown keys picks the fields it needs, or
passes `state` on. See
[Sync with the URL](/docs/blocks/saved-views#sync-with-the-url).
