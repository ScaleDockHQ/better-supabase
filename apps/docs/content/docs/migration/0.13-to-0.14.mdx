---
title: From 0.13 to 0.14
description: What to change when upgrading to better-supabase 0.14, where block methods take a subject ref and read the tenant from the block.
---

0.14 changes the signature of every block method that works on a record.
Update the calls below, then run `better-supabase sql sync` and generate a
migration for the new comments and attachments author functions.

## Block methods take a subject and read the tenant from the block

The methods of comments, attachments, tags, reactions, relations, versions,
sla, share links, custom fields, reminders, time tracking, approvals and the
state machine take the record they work on as a `SubjectRef`, `{ type, id }`,
as their first argument. They no longer take an `organizationId`: the
blocks read it from their new `tenant` option, an organization id or a
function that returns the current one. A call without a tenant fails with
`invalid_request` and the hint `TENANT_REQUIRED`. The state machine and the
sla clock methods take no tenant, since the record decides it.

Rows carry `subject` in place of `subjectType` and `subjectId`. Batch methods
take a list of subjects and return a record keyed `type:id`, which
`subjectKey(subject)` from `better-supabase/blocks` builds. Event payloads,
the SQL functions and their columns keep `subjectType` and `subjectId`.

| `useReactions({ organizationId, subjectType, subjectIds, schema?, topic? })`                          | `useReactions({ subjects, topic? })`                                                                                            |

To upgrade:

1. Pass `tenant` to the blocks you create yourself
   (`createComments({ transport, tenant: () => ctx.tenant })`), or build them
   with `createBlockClient` or `blockSet.client`, which pass the request's
   tenant (see [one block per request](/docs/blocks/create-blocks#one-block-per-request)).
2. Replace each `organizationId, subjectType, subjectId` argument list with
   one `{ type, id }` object, and read `row.subject` instead of
   `row.subjectType` and `row.subjectId`. Read batch results by
   `subjectKey(subject)`.
3. Pass `blocks: blockConfig` to the browser `createClient`, and `tenant`
   when the tenant isn't the session's tenant claim, then drop `schema` and
   `organizationId` from the hooks (see [block hooks](/docs/frontend/client#block-hooks)).
4. Run `better-supabase sql sync`, then generate a migration, for the
   comments and attachments author functions.

## One block client per request instead of a wrapper per block

A `lib/blocks.ts` that wrapped each block to pass the organization can go.
`createBlockClient(ctx.db, commentsBlock, { config: blockConfig })` and
`blockSet.client(ctx.db, "comments")` build one block for a request: they
call through `ctx.db` and act in `ctx.db.$context.tenant`.

## Comments and attachments return their author

`comments.list` and `attachments.list` return `author` on each row, with the
name and avatar URL from the profiles module, through the new security
definer functions `comment_authors(uuid[])` and `attachment_authors(uuid[])`.
They return only authors of rows the caller may read. Without the profiles
module, `author.name` and `author.avatarUrl` are `undefined`.

## Stock, leave balances and invoice payments move onto the ledger

Inventory, leave and invoices now require the new [ledger](/docs/blocks/ledger)
module, and `better-supabase add` installs it with them. Their client methods
and SQL functions keep their names and results. The tables underneath change:

| Before                         | After                                                                                    |
| ------------------------------ | ---------------------------------------------------------------------------------------- |
| `stock_movements`              | `ledger_transactions` of kind `stock.<reason>` on a `stock:<variant>:<location>` account |
| `leave_ledger`                 | `ledger_transactions` of kind `leave.<entry>` on a `leave:<type>:<user>:<year>` account  |
| `invoice_payments`             | `ledger_transactions` of kind `invoice.payment` or `invoice.refund` on `invoice:<id>`    |
| `apply_stock_movement` trigger | the ledger's balance trigger and `ledger_balances`                                       |

Run `better-supabase sql upgrade`. Each module's upgrade copies the old rows
into ledger transactions with the same ids, so movement, entry and payment ids
you stored stay valid, then drops the old table. A schema diff from `sql sync` alone
drops the tables without copying them, so upgrade before you deploy.

Code that read those tables directly reads the ledger instead: `ledger_entries`
joined to `ledger_accounts` by code, or `createLedger(...).entries(accountId)`.
An adopted `stock_movements`, `leave_ledger` or `invoice_payments` table in
`blocks.<name>.tables` is no longer a key; remove it from the config.

## Reactions carry votes

[Reactions](/docs/blocks/reactions#votes) store up and down votes next to
emoji. Each row gains `kind` (`emoji` or `vote`) and `value` (`1` for emoji,
`1` or `-1` for a vote), the unique key gains `kind`, and a new
`reaction_scores` table keeps each subject's vote score. Run
`better-supabase sql upgrade`: the reactions upgrade adds the columns with
`kind = 'emoji'` and `value = 1` for the rows you have, so existing reactions
keep their meaning.

`reaction.added` and `reaction.removed` now also fire for votes, with
`kind: "vote"` and the `value`. A consumer that should only see emoji
reactions filters on `kind === "emoji"`. `summary()`, `react()` and the
realtime counts stay emoji-only.

With `blocks.reactions.mode: "custom"`, add `kind text not null default
'emoji'` and `value smallint not null default 1` to your own table, and
include `kind` in its unique key on subject, actor and emoji.
