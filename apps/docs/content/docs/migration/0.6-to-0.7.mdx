---
title: From 0.6 to 0.7
description: What to change when upgrading the AI blocks to better-supabase 0.7, which shares one run-state vocabulary, renames the ai_chat permission keys of the other AI blocks to ai, and moves sandboxes to ai-chat.
---

0.7 makes the AI blocks agree with each other. Runs end with the same
status names in ai-chat, ai-tasks and workflows, the blocks around ai-chat
check `ai.*` permission keys, and one sandbox table in ai-chat holds the
sandboxes of chats and harness sessions. Every old name keeps working until
0.8, so you can upgrade first and rename afterwards.

## Upgrade the database

Update the package, then run the SQL upgrade. It writes the forward steps
into a migration and rewrites the module files; create the schema migration
afterwards, so the steps run first (see
[upgrading modules](/docs/blocks/sql#upgrading-modules)):

```bash
better-supabase sql upgrade
```

| Module         | From 1 to 2                                                                                                          |
| -------------- | -------------------------------------------------------------------------------------------------------------------- |
| `ai-chat`      | Rewrites run statuses to the new names, creates `ai_sandboxes` and moves each harness session's `sandbox_id` into it |
| `ai-tasks`     | Rewrites `succeeded` runs to `completed`                                                                             |
| `ai-providers` | Leaves `ai_sandboxes` to ai-chat; stops with an error while the table holds rows and ai-chat is not installed        |
| `memory`       | Adds a `project_id` column and the `project` scope                                                                   |

If you installed ai-providers without ai-chat and have sandbox rows, add
ai-chat to `sql.modules` before the upgrade, or delete the rows.

## Run statuses

| 0.6         | 0.7         | Where         |
| ----------- | ----------- | ------------- |
| `done`      | `completed` | ai-chat runs  |
| `error`     | `failed`    | ai-chat runs  |
| `stopped`   | `cancelled` | ai-chat runs  |
| `succeeded` | `completed` | ai-tasks runs |

`runs.release` and `release_ai_chat_stream` still accept `done`, `error` and
`stopped` and store the new names. What the blocks return is always the new
name, so code that compares a run's `status` with `"done"` needs the new
name now. `RunState`, `FinalRunState` and `FINAL_RUN_STATES` from
`better-supabase/blocks` list the shared names. Run step statuses
(`running`, `done`, `error`, `skipped`) and message statuses don't change.

## Permission keys

The ai-files, knowledge, memory, agents, connectors, ai-tasks and
ai-providers blocks check `ai.read`, `ai.create`, `ai.share`, `ai.moderate`
and `ai.admin` instead of the `ai_chat.*` keys. A grant of the old key (or
of `ai_chat.*`) still passes the check until 0.8, and a config that sets a
module's permission to an old key keeps working. ai-chat itself keeps its
`ai_chat.*` keys. Grant the new keys in your roles, then remove the old
grants once nothing checks them.

## Runs on the chat client

`createAiRuns` and the `runs` key of the durable chat context are
deprecated. The chat client has the same lookups:

| 0.6                                       | 0.7                                             |
| ----------------------------------------- | ----------------------------------------------- |
| `createAiRuns(options)`                   | `createAiChat(options).runs`                    |
| `{ ...context, runs: createAiRuns(...) }` | `context` (its `chats.runs` serves the lookups) |

## Sandboxes

| 0.6                                                | 0.7                                            |
| -------------------------------------------------- | ---------------------------------------------- |
| `createAiProviders(options).sandboxes`             | `createAiChat(options).sandboxes`              |
| `AiSandbox` and friends from `blocks/ai-providers` | the same names from `blocks/ai-chat`           |
| `idleSandboxStop({ sessions, stop })`              | `chat.sandboxes.idleStopJob(stop)`             |
| `sql.modules.ai-providers.options.idleAfter`       | `sql.modules.ai-chat.options.sandboxIdleAfter` |

A harness session still saves and loads `sandboxId`; the block stores it as a
row in `ai_sandboxes` with the session's `harnessId`. The idle-stop job hands
those rows to your stopper with `provider` set to `harness` unless the save
named one with `sandboxProvider`, so a stopper that serves both kinds checks
`harnessId` or `provider`.

## Memory

`MemoryScope` gains `project`. A namespace `{ scope: "project", projectId }`
names an ai-chat project, and memory rows carry `projectId`. A `switch` over
`MemoryScope` needs the new case.
