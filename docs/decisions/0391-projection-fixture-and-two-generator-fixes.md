# 0391: Check the projection shape in a Lienlink fixture, and fix two gaps it found

## Status

Accepted

## Context

Part 2 of the base layer plan has the app own views over block tables, with an `instead of` insert trigger on `job_attachments`, and asks for a fixture that mirrors Lienlink (ADR 0390 holds the first fixture). Building it found two gaps.

A stored generated column the app adds to a block table (`job_id` on attachments) became a field of the block. The block granted insert on it and wrote it in `create_attachment`, which Postgres refuses at run time. And doctor BS107 asked for a restrictive `using (false)` policy to state that a tenant table takes no insert, but an insert policy has no `using`, so the rule could not be satisfied for insert.

## Decision

`tests/validation-lienlink` mirrors the shape of the plan: projection views in `public` over block tables, the `job_attachments` insert trigger, app ALTERs, a composite foreign key into `teams`, an audit trigger, a trigger on `auth.users`, a generated `job_id` and an end-state grants file. It runs the same checks as ADR 0390.

`appColumnsOf` skips a column whose definition says `generated always as` or `generated by default as`. BS107 counts a restrictive `with check (false)` insert policy as the denial of insert.

## Consequences

The projection views stay the app's files, and `upgrade` leaves them alone, which the fixture proves. The generator does not yet move reads to the view, fail calls that bypass it, or generate PowerSync streams from the projection; those parts of the plan's `projections` and `powersync` items remain open.
