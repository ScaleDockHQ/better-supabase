# 0196: Seeds are declared by modules, with defaults in SQL and sample data in the cloud

- Status: accepted
- Date: 2026-11-01

## Context

`db seed` runs the app's own `defineSeed` and `defineTenantSeed` files. A block
has no way to say which rows it needs in a new organization (default roles,
statuses, templates), so every app copies them by hand, and an organization
that exists before a block is added never gets them. Realistic demo data is a
separate need that a library can't generate well offline.

## Decision

Seeds have three tiers.

1. System rows stay in the module's own SQL.
2. Tenant defaults are declared by a module in `BlockSql.seeds.defaults(ctx)`,
   which returns `SeedTable[]` (`src/sql/seeds.ts`). `moduleSql` renders them
   into an idempotent function `seed_<module>_defaults(p_tenant, p_variant,
   p_locale)` that inserts with `insert ... select ... where not exists`
   keyed on the table's key columns. `renderSeedUmbrella` renders
   `seed_tenant_defaults(p_tenant, p_variants jsonb, p_locale)` over them.
   `BlockSql.seeds.variants` names the starting sets a module offers.
3. Sample data is generated by the Better Supabase cloud for Pro accounts.

`database.seed` gains `defaults` (`onCreate`, `locale`, `variants`) and
`sample` (`size`, `seed`, `locale`, `output`). The keys sit under
`database.seed` because that is where `entry`, `output` and `perTenant`
already live.

The CLI gets `db seed --defaults` (with `--tenant`, `--variant block=name`,
`--locale`), `db seed --sample` (with `--size`, `--seed`, `--demo-org`,
`--tenant`, `--out`), and `login`, `logout` and `whoami`.

### Cloud contract

- `POST /api/cli/auth/start` answers `{ deviceCode, userCode, verificationUrl,
  interval, expiresIn }`.
- `POST /api/cli/auth/poll` with `{ deviceCode }` answers 202
  `{ status: "pending" }`, then 200 `{ status: "approved", accessToken,
  refreshToken, expiresAt, email }`, or 410 `{ status: "expired" | "denied" }`.
- `POST /api/cli/auth/refresh` with `{ refreshToken }` answers 200 with the
  same body as an approved poll (`{ status: "approved", accessToken,
  refreshToken, expiresAt, email }`). The cloud rotates the refresh token, so
  the CLI saves the new one. A refresh token that is unknown, used or expired
  gets 401 (400 and 410 mean the same); the CLI then reports "Not logged in".
  The CLI calls it when `expiresAt` is less than a minute away, before
  `whoami` and `db seed --sample`. The route needs no Bearer header.
- `GET /api/billing` with a Bearer token answers `{ plan, email? }`.
- `POST /api/seeds/sample` with a Bearer token takes `{ design?, preset?,
  instances?, variants, locale, size, seed, target: "tenant" | "demoOrg",
  tenant? }` and answers 200 `{ statements[], summary, estimatedRows }`.
  An account without sample data gets 402 `application/problem+json` with an
  `upgrade` URL, which the CLI reports with exit code 3.

The login is stored in `$XDG_CONFIG_HOME/better-supabase/auth.json` (mode
0600). `$BSB_CLOUD_URL` overrides the default `https://app.bettersupabase.com`.
The types and guards are in `src/cli/seeds/contract.ts`.

## Alternatives considered

- Generating sample data in the library: needs locale data and large
  dictionaries the core must not carry (architecture invariant 1).
- Per-block seed scripts in TypeScript: can't run for organizations created by
  SQL or by another client, so defaults would drift from the database.

## Consequences

Defaults run anywhere the database runs. This change ships the machinery,
the config, the CLI and the contract. No shipped module declares defaults yet,
so `--defaults` reports that nothing is declared until modules adopt it, one
at a time, each with its own `pnpm db:gen` and migration. A token refresh is
not implemented: an expired login asks for `login` again. Design format 9
(`seeds` in a Create design), preset variants and doctor findings for unknown
variants are follow-ups.
