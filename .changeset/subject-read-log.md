Reads of a record can be logged. Set `subjects.<type>.auditReads: true` (it needs the `audit` block and a tenant column) and the block read functions for that type, `record_summary`, `list_comments`, `list_activity`, `list_status_history` and `read_field_values`, call `record_subject_read`, which writes one audit entry in the `read` category with `{ subjectType, subjectId, purpose, emergency, block, function }` and emits `subject.accessed`. Repeated reads by the same person with the same purpose collapse within `blocks.subjects.options.reads.collapseSeconds` (60 by default; 0 logs every read), and a read made during emergency access is flagged `emergency`. `subject_access_log(subject_type, subject_id, since, max_rows)` lists the reads to the record's team leads, `audit.read` holders, and through guests the client or a representative with `act` authority; anyone else gets `SUBJECT_READ_FORBIDDEN`. The client adds `db.subjects.reads.log()` and `reads.list()`. Plain PostgREST selects are not logged, so revoke `select` on the table when every read must go through a function. Block SQL gains `ctx.read()` and `ctx.readVolatility()` to log reads from its own functions. Run `better-supabase upgrade` and generate a migration to pick up the functions.
