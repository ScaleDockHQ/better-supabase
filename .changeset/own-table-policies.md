Add `ownTablePolicies` to keep blocks' policies off your own tables. Set `database.sql.ownTablePolicies: "app"` for every block, or `blocks.<name>.ownTablePolicies` for one, which wins. With `app`, a block that runs over a table your schema creates adds none of its `bsb_<table>_<command>` policies there, even where none of your policies repeats its condition, and no restrictive `bsb_tenant_scope` either, so your policies alone decide who reaches the rows (a platform permission that reads across organizations keeps working). It still writes its functions, triggers, indexes and grants. Its file keeps the `drop policy if exists` and a comment that your policies govern the table, so `upgrade` removes the copies an earlier install left. The default, `block`, keeps the behaviour since 0.15, and `add --adopt` suggests `app` when an adopted table already has permissive policies of its own. Doctor skips such tables in BS347, and the new BS350 (info) reports one with row level security on but no permissive policy for a command the block's policies would have granted.

The `organizations` block adds its `stripe_customer_id text unique` column only when the entitlements block reads the Stripe customer from it: not with a `plans` or `custom` source, a configured `auth.entitlements.customer` on another column, or the managed `billing` block's customers table. Otherwise the column leaves the block's file on `upgrade`: on a managed organizations table the next declarative schema diff drops the column and its data, and `stripeCustomerId` leaves the generated models. If your app reads or writes that column, declare it in your own schema file, or set `auth.entitlements.customer` to it (`better_supabase.organizations.stripe_customer_id` for the managed table), which keeps the block adding it, before you run `upgrade` and the diff.

When tenant and platform invitations share one table (`blocks.invitations.tables.platformInvitations` names the tenant table), the platform invitations' open-email unique index is limited to rows without a tenant, so a person can hold open invitations to several organizations at once. The block's file drops the old `platform_invitations_open_email_idx` and creates `invitations_platform_open_email_idx` in its place.

Add `options.stamp` to the `updated-at` and `created-by` blocks: `client` (the default) keeps stamping `createdAt`, `updatedAt`, `createdBy` and `updatedBy` in the repository, and `trigger` leaves them to the `track_updated_at` and `track_actor` triggers, so tables with column-level grants that leave those columns out accept the app's writes. `gen` passes it to `updatedAtExtension({ stamp })` and `createdByExtension({ stamp })`, which still mark the columns read-only and refuse caller-supplied values without `{ override: true }`.

The filter form `update({ where }, patch, args)` accepts `override` in its types, as the runtime already did.
