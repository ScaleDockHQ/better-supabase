A block's SQL and TypeScript halves now read one config. `better-supabase gen` writes `blocks.generated.ts` next to `generated.ts`: each installed block's schema, API schema and the options both halves share (`attachments.requireScan`, `bulk.limit`, the realtime topics of notifications, announcements, inbox, reactions and ai-chat, `time-tracking.timeZone`, `waitlist.codeField`, `webhooks-out.allowHttp`), with the module defaults filled in. `defineBlocks(blockConfig, blocks, ...appEvents)` takes it as its first argument and passes each block its schema (the API schema when there is one) and those options, so the app no longer repeats them. `createBlocks` takes it as `config`, and its shared `schema` option is removed. `generatedOptions(entry)` gives a creator you call yourself the same values, and `fillTopic(template, values)` fills in a topic template such as `notifications:{userId}`.

`blocks.<name>.options` is typed from each block manifest's options schema: an unknown block, an unknown option or a value of the wrong kind is a type error, and the SQL renderer refuses it too. Manifests describe their options with `blockOptions({ key: option.string(), ... })` in place of `optionKeys([...])`, which is removed, and `schemas/config-v1.json` is generated from the same schemas. `BlocksConfig` is the typed input; the resolved config and the SQL renderer use `AnyBlocksConfig`. Preset wiring (`init --preset`) and the `blocks` registry item build on `defineBlocks(blockConfig, ...)`, and `add` edits a `defineBlocks` call as well as a `createBlocks` one.
